# 1.3 — Greedy longest-match-first

## One-line answer

WordPiece **does not replay a merge list** — it walks the word left to right taking the longest vocabulary
entry it can at each step, so encoding needs only a `set` of tokens and no ordering at all; hand-rolled in
twenty lines it agrees with the library on **7 of 7** probes.

---

## The story

You are reading a road sign in a language you half know, and you have a dictionary.

You do not try every possible way of cutting the sign into words. You start at the left edge, find the
longest thing in the dictionary that matches from there, take it, and start again after it. Then you repeat
until you reach the end.

It is fast and it usually works. It is also not guaranteed to be right — take a long word early and you may
strand a fragment at the end that is in no dictionary at all, when a shorter first word would have left
something readable. You will not know, because you never looked back.

---

## The idea in plain language

Day 13 part
[1.1](../../../day-013-bpe-encode-decode-bytes/parts/01-encode-and-decode/1.1-encoding-applies-merges-by-rank.md)
established how BPE encodes: the merge list is *ordered*, and encoding replays it — repeatedly find the
adjacent pair with the lowest rank and merge it. The order is the algorithm. Take the merges out of order
and you get different tokens.

WordPiece encodes completely differently, and the difference is bigger than the training difference in part
[1.1](1.1-scoring-a-pair-by-likelihood.md):

```text
start at position 0
repeat:
    take the LONGEST vocabulary entry matching from here
    (prefix it with ## if we are not at position 0)
    move past it
until the end of the word
```

**There is no merge list.** The vocabulary is a *set*. Order is irrelevant. You could shuffle a WordPiece
vocabulary file and nothing would change, where shuffling a BPE merge list produces a different tokenizer
entirely — Day 12 part
[2.5](../../../day-012-bpe-the-merge-loop/parts/02-training-a-vocabulary/2.5-the-vocabulary-that-depended-on-the-order-of-the-corpus.md)
measured 21 tokens against 15 for exactly that.

This has two consequences worth holding on to:

- **The file is simpler.** A WordPiece vocabulary is a plain list of strings, one per line. No ranks, no
  pairs, no version header — none of part
  [1.3](../../../day-014-tiktoken-and-the-pipeline/parts/01-tiktoken/1.3-what-a-vocabulary-file-looks-like.md)
  of Day 14's off-by-one hazards.
- **Encoding can fail.** BPE always terminates with *something*, because the base alphabet covers every
  input. Greedy matching can walk into a position where nothing matches, and then it has to give up. What
  it gives up on is the subject of part [1.4](1.4-the-word-that-became-one-unk.md), and it is worse than
  you would guess.

## Why Akshara needs it

**Because "greedy longest-match" is a pattern you will use again.** It is how constrained decoding matches
grammar terminals on Day 47 (`INFER-*`), and how a trie-based lookup works generally. Writing it once, in
twenty lines, on a problem you already understand, is cheap.

**Because it is the strongest evidence that you understand WordPiece.** Principle 3 in its purest form: if
your twenty lines agree with a Rust library on real input, you have the algorithm, not an impression of it.

**Because the failure mode is instructive and specific.** Most algorithms degrade at the edges. This one
falls off a cliff, and the cliff is a design choice somebody made rather than an accident. Seeing where the
`return [unk]` sits in your own code is what makes part 1.4 land.

## The mechanism

### Step 1 — write it

```python
def wordpiece_encode(word: str, vocab: set[str], unk: str = "[UNK]",
                     max_chars: int = 100) -> list[str]:
    """Greedy longest-match-first. Fails the WHOLE word if any piece is missing."""
    if len(word) > max_chars:
        return [unk]
    start, pieces = 0, []
    while start < len(word):
        end = len(word)
        cur = None
        while start < end:                      # longest first
            sub = word[start:end]
            if start > 0:
                sub = "##" + sub
            if sub in vocab:
                cur = sub
                break
            end -= 1
        if cur is None:
            return [unk]                        # <- the whole word, not one character
        pieces.append(cur)
        start = end
    return pieces
```

**Line by line:**

- `vocab: set[str]` — a set, not a list and not a dict. Membership is all the algorithm asks of it, and the
  type signature says the ordering carries no information. This is the API-level statement of the section's
  main point.
- `if len(word) > max_chars: return [unk]` is a guard against the inner loop's cost. The two nested loops
  are `O(n²)` in the word length, so a pathological 10,000-character "word" — a base64 blob, a minified
  line of JavaScript — would do 50 million substring operations. Real implementations carry this limit;
  `tokenizers` exposes it as `max_input_chars_per_word`, defaulting to 100.
- `end = len(word)` then `end -= 1`: start at the **longest** possible substring and shrink. Reversing this
  to shortest-first would produce a valid segmentation too, and a much worse one — it would take single
  characters forever.
- `if start > 0: sub = "##" + sub` applies part [1.2](1.2-the-hash-hash-convention.md)'s convention exactly
  where it belongs: position 0 is word-initial, everything after is a continuation. This one line is the
  entire `##` mechanism at encode time.
- `if cur is None: return [unk]` — the cliff. Note it returns `[unk]` for the **whole word**, discarding the
  pieces already found. `pieces` might hold four perfectly good tokens and they are thrown away. That is
  not a shortcut in my code; it is what the algorithm specifies, and part 1.4 is about why it matters.
- `start = end` moves past the matched piece. `end` is where the successful match stopped, so this is
  correct without an offset — an easy place to write `start = end + 1` and silently drop a character.

### Step 2 — check it against the library

```python
V = set(wp.get_vocab())
probes = ["dollars", "costs", "supercalifragilistic", "café", "plan", "tokenizer", "The"]
for p in probes:
    mine, theirs = wordpiece_encode(p, V), wp.encode(p).tokens
    print(f"  {p!r:22s} {str(mine):58s} same={mine == theirs}")
```

**Line by line:**

- `set(wp.get_vocab())` takes the keys of the token→id dict. Your function needs no ids at all, which is
  another way of seeing that the vocabulary carries no ordering.
- The probes are chosen to cover the cases: a word with a clean split, a word with a suffix, a very long
  word, a word with a non-ASCII character, and three that are single vocabulary entries.
- Comparing against the library is the oracle, exactly as Day 13 part 1.1 kept a slow encoder to check the
  fast one, and Day 14 part
  [2.2](../../../day-014-tiktoken-and-the-pipeline/parts/02-the-tokenizers-pipeline/2.2-the-same-vocabulary-trained-twice.md)
  used an independent implementation.

Measured, corpus `9760f2b6d4340b97`, `tokenizers==0.23.1`:

```text
  'dollars'              ['do', '##l', '##l', '##ar', '##s']              same=True
  'costs'                ['cost', '##s']                                  same=True
  'supercalifragilistic' ['s', '##up', '##er', '##c', '##al', '##if',
                          '##ra', '##g', '##il', '##ist', '##ic']         same=True
```

**Seven of seven.** Twenty lines of Python reproduce the library exactly, including the `[UNK]` case.

### Step 3 — see the greediness

Trace `dollars` against the vocabulary by hand:

| position | longest match tried | result |
| --- | --- | --- |
| 0 | `dollars`, `dollar`, `dolla`, `doll`, `dol`, `do` | **`do`** ✅ |
| 2 | `##llars`, `##llar`, `##lla`, `##ll`, `##l` | **`##l`** ✅ |
| 3 | `##lars`, `##lar`, `##la`, `##l` | **`##l`** ✅ |
| 4 | `##ars`, `##ar` | **`##ar`** ✅ |
| 6 | `##s` | **`##s`** ✅ |

Five tokens, and at every step the algorithm took the longest thing available and never reconsidered. Note
position 2: it took `##l` because `##ll` was not in the vocabulary. Had it looked ahead it might have found
that `##lla` + `##rs` was reachable — it does not look ahead. That is what "greedy" means, and part
[2.3](../02-unigram/2.3-viterbi-picks-the-best-segmentation.md) is the algorithm that *does* look ahead.

## Shapes

| Name | Symbolic | Concrete | Meaning |
| --- | --- | --- | --- |
| `vocab` | `(V,)` | `(1000,)` | a **set**; order carries nothing |
| `word` | `(n_chars,)` | `(7,)` | `dollars` |
| `pieces` | `(k,)` | `(5,)` | `k <= n_chars` always |
| inner-loop work | `O(n²)` | `≈ 28` | substring tests for a 7-character word |

`k <= n_chars` holds because every successful match consumes at least one character. That is the invariant
that makes the outer loop terminate, and it is worth asserting.

---

## When it breaks

**The whole word becomes `[UNK]`, not the bad character.** Part 1.4 is the measurement, but the line is
right here in your code: `return [unk]` discards `pieces`. A single unusual character destroys the entire
word.

**Greedy is not optimal.** Taking the longest piece first can leave an unmatched remainder where a shorter
first piece would have succeeded. On a vocabulary that includes all single characters this cannot cause a
failure — the fallback always exists — but it can produce a worse segmentation than necessary, and
nothing reports that it happened.

**The `max_input_chars_per_word` limit turns long input into `[UNK]` silently.** Default 100. A base64
string, a long URL, a minified line of code, a chemical name — all become one `[UNK]`, and all are
plausible corpus content:

```text
'a' * 101   ->   ['[UNK]']
```

No warning. This is a real cause of quiet data loss in corpora with any machine-generated text.

**Shortest-match-first is a plausible bug that produces valid output.** Reverse the inner loop and every
word becomes a string of single characters. It round-trips, it never raises, it never emits `[UNK]`, and
compression collapses. The check is compression, not correctness — a reminder that the round trip has now
failed to catch a bug for the fourth day running.

## In production

**Real implementations use a trie, not repeated substring slicing.** The `O(n²)` inner loop is fine for a
seven-character word and wasteful at corpus scale. A trie walks the word once per position, giving `O(n)`
per start, and the longest match falls out of the walk. The algorithm is identical; the data structure is
the optimization, and this is why the library is faster rather than because it is Rust.

**Encoding needs no ordering, so a WordPiece vocabulary can be edited.** You can append a domain term to a
`vocab.txt` and it works immediately — no retraining, no rank recomputation. You cannot do that to a BPE
merge list, where every entry's position is its priority. This is a genuine operational advantage of the
family and the reason it persists in domain-specific encoder models.

**But the embedding matrix disagrees.** Adding a vocabulary entry means adding a row to a `(V, C)` matrix,
and that row is untrained. The tokenizer accepts the edit instantly; the model needs fine-tuning to make it
mean anything. Day 16 (`TOK-17`) does that resize deliberately.

**Greedy matching is everywhere once you know its shape.** Constrained decoding, grammar terminals,
dictionary-based segmentation for languages without spaces, and the `[UNK]`-free variants that fall back to
bytes instead of giving up — part [3.2](../03-sentencepiece/3.2-byte-fallback.md) is that repair, applied to
a different family.

## Check yourself

```python
from tokenizers import Tokenizer, models, pre_tokenizers, decoders, trainers
from pathlib import Path

text = Path("docs/00_MASTER_PLAN.md").read_text(encoding="utf-8")
wp = Tokenizer(models.WordPiece(unk_token="[UNK]"))
wp.pre_tokenizer = pre_tokenizers.Whitespace()
wp.decoder = decoders.WordPiece()
wp.train_from_iterator([text], trainers.WordPieceTrainer(
    vocab_size=1000, show_progress=False, special_tokens=["[UNK]"]))
V = set(wp.get_vocab())

# the eval that can go red: your twenty lines against a Rust library
PROBES = ["dollars", "costs", "supercalifragilistic", "café", "plan", "tokenizer", "The"]
for p in PROBES:
    mine, theirs = wordpiece_encode(p, V), wp.encode(p).tokens
    assert mine == theirs, f"{p!r}: mine {mine} != theirs {theirs}"
print(f"agreement: {len(PROBES)}/{len(PROBES)}")

# the invariant that makes the loop terminate
for p in PROBES:
    assert len(wordpiece_encode(p, V)) <= max(len(p), 1)

# order genuinely carries nothing: shuffle the vocabulary and nothing moves
import random
shuffled = list(V)
random.Random(0).shuffle(shuffled)
for p in PROBES:
    assert wordpiece_encode(p, set(shuffled)) == wordpiece_encode(p, V), \
        "shuffling changed the output - your vocab is being used as if it were ordered"
print("shuffling the vocabulary changes nothing - unlike a BPE merge list")

# the length guard fires, silently
assert wordpiece_encode("a" * 101, V) == ["[UNK]"]
assert wordpiece_encode("a" * 99, V) != ["[UNK]"]
print("max_input_chars_per_word turns a 101-character word into one [UNK], with no warning")
```

**Line by line:**

- The shuffle test is the eval that can go red and it is the one worth keeping. It asserts a *negative*
  property — that order does not matter — which is exactly the claim distinguishing WordPiece from BPE.
  Run the same test against a BPE merge list and it fails immediately.
- `random.Random(0)` rather than `random.shuffle`: an explicit seeded generator, per Principle 9. An
  unseeded shuffle in a test is a flaky test, and the plan calls a flaky test indistinguishable from
  Silent Failure #4.
- `max(len(p), 1)` guards the empty-string case, where `len(p)` is 0 and the assertion would be trivially
  false for any output.
- The last two lines assert the guard fires at 101 and not at 99. Pinning both sides of a threshold is
  worth more than pinning one, because it catches an off-by-one in either direction.
