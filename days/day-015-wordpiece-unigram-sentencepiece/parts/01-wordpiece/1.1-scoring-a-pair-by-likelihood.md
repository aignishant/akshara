# 1.1 — Scoring a pair by likelihood

## One-line answer

WordPiece changes one line of Day 12's merge loop — it maximizes `count(ab) / (count(a) × count(b))`
instead of `count(ab)` — and that single change makes the rule **degenerate without a minimum frequency**:
measured here, the raw score picks a pair that occurs **once**, scoring a perfect 1.0.

---

## The story

Two shops each want to know which pair of items customers buy together most.

The first shop counts. Bread and milk, 1,233 times this month. That is the pair.

The second shop asks a different question: which pair turns up together *more often than you would expect
from how popular each one is on its own?* Bread and milk are both bought constantly, so of course they
appear together — that is not surprising, it is arithmetic. What is surprising is two rare things that
always arrive in the same basket.

The second question is a better question. It also has a trap in it, and you can see the trap from here: the
most "surprising" pair of all is two items bought exactly once, by the same person, on the same day.

---

## The idea in plain language

Day 12 part [1.1](../../../day-012-bpe-the-merge-loop/parts/01-the-merge-loop/1.1-merge-the-commonest-pair.md)
built BPE's rule in one line:

```text
best = argmax over pairs of   count(a, b)
```

WordPiece keeps the entire loop — the same starting symbols, the same merge, the same repeat-until-`V` —
and changes only that line:

```text
best = argmax over pairs of   count(a, b) / (count(a) × count(b))
```

That is the whole algorithmic difference. It is worth saying plainly, because "WordPiece" and "BPE" are
usually presented as two different things and they are one thing with two scoring functions.

**What the new score means.** The denominator is what you would expect the pair to appear if `a` and `b`
were independent. So the ratio asks: *how much more often do these appear together than chance predicts?*
A high score means the two pieces genuinely belong to each other, rather than both simply being common.

The name for this is a likelihood ratio, and the motivation is that a merge should buy you *information*,
not just shorten a frequent string.

**And it does not work on its own.** The measurement below shows the score is maximized by pairs seen once,
because a pair that occurs once, made of two units that each occur once, scores exactly `1 / (1 × 1) = 1`.
No frequent pair can beat that. Every real WordPiece trainer therefore carries a minimum frequency, and
that guard is not a detail — it is load-bearing.

---

## Why Akshara needs it

**Because it is the cleanest example of "the formula is not the algorithm".** You can read the WordPiece
scoring rule in one line, implement it faithfully, and get a vocabulary of one-off noise. The published
rule and the working trainer differ by a guard that rarely gets written down. Meeting that here — where a
tokenizer is cheap — is training for every later day where a loss function has the same property.

**Because Akshara will meet WordPiece vocabularies in the wild.** A large family of models ships them, and
their tokenizer files look different from what Days 12–14 built: no merge list at all, a `##` prefix,
an `[UNK]` token that Day 13 taught you to consider impossible.

**Because Principle 3 says build first.** This part changes one line of code you already own. If you
understood Day 12's loop, you can hold WordPiece's trainer in your head, and that is worth far more than
being able to import it.

---

## The mechanism

The corpus is `docs/00_MASTER_PLAN.md`, sha256 `9760f2b6d4340b97`, 110,837 code points. Every script
prints the hash first.

### Step 1 — the same starting state, with one difference

```python
import re
from collections import Counter

words = Counter(re.findall(r"\w+|[^\w\s]", text))
sym = {w: tuple(w[0:1]) + tuple("##" + c for c in w[1:]) for w in words}
```

**Line by line:**

- `re.findall(r"\w+|[^\w\s]", text)` is the pre-tokenizer: one chunk per word or per punctuation mark. It
  is *not* the byte-level pattern of Day 13 — WordPiece's classic pre-tokenizer splits on whitespace and
  throws the whitespace away, which is the subject of part
  [1.4](1.4-the-word-that-became-one-unk.md)'s wider damage.
- `tuple(w[0:1]) + tuple("##" + c for c in w[1:])` is the one structural difference from Day 12's starting
  state. The first character stays bare; **every later character is prefixed with `##`**. So `dollars`
  starts as `('d', '##o', '##l', '##l', '##a', '##r', '##s')` rather than seven plain characters. Part
  [1.2](1.2-the-hash-hash-convention.md) is entirely about why.
- `w[0:1]` rather than `w[0]` so a hypothetical empty word yields `()` instead of raising `IndexError`.

### Step 2 — count units and pairs

```python
unit, pair = Counter(), Counter()
for w, n in words.items():
    s = sym[w]
    for a in s:
        unit[a] += n                       # how often each symbol appears
    for a, b in zip(s, s[1:]):
        pair[(a, b)] += n                  # how often each adjacent pair appears
```

**Line by line:**

- `unit` is the new bookkeeping. Day 12 never needed it — BPE's rule only looks at pairs. WordPiece needs
  the individual counts for its denominator, so the trainer carries a second table.
- `+= n`, not `+= 1`: `words` is a count of *distinct* chunks, so each occurrence of a symbol inside a
  chunk seen `n` times counts `n` times. Getting this wrong makes rare words as influential as common ones
  and is a bug that produces plausible output.
- `zip(s, s[1:])` walks adjacent pairs — Day 12 part 1.1's idiom, unchanged.

### Step 3 — the two rules, side by side

```python
bpe_best = max(pair.items(), key=lambda kv: (kv[1], kv[0]))
wp_best = max(pair.items(),
              key=lambda kv: (kv[1] / (unit[kv[0][0]] * unit[kv[0][1]]), kv[0]))
print("BPE rule       (max count)     :", bpe_best[0], "count =", bpe_best[1])
print("WordPiece rule (max likelihood):", wp_best[0], "count =", pair[wp_best[0]])
```

**Line by line:**

- Both use the `(score, pair)` tuple key from Day 12 part
  [2.5](../../../day-012-bpe-the-merge-loop/parts/02-training-a-vocabulary/2.5-the-vocabulary-that-depended-on-the-order-of-the-corpus.md),
  so ties break stably rather than on dictionary order.
- `kv[0][0]` and `kv[0][1]` are the two halves of the pair — `kv[0]` is the pair, `kv[1]` is its count.
  Dense, and worth reading slowly once.
- The denominator is a **product**, not a sum. That is what makes it an independence baseline: if `a` and
  `b` were independent, the expected joint rate would be the product of the marginals.

Measured:

```text
BPE rule       (max count)     : ('##h', '##e') count = 1233
WordPiece rule (max likelihood): ('ष', '##र')   count = 1
```

**The likelihood rule picks a pair that occurs once.** Not a near-miss — a catastrophe. Here is why, in
the same table:

| pair | count(ab) | count(a) | count(b) | score |
| --- | ---: | ---: | ---: | ---: |
| `('##h', '##e')` | 1,233 | 2,464 | 8,060 | 6.209e-05 |
| `('##e', '##r')` | 1,146 | 8,060 | 3,921 | 3.626e-05 |
| `('t', '##h')` | 1,068 | 1,713 | 2,464 | 2.530e-04 |
| `('ष', '##र')` | **1** | **1** | **1** | **1.000e+00** |

A pair seen once, whose halves are each seen once, scores `1 / (1 × 1) = 1`. Nothing frequent can approach
it. The score is not slightly biased toward rare pairs; it is **maximized** by the rarest possible event.

(The Devanagari pair is from `अक्षर` — the Sanskrit word the project is named after — which appears in the
plan a handful of times. A corpus containing one rare script is enough to break the rule.)

### Step 4 — the guard that makes it an algorithm

```python
for min_freq in (1, 2, 10, 100):
    candidates = {k: v for k, v in pair.items() if v >= min_freq}
    best = max(candidates.items(),
               key=lambda kv: (kv[1] / (unit[kv[0][0]] * unit[kv[0][1]]), kv[0]))
    print(f"min_frequency={min_freq:4d} -> {best[0]} count={best[1]}")
```

**Line by line:**

- The filter is applied **before** the `max`, not as a tie-break after it. A pair below the threshold is
  not a worse candidate; it is not a candidate.
- `>= min_freq` on the pair count only. The unit counts are left alone — they are the denominator, and
  filtering them would change what "expected" means.

Measured:

```text
min_frequency=   1 -> ('ष', '##र')   count=    1  score=1.000e+00
min_frequency=   2 -> ('X', '##X')   count=    2  score=5.000e-02
min_frequency=  10 -> ('##M', '##B') count=   26  score=5.612e-03
min_frequency= 100 -> ('t', '##h')   count= 1068  score=2.530e-04
```

Watch the threshold climb and the answer become sensible. At `min_frequency=100` the rule finally picks
something a person would defend — `('t', '##h')`, the start of *the*, *this*, *that*, *they* — and note
that it is **not** what BPE picked. BPE took `('##h', '##e')`, the commonest pair. WordPiece took
`('t', '##h')`, which is rarer (1,068 against 1,233) but far more *predictive*: `t` is followed by `h`
much more often than `t`'s and `h`'s separate popularity would suggest.

**That is the genuine difference between the two rules, and it is only visible once the degenerate cases
are excluded.** With `min_frequency=1` you cannot see it at all, because the rule never gets past the noise.

BPE needs no such guard. `argmax count(ab)` is monotone in the thing you care about, so it cannot be
hijacked by a rare event.

## Shapes

No tensors. The two tables the trainer carries:

| Name | Symbolic | Concrete | Meaning |
| --- | --- | --- | --- |
| `words` | `(n_distinct_chunks,)` | `(3118,)` | pre-token chunk → count |
| `unit` | `(n_symbols,)` | `(209,)` | symbol → total occurrences; **WordPiece only** |
| `pair` | `(n_pairs,)` | `(1255,)` | adjacent pair → count; same as Day 12 |

`3118` is the same number Day 14 part
[4.1](../04-together/4.1-nine-tokenizers-one-table.md) reported as the word tokenizer's vocabulary size,
because it is the same pre-tokenizer and the same corpus — a small consistency check worth noticing.

`unit` is the whole extra cost of WordPiece over BPE at training time: one more counter, updated in the
same pass.

---

## When it breaks

**The rule with no guard produces a vocabulary of noise.** Not an error — a vocabulary. It trains, it
saves, it encodes, and its early merges are one-off sequences from the rarest text in your corpus. Because
early merges have the highest priority, the damage lands where it hurts most.

**A single rare script is enough.** This corpus is English markdown with a handful of Devanagari
characters, and that was sufficient. A trainer that looked fine on pure English breaks the moment one
foreign word appears — Silent Failure #5 again, and the third day running that it has surfaced.

**Reading the published formula as the algorithm.** The likelihood ratio is the part that gets written
down; `min_frequency` is the part that lives in a configuration file. Implementing from the paper and
skipping the config is a specific, common, silent mistake.

**Floating-point underflow at scale.** With counts in the billions the denominator `count(a) × count(b)`
overflows a 32-bit integer and loses precision in a float. Real trainers work in logs:
`log count(ab) − log count(a) − log count(b)`. On a 113 KB corpus you will never see it; at scale it is
mandatory, and part [2.2](../02-unigram/2.2-every-token-carries-a-probability.md) shows the same reflex in
Unigram, where every score is already a log.

## In production

**The `min_frequency` default matters more than the scoring rule.** When you inherit a WordPiece
vocabulary, the threshold used to train it is usually not recorded anywhere, and it changes the vocabulary
more than the choice of algorithm does. This is a good argument for the Day 14 discipline: ship the file,
because the settings are not reconstructible from the output.

**The two rules end up more similar than the theory suggests.** Part
[4.1](../04-together/4.1-nine-tokenizers-one-table.md) measures WordPiece and BPE at the same `V` on the
same corpus, and they compress within a few percent of each other. The scoring rule is a real difference
that produces a small measured difference — which is worth knowing before you spend a week choosing.

**Nobody trains WordPiece from scratch any more, and it is not because it is bad.** It is because
byte-level BPE and Unigram both solve the unknown-token problem that part
[1.4](1.4-the-word-that-became-one-unk.md) is about, and WordPiece as classically configured does not.
The algorithm is fine; its usual packaging is what dates it.

**The likelihood idea did not go away.** "Score a candidate by how much more likely it makes the data than
chance" is the same reflex behind Unigram's pruning in part
[2.1](../02-unigram/2.1-start-big-and-prune.md), and behind a great deal of what you will do from Day 20
onwards. WordPiece is where it appears first and most simply.

## Check yourself

```python
import hashlib, re
from collections import Counter
from pathlib import Path

P = Path("docs/00_MASTER_PLAN.md")
text = P.read_text(encoding="utf-8")
print("corpus", hashlib.sha256(P.read_bytes()).hexdigest()[:16])

words = Counter(re.findall(r"\w+|[^\w\s]", text))
sym = {w: tuple(w[0:1]) + tuple("##" + c for c in w[1:]) for w in words}
unit, pair = Counter(), Counter()
for w, n in words.items():
    s = sym[w]
    for a in s:
        unit[a] += n
    for a, b in zip(s, s[1:]):
        pair[(a, b)] += n

def score(p):
    return pair[p] / (unit[p[0]] * unit[p[1]])

bpe = max(pair, key=lambda p: (pair[p], p))
wp = max(pair, key=lambda p: (score(p), p))
print("BPE      :", bpe, pair[bpe])
print("WordPiece:", wp, pair[wp])

# the eval that can go red: the unguarded rule MUST be degenerate
assert pair[wp] < 5, \
    "the raw likelihood rule picked a frequent pair - your corpus has no rare pairs, so this part's " \
    "lesson is invisible; add a sentence of another script and re-run"
assert score(wp) > score(bpe), "the likelihood rule did not prefer the rare pair - check the formula"

# and the guard must fix it
guarded = max((p for p in pair if pair[p] >= 100), key=lambda p: (score(p), p))
print("guarded  :", guarded, pair[guarded])
assert pair[guarded] >= 100
assert guarded != bpe, \
    "guarded WordPiece agrees with BPE on your corpus - the two rules can agree; say so in your notes"
```

**Line by line:**

- `assert pair[wp] < 5` is the eval that can go red, and it asserts the **failure**. The point of this part
  is that the unguarded rule is degenerate; a test that only checked it ran would miss that entirely.
- The failure message tells you what to do if it passes — your corpus lacks rare pairs, so the lesson is
  hidden rather than absent. A test that explains its own precondition is worth the extra line.
- The final `assert guarded != bpe` may legitimately fail on a different corpus, and its message says so
  rather than claiming a bug. Two rules agreeing is a finding, not an error.
