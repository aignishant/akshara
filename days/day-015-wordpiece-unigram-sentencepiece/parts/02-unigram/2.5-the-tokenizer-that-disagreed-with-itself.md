# 2.5 — 💥 The tokenizer that disagreed with itself

## One-line answer

`assert_same_tokenizer(ug, ug)` — the check Day 14 built, comparing a tokenizer against **itself** — fails:
measured here, 50 encodings of one string give **40 distinct id sequences**, every one round-trips
perfectly, and the tokenizer is behaving exactly as configured.

---

## The story

🎬 **The scene.** A shop weighs loose sweets and the till prints a price. Two customers buy what looks like
the same scoop and get different prices. Somebody complains that the scales are broken.

😬 **The naive fix.** Test the scales. Put a known weight on twice — same reading both times. The scales
are fine, so the complaint is dismissed.

💥 **Why it fails.** The scales were never the variable. The scoop is, and it was always going to be. The
test that "proved" the scales work tested a *different thing* from the one that varies, and passing it made
everyone stop looking.

💡 **The insight.** A test only rules out what it actually varies. When a system has a deliberate source of
variation in it, a test that holds that source fixed is not evidence about the system — it is evidence
about the test.

---

## The idea in plain language

Day 14 part
[3.3](../../../day-014-tiktoken-and-the-pipeline/parts/03-the-remaining-gap/3.3-the-mismatch-the-library-will-not-catch.md)
built the check that catches tokenizer mismatch, and argued hard for it:

```python
def assert_same_tokenizer(a, b, probes):
    """Two tokenizers agree iff they produce identical IDS on every probe."""
    for p in probes:
        assert a.encode(p).ids == b.encode(p).ids
```

**Line by line:**

- This is Day 14 part 3.3's function, copied unchanged, docstring included. Nothing has been weakened; the
  check that worked yesterday is the check that fails today.
- `a.encode(p).ids == b.encode(p).ids` — ids against ids, the rule that has been right all week and is
  about to meet the one configuration it cannot express.

That check is correct and it rests on an assumption that was never stated because it never needed to be:
**a tokenizer is a deterministic function of its input.** Every tokenizer in Days 11–14 was. The assumption
was so obviously true that it was invisible.

Part [2.4](2.4-subword-regularization.md) made it false, on purpose, for a good reason.

So now you have a check that fails on a correctly configured tokenizer, and it fails in the most alarming
way available: **compared against itself.** Nothing is broken. The check is asking a question that no longer
has a single answer.

This is not a story about a bug. It is about what happens when a system acquires a property your tests were
built before it had — which is the ordinary condition of every codebase that lives longer than a month.

---

## Why Akshara needs it

**Because `assert_same_tokenizer` goes into `tests/` and stays there.** Day 14's checklist puts it in the
suite for the rest of the curriculum. If it can fail on a valid configuration, it needs to say which
configuration it assumes — today, while you remember why.

**Because "determinism is a property you choose" is the generalisable lesson.** From Day 20 the same
question appears for dataloaders, dropout, sampling and data augmentation: is this run reproducible, and
*what did I have to fix* to make it so? A tokenizer is the smallest possible instance.

**Because the plan calls a flaky test indistinguishable from Silent Failure #4** and demands it be fixed
rather than re-run. A test that passes or fails depending on a sample is exactly that, and this part is how
you tell the two apart: a flaky test is one whose *variation you did not intend*, and this one's variation
is deliberate.

---

## The mechanism

### Step 1 — the check passes, as it always has

```python
def assert_same_tokenizer(a, b, probes):
    for p in probes:
        ia, ib = a.encode(p).ids, b.encode(p).ids
        assert ia == ib, f"mismatch on {p!r}: {ia} != {ib}"

PROBES = ["plan", "The plan costs zero.", "zero budget", "Akshara"]
assert_same_tokenizer(ug, ug, PROBES)
print("  assert_same_tokenizer(ug, ug) passes")
print("  round trip on corpus:", ug.decode(ug.encode(text).ids) == text)
```

**Line by line:**

- `assert_same_tokenizer(ug, ug, ...)` passes the **same object twice**. On Day 14 that was the positive
  control — the case that must trivially pass, proving the check is not broken. Here it is about to become
  the failing case, which is why it is worth running first.
- The probe list is Day 14's, unchanged, so the comparison is like for like.

Measured, sampling off:

```text
  assert_same_tokenizer(ug, ug) passes
  round trip on corpus: True
```

Everything green. The tokenizer is deterministic and lossless.

### Step 2 — turn on the feature from part 2.4

```python
ug.model.nbest_size = 8
ug.model.alpha = 0.1

try:
    assert_same_tokenizer(ug, ug, PROBES)
except AssertionError as e:
    print("  FAILS:", str(e)[:90])
```

**Line by line:**

- Two lines of configuration and nothing else changes — same object, same probes, same function.
- `str(e)[:90]` truncates because the assertion message contains two full id sequences and the interesting
  part is the beginning: which probe, and that the two sides differ at all.
- Catching `AssertionError` specifically rather than `Exception`. If something else were raised, that would
  be a different and more alarming result, and it should not be swallowed here.

Measured:

```text
  FAILS: mismatch on 'The plan costs zero.': [54, 324, 422, 4, 594, 20] != [54, 80, 36, 13, 24, 120...
```

**The same object, compared against itself, disagrees.** Two calls, two different id sequences, one line
apart. Nothing changed between them except that a random draw happened.

Note that even the *lengths* differ — 6 ids against more than 6 — so a check on sequence length would also
fail, and a check on the first id (`54` in both) would pass. There is no cheap version of this check that
survives.

### Step 3 — how much variation is there?

```python
n = len({tuple(ug.encode("The plan costs zero.").ids) for _ in range(50)})
print(f"  same tokenizer, same string, 50 calls -> {n} distinct id sequences")
```

**Line by line:**

- A `set` of tuples counts distinct outcomes. `tuple` because lists are unhashable.
- Fifty calls on a twenty-character string.

Measured, on two separate runs:

```text
  same tokenizer, same string, 50 calls -> 40 distinct id sequences
  same tokenizer, same string, 50 calls -> 45 distinct id sequences
```

**Around forty distinct outputs from fifty calls** — and the count is itself a sample, so yours will
differ. Not an occasional flake that a retry would paper over: the odds of two consecutive calls agreeing
are low. A test suite containing this would fail most of the time, which is at least honest.

The dangerous version is the one that fails *rarely*. On the second run above, `assert_same_tokenizer`
happened to fail on the probe `'plan'` rather than on `'The plan costs zero.'` — a four-character word
with fewer segmentations, so its argmax dominates and it disagrees less often. Build a probe set out of
short common words and the check fails one run in twenty instead of nineteen in twenty, and then somebody
re-runs it until it goes green.

### Step 4 — and the round trip is still green

```python
print("  every sampled encoding round-trips:",
      all(ug.decode(ug.encode(p).ids) == p for p in PROBES for _ in range(20)))
```

**Line by line:**

- The same eighty-encoding check as part [2.4](2.4-subword-regularization.md), repeated deliberately in the
  part about a failing test. It is the control: the tokenizer is not broken, and this line is the evidence.
- Placing it immediately after the failure is the argument of the whole part — one check screaming, one
  check silent, and both correct.

```text
  every sampled encoding round-trips: True
```

**Fifth day running.** The tally, now complete:

| Day | The bug | Round trip |
| --- | --- | --- |
| 13 | non-canonical ids from concatenation | ✅ |
| 14 | merge list missing; special token forged; train/serve mismatch | ✅ |
| 15 part 1.4 | `[UNK]` swallowed the word — decoded to `''` | ❌ *(the one time it caught something)* |
| **15 part 2.5** | **the tokenizer is not a function** | ✅ |

The one time the round trip earned its place was part
[1.4](../01-wordpiece/1.4-the-word-that-became-one-unk.md), where information was genuinely destroyed. Every
other failure this week has been a *disagreement between two encodings*, and a round trip cannot see those
because each encoding is internally consistent.

### Step 5 — the fix, which is not to delete the check

The check is right. What is missing is a statement of what it assumes:

```python
def assert_same_tokenizer(a, b, probes):
    """Two tokenizers agree iff they produce identical ids on every probe.

    Requires both tokenizers to be DETERMINISTIC. A Unigram model with
    `nbest_size`/`alpha` set samples its segmentation (part 2.4), so this
    check does not apply to it - assert on the argmax instead.
    """
    for tok in (a, b):
        model = getattr(tok, "model", None)
        if getattr(model, "alpha", None) is not None:
            raise ValueError(
                "tokenizer has sampling enabled (alpha="
                f"{model.alpha}); disable it or compare argmax segmentations"
            )
    for p in probes:
        assert a.encode(p).ids == b.encode(p).ids, f"mismatch on {p!r}"
```

**Line by line:**

- The guard **raises `ValueError`, not `AssertionError`**. That distinction is the whole repair: an
  assertion failing means "these tokenizers disagree"; a `ValueError` means "this question does not apply
  here". Conflating them is what made the original confusing.
- `getattr(model, "alpha", None)` rather than `model.alpha`, because a BPE or WordPiece model has no
  `alpha` attribute at all. The check must work across all three families, and duck-typing with a default
  is the honest way to express "if this concept exists here".
- Checking `alpha` and not `nbest_size` because part 2.4 measured that **both** must be set for sampling to
  occur; testing either one alone is sufficient to catch the configuration.
- The docstring says what to do instead. An error that names the alternative is worth several times one
  that only says no.

And the test for a sampling tokenizer asserts a *property*, not a value:

```python
def assert_samples_are_valid(tok, probes, n=20):
    """A sampling tokenizer cannot be pinned to exact ids. Pin what must hold."""
    for p in probes:
        outputs = {tuple(tok.encode(p).ids) for _ in range(n)}
        assert len(outputs) > 1, f"{p!r} never varied - is sampling actually on?"
        for ids in outputs:
            assert tok.decode(list(ids)) == p, f"a sampled encoding of {p!r} did not round-trip"
```

**Line by line:**

- `assert len(outputs) > 1` asserts the variation **exists**, which is the configured behaviour. If it ever
  stopped varying, sampling has been silently turned off — the production bug from part 2.4, caught.
- The inner loop asserts every sampled encoding is *valid*. That is the invariant that survives sampling:
  the ids are not fixed, but they must always mean the string. This is the one place today where the round
  trip is exactly the right check.

## Shapes

| Name | Symbolic | Sampling off | Sampling on |
| --- | --- | --- | --- |
| `encode(p).ids` | `(T,)` | `(6,)`, always | `(6,)` … `(12,)`, varies |
| distinct outputs, 50 calls | scalar | `1` | **`40`** |
| corpus tokens | `(T,)` | `(43038,)` | `(61048,)`, `(61110,)`, `(60858,)` |
| round trips passing | scalar | all | all |

The first row is the one that breaks things downstream. `T` is the sequence axis of every `(B, T)` batch
from Day 16 onward, and it has stopped being a function of the input.

---

## When it breaks

**The failure is loud and it is the *diagnosis* that goes wrong.** `assert_same_tokenizer(ug, ug)` failing
reads as catastrophic — a tokenizer that disagrees with itself sounds like memory corruption. The instinct
is to hunt for a bug in the library. The actual cause is two lines you wrote yourself in another file.

**Sampling survives save and load**, because `alpha` and `nbest_size` are on the model and the model is
serialized. So the tokenizer that arrives in your serving stack can be sampling without anyone in that
stack having chosen it — Day 14's "the file is the contract" working exactly as designed, faithfully
carrying a setting you meant for training only.

**The dangerous version is a test that fails rarely.** With `alpha = 0.5` the argmax wins about two thirds
of the time, so a single-probe test fails roughly one run in three; with a shorter word it could be one in
fifty. That is the profile of a test everybody re-runs until it goes green — the exact behaviour the plan
forbids, because it is indistinguishable from Silent Failure #4.

**Deleting the check is the tempting wrong repair.** It caught a real bug on Day 14 — 4 of 4 probes
disagreeing from one flipped flag — and that bug has not gone away. The repair is to state the
precondition, not to remove the check.

---

## In production

**Save the deterministic tokenizer; sample in the data pipeline.** The artifact that travels should have
`alpha` unset, and the training loop should apply sampling as it builds batches. Then the file is a
function again, and every downstream consumer can rely on it.

**Log the tokenizer's configuration, not only its hash.** Day 14's advice was to hash `tokenizer.json` and
compare at both ends. That still works — two different `alpha` values give two different hashes — but the
hash tells you *that* something differs, not *what*. For a setting this consequential, log the value.

**Reproducibility is a property you arrange, and you should know its cost.** Principle 9 asks for seeds,
configs and hardware. This part adds the tokenizer to that list: "which tokenizer" is not enough, because
the same file can behave two ways. Every `docs/RUNS.md` row from Day 20 onwards should be able to answer
whether tokenization was deterministic.

**The general shape outlives the tokenizer.** A test written when a component was pure, kept after the
component acquired randomness, is one of the most common ways a suite decays into noise. The repair is
always the same and it is what step 5 does: make the precondition explicit and executable, so the test
tells you it does not apply rather than telling you something false.

## Check yourself

```python
from pathlib import Path
from tokenizers import Tokenizer, models, pre_tokenizers, decoders, trainers

text = Path("docs/00_MASTER_PLAN.md").read_text(encoding="utf-8")
ug = Tokenizer(models.Unigram())
ug.pre_tokenizer = pre_tokenizers.Metaspace()
ug.decoder = decoders.Metaspace()
ug.train_from_iterator([text], trainers.UnigramTrainer(
    vocab_size=1000, show_progress=False, special_tokens=["<unk>"], unk_token="<unk>"))

PROBES = ["plan", "The plan costs zero.", "zero budget", "Akshara"]

def naive_same(a, b, probes):
    for p in probes:
        assert a.encode(p).ids == b.encode(p).ids, f"mismatch on {p!r}"

# 1. deterministic: the Day 14 check works, including against itself
naive_same(ug, ug, PROBES)
print("sampling off: assert_same_tokenizer(ug, ug) passes")

# 2. the eval that can go red: enable sampling and it must FAIL
ug.model.nbest_size = 8
ug.model.alpha = 0.1
try:
    naive_same(ug, ug, PROBES)
    raise SystemExit("it passed - sampling is not actually enabled, so this part proves nothing")
except AssertionError as e:
    print("sampling on : FAILS against itself ->", str(e)[:60])

n = len({tuple(ug.encode("The plan costs zero.").ids) for _ in range(50)})
print(f"50 calls -> {n} distinct id sequences")
assert n > 10, "too little variation to make the point - raise nbest_size or lower alpha"

# 3. the round trip is still green, as it has been all week
assert all(ug.decode(ug.encode(p).ids) == p for p in PROBES for _ in range(20))
print("80 sampled encodings, 80 exact round trips")

# 4. the repair: a guard that says 'not applicable' rather than 'they disagree'
def guarded_same(a, b, probes):
    for tok in (a, b):
        if getattr(getattr(tok, "model", None), "alpha", None) is not None:
            raise ValueError("tokenizer has sampling enabled; disable it or compare argmax")
    for p in probes:
        assert a.encode(p).ids == b.encode(p).ids, f"mismatch on {p!r}"

try:
    guarded_same(ug, ug, PROBES)
    raise SystemExit("the guard did not fire")
except ValueError as e:
    print("guarded check correctly refuses:", e)
except AssertionError:
    raise SystemExit("got AssertionError - the guard must fire FIRST, before any encoding")

# 5. and with sampling off, the guard lets it through again
ug.model.nbest_size = None
ug.model.alpha = None
guarded_same(ug, ug, PROBES)
print("sampling off: guarded check passes")
```

**Line by line:**

- Block 2 is the eval that can go red, and it is inverted: the test fails if `naive_same` **succeeds**.
  `raise SystemExit` in the `try` rather than after it, so a pass cannot be mistaken for the expected path.
- `except AssertionError` in block 4 is separate from `except ValueError` and raises a *different* message.
  That distinction is the entire repair being tested: getting an `AssertionError` there would mean the
  guard ran too late and the check answered a question it should have refused.
- Block 5 is the positive control. A guard that refuses everything is not a fix, and without this block you
  would not know the difference.
- `assert n > 10` states the precondition for the finding, with a message saying which knob to turn — the
  same reflex as parts 1.1 and 2.1.
