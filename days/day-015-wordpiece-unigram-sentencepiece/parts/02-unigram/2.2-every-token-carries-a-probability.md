# 2.2 — Every token carries a probability

## One-line answer

A Unigram vocabulary is not a list of strings but a list of `(token, log probability)` pairs — measured
here, `▁` scores `-2.3162` (about 9.9% of all tokens) and the rarest score `-11.2305` — and those
probabilities sum to **0.972**, which makes the vocabulary a genuine probability distribution rather than a
lookup table.

---

## The story

A shop keeps two kinds of stock list.

The first is just what they sell: bread, milk, tea, matches. Useful for checking whether something is
stocked, useless for anything else.

The second records what fraction of a typical basket each item is. Bread turns up in a tenth of them;
matches in one in a thousand. Same items, and now the list can answer questions the first cannot — *is this
basket normal? which of two shopping lists is more likely to be real?*

The second list is bigger and harder to keep accurate. It also stops being an inventory and starts being a
model of the customers.

---

## The idea in plain language

Look at what the three families store, side by side. This is the difference that matters most:

| Family | The vocabulary is | Ordered? | Carries numbers? |
| --- | --- | --- | --- |
| **BPE** | an ordered list of merge *pairs* | **yes** — rank is priority | no |
| **WordPiece** | a set of strings | no | no |
| **Unigram** | a set of strings, **each with a log probability** | no | **yes** |

BPE's ranks look like numbers but are not quantities — rank 24 is not "twice as good" as rank 48, it is
simply earlier. WordPiece stores no numbers at all. Unigram stores a real probability per token, and that
probability is what makes parts [2.3](2.3-viterbi-picks-the-best-segmentation.md) and
[2.4](2.4-subword-regularization.md) possible.

The model is called a *unigram language model*, and the name is exact. It assumes each token is drawn
independently of its neighbours, so the probability of a segmentation is just the product of its pieces:

```text
P(pieces) = P(p₁) × P(p₂) × … × P(pₖ)
```

That independence assumption is obviously false — real text is not a bag of independent tokens — and it is
deliberately false. The whole job of the transformer you build from Day 30 is to model the dependence
between tokens. The tokenizer's job is only to propose the pieces, and for that a crude model is enough.

**Everything is stored as a log.** Multiplying a hundred probabilities each around `0.001` underflows a
64-bit float to exactly `0.0`, and then every segmentation ties at zero. Adding their logarithms cannot
underflow. So the product above becomes a sum, and the vocabulary file stores `log P` directly.

---

## Why Akshara needs it

**Because "store logs, add instead of multiply" is a reflex you need permanently.** It reappears in the
cross-entropy loss on Day 21, in log-softmax on Day 33, in beam search scoring on Day 45, and in every
place probabilities get combined. Meeting it here — where you can print the whole table and see the range
— is the cheap introduction.

**Because it is the concrete answer to "what makes Unigram probabilistic".** The word gets used loosely.
It means precisely this: there is a number attached to every token, the numbers form a distribution, and
the tokenizer uses them to *choose* rather than to follow a rule.

**Because the numbers are auditable.** You can sort the vocabulary by probability and read off what the
model thinks the corpus is made of. That is a debugging tool BPE and WordPiece do not offer, and part 2.3
uses it to explain a segmentation exactly.

---

## The mechanism

### Step 1 — the vocabulary is pairs

```python
import json, math

blob = json.loads(ug.to_str())
print("model keys:", list(blob["model"].keys()))
vocab = blob["model"]["vocab"]
print("entries:", len(vocab), "first 5:", vocab[:5])
```

**Line by line:**

- `ug.to_str()` serializes through the same JSON path Day 14 part
  [3.1](../../../day-014-tiktoken-and-the-pipeline/parts/03-the-remaining-gap/3.1-the-file-is-the-contract.md)
  dissected — reading what would ship rather than an in-memory accessor.
- `blob["model"]["vocab"]` is a **list of two-element lists**, not a dict. That shape is itself
  information: a BPE `vocab` is `{token: id}` and a Unigram `vocab` is `[[token, score], …]`, where the id
  is the *position* in the list.

Measured, `tokenizers==0.23.1`, corpus `9760f2b6d4340b97`:

```text
model keys: ['type', 'unk_id', 'vocab', 'byte_fallback']
entries: 1000 first 5: [['<unk>', 0.0], ['▁', -2.3161703602919843],
                        ['▁|', -3.432299280937719], [',', -3.565896536690645],
                        ['s', -3.5908350895468173]]
```

Note `byte_fallback` sitting right there in the model — the flag Day 14 part 3.1 listed and deferred. Part
[3.2](../03-sentencepiece/3.2-byte-fallback.md) turns it on.

### Step 2 — read the distribution

```python
for tok, score in sorted(vocab, key=lambda kv: -kv[1])[:12]:
    print(f"  {tok!r:12s} log p = {score:8.4f}   p = {math.exp(score):.5f}")
```

**Line by line:**

- `-kv[1]` sorts descending by score. Because these are logs of probabilities they are all negative, so
  "highest score" means "closest to zero" means "most probable".
- `math.exp(score)` converts back to a probability for reading. Do this for *display* only — never
  accumulate in probability space, which is the point of storing logs at all.

Measured:

```text
  '<unk>'      log p =   0.0000   p = 1.00000
  '▁'          log p =  -2.3162   p = 0.09865
  '▁|'         log p =  -3.4323   p = 0.03231
  ','          log p =  -3.5659   p = 0.02827
  's'          log p =  -3.5908   p = 0.02758
  '▁the'       log p =  -3.9815   p = 0.01866
  '|'          log p =  -3.9824   p = 0.01864
  '▁|\n'       log p =  -4.1438   p = 0.01586
  't'          log p =  -4.1937   p = 0.01509
  '-'          log p =  -4.2737   p = 0.01393
  '—'          log p =  -4.2946   p = 0.01364
  '▁and'       log p =  -4.3476   p = 0.01294
```

Three things to read out of this table.

**`▁` alone is 9.87% of all tokens.** A bare space-marker with nothing attached. That is what a
whitespace-heavy markdown document looks like to a tokenizer, and it is the same signal Day 14 part
[1.4](../../../day-014-tiktoken-and-the-pipeline/parts/01-tiktoken/1.4-your-merges-against-theirs.md) read
off the merge list when rank 0 came back as `('Ġ', '|')`.

**`▁|` and `|` are both in the top ten.** Markdown tables again — the corpus fingerprint, visible from a
completely different algorithm. Two independent methods agreeing about what this corpus is made of is
worth more than either alone.

**`<unk>` scores `0.0`, meaning probability 1.0.** That is not a real probability; it is a sentinel. The
unknown token is not competing with the others, and treating its score as a probability is a mistake the
next step guards against.

The bottom of the table is flat:

```text
  ']'   log p = -11.2305   p = 1.326e-05
  '%'   log p = -11.2305
  '~'   log p = -11.2305
  '↔'   log p = -11.2305
  '😬'   log p = -11.2305
```

Identical scores — **14 tokens share that exact floor** — for characters as different as `]` and an emoji.
That is the
floor: every one of these appeared once or twice, so the trainer assigned them all the same minimum. **The
tail of the distribution carries no information** — it says "rare" and nothing more. This matters for part
2.3, because ties in the tail mean several segmentations of a rare word can score identically.

### Step 3 — is it actually a distribution?

```python
total = sum(math.exp(s) for t, s in vocab if t != "<unk>")
print("probability mass excluding <unk>:", total)
```

**Line by line:**

- Excluding `<unk>` is mandatory, not tidying. Its sentinel score of `0.0` exponentiates to `1.0`, which
  would push the total to 1.97 and make the check meaningless.
- Summing in probability space is safe *here* because there are only 1,000 terms and none is
  vanishingly small. This is the exception that proves the rule about staying in log space.

Measured:

```text
probability mass excluding <unk>: 0.9724
```

**0.972, not 1.000.** The vocabulary is very nearly a probability distribution and deliberately not exactly
one. The missing 2.8% is the mass the EM loop assigned to candidates that were then **pruned** — part
[2.1](2.1-start-big-and-prune.md)'s 98.2% discard — and the surviving probabilities were not renormalized
afterwards.

That is worth knowing rather than worrying about. Segmentations are compared against each other, so a
constant factor common to all of them cancels; a missing 2.8% shifts every score by the same amount and
changes no ranking. But if you ever use these numbers as probabilities in their own right — computing a
perplexity, comparing across two vocabularies — you must renormalize first, and nothing in the file warns
you.

---

## Shapes

| Name | Symbolic | Concrete | Meaning |
| --- | --- | --- | --- |
| `vocab` | `(V, 2)` | `(1000, 2)` | `(token, log p)`; **id is the row index** |
| scores | `(V,)` | `(1000,)` | range `-11.2305 … 0.0` |
| probability mass | scalar | `0.9724` | excluding the `<unk>` sentinel |
| tokens tied at the floor | scalar | `14` at `-11.2305` | the uninformative tail |

`(V, 2)` is the shape that distinguishes this family. BPE's merge list is also `(n, 2)` but the second
column is a *string*, not a number — and that difference is the whole of parts 2.3 and 2.4.

---

## When it breaks

**Multiplying probabilities instead of adding logs.** A 100-token sequence of probabilities around `0.01`
gives `10⁻²⁰⁰`, which is `0.0` in float64. Every segmentation then scores exactly zero and the argmax is
whichever the sort happened to put first. No exception, no warning, and the output is a valid
segmentation — just an arbitrary one.

```text
math.prod([0.01] * 200)  ->  0.0
sum([math.log(0.01)] * 200)  ->  -921.03
```

**Treating `<unk>`'s score as a probability.** `exp(0.0) = 1.0` says the unknown token is certain. Include
it in a sum and you get 1.97; use it in a comparison and `<unk>` beats every real token. The sentinel must
be excluded explicitly, every time.

**Assuming the scores are normalized.** They sum to 0.972 here, and to something else on your corpus. Any
computation whose result depends on the absolute value rather than the differences is wrong by an amount
you have not measured.

**Reading meaning into the tail.** Five characters sharing the score `-11.2305` are not five equally
important tokens; they are five tokens the trainer had no evidence about. Sorting the vocabulary and
studying the bottom fifty tells you nothing, and it looks like it should.

---

## In production

**A tokenizer that carries probabilities can be sampled from**, and part
[2.4](2.4-subword-regularization.md) does. That is the capability BPE and WordPiece structurally cannot
offer: there is no distribution in a merge list to sample.

**The probabilities are also a corpus audit.** Sort by score and the top hundred tokens tell you what your
training data is — here, markdown tables and whitespace. Day 14 part 1.4 got the same signal from a merge
list by reading the ordering; here you read a quantity, which is easier to compare across vocabularies.

**Storing logs is not an optimization, it is a correctness requirement.** Every scoring path in this
curriculum from Day 21 onwards works in log space for the reason above. When you meet
`torch.log_softmax` rather than `softmax` followed by `log`, this is the same concern, handled by a
library that also cares about the numerics of the subtraction.

**The independence assumption is the model's known weakness and its reason for existing.** Unigram assumes
tokens are independent, which is wrong; the transformer exists to model exactly what Unigram ignores. A
tokenizer that tried to model context would be doing the model's job with none of the model's capacity, and
would bake its mistakes into the ids permanently.

## Check yourself

```python
import json, math
from pathlib import Path
from tokenizers import Tokenizer, models, pre_tokenizers, decoders, trainers

text = Path("docs/00_MASTER_PLAN.md").read_text(encoding="utf-8")
ug = Tokenizer(models.Unigram())
ug.pre_tokenizer = pre_tokenizers.Metaspace()
ug.decoder = decoders.Metaspace()
ug.train_from_iterator([text], trainers.UnigramTrainer(
    vocab_size=1000, show_progress=False, special_tokens=["<unk>"], unk_token="<unk>"))

vocab = json.loads(ug.to_str())["model"]["vocab"]
real = [(t, s) for t, s in vocab if t != "<unk>"]

# 1. every score is a log probability: negative, and exp() in (0, 1)
assert all(s < 0 for t, s in real), "a non-<unk> score was >= 0 - that is not a log probability"
assert all(0 < math.exp(s) < 1 for t, s in real)

# 2. the eval that can go red: near a distribution, and NOT exactly one
mass = sum(math.exp(s) for t, s in real)
print(f"probability mass: {mass:.4f}")
assert 0.9 < mass < 1.0, \
    f"mass {mass:.4f} outside (0.9, 1.0) - if it is >1 you left <unk> in; if far below, check pruning"

# 3. the id of a token is its row index
for i, (t, s) in enumerate(vocab[:20]):
    assert ug.token_to_id(t) == i, f"{t!r} is at row {i} but token_to_id says {ug.token_to_id(t)}"
print("id == row index, confirmed for the first 20")

# 4. the tail is flat - ties carry no information
floor = min(s for t, s in real)
n_floor = sum(1 for t, s in real if s == floor)
print(f"{n_floor} tokens share the floor score {floor:.4f}")
assert n_floor > 1, "no tied floor - your corpus may be large enough that every token has evidence"

# 5. why logs: show the underflow
print("product of 200 probabilities of 0.01:", math.prod([0.01] * 200))
print("sum of their logs                   :", sum([math.log(0.01)] * 200))
assert math.prod([0.01] * 200) == 0.0
```

**Line by line:**

- Check 2 is the eval that can go red and it is deliberately two-sided. `mass < 1.0` catches the `<unk>`
  mistake; `mass > 0.9` catches a broken or truncated vocabulary. The failure message names which side you
  fell off, because the two causes have nothing to do with each other.
- Check 3 pins the file format claim — that a Unigram id *is* a row index. If a future version reordered
  the list, every id in every trained model would shift, so this is worth an assertion rather than a
  comment.
- Check 5 asserts the underflow **happens**. Demonstrating the failure you are avoiding is more convincing
  than describing it, and it takes one line.
