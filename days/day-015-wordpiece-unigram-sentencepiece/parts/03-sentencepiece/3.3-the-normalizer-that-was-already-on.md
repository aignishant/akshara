# 3.3 — 💥 The normalizer that was already on

## One-line answer

SentencePiece applies a compatibility normalizer **by default**, so training on this corpus silently
destroys all **1,646** newlines, both `²` characters and all five `…` — a 1.24% character loss you never
switched on, never saw a warning about, and cannot recover.

---

## The story

🎬 **The scene.** You buy a second-hand car and drive it for a month. It handles beautifully.

Then a passenger asks why the seat is so far forward, and you realise you have never touched the seat. It
was where the previous owner left it. It suited you well enough that you never noticed it was a *setting*
rather than the car.

😬 **The naive fix.** Adjust the seat now. Fine — but the question that matters is not the seat.

💥 **Why it fails.** Every other adjustable thing in the car is also still where somebody else put it: the
mirrors, the suspension mode, the tyre pressures. You never audited any of them, because nothing failed.
Comfort is not evidence of correctness; it is evidence that nothing has hurt yet.

💡 **The insight.** The dangerous configuration is not the one you set wrongly. It is the one you never
knew was a configuration — and defaults are exactly that, arriving pre-decided and looking like the nature
of the thing.

---

## The idea in plain language

Day 14 part
[2.5](../../../day-014-tiktoken-and-the-pipeline/parts/02-the-tokenizers-pipeline/2.5-the-normalizer-that-broke-the-round-trip.md)
established what a compatibility normalizer does: NFKC rewrites `ﬁ` to `fi`, `½` to `1⁄2`, `²` to `2`. It
is a one-way door, it edits your corpus before any merge is learned, and it breaks
`decode(encode(s)) == s`.

That part switched it on deliberately, measured the damage, and concluded with a recommendation: modern
byte-level tokenizers use **no normalizer at all**, which is why the `tokenizers` pipeline printed
`normalizer: None`.

Then this section trained a SentencePiece model with no normalizer argument at all.

**It has one anyway.** SentencePiece's default `normalization_rule_name` is `nmt_nfkc` — an NFKC variant
with extra whitespace handling. So everything Day 14 part 2.5 warned about has been quietly happening
throughout section 3, including in the byte-fallback measurements of part
[3.2](3.2-byte-fallback.md).

This part measures it, and the point is not that the default is wrong. It is that **a default is a
decision somebody else made, and it is invisible precisely when it is working.**

---

## Why Akshara needs it

**Because Akshara's tokenizer gets built on Day 16 and will inherit somebody's defaults unless you look.**
Every parameter you do not pass is a parameter that was chosen for you, by people optimising for a
different corpus than yours.

**Because this one destroys newlines, and Akshara must write code.** 1,646 newlines gone from a 113 KB
document is not a subtlety. A model trained on this corpus through this tokenizer would never see a line
break and could never produce one.

**Because it is the last and best instance of this week's recurring lesson.** Five days, five silent
losses, and every one was found by measuring rather than reading. The habit generalises far past
tokenizers.

## The mechanism

### Step 1 — the round trip, on a model nobody configured

```python
sp = spm.SentencePieceProcessor(model_file="sp_True.model")
ids = sp.EncodeAsIds(text)
back = sp.Decode(ids)
print("chars in", len(text), "-> out", len(back), " exact:", back == text)
```

**Line by line:**

- This is the byte-fallback model from part [3.2](3.2-byte-fallback.md), which proved every byte
  representable. If anything should round-trip, it is this one.
- `Decode(ids)` and not `DecodePieces` — part 3.2's lesson, applied.

Measured, corpus `9760f2b6d4340b97`:

```text
chars in 110837 -> out 109468  exact: False
```

**1,369 characters gone — 1.24% of the corpus.** On a tokenizer whose whole selling point in part 3.2 was
that every byte round-trips.

Byte fallback did its job perfectly. The loss happened *before* the tokenizer ever saw the text.

### Step 2 — find what went

```python
from collections import Counter

co, cb = Counter(text), Counter(back)
for ch in ("\n", " "):
    print(f"  {ch!r:5s} orig {co[ch]:6d}  back {cb[ch]:6d}")

nonws_o = sum(v for k, v in co.items() if not k.isspace())
nonws_b = sum(v for k, v in cb.items() if not k.isspace())
print(f"  non-whitespace: {nonws_o} -> {nonws_b}")
```

**Line by line:**

- Counting **characters**, not comparing strings. Once a difference appears early, a positional comparison
  reports everything after it as different; a character census tells you *what* changed regardless of
  where.
- Separating whitespace from non-whitespace first, because they turn out to have different causes.

Measured:

```text
  '\n'  orig   1646  back      0
  ' '   orig  19504  back  19771
  non-whitespace: 89687 -> 89697
```

**Every newline in the document is gone — all 1,646 of them** — and the space count went *up*. Newlines
were converted to spaces and runs of whitespace collapsed. That is the `nmt` half of `nmt_nfkc`: whitespace
normalization aimed at sentence-per-line translation corpora, where a newline genuinely is just a
separator.

And non-whitespace went *up* by ten, which needs its own explanation.

### Step 3 — the ten extra characters

```python
for ch in sorted(set(co) | set(cb)):
    if not ch.isspace() and co[ch] != cb[ch]:
        print(f"  {ch!r:8s} U+{ord(ch):04X}  {co[ch]:5d} -> {cb[ch]:5d}  ({cb[ch] - co[ch]:+d})")
```

**Line by line:**

- `set(co) | set(cb)` is the union of characters in **both** strings, so a character that appears only
  after normalization — like the extra full stops from `…` — is not missed. Iterating over `co` alone would
  show the losses and hide the substitutions.
- `co[ch] != cb[ch]` on a `Counter` returns `0` for a missing key rather than raising, which is what makes
  the one-line comparison safe.
- Printing `U+{ord(ch):04X}` alongside the character, because `²` and `2` are hard to tell apart in a
  terminal and the code point is unambiguous. Day 10's habit.

Measured:

```text
  '.'      U+002E    935 ->   950  (+15)
  '2'      U+0032    445 ->   447  (+2)
  '²'      U+00B2      2 ->     0  (-2)
  '…'      U+2026      5 ->     0  (-5)
```

Four rows, two substitutions, and both are exactly the compatibility mappings Day 14 named:

- **`²` → `2`.** Two occurrences, two extra `2`s. This is *the same character* Day 14 part
  [1.2](../../../day-014-tiktoken-and-the-pipeline/parts/01-tiktoken/1.2-the-published-pattern-verbatim.md)
  identified as the single difference between the published regex and the stdlib approximation — category
  `No`, the one that made `n²` split differently. It turns up again here as the character SentencePiece
  destroys.
- **`…` → `...`.** Five ellipses gone, fifteen extra full stops. `5 × 3 = 15`. ✅

`x²` and `x2` are now indistinguishable to any model trained through this tokenizer. So are `…` and `...`.

Confirm it directly rather than inferring:

```python
for s in ["“quoted”", "café", "ﬁle", "½", "x²", "\xa0nbsp"]:
    print(f"  {s!r:12s} -> {sp.Normalize(s)!r}")
```

**Line by line:**

- `Normalize` runs the normalizer **alone**, without tokenizing. This is the cheapest possible audit of a
  tokenizer's normalization: six probes, one line, no training.
- The `▁` in every output is the metaspace prefix from part [3.1](3.1-the-metaspace-trick.md) — `Normalize`
  includes it, which is a reminder that "normalization" here bundles the whitespace handling with the
  Unicode folding.
- The last probe is a non-breaking space, U+00A0, written as an escape so it is visible in the source.

```text
  '“quoted”'   -> '▁“quoted”'
  'café'       -> '▁café'
  'ﬁle'        -> '▁file'
  '½'          -> '▁1⁄2'
  'x²'         -> '▁x2'
  '\xa0nbsp'   -> '▁nbsp'
```

`ﬁ` → `fi`, `½` → `1⁄2`, `²` → `2`, and a non-breaking space deleted outright. Day 14 part 2.5's exact
table, running by default, on a tokenizer nobody configured.

Note `café` survives — canonical characters are untouched. It is only *compatibility* mappings that
destroy, which is the NFC/NFKC distinction Day 10 part
[1.3](../../../day-010-unicode-code-points-bytes/parts/01-code-points/1.3-the-same-text-two-encodings.md)
drew and Day 14 part 2.5 priced.

### Step 4 — how it stayed hidden

Every check available in section 3 passed:

| Check | Result | Why it missed this |
| --- | --- | --- |
| `DecodePieces(pieces) == probe` | ✅ passes | reads surface strings, not ids (part 3.2) |
| byte fallback covers every byte | ✅ true | the loss is upstream of tokenization |
| no `<unk>` ids on any probe | ✅ true | normalization is not an unknown |
| short probes round-trip | ✅ `'The plan.'` | contains no newline and no compatibility character |
| `tokenizers` Metaspace round trip | ✅ `True` | **different library, no normalizer by default** |

The last row is the sharpest. Part [3.1](3.1-the-metaspace-trick.md) measured `tokenizers`' Unigram +
Metaspace round-tripping this corpus **exactly** — same algorithm, same `V`, same corpus. The difference is
not the algorithm; it is that one library defaults to a normalizer and the other defaults to none.

**Two implementations of one algorithm, disagreeing about 1,369 characters, because of a default neither
of them announced.** That is Day 14 part
[3.3](../../../day-014-tiktoken-and-the-pipeline/parts/03-the-remaining-gap/3.3-the-mismatch-the-library-will-not-catch.md)'s
mismatch, arriving from the one direction that day did not cover: not two configurations of one library,
but two libraries' idea of "the default".

### Step 5 — turn it off

```python
spm.SentencePieceTrainer.train(
    input="corpus.txt", model_prefix="sp_identity", vocab_size=1000,
    model_type="unigram", byte_fallback=True,
    normalization_rule_name="identity",        # <- the fix
    add_dummy_prefix=False,                     # <- and the leading-space fix from part 3.1
    remove_extra_whitespaces=False,              # <- and the whitespace collapse
    character_coverage=0.9995, minloglevel=2)
```

**Line by line:**

- `normalization_rule_name="identity"` is the no-op normalizer. It is a named rule, not a `None`, because
  SentencePiece always runs a normalizer — the question is only which one.
- `add_dummy_prefix=False` is the `prepend_scheme` from part 3.1 under its SentencePiece name, and it is
  the setting that ate a leading space there.
- `remove_extra_whitespaces=False` — **plural**, and the plural matters. `remove_extra_whitespace`
  (singular) is not a field, and passing it raises
  `RuntimeError: NOT_FOUND: unknown field name "remove_extra_whitespace" in TrainerSpec.` I wrote the
  singular first and the trainer refused it, which is Principle 7 working: the API told me, immediately,
  that I had guessed. It stops the whitespace collapse of step 2, which `identity` alone does not cover —
  a separate flag, found by probing the trainer rather than by assuming one switch did everything.

Three flags, none of which you would think to pass, all of which change the corpus. Measured, the three
together are exactly lossless:

```text
default : 110837 -> 109468  lost 1369 = 1.24%
identity: 110837 -> 110837  exact=True
```

## Shapes

| Name | Symbolic | Default | `identity` | Meaning |
| --- | --- | ---: | ---: | --- |
| corpus characters in | `(n,)` | `(110837,)` | `(110837,)` | what you have |
| characters out | `(n',)` | **`(109468,)`** | `(110837,)` | what survives |
| newlines | scalar | `1646 → 0` | preserved | every one |
| `²` | scalar | `2 → 0` | preserved | folded to `2` |
| `…` | scalar | `5 → 0` | preserved | folded to `...` |
| loss | scalar | **1.24%** | 0% | silent |

`n ≠ n'` is the row that matters, and it is the same row Day 14 part 2.5's Shapes table flagged. The
difference is that there you had switched the normalizer on.

---

## When it breaks

**It does not break. It is working as designed, for a corpus that is not yours.** `nmt_nfkc` was chosen for
machine-translation data: one sentence per line, where a newline is a record separator and `²` versus `2`
does not matter. Applied to markdown, code or mathematics, the same default is destructive.

**The loss is upstream of every check you have.** Byte fallback, unknown-id counts, piece inspection — all
operate on text that has *already* been normalized. There is no tokenizer-level check that can find this,
because by the time the tokenizer runs, the characters are gone. The only check is comparing the decoded
output against the **original file**.

**Comparing two libraries' output will point at the wrong cause.** `tokenizers` Unigram round-trips this
corpus; SentencePiece Unigram does not. The instinct is to conclude one implementation is buggy. Both are
correct; they disagree about a default. Day 14 part 3.3's remedy — compare configs, not just behaviour —
is what settles it.

**A model trained through this can never emit a newline.** Not "rarely" — never. The character does not
occur in its training data. That is the same absolute ceiling part
[1.4](../01-wordpiece/1.4-the-word-that-became-one-unk.md) established for `[UNK]`, reached by a completely
different route.

## In production

**Read every default before training a vocabulary, and write down what you chose.** Not because the
defaults are bad, but because they encode assumptions about a corpus. `docs/PACKAGES.md` records the
version; the training *configuration* deserves the same treatment, and Principle 9's "configs are
committed" is exactly this.

**Modern practice is `identity` plus byte fallback.** Do nothing to the text; represent everything. That
combination gives Day 13's guarantee and Day 14's losslessness together, and it is the configuration Day 16
should start from.

**Normalization has moved out of the tokenizer.** Where it is wanted, it belongs in the data pipeline,
where it is visible, versioned and auditable — not hidden inside a `.model` file as a default nobody
passed. The tokenizer's job is to represent text, not to decide what text means.

**This is the strongest case for the artifact discipline of Day 14.** A tokenizer file that carries its
normalizer explicitly makes this auditable: you can read the rule and know. A trainer default that is not
recorded in the output makes it archaeology.

## Check yourself

```python
from collections import Counter
from pathlib import Path
import sentencepiece as spm

text = Path("docs/00_MASTER_PLAN.md").read_text(encoding="utf-8")
Path("corpus.txt").write_text(text, encoding="utf-8")

def train(prefix, **kw):
    spm.SentencePieceTrainer.train(
        input="corpus.txt", model_prefix=prefix, vocab_size=1000,
        model_type="unigram", byte_fallback=True,
        character_coverage=0.9995, minloglevel=2, **kw)
    return spm.SentencePieceProcessor(model_file=prefix + ".model")

default = train("sp_default")
identity = train("sp_identity", normalization_rule_name="identity",
                 add_dummy_prefix=False, remove_extra_whitespaces=False)

# 1. the eval that can go red: the DEFAULT must lose characters
back = default.Decode(default.EncodeAsIds(text))
lost = len(text) - len(back)
print(f"default : {len(text)} -> {len(back)}  lost {lost} = {lost/len(text)*100:.2f}%")
assert back != text, "the default round-tripped - check your corpus has newlines"
assert text.count("\n") > 0 and back.count("\n") == 0, \
    "newlines survived the default normalizer - your sentencepiece version may differ; measure and record"

# 2. and 'identity' must not
back2 = identity.Decode(identity.EncodeAsIds(text))
print(f"identity: {len(text)} -> {len(back2)}  exact={back2 == text}")
assert back2 == text, "identity + byte_fallback should be lossless - print the first difference"

# 3. name the substitutions rather than just counting them
co, cb = Counter(text), Counter(back)
changed = {c: (co[c], cb[c]) for c in set(co) | set(cb)
           if not c.isspace() and co[c] != cb[c]}
print("non-whitespace changes:", {repr(c): v for c, v in sorted(changed.items())})
assert "²" in changed and "…" in changed, \
    "expected ² and … to be folded - if absent, your corpus differs from mine"

# 4. the normalizer is inspectable without training anything
for s in ["ﬁle", "½", "x²", "café"]:
    print(f"  {s!r:8s} -> {default.Normalize(s)!r}   identity: {identity.Normalize(s)!r}")
assert default.Normalize("x²") != identity.Normalize("x²")
```

**Line by line:**

- Check 1 is the eval that can go red and it asserts a **loss**, on a configuration nobody chose. Its
  second assertion names the newlines specifically, because a character count alone would not tell you the
  loss was structural rather than incidental.
- The failure messages say "measure and record" rather than "this is broken", because a different
  `sentencepiece` version could legitimately have different defaults — and Principle 6's answer to that is
  to look it up on the day, not to assume mine.
- Check 2 is the positive control. Without it, check 1 only proves something was lost, not that you can
  stop it.
- Check 4 uses `Normalize` directly, which is the cheapest possible audit: you can inspect a normalizer's
  behaviour on a probe **without training a vocabulary at all**. Do this before committing to a
  configuration, not after.
