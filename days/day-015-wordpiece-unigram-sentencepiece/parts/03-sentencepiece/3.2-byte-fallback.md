# 3.2 — Byte fallback

## One-line answer

`byte_fallback=True` adds 256 tokens spelled `<0x00>` … `<0xFF>` so a character with no vocabulary entry
becomes its raw UTF-8 bytes instead of `<unk>` — measured here, `café` goes from a lost `é` to
`['▁c','a','f','<0xC3>','<0xA9>']` — restoring Day 13's zero-OOV guarantee to a tokenizer that is not
byte-level.

---

## The story

A hotel takes messages for guests. The clerk writes down the caller's name, and when they cannot spell it,
the message says "someone called".

The guest gets a note that tells them nothing. Not the name spelled approximately — nothing.

The fix is not a better speller. It is a rule that when the clerk cannot spell a name, they write it down
**letter by letter as they heard it**. Ugly on the page, and the guest can read it back.

---

## The idea in plain language

Part [1.4](../01-wordpiece/1.4-the-word-that-became-one-unk.md) measured the worst failure in this day:
`café` becomes one `[UNK]` and decodes to the empty string. The word disappears. Six ordinary words out of
six were destroyed, and the corpus-level unknown rate said 0.000%.

Day 13 part
[3.3](../../../day-013-bpe-encode-decode-bytes/parts/03-byte-level-bpe/3.3-zero-out-of-vocabulary.md)
solved this completely by making the *alphabet* the 256 bytes. Every string is a sequence of bytes;
every byte has a token; therefore every string encodes. Guaranteed by construction, not by coverage.

But that solution is only available if you build the whole vocabulary out of bytes — which means paying
Day 13's cost, where a non-Latin character takes three tokens even when it is common. Unigram and
SentencePiece want a *character*-based vocabulary, so `योजना` can be one token if it is frequent enough.

**Byte fallback is the compromise.** Keep the character-based vocabulary, and add 256 extra entries — one
per byte value — used only when a character has no token of its own:

```text
'é' has no token         ->  emit <0xC3> <0xA9>    (its two UTF-8 bytes)
'योजना' has no token      ->  emit 15 byte tokens
'the' has a token        ->  emit that token, one id
```

Common text pays nothing. Unrepresentable text becomes expensive rather than impossible. And the round trip
is exact again, because bytes reconstruct anything — Day 10 part
[2.2](../../../day-010-unicode-code-points-bytes/parts/02-bytes-and-utf-8/2.2-how-utf-8-encodes-a-code-point.md)'s
whole point.

The cost is 256 vocabulary slots, permanently. That is 25.6% of a `V = 1000` vocabulary and 0.5% of a
`V = 50000` one — which tells you immediately why this is standard at production scale and awkward at toy
scale.

---

## Why Akshara needs it

**Because it is the property that decides whether a tokenizer can be used for generation at all.** Part 1.4
established the constraint: a model cannot write a character its tokenizer cannot represent. Byte fallback
is the general repair, available to every family, and Day 16 will want it.

**Because it explains a thing you will see in real vocabulary files.** `<0x0A>` entries in a
`tokenizer.json` mean byte fallback is on. Recognising that on sight tells you the model can handle
arbitrary input, which is worth knowing before you send it any.

**Because the trade is a clean example of "buy a guarantee with a fixed cost".** 256 slots, once, for
completeness forever. Most engineering trades are murkier than this one, and having a clean instance to
compare against is useful.

---

## The mechanism

This part uses `sentencepiece==0.2.2` directly, the canonical implementation, so you can see the
`.model` file the flag produces. Version looked up live on PyPI on 2026-08-27; licence Apache-2.0, read
from the installed distribution's METADATA.

### Step 1 — train the same vocabulary twice

```python
import sentencepiece as spm

for bf in (False, True):
    spm.SentencePieceTrainer.train(
        input="corpus.txt", model_prefix=f"sp_{bf}", vocab_size=1000,
        model_type="unigram", byte_fallback=bf,
        character_coverage=0.9995, minloglevel=2)
```

**Line by line:**

- `input=` takes a **file path**, not a string. SentencePiece is a command-line tool with a Python wrapper,
  so the corpus goes to disk first. Worth knowing before you wonder why a string argument fails.
- `model_type="unigram"` is the default, and it is the algorithm of section 2 — the pruning trainer, the
  probabilities, the Viterbi encoder. This section is the *packaging* around that algorithm, not a
  different one.
- `byte_fallback=bf` is the whole experiment: one flag, everything else held fixed.
- `character_coverage=0.9995` tells the trainer to cover 99.95% of characters seen and let the rest go —
  the knob that *creates* unknowns. With byte fallback on, the discarded 0.05% become byte sequences
  instead of unknowns.
- `minloglevel=2` suppresses the trainer's progress chatter. Cosmetic.

Measured, corpus `9760f2b6d4340b97`, `sentencepiece==0.2.2`:

| | `V` | tokens | chars/token | `.model` size |
| --- | ---: | ---: | ---: | ---: |
| `byte_fallback=False` | 1,000 | 42,049 | 2.636 | 256,209 B |
| `byte_fallback=True` | 1,000 | **46,770** | **2.370** | 255,791 B |

**Byte fallback cost 11.2% more tokens on the training corpus** — 46,770 against 42,049 — even though the
corpus contains almost nothing the vocabulary cannot represent. The 256 byte tokens took 256 slots that
would otherwise have held useful multi-character pieces, so every ordinary word is segmented slightly
worse. **You pay on common text for a guarantee about rare text.**

### Step 2 — what it buys

```python
for name, sp in (("off", model_off), ("on", model_on)):
    for probe in ["café", "กขฃ"]:
        ids = sp.EncodeAsIds(probe)
        print(f"  {name}: {sp.EncodeAsPieces(probe)}")
        print(f"       ids={ids}  n_unk={sum(1 for i in ids if i == sp.unk_id())}")
        print(f"       Decode(ids)={sp.Decode(ids)!r}  exact={sp.Decode(ids) == probe}")
```

**Line by line:**

- `EncodeAsPieces` returns token strings, which is what makes the byte tokens visible.
- **`Decode(ids)`, not `DecodePieces(pieces)`.** This distinction is the whole step and it is easy to get
  wrong — I got it wrong in the first draft of this part. `DecodePieces` reconstructs from the *piece
  strings*, and an unknown piece carries the original surface text, so it appears to round-trip. `Decode`
  goes through the **ids**, which is what a model actually receives, and an unknown id has no text in it.
- `sp.unk_id()` looked up rather than assumed, and counted — the check part
  [2.1](../02-unigram/2.1-start-big-and-prune.md) established: **count ids, never search token strings.**

Measured, `byte_fallback=False` — on `café` and on Thai, a script this corpus does not contain at all:

```text
  off: ['▁c', 'a', 'f', 'é']
       ids=[76, 10, 32, 0]  n_unk=1
       Decode(ids)='caf ⁇ '  exact=False
  off: ['▁', 'กขฃ']
       ids=[3, 0]  n_unk=1
       Decode(ids)=' ⁇ '  exact=False
```

Measured, `byte_fallback=True`:

```text
  on : ['▁c', 'a', 'f', '<0xC3>', '<0xA9>']
       ids=[332, 266, 288, 198, 172]  n_unk=0
       Decode(ids)='café'  exact=True
  on : ['▁', '<0xE0>', '<0xB8>', '<0x81>', '<0xE0>', '<0xB8>', '<0x82>', '<0xE0>', '<0xB8>', '<0x83>']
       ids=[259, 227, 187, 132, 227, 187, 133, 227, 187, 134]  n_unk=0
       Decode(ids)='กขฃ'  exact=True
```

Three things, and the first is a warning about how easy this is to get wrong.

**The piece strings lie and the ids do not.** Look at the `off` rows: `EncodeAsPieces` reports `'é'` and
`'กขฃ'` — the original text, apparently intact. The **id is `0`**, which is `unk_id()`. Decoding through the
pieces reconstructs the surface text and looks perfect; decoding through the ids gives `'caf ⁇ '`, where
`⁇` is U+2047 DOUBLE QUESTION MARK, SentencePiece's rendering of an unknown. **A model receives ids.** This
is the third time today that a token string has misreported an unknown — part
[2.1](../02-unigram/2.1-start-big-and-prune.md) with `.tokens`, part
[1.4](../01-wordpiece/1.4-the-word-that-became-one-unk.md) with `skip_special_tokens`, and now
`DecodePieces` — and every time the repair is the same: **count ids.**

**Without the flag, characters outside coverage are destroyed.** `café` → `'caf ⁇ '`. Not as badly as
WordPiece's whole-word `[UNK]` from part 1.4, which decoded to nothing at all, but destroyed: the `é` is
unrecoverable and the text has gained a space.

**With the flag, both are exact**, including a script the vocabulary has never seen. That is the difference
between coverage as a *measurement* — 99.95% of characters seen, anything else lost — and coverage as a
*construction*: any byte sequence decodes, including characters that were never in the corpus and never
could have been.

That is exactly the distinction Day 13 part 3.3 drew between a coverage percentage and a coverage
construction, arriving here from a different direction.

**And the byte counts are the UTF-8 widths from Day 10.** `é` → 2 bytes, each Devanagari character → 3
bytes (five characters, 15 tokens), the emoji → 4 bytes. Day 10 part
[2.2](../../../day-010-unicode-code-points-bytes/parts/02-bytes-and-utf-8/2.2-how-utf-8-encodes-a-code-point.md)'s
width table, showing up as token counts.

### Step 3 — the cost, stated properly

The Devanagari row is the one to hold on to. `योजना` is five characters and becomes **15 tokens**, one per
byte. Day 14 part
[3.2](../../../day-014-tiktoken-and-the-pipeline/parts/03-the-remaining-gap/3.2-the-tax-a-vocabulary-charges-a-language.md)
measured the general tax a vocabulary charges a language; this is the *floor* of that tax — what you get
when the vocabulary has learned nothing at all about a script.

So byte fallback is not a fix for the multilingual tax. It converts **impossible** into **expensive**, and
those are different problems with different solutions:

| Problem | Symptom | Fix |
| --- | --- | --- |
| character not representable | `<unk>`, decodes to `''` | **byte fallback** |
| character representable but costly | 15 tokens for 5 characters | multilingual training corpus |

Part 1.4's `café` needed the first. Day 14 part 3.2's Hindi needed the second. Confusing them leads to
turning on byte fallback and expecting the token counts to improve, which is the opposite of what step 1
measured.

## Shapes

| Name | Symbolic | Without | With | Meaning |
| --- | --- | --- | --- | --- |
| `V` | scalar | 1,000 | 1,000 | same budget |
| slots spent on bytes | scalar | 0 | **256** | 25.6% of this vocabulary |
| corpus `ids` | `(T,)` | `(42049,)` | `(46770,)` | **+11.2%** |
| `café` | `(T,)` | `(4,)` | `(5,)` | `é` → 2 byte tokens |
| `योजना` | `(T,)` | `(2,)` | `(16,)` | 5 characters → 15 bytes + `▁` |
| unknown characters possible | — | yes | **no** | the guarantee |

The last row is the only one that improves, and it is the only one that is a *guarantee* rather than a
measurement.

---

## When it breaks

**Turning it on and expecting better compression.** Measured: 11.2% *worse* on this corpus. The 256 slots
come out of the same budget. If your `V` is small this is a large fraction — 25.6% here — and the
compression loss is real and immediate.

**Byte tokens are meaningless individually.** `<0xC3>` is not a character; it is the first half of one.
A model that generates `<0xC3>` and then something other than a valid continuation byte has produced
invalid UTF-8, and the decoder must handle it — the incomplete-character problem Day 13 part
[1.4](../../../day-013-bpe-encode-decode-bytes/parts/01-encode-and-decode/1.4-the-token-that-was-half-a-character.md)
built a streaming decoder for. Byte fallback makes that failure reachable in a tokenizer that otherwise
never emits partial characters.

**It does not help a model learn the script.** Fifteen tokens of undifferentiated bytes for one Hindi word
give the model very little structure to work with, and consume context at Day 14 part 3.2's worst rate. The
text is representable; that is all.

**`character_coverage` is the setting that creates the problem byte fallback solves**, and the two are
usually set without reference to each other. At `1.0` there are no unknowns to fall back for on the training
corpus — but unseen characters at inference still need the fallback, which is the whole point of a
construction over a measurement.

---

## In production

**This is standard on modern vocabularies and the 256 slots are a rounding error there.** At `V = 32000` or
`V = 128000`, 256 tokens is 0.8% or 0.2% of the budget, and the measured compression loss shrinks to
nothing because there are plenty of slots left for real pieces. The trade this part measured at `V = 1000`
is the worst case, not the typical one.

**It is why `<unk>` has largely disappeared from new tokenizers.** An unknown token is a design from before
byte fallback was standard. When you meet one now — as in part 1.4's WordPiece — it tells you something
about the vintage and the intended use of the model.

**The interaction with special tokens matters.** Byte tokens are written `<0xC3>`, which looks like the
special-token syntax from Day 14 part
[1.5](../../../day-014-tiktoken-and-the-pipeline/parts/01-tiktoken/1.5-the-special-token-that-was-just-text.md).
They are not special tokens — they are ordinary vocabulary entries that happen to be spelled that way — and
code that filters "anything matching `<...>`" out of model output will silently corrupt every non-ASCII
character. That is the `##` collision of part
[1.2](../01-wordpiece/1.2-the-hash-hash-convention.md) once more: a marker sharing a channel with data.

**Choose it at vocabulary-training time or not at all.** Adding byte fallback later means 256 new
vocabulary entries, which means 256 untrained rows in a `(V, C)` embedding matrix. Day 16 (`TOK-17`) does
that resize deliberately and measures what it costs.

## Check yourself

```python
import json
from pathlib import Path
import sentencepiece as spm

text = Path("docs/00_MASTER_PLAN.md").read_text(encoding="utf-8")
Path("corpus.txt").write_text(text, encoding="utf-8")

models = {}
for bf in (False, True):
    prefix = f"sp_{bf}"
    spm.SentencePieceTrainer.train(
        input="corpus.txt", model_prefix=prefix, vocab_size=1000,
        model_type="unigram", byte_fallback=bf,
        character_coverage=0.9995, minloglevel=2)
    models[bf] = spm.SentencePieceProcessor(model_file=prefix + ".model")

# 1. the flag adds exactly 256 tokens spelled <0xNN>
byte_toks = {bf: [m.IdToPiece(i) for i in range(m.GetPieceSize())
                  if m.IdToPiece(i).startswith("<0x")] for bf, m in models.items()}
print({bf: len(v) for bf, v in byte_toks.items()})
assert len(byte_toks[False]) == 0, "byte tokens present without the flag"
assert len(byte_toks[True]) == 256, f"expected 256, got {len(byte_toks[True])}"

# 2. the eval that can go red: byte fallback COSTS compression
n_off = len(models[False].EncodeAsIds(text))
n_on = len(models[True].EncodeAsIds(text))
print(f"tokens: off {n_off}, on {n_on} -> {(n_on/n_off - 1) * 100:+.1f}%")
assert n_on > n_off, "byte fallback did not cost anything - check the 256 slots came from V"

# 3. what it buys is a guarantee, so test it on characters NOT in the corpus
UNSEEN = ["กขฃ", "აბგ", "🧪"]   # Thai, Georgian, an emoji
off, on = models[False], models[True]
for probe in UNSEEN:
    assert probe not in text, "pick a probe your corpus does not contain"
    ids_off, ids_on = off.EncodeAsIds(probe), on.EncodeAsIds(probe)
    # without fallback: the PIECES look fine and the IDS say otherwise
    assert off.unk_id() in ids_off, f"{probe!r} was covered without fallback - pick a rarer script"
    assert off.DecodePieces(off.EncodeAsPieces(probe)) == probe,         "DecodePieces round-tripped - that is the trap; it reads surface strings, not ids"
    assert off.Decode(ids_off) != probe, "Decode(ids) round-tripped without fallback - it should not"
    # with fallback: no unknown ids at all, and Decode(ids) is exact
    assert on.unk_id() not in ids_on, f"{probe!r} still produced <unk> with fallback on"
    assert on.Decode(ids_on) == probe, f"{probe!r} did not round-trip through ids"
    print(f"  {probe!r:8s} off -> {off.Decode(ids_off)!r:8s}   on -> {on.Decode(ids_on)!r}")

# 4. the byte counts are UTF-8 widths (Day 10)
for probe in ["café", "योजना", "😀"]:
    pieces = models[True].EncodeAsPieces(probe)
    n_bytes = sum(1 for p in pieces if p.startswith("<0x"))
    print(f"  {probe!r:10s} {n_bytes} byte tokens")
```

**Line by line:**

- Check 1 asserts **exactly 256**, not "at least one". The flag's contract is one token per byte value; a
  different count means something else is happening.
- Check 2 is the eval that can go red, and it asserts the **cost**. Most people turn this flag on expecting
  a free improvement; pinning the regression is how you remember it is a trade.
- Check 3 is the one that actually tests the guarantee, and it uses scripts **absent from the corpus** —
  asserted, with `assert probe not in text`. Testing byte fallback on characters your corpus contains
  measures nothing. Silent Failure #5, guarded against explicitly.
- Inside it, the pair of assertions on `DecodePieces` and `Decode` is the trap made executable: the first
  asserts the misleading call **succeeds**, the second asserts the honest one **fails**. Writing both down
  is how you stop yourself reaching for the convenient one next time — it is the mistake that got into this
  part's first draft.
- Check 4 connects the token counts back to Day 10's UTF-8 width table, so the numbers are predictable
  rather than surprising.
