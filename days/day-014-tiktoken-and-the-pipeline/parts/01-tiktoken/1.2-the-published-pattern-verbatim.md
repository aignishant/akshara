# 1.2 — The published pattern, verbatim

## One-line answer

Day 13 could only approximate the published split pattern because the standard library has no `\p{L}`;
with `regex` installed you can now run the real thing, and measured on this corpus the approximation was
wrong in exactly **two places out of 28,889** — both of them the string `n²`, both caused by one character
whose Unicode category is `No`.

---

## The story

You copy a recipe from a friend over the phone. They say "a pinch of the red one" and you write down
"chilli". Everything you cook from that note tastes right for a year.

Then you finally see the written recipe, and it says paprika.

For a year, nothing went wrong — because almost everything you cooked, chilli and paprika would both have
been fine in. The note was not right. It was *right on the things you happened to cook*.

Finding the one dish where it matters is not a failure of the note. It is the only way you were ever going
to learn the note was a guess.

---

## The idea in plain language

Day 13 part
[2.2](../../../day-013-bpe-encode-decode-bytes/parts/02-the-regex-pre-tokenizer/2.2-the-gpt-pattern-symbol-by-symbol.md)
took the published GPT-2 split pattern apart branch by branch, and then hit a wall: two of its branches use
`\p{L}` and `\p{N}`, meaning "any Unicode letter" and "any Unicode number", and Python's built-in `re`
module does not support them. That day wrote an approximation and said so in writing:

> `[^\W\d_]` is the stdlib idiom for "a letter".

It also promised that Day 14 would install `regex` and check. This part is that check. This is what
Principle 7 means in practice: **an approximation is a `TODO` with a date on it, not a conclusion.**

The question is not "is the approximation good?" — it is "**where exactly** is it wrong, and would I have
noticed?" A difference you cannot characterise is a difference you cannot reason about. A difference you
can name in one sentence ("it disagrees on characters in category `No`") is something you can decide about.

---

## Why Akshara needs it

Because the pre-tokenizer is baked into the merge list, and the merge list is a file you ship.

Day 13 part [2.3](../../../day-013-bpe-encode-decode-bytes/parts/02-the-regex-pre-tokenizer/2.3-what-the-pattern-costs-and-buys.md)
established that a merge list is only valid under the pattern it was trained with. If you train under an
approximation and serve under the real pattern — or the reverse — you have manufactured Silent Failure #2,
and the round-trip test will not catch it. Part
[3.3](../03-the-remaining-gap/3.3-the-mismatch-the-library-will-not-catch.md) demonstrates that failure end
to end.

So before Akshara's tokenizer becomes load-bearing on Day 16, the pattern has to be the real one, verified
against the source it came from, on the version actually pinned. That is Principle 7, and this part is
where the debt gets paid rather than carried.

## The mechanism

### Step 1 — read the pattern from the library, not from memory

```python
import inspect
import tiktoken_ext.openai_public as op

src = inspect.getsource(op)
i = src.find("r50k_pat_str =")
print(src[i:src.find("\n\n", i)])
```

**Line by line:**

- `inspect.getsource(op)` reads the source of the module that actually shipped in the installed wheel. Not
  a blog post, not a docs page, not my memory — the file on this disk, for `tiktoken==0.14.0`. That is what
  Principle 7 asks for: verified against the library's own source, for the version pinned, on the day it
  is used.
- `tiktoken_ext.openai_public` is a plugin module `tiktoken` loads to find its built-in encodings. It is
  importable, which makes the pattern inspectable without unzipping anything.
- Printing up to the first blank line captures the whole assignment, which spans several lines.

Output, verbatim, from `tiktoken==0.14.0`:

```text
r50k_pat_str = (
    r"""'(?:[sdmt]|ll|ve|re)| ?\p{L}++| ?\p{N}++| ?[^\s\p{L}\p{N}]++|\s++$|\s+(?!\S)|\s"""
)
```

Two things in there are worth stopping on, because neither appeared in Day 13's reconstruction.

**`++` is a possessive quantifier.** `\p{L}++` means "as many letters as possible, and never give any
back". An ordinary `+` will backtrack — if the rest of the pattern fails to match, the engine retreats one
character at a time and tries again. A possessive `+` refuses. For this pattern the matches are identical
either way, and the possessive form makes the runtime linear instead of potentially catastrophic on
adversarial input. It is a denial-of-service guard on a function that runs on untrusted user text.

Possessive quantifiers **are** supported by the standard library on this Python (3.12.12) — verified by
compiling `r" ?\w++"` with `re`, which succeeds. They arrived in Python 3.11. So `++` was never what
blocked Day 13; `\p{L}` was, and it was the only thing that was.

**`\s++$` is a branch Day 13's reconstruction did not have.** It handles trailing whitespace at the end of
the string. Day 13's approximation used `\s+(?!\S)|\s+`, whose final `\s+` catches that case anyway — which
is why the chunk counts come out so close.

### Step 2 — run both and count

```python
import re as stdre
import regex
import tiktoken

R50K = tiktoken.get_encoding("gpt2")._pat_str
GPT_LIKE = r"'(?:[sdmt]|ll|ve|re)| ?[^\W\d_]+| ?\d+| ?[^\s\w]+| ?_+|\s+(?!\S)|\s+"

published = regex.findall(R50K, text)
approx = stdre.findall(GPT_LIKE, text)

print(f"published : {len(published):6d} chunks, {len(set(published)):5d} distinct, "
      f"lossless={''.join(published) == text}")
print(f"approx    : {len(approx):6d} chunks, {len(set(approx)):5d} distinct, "
      f"lossless={''.join(approx) == text}")
print("identical chunk lists:", published == approx)
```

**Line by line:**

- `import regex` — the third-party module, pinned at `2026.7.19` and recorded in `docs/PACKAGES.md`. It
  arrived as a dependency of `tiktoken` rather than a direct pin, which is why its row says so. It is a
  near drop-in for `re` with full Unicode property support.
- `enc._pat_str` has a leading underscore, which means it is not a promised public API and could change
  between versions. It is used here because it is the value the *installed* object is actually using,
  which is stronger evidence than the source text for the purpose of "what will this encoder do". The
  source read in step 1 is the citation; this is the runtime check. When they agree, you know the
  encoding you loaded is the one the source describes.
- `''.join(chunks) == text` is the losslessness check from Day 12 part
  [1.4](../../../day-012-bpe-the-merge-loop/parts/01-the-merge-loop/1.4-the-pre-tokenizer.md). A
  pre-tokenizer that drops a character is a pre-tokenizer that has silently edited your corpus. Both
  patterns pass.
- `set(chunks)` counts distinct chunks, which is what drives training cost — Day 13 part 2.3 measured that.

Measured on corpus `9760f2b6d4340b97`:

| Pattern | chunks | distinct | lossless |
| --- | ---: | ---: | --- |
| published, under `regex` | 28,889 | 3,699 | ✅ |
| Day 13 approximation, under `re` | 28,887 | 3,699 | ✅ |

**Two chunks apart out of 28,889** — a disagreement rate of 0.007%. The distinct-chunk counts are
identical.

### Step 3 — find the two, and name the cause

A difference of two is not a result. *Which* two, and *why*, is the result. Comparing the chunk lists
element by element stops being meaningful after the first disagreement, because everything shifts by one.
Compare **boundaries** instead:

```python
def spans(chunks):
    """Chunks -> the (start, end) character offsets they occupy."""
    out, pos = [], 0
    for c in chunks:
        out.append((pos, pos + len(c)))
        pos += len(c)
    return out

only_approx = sorted(set(spans(approx)) - set(spans(published)))
for a, b in only_approx:
    print(f"approx keeps {text[a:b]!r} as one chunk; published splits it")
```

**Line by line:**

- `spans` converts a chunk list into the set of character ranges it covers. Because both lists are lossless
  and cover the same string, this makes them directly comparable regardless of how many chunks each has.
- `set(...) - set(...)` gives the spans that exist in one segmentation and not the other. This is the right
  comparison for two segmentations of the same string, and it is a technique worth keeping: it will come
  back for aligning offsets in part [2.3](../02-the-tokenizers-pipeline/2.3-offsets-are-the-product.md).
- Sorting keeps the report in document order.

Output:

```text
approx keeps 'n²' as one chunk; published splits it
approx keeps 'n²' as one chunk; published splits it
```

Two occurrences of the same two-character string. Now the cause:

```python
import unicodedata
c = "²"
print(f"{c!r} U+{ord(c):04X} {unicodedata.name(c)}")
print("  category            :", unicodedata.category(c))
print("  Python .isalnum()   :", c.isalnum())
print("  matches [^\\W\\d_]    :", bool(stdre.fullmatch(r"[^\W\d_]", c)))
print("  matches \\p{L}       :", bool(regex.fullmatch(r"\p{L}", c)))
print("  matches \\p{N}       :", bool(regex.fullmatch(r"\p{N}", c)))
```

**Line by line:**

- `unicodedata.category` returns the two-letter general category from Day 10 part
  [1.2](../../../day-010-unicode-code-points-bytes/parts/01-code-points/1.2-what-a-code-point-carries.md).
  `L*` is a letter, `N*` is a number; `Nd` is specifically a *decimal digit*, `No` is "other number".
- `[^\W\d_]` reads as "a word character that is neither a digit nor an underscore". The subtlety is what
  each class means to Python: `\w` matches anything `str.isalnum()` accepts, which includes `No`; `\d`
  matches **only** category `Nd`. So a `No` character is `\w`, is not `\d`, is not `_` — and falls through
  the negation into the "letter" class.
- `fullmatch` rather than `search`, so the whole character must match the class.

Output:

```text
'²' U+00B2 SUPERSCRIPT TWO
  category            : No
  Python .isalnum()   : True
  matches [^\W\d_]    : True
  matches \p{L}       : False
  matches \p{N}       : True
```

There it is, in one line. **`²` is a number, and the stdlib approximation calls it a letter.** So the
approximation glues it to the preceding `n` under the letter branch, while the published pattern sends it
to the `\p{N}` branch and splits.

The class of characters affected is exactly `No` and `Nl` — superscripts, subscripts, fractions like `½`,
circled digits, Roman numerals. They are rare in English prose and not rare at all in mathematics, physics,
recipes, or anything with a footnote marker.

No tensors in this part. The relevant quantity is the chunk count, which is the input to training and the

| `set(published)` | `(n_distinct,)` | `(3699,)` | what the trainer actually counts over |

## When it breaks

**The stdlib refuses the published pattern, loudly.** Paste it into `re.compile` and you get:

```text
re.error: bad escape \p at position 23
```

This is the error Day 13 part 2.2 predicted and could not run. It is a good failure: `re` does not guess
what `\p` might have meant. Position 23 is the first `\p{L}` in the pattern — the `'(?:[sdmt]|ll|ve|re)| ?`
prefix is 23 characters long, and everything before that point is ordinary `re` syntax.

**The failure that is *not* loud** is the one this part exists for. Both patterns are lossless. Both give
3,699 distinct chunks. Both train without complaint. Train a vocabulary under one and encode with the
other, and every string containing a `No` character tokenizes differently — with no error, no warning, and
a passing round-trip test. On this corpus that is two strings; on a physics corpus it could be thousands.

Here is that silent difference, made visible:

```text
probe        published                    approximation
'n²'         ['n', '²']                   ['n²']
'½ cup'      ['½', ' cup']                ['½', ' cup']
'x³ + y²'    ['x', '³', ' +', ' y', '²']  ['x³', ' +', ' y²']
```

Note the middle row: `½` at the *start* of a chunk behaves identically under both, because there is no
preceding letter to glue it to. The bug only appears when a `No` character follows a letter. That is
precisely why a small probe set misses it — and precisely Silent Failure #5, evaluated on the format you
trained on. An English-only probe list will never contain `n²`.

## In production

**Nobody writes this pattern by hand any more, and you should not either.** Having now written it twice —
approximately on Day 13, exactly here — you know what it does, which is the point of Principle 3. In
Akshara from Day 16 onwards the pattern comes from the tokenizer file, not from a string literal in your
code. Part [3.1](../03-the-remaining-gap/3.1-the-file-is-the-contract.md) is about that file.

**The patterns have kept changing.** The `cl100k_base` encoding uses a different pattern from `gpt2` — most
visibly it caps runs of digits at three, which is the fix Day 13 part
[2.4](../../../day-013-bpe-encode-decode-bytes/parts/02-the-regex-pre-tokenizer/2.4-the-number-that-was-three-tokens.md)
worked out from first principles. The `o200k_base` pattern goes further again, splitting on
letter-category boundaries so that scripts do not merge into one another. Each change is a bet about what
text the model will see, and each one is baked permanently into a vocabulary that cannot be changed after
training without retraining the model.

**Regex is a real cost at scale.** Pre-tokenization is the slowest stage of tokenizing in most
implementations — this is why the possessive quantifiers are there, and why `tokenizers` and `tiktoken`
both implement the split in Rust rather than calling back into Python.

**The `No` bug is the shape of most Unicode bugs.** Not a crash — a category you did not think about,
handled by a class you assumed meant something slightly different, on input you did not test. The defence
is not cleverness; it is testing on text that is not English, which Day 17 (`TOK-18`) makes a standing
practice.

## Check yourself

```python
import re as stdre
import regex
import unicodedata
from pathlib import Path
import tiktoken

text = Path("docs/00_MASTER_PLAN.md").read_text(encoding="utf-8")
R50K = tiktoken.get_encoding("gpt2")._pat_str
GPT_LIKE = r"'(?:[sdmt]|ll|ve|re)| ?[^\W\d_]+| ?\d+| ?[^\s\w]+| ?_+|\s+(?!\S)|\s+"

pub, ap = regex.findall(R50K, text), stdre.findall(GPT_LIKE, text)
assert "".join(pub) == text, "published pattern is lossy"
assert "".join(ap) == text, "approximation is lossy"
print("published", len(pub), "approx", len(ap), "delta", len(pub) - len(ap))

# the eval that can go red: every disagreement must be a No/Nl character
def spans(cs):
    out, p = [], 0
    for c in cs:
        out.append((p, p + len(c))); p += len(c)
    return out

diff = set(spans(ap)) - set(spans(pub))
culprits = {c for a, b in diff for c in text[a:b] if not c.isascii()}
print("culprits:", {c: unicodedata.category(c) for c in culprits})
assert all(unicodedata.category(c) in ("No", "Nl") for c in culprits), \
    "a disagreement that is NOT explained by the No/Nl category — investigate"
```

**Line by line:**

- The final `assert` is the eval that can go red (Principle 11), and it is stronger than a count. Counting
  says "two differences"; this says "**every** difference is explained by the one cause I named". If you
  run this on a corpus with a different Unicode profile and it fails, you have found a second cause — which
  is exactly what you want a test to tell you.
- `c.isascii()` filters to non-ASCII characters, since an ASCII-only disagreement would mean something
  quite different and should be investigated by hand.
- Note that `diff` is `approx - published`: spans the approximation kept that the published pattern split.
  The reverse direction contains the split pieces and is less informative.
