# 1.3 — What a vocabulary file looks like

## One-line answer

`gpt2` ships **two** files — a 50,000-line merge list and a 50,257-entry token→id map — while
`cl100k_base` ships **one** 100,256-line file of `base64(token bytes) rank` and **no merge list at all**,
because the rank-based encoder you wrote on Day 13 does not need one.

---

## The story

Two shops keep track of their prices differently.

The first keeps the old paper trail: every time a price changed, a dated line in a ledger. To find today's
price you read the ledger from the top and apply every change in order.

The second keeps one card per item with today's price on it. No history. If you ask *why* the price is what
it is, nobody can tell you — but if you just want to charge somebody, the card is faster and it cannot be
read out of order.

Both shops sell the same things for the same money. One of them can answer a question the other cannot, and
the other never needs to ask it.

---

## The idea in plain language

A trained BPE tokenizer has two things in it, and Day 13 part
[1.3](../../../day-013-bpe-encode-decode-bytes/parts/01-encode-and-decode/1.3-from-tokens-to-ids.md)
established both:

1. **The merge list** — an *ordered* sequence of pairs. Order is meaning: the pair at index 0 is applied
   before the pair at index 1, always. This is the history.
2. **The token→id map** — which integer stands for which byte string. This is the card.

The surprise is that you can throw the merge list away.

Day 13 part [1.1](../../../day-013-bpe-encode-decode-bytes/parts/01-encode-and-decode/1.1-encoding-applies-merges-by-rank.md)
built the fast encoder by turning the merge list into a *rank* dictionary — pair → position in the list —
and then repeatedly merging whichever adjacent pair had the lowest rank. That encoder never walks the merge
list in order. It only ever asks "what rank does this pair have?"

And here is the step that makes the file format make sense: **the rank of a merged token is the same number
as the id it would get.** Merge number 5 creates a token that lands at id `256 + 5`. So a table of
token → id *already is* a table of merge → rank. You do not need to store the pairs, because you can look
up the id of the concatenation directly.

That is why `cl100k_base` is one file with no merge list, and it is the same insight you implemented on
Day 13 without knowing it had a file format attached.

---

## Why Akshara needs it

**Because you are going to save and load one.** Akshara's tokenizer becomes a file on Day 16, and a file
format is a set of decisions about what to keep. Seeing three real formats before you design yours means
you choose rather than default.

**Because the format tells you what the tool can do.** A tool that keeps the merge list can answer "why is
this token here?" and can continue training. A tool that keeps only ranks cannot do either, and gains speed
and a smaller file. Reading the format tells you which tool you are holding — before you need the answer it
cannot give.

**Because "which files do I need?" is a real question with a wrong answer.** Ship `encoder.json` without
`vocab.bpe` and your tokenizer will load, encode short strings correctly, and silently mis-tokenize
anything that needed a merge. Part [3.1](../03-the-remaining-gap/3.1-the-file-is-the-contract.md) is about
the file as a contract; this part is about what is inside it.

---

## The mechanism

`tiktoken` downloads these files and caches them. You recorded all three in `docs/MODELS.md` before loading
them, with the SHA-256 hashes the library verifies. Now open them.

### Step 1 — where they went

```python
import os, tempfile

cache = os.environ.get("TIKTOKEN_CACHE_DIR") or os.path.join(
    tempfile.gettempdir(), "data-gym-cache")
for f in sorted(os.listdir(cache)):
    p = os.path.join(cache, f)
    print(f"{f}  {os.path.getsize(p):,} bytes")
```

**Line by line:**

- `TIKTOKEN_CACHE_DIR` is the environment variable `tiktoken` honours to relocate its cache. Worth knowing
  because the default lives under the system temp directory, which some machines clear on reboot — on a
  metered or offline setup you want this pointed somewhere permanent.
- The filenames are SHA-1 hashes of the source URL, not readable names. That is a deliberate choice: the
  cache key is the URL, so two encodings that share a file share a cache entry, and a changed URL is a
  cache miss rather than a stale hit.

Measured on this machine after loading `gpt2`, `cl100k_base` and `o200k_base`:

```text
6c7ea1a7e38e3a7f062df639a5b80947f075ffe6  1,042,301 bytes
6d1cbeee0f20b3d9449abfede4726ed8212e3aee    456,318 bytes
9b5ad71b2ce5302211f9c61530b329a4922fc6a4  1,681,126 bytes
fb374d419588a4632f3f557e76b4b70aebbca790  3,613,922 bytes
```

Four files for three encodings, because `gpt2` needs two.

### Step 2 — the `cl100k_base` format: base64 and a rank

```python
import base64
from tiktoken.load import read_file_cached

raw = read_file_cached(
    "https://openaipublic.blob.core.windows.net/encodings/cl100k_base.tiktoken",
    expected_hash="223921b76ee99bde995b7ff738513eef100fb51d18c93597a113bcffe865b2a7",
)
lines = raw.decode().splitlines()
print("lines:", len(lines))
for line in lines[:5]:
    b64, rank = line.split()
    print(f"  {line!r:12s} -> token bytes {base64.b64decode(b64)!r}  rank {rank}")
```

**Line by line:**

- `read_file_cached(url, expected_hash=...)` is `tiktoken`'s own loader. Passing the hash means the bytes
  are verified on every read, not only on download. Reading the loader's source shows the two cases are
  handled differently, and the difference is worth knowing: a **cached** file whose hash does not match is
  silently deleted and re-fetched, while a freshly **downloaded** file whose hash does not match raises.
  So a corrupted cache self-heals, and a corrupted *source* stops you. Those hashes are the ones sitting in
  `docs/MODELS.md`.
- `raw.decode()` — the file is ASCII, because base64 is ASCII. That is the point of the encoding: token
  *bytes* can be any of the 256 values, including bytes that are not valid UTF-8, and base64 makes them
  safe to put in a line-oriented text file. Day 13 part
  [3.2](../../../day-013-bpe-encode-decode-bytes/parts/03-byte-level-bpe/3.2-the-byte-to-unicode-trick.md)
  solved the same problem a different way, by mapping every byte to a printable character. Base64 and the
  byte→unicode trick are two answers to one question: *how do you write arbitrary bytes into a text file?*
- `line.split()` gives exactly two fields. No JSON, no escaping, no quoting.

Output:

```text
lines: 100256
  'IQ== 0'     -> token bytes b'!'  rank 0
  'Ig== 1'     -> token bytes b'"'  rank 1
  'Iw== 2'     -> token bytes b'#'  rank 2
  'JA== 3'     -> token bytes b'$'  rank 3
  'JQ== 4'     -> token bytes b'%'  rank 4
```

100,256 lines for a vocabulary `tiktoken` reports as `n_vocab = 100277`. The 21 missing ids are special
tokens, which are not in this file at all — they are declared in code, and part
[1.5](1.5-the-special-token-that-was-just-text.md) is about why that separation exists.

Notice what is **not** here: no pairs, no merge list, no order beyond the rank column itself. To encode,
you take a chunk, look up the rank of every adjacent pair's concatenation, merge the lowest, repeat. That
is Day 13's `encode_chunk` exactly.

### Step 3 — the `gpt2` format: a merge list and a map

```python
vb = read_file_cached(
    "https://openaipublic.blob.core.windows.net/gpt-2/encodings/main/vocab.bpe",
    expected_hash="1ce1664773c50f3e0cc8842619a93edc4624525b728b188a9e0be33b7726adc5",
)
for line in vb.decode().splitlines()[:5]:
    print(repr(line))
```

Output:

```text
'#version: 0.2'
'Ġ t'
'Ġ a'
'h e'
'i n'
```

**Line by line:**

- The first line is a version marker, and the merges start at line 2 — an off-by-one waiting to happen if
  you write your own loader. `tiktoken`'s loader skips it explicitly.
- `'Ġ t'` is a **pair**, space-separated: merge the token `Ġ` with the token `t`. That `Ġ` is the byte
  0x20 under the byte→unicode map from Day 13 part 3.2 — so this line reads "merge a space with a `t`".
- The file is 50,001 lines: one version line and 50,000 merges. And `50257 = 256 + 50000 + 1` — the 256
  byte symbols, the 50,000 merged tokens, and one special token. The arithmetic from Day 13 part 1.3,
  `V = 256 + len(merges)`, holds exactly, with `+1` for `<|endoftext|>`.

The second file is the map:

```python
import json
ej = read_file_cached(
    "https://openaipublic.blob.core.windows.net/gpt-2/encodings/main/encoder.json",
    expected_hash="196139668be63f3b5d6574427317ae82f612a97c5d1cdaf36ed2256dbf636783",
)
enc_json = json.loads(ej)
print(f"{len(ej):,} bytes, {len(enc_json)} entries")
print("first 5:", list(enc_json.items())[:5])
```

Output:

```text
1,042,301 bytes, 50257 entries
first 5: [('!', 0), ('"', 1), ('#', 2), ('$', 3), ('%', 4)]
```

**Line by line:**

- JSON, and therefore the keys must be valid strings — which is why the byte→unicode trick is mandatory
  here rather than optional. Raw token bytes could not be JSON keys.
- 1,042,301 bytes for 50,257 entries, versus 1,681,126 bytes for `cl100k_base`'s 100,256 entries. Per
  entry, base64 plus a rank is slightly *smaller* than JSON plus a byte-mapped string, and it carries the
  merge information too.

### Step 4 — the three formats side by side

| | `gpt2` | `cl100k_base` | yours (Day 13) |
| --- | --- | --- | --- |
| files | 2 | 1 | 1 |
| total bytes | 1,498,619 | 1,681,126 | 12,373 |
| merge list stored? | ✅ ordered pairs | ❌ | ✅ ordered pairs |
| token→id stored? | ✅ JSON | ✅ implied by rank column | derived at load |
| byte encoding | byte→unicode map | base64 | byte→unicode map |
| can resume training? | ✅ | ❌ | ✅ |
| can explain a token? | ✅ | ❌ | ✅ |
| special tokens in file? | ❌ (in code) | ❌ (in code) | ❌ (none yet) |

The last row is the one that bites people, and it is Day 16's subject.

---

## Shapes

| Name | Symbolic | Concrete (`gpt2`) | Meaning |
| --- | --- | --- | --- |
| merge list | `(n_merges, 2)` | `(50000, 2)` | ordered pairs; index **is** priority |
| token→id | `(V,)` | `(50257,)` | one entry per id, including specials |
| rank table | `(n_merges,)` | `(50000,)` | pair → priority; what encoding actually reads |
| byte block | `(256,)` | `(256,)` | ids 0..255 under the byte→unicode map |

`n_merges = V - 256 - n_special` in every row. For `gpt2`: `50257 - 256 - 1 = 50000`. ✅

## When it breaks

**A wrong or truncated download is caught by the hash.** The message, read from `tiktoken/load.py` in the
installed `tiktoken==0.14.0`:

```text
ValueError: Hash mismatch for data downloaded from
https://openaipublic.blob.core.windows.net/encodings/cl100k_base.tiktoken
(expected 223921b76ee99bde995b7ff738513eef100fb51d18c93597a113bcffe865b2a7).
This may indicate a corrupted download. Please try again.
```

Loud, immediate, and exactly what you want. Contrast that with the failure mode you would get from a
loader that did not check.

**Shipping `encoder.json` without `vocab.bpe`** is the quiet one. The tokenizer loads — the map is all it
needs to turn tokens into ids. It then encodes every chunk as individual bytes, because with no merges
nothing ever combines. Your text still round-trips perfectly. It is simply four times longer than it should
be, in ids the model was never trained to see:

```text
text : "the plan"
right: ['the', 'Ġplan']                              -> 2 ids
wrong: ['t','h','e','Ġ','p','l','a','n']             -> 8 ids
```

No exception, no warning, a passing round trip. This is Silent Failure #2 in file-format clothing, and the
only check that catches it is comparing *ids*, not strings — the theme part
[3.3](../03-the-remaining-gap/3.3-the-mismatch-the-library-will-not-catch.md) closes on.

**Skipping the `#version: 0.2` line, or not skipping it.** If your loader treats it as a merge, you get a
merge of `#version:` and `0.2` at rank 0 — the highest priority in the entire table. It will fire on any
text containing that pair, which is almost none, so almost everything is fine and one input in a million is
not. Off-by-one errors in an *ordered* file are the worst kind, because rank 0 is the most powerful slot.

## In production

**The formats are converging on JSON, and the reason is the missing rows above.** `tokenizer.json` — the
format `tokenizers` writes, and part [3.1](../03-the-remaining-gap/3.1-the-file-is-the-contract.md) opens
— puts the normalizer, the pre-tokenizer, the merges, the vocabulary, the special tokens and the decoder
in **one** file. Every one of those is something that has to match between training and serving, and every
one of them was, in the older formats, a thing you had to know rather than a thing you could load.

**A vocabulary file is small and a model is not.** 1.5 MB next to gigabytes of weights. This is why nobody
optimizes the format for size and why it is worth storing more in it, not less.

**Neither format records the corpus.** Not its hash, not its licence, not its date. You cannot tell from
`vocab.bpe` what text produced it — which is exactly what `docs/DATASETS.md` and `docs/MODELS.md` exist to
prevent for your own work. Part [1.4](1.4-your-merges-against-theirs.md) shows how much you can *infer*
about a corpus from its merge list alone, and it is more than you might expect.

**Loading a vocabulary is not loading a model.** These are text files: base64, JSON, space-separated pairs.
Nothing in them executes. That is why Principle 13 lets these through when it forbids pickles — you should
still write the `docs/MODELS.md` row, and you did, but the blast radius of a malformed `.tiktoken` file is
a `ValueError`, not code execution.

## Check yourself

```python
import base64, json
from tiktoken.load import read_file_cached

CL = ("https://openaipublic.blob.core.windows.net/encodings/cl100k_base.tiktoken",
      "223921b76ee99bde995b7ff738513eef100fb51d18c93597a113bcffe865b2a7")
VB = ("https://openaipublic.blob.core.windows.net/gpt-2/encodings/main/vocab.bpe",
      "1ce1664773c50f3e0cc8842619a93edc4624525b728b188a9e0be33b7726adc5")

cl = read_file_cached(*CL).decode().splitlines()
vb = read_file_cached(*VB).decode().splitlines()

# ranks must be exactly 0..N-1, in order: the file IS the ordering
ranks = [int(line.split()[1]) for line in cl]
assert ranks == list(range(len(cl))), "cl100k ranks are not dense and ordered"

# the first 256 cl100k tokens should be single bytes
singles = sum(1 for line in cl[:256] if len(base64.b64decode(line.split()[0])) == 1)
print(f"single-byte tokens in the first 256: {singles}")

# gpt2 arithmetic: 256 bytes + merges + specials == n_vocab
merges = len(vb) - 1                       # minus the '#version: 0.2' line
print(f"gpt2 merges={merges}  256+merges+1={256 + merges + 1}")
assert 256 + merges + 1 == 50257, "V = 256 + len(merges) + n_special does not hold"
```

**Line by line:**

- `ranks == list(range(len(cl)))` is the eval that can go red. It asserts the rank column is dense and
  ascending — the property that lets you treat line number as rank and skip parsing the second field
  entirely. If a future file ever violated it, a loader that assumed line order would break silently.
- `len(vb) - 1` encodes the version-line skip explicitly, with a comment, because it is exactly the
  off-by-one described above.
- The `singles` count is a probe, not an assertion, because you should look at it before deciding what it
  ought to be. Predict it before you run it.
