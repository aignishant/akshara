# 1.5 — 💥 The special token that was just text

## One-line answer

The string `hello <|endoftext|> world` encodes to **nine** ids or **four** depending on one keyword
argument, and the four-id version contains id 50256 — the token that tells a model the document has ended —
so `tiktoken` refuses to guess and raises instead.

---

## The story

🎬 **The scene.** You run a form where people type a message, and your program wraps each message in
markers so it can tell where one ends and the next begins. The marker is a line reading `--- END ---`.

For two years nobody types that. Then somebody does — a person quoting an email that had it in the footer.

Your program reads their message, hits `--- END ---` halfway through, and decides the message finished
there. The rest of what they wrote becomes the *next* message. Nothing crashes. Somebody just gets a reply
to half a sentence.

😬 **The naive fix.** Strip `--- END ---` from user input before wrapping it.

💥 **Why it fails.** Now you have two rules — one that writes the marker and one that removes it — and they
live in different files, maintained by different people, and they will drift. And the person quoting the
email has had their text quietly edited, which is its own bug.

💡 **The insight.** The marker and the message must not be able to occupy the same channel. Either the
marker travels out of band, or the boundary between "this is control" and "this is content" is decided
**once**, explicitly, by the caller — and if the caller does not say, the program refuses.

---

## The idea in plain language

A vocabulary has two kinds of entry, and part [1.3](1.3-what-a-vocabulary-file-looks-like.md) showed they
live in different places — the 100,256 ordinary tokens in the `.tiktoken` file, the 21 special tokens
declared in code.

**Ordinary tokens** come from the merge list. Any text can produce them.

**Special tokens** are ids the model was trained to treat as structure, not language: end of document,
start of a turn, a padding slot. `<|endoftext|>` is id 50256 in `gpt2`, and a model that sees it treats
everything before it as a finished document.

Now the question that makes this a failure part: what should happen when *user text* contains the literal
characters `<|endoftext|>`?

There are only three answers, and two of them are wrong:

| Answer | Result |
| --- | --- |
| Encode it as the special token | User input can now inject control structure into your prompt |
| Encode it as ordinary text | Correct for user input; silently wrong when *you* meant the marker |
| Refuse, and make the caller say | What `tiktoken` does |

The third is the only one that cannot be silently wrong, because it has no default.

---

## Why Akshara needs it

This is **Silent Failure #2 — tokenizer/template mismatch** — in its purest form, and the plan's §6 names
it as one of the five that quietly destroy a training run.

Day 16 (`TOK-16`, `TOK-17`) builds Akshara's chat template on top of exactly these markers. When that day
arrives you will be writing strings that separate a system prompt from a user turn from the model's reply,
and *every one of those boundaries is a special token*. If user text can forge them, then:

- **At training**, a document containing the literal marker splits into two training examples in the middle
  of a sentence, and your loss is computed over a boundary that does not exist.
- **At serving**, a user types the marker and ends the system prompt early. That is prompt injection, and
  it is a security bug rather than a quality bug.

Meeting this now — in a library that has already made the safe choice, with an error message you can read —
is much cheaper than meeting it on Day 16 in your own code.

---

## The mechanism

### Step 1 — the three encodings of one string

```python
import tiktoken

enc = tiktoken.get_encoding("gpt2")
s = "hello <|endoftext|> world"

print("special tokens :", enc.special_tokens_set)
print("encode_ordinary:", enc.encode_ordinary(s))
print("allowed_special:", enc.encode(s, allowed_special="all"))
```

**Line by line:**

- `enc.special_tokens_set` is the set of strings this encoding treats as special. For `gpt2` it is a set of
  one. For `cl100k_base` it is five, and the 21-token gap from part 1.3 is because ids are also *reserved*
  beyond the ones named.
- `encode_ordinary(s)` means "there are no special tokens in this string; it is all text". This is the
  method to use on anything a user typed.
- `encode(s, allowed_special="all")` means the opposite: "if you see a marker, it is a marker". This is the
  method for a string *you* assembled from a template.
- Note there is no argument for "guess". That absence is the design.

Measured, `tiktoken==0.14.0`:

```text
special tokens : {'<|endoftext|>'}
encode_ordinary: [31373, 1279, 91, 437, 1659, 5239, 91, 29, 995]
allowed_special: [31373, 220, 50256, 995]
```

**Nine ids versus four.** The same 25 characters. Look at what the ordinary path did:

```python
print([enc.decode([i]) for i in enc.encode_ordinary(s)])
```

**Line by line:**

- `enc.decode([i])` decodes **one id at a time**, in a list, so you see the token boundaries. Decoding the
  whole sequence at once would hand back the original string and hide exactly what this line is for.
- The single-element list is required: `decode` takes a sequence of ids, not a scalar.

```text
['hello', ' <', '|', 'end', 'of', 'text', '|', '>', ' world']
```

The marker was taken apart into six ordinary tokens — `' <'`, `'|'`, `'end'`, `'of'`, `'text'`, `'|'`,
`'>'` — because the merge list has no token for the whole thing. It never could: the marker was never in
the training corpus as a unit, it was bolted on afterwards. Meanwhile the `allowed_special` path produced
id **50256**, a single token carrying "the document ends here".

### Step 2 — what happens when you do not choose

```python
enc.encode(s)
```

**Line by line:**

- One call, no keyword arguments. That is the point — this is what a caller writes when they have not
  thought about special tokens, which is most callers most of the time.

Verbatim, from `tiktoken==0.14.0`:

```text
ValueError: Encountered text corresponding to disallowed special token '<|endoftext|>'.
If you want this text to be encoded as a special token, pass it to `allowed_special`, e.g. `allowed_special={'<|endoftext|>', ...}`.
If you want this text to be encoded as normal text, disable the check for this token by passing `disallowed_special=(enc.special_tokens_set - {'<|endoftext|>'})`.
To disable this check for all special tokens, pass `disallowed_special=()`.
```

**This is a good error, and it is worth studying as an error.** It names the exact token found, gives the
call for each of the two intents, and gives the escape hatch. It does not pick for you. Compare that with
the alternative designs:

- A library that defaulted to "treat as special" would have a prompt-injection hole with no error message.
- A library that defaulted to "treat as text" would silently drop your template markers, and you would find
  out from a model that never stops generating.

The plain `encode` method is the one with no safe default, so it is the one that raises.

### Step 3 — the cost of the literal

```python
plain = enc.encode_ordinary("hello  world")
marked = enc.encode_ordinary(s)
print(f"literal marker costs {len(marked) - len(plain)} extra tokens")
```

**Line by line:**

- `"hello  world"` has **two** spaces, not one. That is deliberate: removing `<|endoftext|>` from the probe
  leaves the spaces on either side of it, so the two strings differ by the marker alone. A single space
  would make the comparison off by one token and quietly overstate the cost.
- `encode_ordinary` on both sides, so the difference measures the marker as text rather than the
  difference between two encoding modes.

```text
literal marker costs 6 extra tokens
```

Six tokens of context for a thirteen-character string. That is the *second* reason special tokens exist:
they are structure that would otherwise be expensive to spell out. A chat template with four boundaries
would cost 24 tokens per turn in literal markers, and 4 as special tokens.

---

## Shapes

| Name | Symbolic | Concrete | Meaning |
| --- | --- | --- | --- |
| `encode_ordinary(s)` | `(T,)` | `(9,)` | every id `< 50256`; all ordinary |
| `encode(s, allowed_special="all")` | `(T,)` | `(4,)` | contains id 50256 |
| ordinary id range | — | `[0, 50256)` | from the merge list |
| special id range | — | `[50256, 50257)` | declared in code, not in the file |

The clean split at 50256 is not an accident: specials are appended **after** the merged vocabulary, so
`id >= 256 + n_merges` is a complete test for "this id is special". That test is worth writing down; it is
how a training script can count how many special tokens a batch contains without a lookup table.

---

## When it breaks

**The failure this part is named for is the one with no error at all.** Take the two id sequences and
decode them both:

```python
a = enc.encode_ordinary(s)
b = enc.encode(s, allowed_special="all")
print(repr(enc.decode(a)))
print(repr(enc.decode(b)))
print("round trips equal:", enc.decode(a) == enc.decode(b) == s)
```

**Line by line:**

- `enc.decode(b)` decodes a sequence **containing id 50256** and renders it back as the literal text
  `<|endoftext|>`. That is why the two round trips agree: decode maps the special id back to its string
  form, erasing the very distinction that makes the two sequences different to a model.
- The chained comparison `enc.decode(a) == enc.decode(b) == s` asserts all three are equal in one
  expression. It reads as the test somebody would actually write, which is the point — this is the test
  that passes.

```text
'hello <|endoftext|> world'
'hello <|endoftext|> world'
round trips equal: True
```

**Both round-trip perfectly.** Nine ids and four ids, and the round-trip test — the test everyone writes —
says they are the same. The model does not see the string; it sees the ids, and the two id sequences mean
completely different things. One is a sentence. The other is two documents with a boundary in the middle.

This is the third time this day has shown the round-trip test passing on a real bug — parts 1.1 and 1.3
were the others, and part [3.3](../03-the-remaining-gap/3.3-the-mismatch-the-library-will-not-catch.md)
makes the point terminal. **`decode(encode(s)) == s` is necessary and nowhere near sufficient.** The check
that works is comparing *ids* against ids produced by the exact path used at training.

**The training-corpus version of this failure.** Feed a corpus straight to `encode(..., allowed_special="all")`
and every document that happens to contain the literal marker is split. Your document count goes up, your
average document length goes down, and a handful of training examples begin mid-sentence. Nothing reports
it. The check is to count the specials you *expect* and compare:

```python
expected = n_documents                    # one <|endoftext|> per document, appended by you
actual = sum(1 for i in all_ids if i >= 50256)
assert actual == expected, f"{actual - expected} forged markers came from the corpus itself"
```

**Line by line:**

- `i >= 50256` uses the structural test from the Shapes table rather than an equality check against a
  known id, so it stays correct if more special tokens are added later.
- The assertion compares against a count **you** control — one marker per document, because you appended
  them. Any excess came from the text itself, and the message says so rather than just reporting a
  mismatch.
- This runs over the whole corpus once, before training. It is cheap, and it is the only thing standing
  between a forged marker and a training example that begins mid-sentence.

## In production

**Serving code uses `encode_ordinary` for user input. Always.** The rule is worth stating as a rule,
because the exceptions are what get exploited: anything that arrives from outside your process is text,
and the only code allowed to emit special tokens is the template assembler that wraps it. If those two
responsibilities live in one function, they will eventually be confused.

**This is a documented attack surface.** A user who can get a special token into a prompt can end the
system prompt early, or forge the boundary that says "the assistant's reply starts here" and put words in
the model's mouth. The defence is not filtering the string — filtering is a blocklist and blocklists leak.
The defence is that the *encoding path for user text cannot produce those ids at all*, which is what
`encode_ordinary` guarantees structurally.

**Vocabularies reserve space for specials that do not exist yet.** `cl100k_base` has 21 ids beyond its
100,256 file entries and names only five of them. The unnamed ones are room to add a marker later without
resizing the embedding matrix — because adding a token means growing a `(V, C)` matrix and every trained
weight in it. Day 16 (`TOK-17`) does that resize deliberately and measures what it costs.

**Different serving stacks disagree about this**, which is its own hazard. Some tokenizer wrappers default
to parsing specials in user text, some do not, and the same prompt through two stacks can produce different
ids. When a model behaves differently in two deployments and the weights are identical, this is the first
thing to check.

## Check yourself

```python
import tiktoken

enc = tiktoken.get_encoding("gpt2")
s = "hello <|endoftext|> world"
EOT = enc.encode("<|endoftext|>", allowed_special="all")[0]
print("EOT id:", EOT, " n_vocab:", enc.n_vocab)

ordinary = enc.encode_ordinary(s)
special = enc.encode(s, allowed_special="all")
print("ordinary:", ordinary)
print("special :", special)

# the eval that can go red, twice over
assert all(i < EOT for i in ordinary), "encode_ordinary emitted a special token"
assert EOT in special, "allowed_special did not produce the marker"
assert enc.decode(ordinary) == enc.decode(special) == s, "round trip broke"
assert ordinary != special, \
    "the two paths agree - the whole point of this part is that they must not"

# and the one that must raise
try:
    enc.encode(s)
except ValueError as e:
    print("correctly refused:", str(e).splitlines()[0])
else:
    raise AssertionError("encode() silently guessed - that is the bug this part is about")
```

**Line by line:**

- `EOT = enc.encode("<|endoftext|>", allowed_special="all")[0]` looks the id up rather than hard-coding
  50256, so the script keeps working if you switch encoding. Hard-coded token ids are a classic source of
  the mismatch this part is about.
- `all(i < EOT for i in ordinary)` is the structural check from the Shapes table: specials sit above the
  merged vocabulary, so a single comparison tests the whole sequence. No lookup table needed.
- `assert ordinary != special` is the unusual one — it asserts a *difference*. Most tests assert things
  match. This one exists because the failure mode is two paths quietly converging, and a test that only
  checked round trips would pass in exactly the situation you care about.
- `try/except/else` with `raise AssertionError` in the `else`: the test fails if `encode` **succeeds**.
  Writing this as a bare `try/except: pass` would silently pass whether or not the library refused.
