# 1.1 — The same corpus through both

## One-line answer

On the same 113,283-byte corpus, the tokenizer you built on Day 13 emits **46,311** ids and `tiktoken`'s
`gpt2` emits **33,405** — but that gap is almost entirely **vocabulary size**, not code quality: measured
here, at an equal `V = 1000` a production library lands within **0.04%** of your token count, and the only
thing it genuinely beats you at is **speed**, by about **10×**.

---

## The story

You have spent a week learning to cut vegetables with a kitchen knife. You are slow, but the pieces are
even and the right size.

Then you watch a cook in a busy kitchen do the same tray in a fraction of the time.

There are two different things you could conclude, and only one of them is true. The tempting conclusion
is *my cuts are wrong*. The true one is *my cuts are fine and my hands are slow* — and, separately, *that
kitchen has a bigger board*.

Those are three different facts, and if you mash them into one feeling ("they're better than me") you
learn nothing you can act on. Today you separate them. You measure the pieces, you measure the hands, and
you measure the board, one at a time.

---

## The idea in plain language

Principle 3 of the plan says: **build first, compare after.** You have built. Today you compare, and a
comparison is only worth anything if it changes one thing at a time.

Set your Day 13 tokenizer next to `tiktoken`'s `gpt2` and you are changing **three** things at once:

| Axis | Yours | `gpt2` |
| --- | --- | --- |
| Vocabulary size | 1,000 | 50,257 |
| Training corpus | this repo's plan, 113 KB of markdown | a large English web crawl |
| Implementation language | Python | Rust, called from Python |

Any single number you read off that comparison — "they compress 39% better" — is a blend of all three, and
tells you nothing about which one to fix. So this part measures each axis on its own:

- **Change only the vocabulary size** → how much of the compression gap is `V`?
- **Change only the implementation** → how much of the token count is code quality? (Answer: almost none.)
- **Change only the language it is written in** → how much is speed? (Answer: all of it.)

The headline, stated up front so you read the rest with it in mind: **your implementation is correct.**
What a production library gives you is not a better algorithm. It is a bigger vocabulary trained on more
text, and the same algorithm running roughly ten times faster.

---

## Why Akshara needs it

Three reasons, and the third is the one that matters most.

**One — you are about to depend on this.** From Day 16 onwards Akshara's tokenizer feeds a real training
run. Before you hand that job to a library you should know exactly what it does differently, because every
difference is a place Silent Failure #2 (tokenizer/template mismatch) can live.

**Two — you now have a test oracle.** Day 13 kept the slow sequential encoder as an oracle for the fast
one. Today you gain a much stronger oracle: an independent implementation, written by other people in
another language, that should agree with yours. When your code and `tokenizers` produce the same token
count on the same corpus at the same `V`, that is real evidence — far better than your own tests agreeing
with themselves.

**Three — you need to know what you *cannot* buy.** A library fixes speed. It does not fix the fact that a
vocabulary trained on markdown charges Hindi one token per byte (part
[3.2](../03-the-remaining-gap/3.2-the-tax-a-vocabulary-charges-a-language.md)), and it does not stop you
serving with a different pre-tokenizer than you trained with (part
[3.3](../03-the-remaining-gap/3.3-the-mismatch-the-library-will-not-catch.md)). Knowing which problems
you just outsourced and which you still own is the whole point of a compare day.

---

## The mechanism

Everything below runs on the corpus this repo already has: `docs/00_MASTER_PLAN.md`. Every script prints
the corpus hash first, so that if the plan is edited you find out loudly instead of quietly inheriting
Day 13's numbers. That habit comes from Day 10 part
[3.1](../../../day-010-unicode-code-points-bytes/parts/03-together/3.1-one-string-five-layers.md), and it
is the reason this day's numbers are trustworthy at all.

### Step 1 — the naive comparison, the one that misleads

```python
import hashlib, time
from pathlib import Path
import tiktoken

CORPUS = Path("docs/00_MASTER_PLAN.md")
raw = CORPUS.read_bytes()
text = CORPUS.read_text(encoding="utf-8")
print("corpus sha256[:16] =", hashlib.sha256(raw).hexdigest()[:16])
print("bytes =", len(raw), " code points =", len(text))

for name in ("gpt2", "cl100k_base", "o200k_base"):
    enc = tiktoken.get_encoding(name)
    ids = enc.encode_ordinary(text)
    print(f"{name:14s} V={enc.n_vocab:7d} ids={len(ids):7d} "
          f"chars/tok={len(text)/len(ids):.3f} roundtrip={enc.decode(ids) == text}")
```

**Line by line:**

- `raw = CORPUS.read_bytes()` and `text = CORPUS.read_text(...)` read the *same file twice*, deliberately.
  The hash must be taken over the bytes on disk, not over a decoded string — Day 10 part
  [2.1](../../../day-010-unicode-code-points-bytes/parts/02-utf-8-and-bytes/2.1-text-has-to-become-bytes.md)
  is where that distinction was made. Hashing `text.encode("utf-8")` would happen to agree here, and would
  stop agreeing the moment the file gained a BOM.
- `hashlib.sha256(raw).hexdigest()[:16]` — sixteen hex characters is 64 bits, plenty to notice an edit and
  short enough to paste into a table. This is provenance, not security.
- `tiktoken.get_encoding(name)` fetches the vocabulary. The first call for each name downloads a file over
  the network and verifies its SHA-256 against a hash compiled into the library; later calls read a local
  cache. Those three files were written into `docs/MODELS.md` **before** this line was ever run, which is
  Principle 13: you record what you are about to load, then load it.
- `enc.encode_ordinary(text)` encodes with **no special-token handling at all**. The plain `encode` method
  would raise on this corpus, and part [1.5](1.5-the-special-token-that-was-just-text.md) is entirely
  about why. Using `encode_ordinary` here is not a shortcut — it is the method that means "this is
  user text, treat every character as text".
- `enc.n_vocab` is the full id space including special tokens, so `gpt2` reports 50,257 rather than the
  50,256 merges-plus-bytes you might expect. The extra one is `<|endoftext|>`.
- `enc.decode(ids) == text` is the round-trip check from Day 13 part
  [1.2](../../../day-013-bpe-encode-decode-bytes/parts/01-encode-and-decode/1.2-decode-is-a-lookup-not-a-search.md).
  It is worth printing every time and it is worth remembering how weak it is — part
  [3.3](../03-the-remaining-gap/3.3-the-mismatch-the-library-will-not-catch.md) shows two tokenizers that
  both pass it and disagree on every input.

Measured on this machine, corpus `9760f2b6d4340b97`, 113,283 bytes / 110,837 code points:

| Encoding | `V` | ids | chars/token | round trip |
| --- | ---: | ---: | ---: | --- |
| **yours (Day 13)** | 1,000 | 46,311 | 2.393 | ✅ |
| `gpt2` | 50,257 | 33,405 | 3.318 | ✅ |
| `cl100k_base` | 100,277 | 30,554 | 3.628 | ✅ |
| `o200k_base` | 200,019 | 30,428 | 3.643 | ✅ |

Read naively: "they beat me by 39%." Read carefully: **notice the diminishing returns.** Doubling the
vocabulary from 50k to 100k bought 8.5% fewer tokens. Doubling again, from 100k to 200k, bought **0.4%**.
That shape — big gains early, almost nothing later — is the same curve Day 12 part
[2.2](../../../day-012-bpe-the-merge-loop/parts/02-training-a-vocabulary/2.2-training-to-a-target-size.md)
measured between `V = 300` and `V = 2000`. It did not stop being true at 1,000; it kept going.

And it tells you the 39% gap is not a wall. It is mostly the first stretch of a curve you have already
climbed part of.

### Step 2 — hold the vocabulary size fixed

This is the measurement that actually answers the question. Train a byte-level BPE with the `tokenizers`
library on **the same corpus**, to **the same `V = 1000`**, with the same byte-level pre-tokenizer, and
compare against your Day 13 output.

```python
from tokenizers import Tokenizer, models, pre_tokenizers, decoders, trainers

tok = Tokenizer(models.BPE())
tok.pre_tokenizer = pre_tokenizers.ByteLevel(add_prefix_space=False, use_regex=True)
tok.decoder = decoders.ByteLevel()
tok.train_from_iterator(
    [text],
    trainer=trainers.BpeTrainer(
        vocab_size=1000,
        show_progress=False,
        initial_alphabet=pre_tokenizers.ByteLevel.alphabet(),
    ),
)
out = tok.encode(text)
print(f"tokenizers V=1000  ids={len(out.ids)}  chars/tok={len(text)/len(out.ids):.3f}")
```

**Line by line:**

- `Tokenizer(models.BPE())` builds an empty BPE model — no vocabulary, no merges. In this library the
  *model* is only the merge table and the token→id map. The splitting, the byte mapping and the
  detokenizing are separate objects, which is the subject of part
  [2.1](../02-the-tokenizers-pipeline/2.1-five-stages-not-one.md).
- `pre_tokenizers.ByteLevel(add_prefix_space=False, use_regex=True)` is the library's version of the two
  things you hand-rolled on Day 13: `use_regex=True` applies the published split pattern (part
  [1.2](1.2-the-published-pattern-verbatim.md)), and the `ByteLevel` part applies the byte→unicode map you
  wrote in Day 13 part
  [3.2](../../../day-013-bpe-encode-decode-bytes/parts/03-byte-level-bpe/3.2-the-byte-to-unicode-trick.md).
  `add_prefix_space=False` means "do not silently glue a space onto the front of my input" — set it to
  `True` and you get part [3.3](../03-the-remaining-gap/3.3-the-mismatch-the-library-will-not-catch.md)'s
  disaster.
- `decoders.ByteLevel()` is the inverse map. Without it, `decode` hands back `Ġplan` instead of ` plan` —
  the unreadable vocabulary of Day 13 part
  [3.4](../../../day-013-bpe-encode-decode-bytes/parts/03-byte-level-bpe/3.4-the-vocabulary-you-cannot-read.md).
  The library keeps encode and decode as two separately configured objects, and **nothing checks that they
  are inverses**. That is a real trap and part [2.5](../02-the-tokenizers-pipeline/2.5-the-normalizer-that-broke-the-round-trip.md) springs it.
- `initial_alphabet=pre_tokenizers.ByteLevel.alphabet()` forces all 256 byte symbols into the vocabulary
  before any merging. Without it the trainer only includes characters it actually saw, and you lose the
  zero-OOV guarantee that Day 13 part
  [3.3](../../../day-013-bpe-encode-decode-bytes/parts/03-byte-level-bpe/3.3-zero-out-of-vocabulary.md)
  proved by construction. This one argument is the difference between "no unknown tokens on this corpus"
  and "no unknown tokens, ever".
- `train_from_iterator([text], ...)` takes an iterable of documents. Passing `[text]` treats the whole plan
  as one document — matching what your Day 13 code did, so the comparison stays fair.
- `tok.encode(text)` returns an `Encoding` object, not a list. `.ids` are the numbers; it also carries
  `.tokens`, `.offsets` and more, which part
  [2.3](../02-the-tokenizers-pipeline/2.3-offsets-are-the-product.md) is about.

### Step 3 — the result

Measured on this machine, same corpus, both at `V = 1000`:

| | ids | chars/token | merges learned |
| --- | ---: | ---: | ---: |
| **yours (Day 13, Python)** | 46,311 | 2.393 | 744 |
| `tokenizers` (Rust) | 46,291 | 2.394 | 744 |
| **difference** | **20 ids (0.043%)** | 0.001 | **0** |

Twenty tokens out of forty-six thousand. Both learned exactly 744 merges — as they must, since
`V = 256 + len(merges)` from Day 13 part
[1.3](../../../day-013-bpe-encode-decode-bytes/parts/01-encode-and-decode/1.3-from-tokens-to-ids.md).

Where do the twenty come from? The merge lists are not identical:

| Comparison | Result |
| --- | ---: |
| merges at the same rank in both lists | 93 / 744 |
| first rank where they disagree | **24** |
| merges present in both lists, at any rank | 678 / 744 = **91.1%** |

The two implementations agree on *which* pairs are worth merging (91.1%) and disagree on the *order* from
rank 24 onwards. Part [2.2](../02-the-tokenizers-pipeline/2.2-the-same-vocabulary-trained-twice.md) opens
up rank 24 and shows exactly what happened there — it is not a bug in either program.

### Step 4 — now change only the language

```python
def best_of(fn, n=5):
    """Smallest of n timings: the run least disturbed by other processes."""
    times = []
    for _ in range(n):
        t0 = time.perf_counter()
        result = fn()
        times.append(time.perf_counter() - t0)
    return min(times), result

nbytes = len(text.encode("utf-8"))
t_mine, mine = best_of(lambda: bpe13.tokenize(text, merges))
t_tik, ids = best_of(lambda: enc.encode_ordinary(text))
print(f"yours    {t_mine:.4f}s -> {nbytes / t_mine / 1e6:.3f} MB/s")
print(f"tiktoken {t_tik:.4f}s -> {nbytes / t_tik / 1e6:.2f} MB/s")
```

**Line by line:**

- `best_of` takes the **minimum**, not the mean. A timing is a measurement corrupted upwards by anything
  else your laptop chose to do during it; there is no noise that makes code run faster than it can. The
  minimum is therefore the best estimate of the true cost, and the mean is an estimate of the true cost
  plus whatever your machine was doing. This is not the same situation as Silent Failure #4, where you
  average across seeds because the *thing being measured* is genuinely random — here the thing being
  measured is fixed and only the observation is noisy.
- `n=5` because a single run of this on my first attempt read `12.0×` and the settled value is `9.9×`.
  Reporting the first number would not have been dishonest, but it would have been wrong.
- `time.perf_counter()` rather than `time.time()`: it is monotonic and has the highest resolution the
  platform offers.
- `nbytes / t / 1e6` reports megabytes per second rather than seconds, because seconds only mean something
  next to a corpus size and MB/s is comparable across corpora.

Measured, best of 5, on this machine:

| | time | throughput | relative |
| --- | ---: | ---: | ---: |
| yours, Python, `V = 1000` | 0.2460 s | 0.461 MB/s | 1× |
| `tokenizers`, Rust, `V = 1000` | 0.1550 s | 0.73 MB/s | 1.6× faster |
| `tiktoken`, Rust, `V = 50257` | 0.0250 s | 4.54 MB/s | **9.9× faster** |

Two honest readings, and the difference between them is the discipline of this part:

- Against `tokenizers` **at the same vocabulary size**, the gap is **1.6×**. That is the cost of Python
  versus Rust for this algorithm, and it is much smaller than you probably expected.
- Against `tiktoken` the gap is **9.9×**, but that comparison changes `V` as well as the language, and a
  larger vocabulary means fewer merge steps per chunk. Some of that 9.9× is the bigger board, not the
  faster hands. This day does not separate those two, and part
  [1.3](1.3-what-a-vocabulary-file-looks-like.md) explains the third reason — `tiktoken` does not store a
  merge list at all, so it is not running the same algorithm you are.

## Shapes

Nothing here is a tensor yet, but the id sequence is about to become one on Day 16, and its length is the
sequence axis `T` that the whole transformer is built around. Worth writing down now:

| Name | Symbolic | Concrete (this corpus) | What the axis means |
| --- | --- | --- | --- |
| `text` | `(n_chars,)` | `(110837,)` | Unicode code points, Day 10 layer 3 |
| `raw` | `(n_bytes,)` | `(113283,)` | UTF-8 bytes, Day 10 layer 4 |
| `ids` (yours) | `(T,)` | `(46311,)` | one integer per token, each in `[0, 1000)` |
| `ids` (`gpt2`) | `(T,)` | `(33405,)` | one integer per token, each in `[0, 50257)` |
| context window | `(T_max,)` | `(1024,)` | how many of those ids the model can see at once |

That last row is why the comparison matters. With `gpt2`'s vocabulary a 1,024-token window holds **3,398
characters** of this corpus; with yours it holds **2,450**. Same window, 27.9% less text — and the window is
fixed by the model's architecture, not by the tokenizer. A worse tokenizer costs you *context*, which is
the scarcest thing a language model has.

## When it breaks

**The first call needs a network, and says so plainly.** With no route to the download host:

```
requests.exceptions.ConnectionError: HTTPSConnectionPool(host='openaipublic.blob.core.windows.net', port=443):
Max retries exceeded with url: /encodings/cl100k_base.tiktoken
```

This is a *loud* failure and that is exactly right. The failure to fear is the quiet one: a tokenizer that
loads from a stale cache after the upstream file changed. `tiktoken` forecloses that by checking a
SHA-256 that is compiled into the library, so a changed file is a hash mismatch rather than a silent drift.
Your `docs/MODELS.md` rows record those same hashes, which means the check is reproducible outside the
library too.

**Comparing across different corpora.** If you run this on a plan file you have edited, every number in
this part is wrong for you, and nothing will tell you. That is the whole reason each script prints the
hash. If yours does not read `9760f2b6d4340b97`, your numbers are *yours* — write them down and do not
copy mine.

**Reading one number off a three-variable comparison.** The mistake this part exists to prevent. If you
take away "libraries compress 39% better than hand-rolled code", you have learned something false. At
equal `V` the difference is 0.043%, and it is not in the library's favour by any amount worth measuring.

## In production

At production scale the axes separate even further, and the ranking changes.

**Speed stops being about the language and starts being about the batch.** A 10× per-document gap sounds
decisive until you notice that tokenization is a one-off preprocessing pass over a corpus that then feeds
an entire training run. At 0.461 MB/s a 10 GB corpus is 21,691 CPU-seconds; at 4.54 MB/s it is 2,203. The
ratio is what matters, and both figures are small next to the run they feed — and both parallelize almost
perfectly across cores, because documents are independent. Part
[2.4](../02-the-tokenizers-pipeline/2.4-padding-truncation-and-the-mask.md) measures a 2.57× gain from
batching alone on this machine.

Where the gap *does* bite is **serving**, where you tokenize one short prompt at a time and the tokenizer
sits directly in the user's latency budget. There the per-call overhead matters and 10× is 10×.

**Vocabulary size stops being free.** The table above makes a bigger `V` look like a pure win, and at
inference it nearly is. At training it is not: the embedding matrix is `(V, C)` and the output projection
is `(C, V)`, so doubling the vocabulary from 50k to 100k at `C = 768` adds about 77 million parameters —
which, for a small model, can be a large fraction of the total. You paid 77M parameters for the 8.5%
compression gain in the table, and 77M more for the 0.4%. Day 17 (`TOK-20`) is where you choose `V`
against that trade-off properly, and the memory equation on Day 26 (`EFF-01`) is where the arithmetic
gets done.

**Nobody trains a vocabulary on 113 KB.** Published vocabularies are trained on hundreds of gigabytes.
Part [1.4](1.4-your-merges-against-theirs.md) measures how much of the difference between your merge list
and `gpt2`'s is corpus rather than code — and the answer is a lot more interesting than "they had more
data".

print("corpus:", hashlib.sha256(Path("docs/00_MASTER_PLAN.md").read_bytes()).hexdigest()[:16])

enc = tiktoken.get_encoding("gpt2")

print(f"gpt2       V={enc.n_vocab:6d}  ids={len(big):6d}")
print(f"tokenizers V=  1000  ids={len(small):6d}")
