# 3.2 — The tax a vocabulary charges a language

## One-line answer

The same sentence in Hindi costs `gpt2` **6.88×** more tokens per character than English, `cl100k_base`
**4.50×** and `o200k_base` **1.25×** — so a vocabulary is a decision about which languages are cheap, the
tax is paid in context window and in money, and installing a library does not reduce it by one token.

---

## The story

A bus company sells tickets by the seat. One fare, one seat, everywhere in the country.

In the city that works out fine — the stops are close together and one seat gets you where you are going.
Out in the villages the stops are far apart, so the same journey takes four seats' worth of travel, and the
fare is four times higher for people who did not choose where they live.

Nobody set out to charge villagers more. Somebody chose "per seat" because it was the obvious unit, in an
office in the city, measuring journeys that started and ended there.

---

## The idea in plain language

Day 13 part
[3.3](../../../day-013-bpe-encode-decode-bytes/parts/03-byte-level-bpe/3.3-zero-out-of-vocabulary.md)
proved that byte-level BPE has **zero out-of-vocabulary** — every string in every script encodes, by
construction. That is a guarantee about *possibility*, and it is real.

This part is about *cost*, and the two are completely different.

A merge list is trained on a corpus. Merges exist for sequences that were frequent in that corpus. If your
corpus is English, you get merges for `ing`, `tion`, ` the`. A Hindi word gets no merges at all — so it
falls back to one token per byte, and Devanagari characters are three bytes each in UTF-8 (Day 10 part
[2.2](../../../day-010-unicode-code-points-bytes/parts/02-bytes-and-utf-8/2.2-how-utf-8-encodes-a-code-point.md)).

So the same *meaning* costs three or more times as many tokens. And tokens are the unit of:

- **context window** — a 1,024-token window holds a third as much Hindi as English
- **compute** — attention is `O(T²)`, so three times the tokens is nine times the attention work
- **money** — providers bill per token
- **quality** — a model has fewer parameters' worth of attention to spend per unit of meaning

This is not a bug in anyone's code. It is what a merge list *is*. And it is the clearest possible answer to
"what does the library not fix": nothing you install changes it, because the tax lives in the vocabulary,
and a vocabulary is chosen before a single line of serving code runs.

## The mechanism

### Step 1 — one sentence, five languages, four tokenizers

```python
probes = [
    ("English",     "The plan costs zero dollars to run."),
    ("Hindi",       "योजना चलाने में कोई खर्च नहीं होता।"),
    ("Russian",     "План ничего не стоит."),
    ("Japanese",    "この計画の実行に費用はかかりません。"),
    ("Python code", "def f(x):\n    return x ** 2\n"),
]
for name, s in probes:
    counts = {label: len(e.encode_ordinary(s)) for label, e in encoders.items()}
    print(name, len(s), len(s.encode("utf-8")), counts)
```

**Line by line:**

- Each probe is *the same meaning*, not the same length. That is the only fair comparison — comparing
  equal-length strings would measure how verbose a script is, not what the tokenizer charges for it.
- `len(s)` counts characters and `len(s.encode("utf-8"))` counts bytes, and the gap between them is the
  first half of the story: Day 10's layers 3 and 4.
- `encode_ordinary` throughout, per part [1.5](../01-tiktoken/1.5-the-special-token-that-was-just-text.md).

Measured, on this machine:

| Text | chars | bytes | yours (`V=1000`) | `gpt2` | `cl100k` | `o200k` |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| English | 35 | 35 | 16 | 8 | 8 | 8 |
| Hindi | 35 | 93 | **93** | 55 | 36 | 10 |
| Russian | 21 | 38 | **38** | 24 | 11 | 6 |
| Japanese | 18 | 54 | **54** | 26 | 19 | 15 |
| Python code | 28 | 28 | 17 | 14 | 11 | 11 |

Read the bold column first. **Your tokenizer emits exactly one token per byte for Hindi, Russian and
Japanese** — 93 bytes, 93 tokens; 38 and 38; 54 and 54. Not one merge fired. The 744 merges trained on an
English markdown file are worth nothing to those scripts, so the tokenizer degrades exactly to the 256-byte
alphabet. It still works — that is Day 13's guarantee — and it buys nothing.

### Step 2 — normalize by the English rate

Absolute token counts confuse two things: how much a script costs, and how long the sentence happens to be.
Divide by the English rate to isolate the tax:

```python
en = probes[0][1]
for name, s in probes[1:]:
    for label, e in encoders.items():
        rate = len(e.encode_ordinary(s)) / len(s)
        rate_en = len(e.encode_ordinary(en)) / len(en)
        print(f"{name:9s} {label:7s} {rate / rate_en:.2f}x")
```

**Line by line:**

- `len(...) / len(s)` is tokens per **character**, not per byte. Characters are the unit of meaning here;
  bytes would build the answer into the question, since the whole reason Devanagari is expensive is that
  its characters are three bytes.
- Dividing by `rate_en` gives a ratio against the same tokenizer's English rate, so each number answers
  "how much more does this tokenizer charge for this language than for English?"

Measured:

| | `gpt2` | `cl100k_base` | `o200k_base` |
| --- | ---: | ---: | ---: |
| Hindi | **6.88×** | 4.50× | **1.25×** |
| Russian | 5.00× | 2.29× | 1.25× |
| Japanese | 6.32× | 4.62× | 3.65× |
| Python code | 2.19× | 1.72× | 1.72× |

Three things fall out of this table.

**The tax is large and it is real.** A Hindi speaker using a `gpt2`-vocabulary model gets 6.88× less text
in the same context window than an English speaker, and pays 6.88× more per sentence if billed per token.

**It shrank a lot, deliberately.** 6.88 → 4.50 → 1.25 across three successive vocabularies. That is not an
accident of larger `V`; it is multilingual text in the training corpus and a pre-tokenizer pattern
(part [1.2](../01-tiktoken/1.2-the-published-pattern-verbatim.md) noted `o200k`'s splits on letter-category
boundaries) chosen to serve more scripts.

**It did not shrink evenly.** Japanese is still 3.65× on `o200k_base` where Hindi is 1.25×. Japanese has no
spaces, so the pre-tokenizer cannot use whitespace to find word boundaries, and the merge list has to carry
work the pattern does for other languages. Different scripts are hard for different reasons, and "add more
data" does not fix all of them equally.

### Step 3 — what it costs in the only unit that matters

A model has a fixed context window. Converting the rates into text that actually fits:

```python
T_max = 1024
for name, s in probes:
    chars_per_token = len(s) / len(enc_gpt2.encode_ordinary(s))
    print(f"{name:11s} {T_max * chars_per_token:8.0f} characters fit in {T_max} tokens")
```

**Line by line:**

- `T_max = 1024` is GPT-2's context window, named rather than inlined so you can change it and watch every
  row scale together. The ratios between rows do not move — the tax is a property of the tokenizer, not of
  the window.
- `T_max * chars_per_token` inverts the rate into a unit you can act on. "0.64 characters per token" is
  hard to feel; "652 characters fit" is a paragraph, and you know whether your document is bigger.

Measured with `gpt2`:

| Text | chars/token | fits in a 1,024-token window |
| --- | ---: | ---: |
| English | 4.38 | **4,480 characters** |
| Russian | 0.88 | 896 characters |
| Japanese | 0.69 | 709 characters |
| Hindi | 0.64 | **652 characters** |

The same model, the same window, and a Hindi user gets **14.6% of the text** an English user gets. That is
the tax stated in the unit that decides whether a document fits.

## Shapes

| Name | Symbolic | English | Hindi | Meaning |
| --- | --- | ---: | ---: | --- |
| `s` | `(n_chars,)` | `(35,)` | `(35,)` | same meaning, same character count here |
| `raw` | `(n_bytes,)` | `(35,)` | `(93,)` | UTF-8; Devanagari is 3 bytes/char |
| `ids` (yours) | `(T,)` | `(16,)` | `(93,)` | one token per byte — no merge fired |
| `ids` (`gpt2`) | `(T,)` | `(8,)` | `(55,)` | 6.88× the rate per character |
| attention work | `O(T²)` | `64` | `3025` | **47× the compute for one sentence** |

The last row is the one people forget. The tax is not linear in the token count — attention is quadratic,
so 6.88× the tokens is roughly 47× the attention work for the same sentence.

## When it breaks

**Nothing raises. Ever.** This is the purest form of a silent cost: correct output, correct round trip,
correct everything, at several times the price. Day 13's zero-OOV guarantee is what makes it silent — a
tokenizer that *failed* on Devanagari would be found in an afternoon.

**Evaluating only in English.** This is **Silent Failure #5** — evaluated on the format you trained on — in
its most consequential form. An English test suite reports a tokenizer that is 6.88× worse for a billion
people as fully working. The only check is to run non-English text through and look at the rate, which is
four lines of code and gets skipped because nothing prompts you to write it.

**Reading the zero-OOV guarantee as sufficiency.** "Every string encodes" and "every string encodes
affordably" are different claims, and Day 13 proved the first. Quoting it as though it settled the second
is the specific mistake this part exists to prevent.

**Comparing token counts across tokenizers without normalizing.** `o200k_base` emits 10 tokens for the
Hindi probe and `gpt2` emits 55, which looks like a 5.5× win — but `o200k_base` has 4× the vocabulary, so
some of that is `V` and not multilingual support. The ratio-to-English normalization in step 2 is what
separates them.

## In production

**Vocabulary choice is a fairness decision, and it is made once.** Whoever picks the training corpus
decides which languages are cheap for the entire life of the model. It cannot be revisited afterwards
without retraining from scratch, because changing the vocabulary invalidates the `(V, C)` embedding matrix.

**The cost lands on users, not on the people who chose.** Per-token billing means speakers of
under-represented scripts pay several times more for the same conversation. Shorter effective context means
their documents get truncated first — part [2.4](../02-the-tokenizers-pipeline/2.4-padding-truncation-and-the-mask.md)'s
silent truncation, falling unevenly.

**The fixes are known and each has a price.** More multilingual training text for the tokenizer, which
trades away some English compression. A larger `V`, which costs embedding parameters — part 1.1 measured
77M for one doubling at `C = 768`. A script-aware pre-tokenizer, as `o200k_base` uses. Language-specific
vocabularies, which fragment the ecosystem. Day 17 (`TOK-20`) is where you work the trade-off with
numbers.

**Measuring this is a standing obligation, not a one-off.** Four lines, a handful of probe sentences, one
table. It belongs in the same test file as the round-trip checks, because it is the check that catches what
the round-trip checks structurally cannot.

## Check yourself

```python
import tiktoken

PROBES = {
    "English":  "The plan costs zero dollars to run.",
    "Hindi":    "योजना चलाने में कोई खर्च नहीं होता।",
    "Russian":  "План ничего не стоит.",
    "Japanese": "この計画の実行に費用はかかりません。",
}
encs = {n: tiktoken.get_encoding(n) for n in ("gpt2", "cl100k_base", "o200k_base")}

en = PROBES["English"]
for name, s in PROBES.items():
    row = []
    for label, e in encs.items():
        rate = (len(e.encode_ordinary(s)) / len(s)) / (len(e.encode_ordinary(en)) / len(en))
        row.append(f"{label}={rate:.2f}x")
    print(f"{name:9s} chars={len(s):3d} bytes={len(s.encode('utf-8')):3d}  " + "  ".join(row))

# the eval that can go red: every tokenizer must charge non-English more
for name, s in PROBES.items():
    if name == "English":
        continue
    for label, e in encs.items():
        rate = (len(e.encode_ordinary(s)) / len(s)) / (len(e.encode_ordinary(en)) / len(en))
        assert rate >= 1.0, f"{label} charges {name} LESS than English - check your probes"

# and the guarantee still holds: zero OOV, in every script
for name, s in PROBES.items():
    for label, e in encs.items():
        assert e.decode(e.encode_ordinary(s)) == s, f"{label} failed to round-trip {name}"
print("every script round-trips exactly - and costs up to 6.88x to do it")
```

**Line by line:**

- `rate >= 1.0` is the eval that can go red, and it asserts the *direction* rather than a threshold. A
  specific number like `6.88` would be brittle across probe sentences and library versions; the direction
  is the claim.
- The second loop asserts Day 13's guarantee still holds — every script round-trips exactly — deliberately
  next to the cost measurement. Putting the two assertions in the same block is the point of the part:
  **both are true at once**, and reporting only the first is how the second goes unnoticed.
- Probe sentences are written as literals here for readability. In a real test file, keep them in a data
  file with a note on where each came from, so nobody "tidies" them into English.
