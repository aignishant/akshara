# 3.3 — 💥 The mismatch the library will not catch

## One-line answer

Ship the merge list, rebuild the pre-tokenizer at serving time with `add_prefix_space=True` instead of
`False`, and **4 out of 4 probes produce different ids** — `plan` goes from `[382, 293]` to `[898]` — while
every single one still round-trips perfectly through its own path.

---

## The story

🎬 **The scene.** Two people are reading the same book in different countries, arranging a call about
chapter seven. One has the hardback, one has the paperback. Both say "page 143".

😬 **The naive fix.** Read the first line aloud to check. It matches — because they picked a page where the
text happens to line up.

💥 **Why it fails.** The two editions are typeset differently, so page numbers drift by a few pages, more
in some places than others. The check they ran — "does page 143 look like the same text?" — passed on the
one page they tried and says nothing about page 200. Every later reference is wrong by an amount neither
of them can see, and both are certain they are on the same page.

💡 **The insight.** The number is not the thing. Two systems agreeing on a *number* means nothing unless
they agree on what the number indexes. Checking the content at one shared point does not establish that,
and no amount of checking more points establishes it either — you have to compare the *edition*.

---

## The idea in plain language

This day has now found, in five separate places, that the round-trip test passes on a real bug:

| Part | The bug | Round trip |
| --- | --- | --- |
| [1.1](../01-tiktoken/1.1-the-same-corpus-through-both.md) | two tokenizers, wildly different token counts | ✅ both |
| [1.3](../01-tiktoken/1.3-what-a-vocabulary-file-looks-like.md) | merge list missing; every chunk falls to bytes | ✅ |
| [1.5](../01-tiktoken/1.5-the-special-token-that-was-just-text.md) | 9 ids vs 4 ids, one containing end-of-document | ✅ both |
| [2.2](../02-the-tokenizers-pipeline/2.2-the-same-vocabulary-trained-twice.md) | two merge lists, 651 positions apart | ✅ both |
| **this part** | **train and serve disagree on every input** | **✅ both** |

The pattern is now impossible to miss. `decode(encode(s)) == s` tests that **one** tokenizer is
self-consistent. It cannot test that **two** tokenizers agree, because each one round-trips through its
own configuration.

And "two tokenizers" is not an exotic situation. It is the normal one: the machine that trained the model
and the machine that serves it are different machines, running different code, at different times. Silent
Failure #2 is not a mistake somebody makes — it is the **default outcome** unless something actively
prevents it.

The thing that actively prevents it is part [3.1](3.1-the-file-is-the-contract.md)'s file. This part shows
what happens when you ship the file and then helpfully rebuild one stage anyway.

## Why Akshara needs it

**Because this is the failure Day 16 (`TOK-17`) is named after**, and meeting it here — in five lines,
with a measured table — is far cheaper than meeting it in a training run.

**Because it is the answer to "so should I just use the library?"** Yes, and it will not save you. Every
mechanism in this part is available in a correctly-installed, correctly-pinned, correctly-loaded library.
The library gives you a file that *can* carry the whole configuration; it cannot stop you overriding one
field after loading it.

**Because it names the check that does work**, and that check goes into `tests/` today: compare **ids**
produced by the two paths, on probes chosen to be sensitive. That is the plan's §6 remedy for Silent
Failure #2 — "round-trip the exact training string through the inference path and `assert` equality" —
and this part is where you see why each word in that sentence is doing work.

## The mechanism

### Step 1 — train, save, ship

```python
train_tok = build(add_prefix_space=False)
train_tok.save("tokenizer.json")
```

Nothing suspicious. The tokenizer trains, saves the whole configuration into one file, and that file is
committed and shipped.

### Step 2 — the serving code, which loads the file and then "fixes" it

```python
serve_tok = Tokenizer.from_file("tokenizer.json")
serve_tok.pre_tokenizer = pre_tokenizers.ByteLevel(add_prefix_space=True, use_regex=True)
```

**Line by line:**

- `Tokenizer.from_file` loads everything correctly. At this instant the two tokenizers are identical.
- The second line is the entire bug. Somebody assigned a pre-tokenizer *after* loading — because a
  tutorial showed that line, because a linter complained the pre-tokenizer was unset in a code path,
  because the default in an example had `add_prefix_space=True`. The reason never matters; the shape is
  always the same: **a stage reconstructed in code instead of taken from the file.**
- `add_prefix_space=True` means "prepend a space to the input before splitting", so the tokenizer treats
  `plan` as if it were ` plan`. It is a real setting with a real purpose — it makes the first word of a
  string tokenize the same way as a word in the middle — and it must match what training used.

### Step 3 — the measurement

```python
for probe in ["plan", "The plan costs zero.", "zero budget", "Akshara"]:
    a, b = train_tok.encode(probe), serve_tok.encode(probe)
    print(f"{probe!r:24s} train={str(a.ids):30s} serve={str(b.ids):30s} same={a.ids == b.ids}")
```

**Line by line:**

- The probes are short, and three of the four **start with a bare word**, because that is where
  `add_prefix_space` bites hardest. A list of long sentences would show one differing id in eight and read
  as noise.
- `a.ids == b.ids` compares **lists of integers**. That single comparison is the entire fix this part
  argues for, and it is printed beside the ids so you can see it is not doing anything clever.
- Both tokenizers encode the *same* `probe` string. Nothing is transformed between them; the only
  difference is their configuration.

Measured, `tokenizers==0.23.1`, corpus `9760f2b6d4340b97`:

```text
'plan'                   train=[382, 293]                serve=[898]                     same=False
'The plan costs zero.'   train=[629, 898, 269, 681, 82, 863, 997, 13]
                         serve=[351, 898, 269, 681, 82, 863, 997, 13]  same=False
'zero budget'            train=[89, 997, 415, 67, 711]   serve=[863, 997, 415, 67, 711]  same=False
'Akshara'                train=[32, 643]                 serve=[716]                     same=False
```

**4 out of 4 disagree.** Not an edge case, not a rare input — *every* probe.

Look at `'plan'`:

```text
train tokens: ['pl', 'an']      ids [382, 293]
serve tokens: ['Ġplan']         ids [898]
```

Two tokens versus one. Different ids entirely. And look at the third row: only the **first** id changed —
`89` became `863` — because the difference is confined to the start of the string. That is why the bug is
so hard to see by eye: on a long document, one id in several hundred differs, and it is always the first
one.

### Step 4 — and every one of them round-trips

```python
for probe in probes:
    print(f"{probe!r:24s} train rt={train_tok.decode(train_tok.encode(probe).ids) == probe}  "
          f"serve rt={serve_tok.decode(serve_tok.encode(probe).ids).lstrip(' ') == probe}")
```

Both paths decode back to the original string. Every time.

**Line by line:**

- `.lstrip(' ')` on the serving side is the tell, and it is worth pausing on. The serving tokenizer added a
  space, so its decode returns `' plan'`; stripping it makes the round trip pass. In real code that
  `lstrip` gets added by somebody fixing a cosmetic bug ("there's a leading space in the output"), and it
  makes the round-trip test pass while the underlying mismatch is untouched. **A test that had to be
  loosened to pass is evidence, not a fix.**

So: the ids are wrong on every input, the round trip is green on every input, and there is no error
anywhere. If this tokenizer serves a model trained with the other one, the model receives token sequences
it has never seen for the beginning of every prompt. The output degrades. Nothing points at the tokenizer.

### Step 5 — the check that works

```python
def assert_same_tokenizer(a, b, probes):
    """Two tokenizers agree iff they produce identical IDS on every probe."""
    for p in probes:
        ia, ib = a.encode(p).ids, b.encode(p).ids
        assert ia == ib, f"mismatch on {p!r}: {ia} != {ib}"
```

**Line by line:**

- `a.encode(p).ids == b.encode(p).ids` — **ids against ids**, not strings against strings. That single
  substitution is the whole fix, and it catches every one of the five failures tabulated at the top of this
  part.
- The probes have to be chosen to be sensitive. `"plan"` catches this bug because it is a bare word at the
  start of a string; `"The plan."` catches it more weakly, in one id out of eight. A probe list should
  include: a bare word, a leading space, a multi-byte character, a number, a run of whitespace, and a
  special-token literal. Day 17's failure lab builds the full list.
- It asserts, rather than logging. This runs in `tests/`, CPU-only and offline, and it goes red.

The stronger version compares the files instead of the behaviour:

```python
assert train_tok.to_str() == serve_tok.to_str(), "the two tokenizers are not the same object"
```

**Line by line:**

- `to_str()` serializes all five stages plus padding and truncation, so this compares the **configuration**
  rather than sampling its behaviour. It cannot be defeated by an unlucky probe set.
- It is an exact string comparison, which makes it strict to the point of brittleness — a key-order change
  between library versions would fail it. That is usually the right trade for a check whose job is to
  notice that something moved.

This catches configuration drift *before* you have to guess which probes would reveal it — the "compare the
edition, not the page number" move from the story. It is strictly better where you can use it, and you
cannot always, because the serving side may be a different implementation reading the same file.

## Shapes

| Name | Symbolic | Train | Serve | Meaning |
| --- | --- | --- | --- | --- |
| `'plan'` ids | `(T,)` | `(2,)` | `(1,)` | different length, same string |
| `'The plan costs zero.'` ids | `(T,)` | `(8,)` | `(8,)` | same length, first id differs |
| probes disagreeing | scalar | — | `4 / 4` | every input |
| probes round-tripping | scalar | `4 / 4` | `4 / 4` | the test that passes |

The second row is the dangerous shape: **same length, different content.** A check on sequence length —
which is what a lot of ad-hoc validation actually amounts to — passes.

---

## When it breaks

**It does not break. That is the finding.** No exception, no warning, no log line, from a correctly
installed library on correctly formatted input. The only visible symptom is a model that performs slightly
worse than it did in evaluation, which gets attributed to the model.

**The `lstrip` trap**, from step 4. When a test has to be relaxed to pass, the relaxation is the bug report.
Write down *why* the strip was needed and the mismatch is usually one line away.

**The "it works on my long document" trap.** With a 500-token document, one differing id is 0.2% of the
sequence — easy to dismiss as noise if you are eyeballing. The probe set must contain **short** strings,
where a single differing id is half the sequence.

**Where this really happens.** Not usually as `add_prefix_space`. The common forms are:

- serving code rebuilds the chat template as an f-string instead of loading the post-processor (part 3.1)
- training used a normalizer, serving did not (part [2.5](../02-the-tokenizers-pipeline/2.5-the-normalizer-that-broke-the-round-trip.md))
- two library versions whose defaults changed between releases
- the merge list travelled and the pre-tokenizer did not — the `gpt2`-format problem from part
  [1.3](../01-tiktoken/1.3-what-a-vocabulary-file-looks-like.md)

All four have the identical signature: correct round trips, different ids, degraded output.

## In production

**The remedy is structural, not vigilant.** "Be careful not to override the pre-tokenizer" is not a
control. The controls that work are: load the file and never construct a stage in code; hash the tokenizer
file and log the hash at both training and serving; and run `assert_same_tokenizer` in CI against a
committed probe set.

**Log the tokenizer hash next to the model hash.** If a serving process printed the SHA-256 of its
`tokenizer.json` at startup, and training recorded the same, this entire class of bug becomes a one-line
comparison. That is precisely what `docs/MODELS.md` is for in this repo, and why Principle 13 wants the row
written before the load.

**Golden-file tests are the standard defence.** Commit a file of `(string, expected_ids)` pairs generated
at training time. Any change to any of the five stages, in any library version, on any machine, fails that
test immediately. It is cheap, it is boring, and it is the only thing that reliably catches this.

**This is why tokenizer changes are treated as breaking changes.** A model and its tokenizer are one
artifact. Versioning them separately is how the two drift apart, and the drift is invisible until somebody
measures ids.

## Check yourself

```python
from tokenizers import Tokenizer, models, pre_tokenizers, decoders, trainers
from pathlib import Path

text = Path("docs/00_MASTER_PLAN.md").read_text(encoding="utf-8")

def build(add_prefix_space):
    t = Tokenizer(models.BPE())
    t.pre_tokenizer = pre_tokenizers.ByteLevel(add_prefix_space=add_prefix_space,
                                               use_regex=True)
    t.decoder = decoders.ByteLevel()
    t.train_from_iterator([text], trainer=trainers.BpeTrainer(
        vocab_size=1000, show_progress=False,
        initial_alphabet=pre_tokenizers.ByteLevel.alphabet()))
    return t

train_tok = build(add_prefix_space=False)
train_tok.save("tokenizer.json")

# the bug: load the file, then rebuild one stage in code
serve_tok = Tokenizer.from_file("tokenizer.json")
serve_tok.pre_tokenizer = pre_tokenizers.ByteLevel(add_prefix_space=True, use_regex=True)

PROBES = ["plan", "The plan costs zero.", "zero budget", "Akshara"]

# 1. the weak test passes on both - demonstrate it, do not assume it
for p in PROBES:
    assert train_tok.decode(train_tok.encode(p).ids) == p
    assert serve_tok.decode(serve_tok.encode(p).ids).lstrip(" ") == p
print("round trip: green on both paths")

# 2. the eval that can go red: ids against ids
n_diff = sum(1 for p in PROBES if train_tok.encode(p).ids != serve_tok.encode(p).ids)
print(f"{n_diff}/{len(PROBES)} probes produce different ids")
assert n_diff == len(PROBES), "expected every probe to disagree"

# 3. the stronger check, when both sides are the same implementation
assert train_tok.to_str() != serve_tok.to_str(), "configs should differ - they do"

# 4. and the version that must PASS: reload without touching anything
clean = Tokenizer.from_file("tokenizer.json")
for p in PROBES:
    assert clean.encode(p).ids == train_tok.encode(p).ids, \
        f"a clean reload disagrees on {p!r} - the file does not capture the tokenizer"
assert clean.to_str() == train_tok.to_str()
print("clean reload: ids identical, configs identical")
```

**Line by line:**

- Block 1 asserts the weak test **passes**, which is the point of the part. Asserting a green result is
  unusual and correct here: it records that the check you might have relied on genuinely does not fire.
- Block 2 is the eval that can go red. `n_diff == len(PROBES)` demands *every* probe disagree — a stronger
  claim than "at least one", and it fails loudly if you swap in probes that are not sensitive to this
  particular bug.
- Block 4 is the positive control, and no test suite should ship without one. It proves the file **does**
  round-trip through save and load when nobody interferes, which is what makes block 2's failure
  attributable to the override rather than to the format.
