# 3.1 — The file is the contract

## One-line answer

`tokenizer.json` is one 51,913-byte file holding all five stages plus the padding and truncation settings —
so the thing that travels between the machine that trained and the machine that serves is the **entire
configuration**, not just the merge list, and that is the single biggest practical difference from the
`gpt2` format in part [1.3](../01-tiktoken/1.3-what-a-vocabulary-file-looks-like.md).

---

## The story

You lend somebody your bread recipe. You write down the ingredients and the quantities, because that is
what a recipe is.

Their bread comes out wrong. Not inedible — just wrong, denser, a bit flat. They followed the recipe
exactly.

What you did not write down was the oven temperature, because your oven is always at that temperature; and
that you leave the dough overnight, because you always do; and that you use the tin, not a tray. None of
those felt like part of the recipe. All of them are part of the bread.

The recipe was not wrong. It was incomplete in exactly the places where you had stopped noticing you were
making a choice.

---

## The idea in plain language

Part [2.1](../02-the-tokenizers-pipeline/2.1-five-stages-not-one.md) established that a tokenizer is five
stages, and that four of them must match between training and serving. The obvious follow-up question is:
*how do they match?*

The `gpt2` answer is that they do not, formally. `vocab.bpe` and `encoder.json` contain stage 3 — the merges
and the vocabulary. Stages 1, 2, 4 and 5 are things you have to know, from documentation, from reading
somebody's code, or from folklore. Every mismatch part 2.5 and part
[3.3](3.3-the-mismatch-the-library-will-not-catch.md) describe becomes possible because the file does not
carry enough to prevent it.

The `tokenizer.json` answer is that **everything is in the file**. All five stages, plus the padding and
truncation state, plus the special tokens, serialized together. Load the file and you have reconstructed
the exact tokenizer, including the parts nobody thought to document.

That is what "the file is the contract" means. Not that the format is elegant — it is a fairly ordinary
JSON blob — but that it moved a whole class of bugs from *possible* to *impossible*, by making the
configuration a thing that travels rather than a thing you remember.

---

## Why Akshara needs it

**Because Akshara's tokenizer becomes a committed artifact on Day 16**, and this part is the specification
to copy. What goes in the file determines which mismatches your future self can still make.

**Because Principle 9 says configs are committed.** A tokenizer's config is all five stages. Committing the
merge list alone satisfies the letter and misses the point — part 3.3 shows a bug where the merge list is
byte-identical on both machines and every id still differs.

**Because reading an unfamiliar tokenizer's file is a standing skill.** When you inherit a model, this file
tells you what its text pipeline actually does — including flags whose defaults you would never have
guessed. Two of them, `byte_fallback` and `dropout`, are subjects of Day 15.

---

## The mechanism

### Step 1 — save it and look at the top level

```python
import json
from pathlib import Path

tok.save("tokenizer.json")
blob = json.loads(Path("tokenizer.json").read_text(encoding="utf-8"))
print("bytes:", Path("tokenizer.json").stat().st_size)
print("keys :", list(blob.keys()))
```

**Line by line:**

- `tok.save(path)` writes the whole object. There is no "save the vocabulary" and "save the config" — the
  absence of that choice is the design.
- Reading it straight back with `json.loads` rather than `Tokenizer.from_file` is deliberate here: you are
  inspecting the contract, not using it.

Measured, `tokenizers==0.23.1`, the `V = 1000` tokenizer from part 2.1:

```text
bytes: 51913
keys : ['version', 'truncation', 'padding', 'added_tokens',
        'normalizer', 'pre_tokenizer', 'post_processor', 'decoder', 'model']
```

Nine keys. Map them against the five stages from part 2.1:

| Key | What it is |
| --- | --- |
| `version` | the format version, so a future reader knows how to parse this |
| `truncation` | stage 0.5 — the `max_length` policy from part 2.4 |
| `padding` | ditto: pad id, pad token, direction |
| `added_tokens` | special tokens added after training, with their ids |
| `normalizer` | **stage 1** |
| `pre_tokenizer` | **stage 2** |
| `post_processor` | **stage 4** |
| `decoder` | **stage 5** |
| `model` | **stage 3** — the merges and the vocabulary |

Every stage, and the two settings that are not stages but change the output anyway. Note that `truncation`
and `padding` are in the file: part 2.4 called them "state on the tokenizer", and this is where that state
lives when it travels.

### Step 2 — the `model` key, and the flags you did not choose

```python
print("model keys:", list(blob["model"].keys()))
print("vocab entries:", len(blob["model"]["vocab"]))
print("merges[:3]   :", blob["model"]["merges"][:3])
```

```text
model keys: ['type', 'dropout', 'unk_token', 'continuing_subword_prefix',
             'end_of_word_suffix', 'fuse_unk', 'byte_fallback', 'ignore_merges',
             'vocab', 'merges']
vocab entries: 1000
merges[:3]   : [['Ġ', '|'], ['Ġ', 'a'], ['Ġ', 't']]
```

**Line by line:**

- `vocab` and `merges` are the two things your Day 13 tokenizer had. `merges[0]` is `['Ġ', '|']` — the
  markdown-table merge from part [1.4](../01-tiktoken/1.4-your-merges-against-theirs.md), still at rank 0.
- The other eight keys are configuration you never set, sitting at their defaults. Four of them matter
  enough to name:

| Flag | Default | What it does |
| --- | --- | --- |
| `dropout` | `null` | **BPE-dropout**: randomly skip merges during training so the model sees several tokenizations of the same word. This is subword regularization — Day 15 (`TOK-15`). |
| `byte_fallback` | `false` | If a character has no token, emit its raw bytes rather than `<unk>`. Irrelevant here — byte-level BPE has no unknowns by construction (Day 13 part [3.3](../../../day-013-bpe-encode-decode-bytes/parts/03-byte-level-bpe/3.3-zero-out-of-vocabulary.md)) — and essential for the SentencePiece-style tokenizers of Day 15. |
| `unk_token` | `null` | The token for "I have never seen this". `null` is the correct value for a byte-level tokenizer and setting it would tell the next reader something false. |
| `ignore_merges` | `false` | Look tokens up whole in the vocabulary before applying merges. Changes the output for tokens that exist in the vocabulary but are not reachable by the merge sequence — the non-canonical ids of Day 13 part [1.2](../../../day-013-bpe-encode-decode-bytes/parts/01-encode-and-decode/1.2-decode-is-a-lookup-not-a-search.md). |

**Every one of these changes the ids and none of them raises.** That is the case for putting them in the
file: they are not documentation, they are behaviour, and behaviour has to travel.

### Step 3 — the post-processor, which is Day 16 in miniature

Stage 4 has been `None` all day. Here is what it is for:

```python
from tokenizers import processors

tok2 = Tokenizer.from_file("tokenizer.json")
tok2.add_special_tokens(["<|bos|>", "<|eos|>"])
tok2.post_processor = processors.TemplateProcessing(
    single="<|bos|> $A <|eos|>",
    special_tokens=[("<|bos|>", tok2.token_to_id("<|bos|>")),
                    ("<|eos|>", tok2.token_to_id("<|eos|>"))],
)
out = tok2.encode("The plan.")
print("tokens             :", out.tokens)
print("special_tokens_mask:", out.special_tokens_mask)
print("decode, skip       :", repr(tok2.decode(out.ids)))
print("decode, keep       :", repr(tok2.decode(out.ids, skip_special_tokens=False)))
```

**Line by line:**

- `Tokenizer.from_file` reconstructs everything — this is the contract being honoured. The tokenizer that
  comes back has the same five stages as the one that was saved.
- `add_special_tokens` must come **before** `token_to_id` can find them; the ids are assigned at the moment
  of adding, appended above the trained vocabulary. Part 2.4 measured that: `<|pad|>` got id 1000.
- `TemplateProcessing(single="<|bos|> $A <|eos|>")` — `$A` is the placeholder for the encoded sequence. The
  template is a *string in the file*, not code, which is exactly the point.
- `skip_special_tokens` defaults to `True` on decode, so the structure disappears on the way out. That
  default is what you want for showing a reply to a person, and it is a trap when debugging, because it
  hides the tokens you are trying to inspect.

Measured:

```text
tokens             : ['<|bos|>', 'The', 'Ġplan', '.', '<|eos|>']
special_tokens_mask: [1, 0, 0, 0, 1]
decode, skip       : 'The plan.'
decode, keep       : '<|bos|>The plan.<|eos|>'
```

`special_tokens_mask` — all zeros back in part
[2.3](../02-the-tokenizers-pipeline/2.3-offsets-are-the-product.md) — now marks the two structural
positions. That mask is how a training loop knows which positions are template and which are content, and
Day 16 (`TOK-17`) uses it to build the label mask that prevents Silent Failure #3.

Save this tokenizer and the template goes into the file, under `post_processor`. The serving stack loads
it rather than reimplementing it in an f-string — which is the single most common way real systems
reintroduce Silent Failure #2.

---

## Shapes

| Name | Symbolic | Concrete | Meaning |
| --- | --- | --- | --- |
| `vocab` | `(V,)` | `(1000,)` | token → id, all five stages' shared table |
| `merges` | `(V - 256, 2)` | `(744, 2)` | ordered pairs |
| `added_tokens` | `(n_special,)` | `(0,)` then `(2,)` | ids assigned above `V` |
| `ids` before stage 4 | `(T,)` | `(3,)` | `The plan.` |
| `ids` after stage 4 | `(T + 2,)` | `(5,)` | template adds `<|bos|>`, `<|eos|>` |
| `special_tokens_mask` | `(T + 2,)` | `(5,)` | `[1, 0, 0, 0, 1]` |

The `T + 2` row is the one to carry forward: a post-processor changes the sequence length, so any
`max_length` budget has to account for the template. Truncating to 8 and then adding 2 template tokens
gives 10, which will not fit the tensor you allocated.

---

## When it breaks

**Reimplementing the template in serving code.** The classic. Training used the file; serving uses an
f-string somebody wrote from the documentation. They agree until a space or a newline differs, and then
every prompt is subtly off-distribution. No error, slightly worse outputs, extremely hard to attribute.
The fix is structural: load the template, never write it twice.

**Assuming the defaults in `model` are neutral.** `ignore_merges` and `byte_fallback` change ids. If you
build a tokenizer in code and a colleague builds "the same" one from a file with a different flag, you get
part 3.3's bug.

**Trusting `decode` while debugging.** `skip_special_tokens=True` is the default, so:

```text
decode, skip : 'The plan.'
decode, keep : '<|bos|>The plan.<|eos|>'
```

If you are hunting a template bug and printing `tok.decode(ids)`, the template is invisible. Print
`tok.decode(ids, skip_special_tokens=False)`, or print `out.tokens`, which never hides anything.

**Editing `tokenizer.json` by hand.** It is JSON, so it invites editing, and the `vocab` and `merges` must
stay consistent — a merge whose result is not in the vocabulary, or a vocabulary whose ids are not dense,
produces failures far from the edit. Regenerate the file; do not patch it.

---

## In production

**This file is what a model release ships.** Alongside the weights, one `tokenizer.json`, and the two must
match or the model is useless. Its stability matters more than its elegance: a tokenizer file is loaded by
many independent implementations, so the format is conservative on purpose.

**Which is also why `docs/MODELS.md` exists in this repo.** The file is a contract only if you know *which*
file you have. A revision SHA beside the download is the difference between "we use their tokenizer" and
"we use the exact bytes we tested against". Principle 13's row is written before the load for this reason,
and you wrote three of them at the start of today.

**Loading is not executing, and that distinction is worth stating.** JSON, parsed by a JSON parser. Nothing
in it runs. Contrast with a pickled tokenizer object, which Principle 13 forbids outright — `torch.load` on
an untrusted file executes arbitrary code, and no amount of care about the vocabulary helps.

**The file grows with the model.** A `V = 50000` tokenizer file is a few megabytes; the flags and templates
are a rounding error next to the vocabulary. There is no size pressure to leave things out, which is
precisely why leaving them out was always a mistake rather than a trade-off.

## Check yourself

```python
import json
from pathlib import Path
from tokenizers import Tokenizer, processors

tok.save("tokenizer.json")
blob = json.loads(Path("tokenizer.json").read_text(encoding="utf-8"))

# 1. all five stages present as keys, even when null
for stage in ("normalizer", "pre_tokenizer", "model", "post_processor", "decoder"):
    assert stage in blob, f"{stage} missing from the file - the contract is incomplete"
    print(f"{stage:15s}: {type(blob[stage]).__name__} "
          f"{'(null)' if blob[stage] is None else ''}")

# 2. the eval that can go red: a round trip through the FILE, not the string
reloaded = Tokenizer.from_file("tokenizer.json")
probe = "The plan costs 0 dollars. café ½"
assert reloaded.encode(probe).ids == tok.encode(probe).ids, \
    "saving and loading changed the ids - the file does not capture the tokenizer"
print("file round trip: ids identical")

# 3. vocab and merges must be consistent
vocab, merges = blob["model"]["vocab"], blob["model"]["merges"]
assert len(vocab) == 1000, f"vocab is {len(vocab)}, expected 1000"
assert len(merges) == len(vocab) - 256, "V = 256 + n_merges is broken"
for a, b in merges[:50]:
    assert a + b in vocab, f"merge {(a, b)} produces {a + b!r}, which is not in the vocab"
print(f"{len(vocab)} vocab, {len(merges)} merges, first 50 merges land in the vocab")

# 4. a post-processor changes the length - budget for it
tok2 = Tokenizer.from_file("tokenizer.json")
tok2.add_special_tokens(["<|bos|>", "<|eos|>"])
tok2.post_processor = processors.TemplateProcessing(
    single="<|bos|> $A <|eos|>",
    special_tokens=[("<|bos|>", tok2.token_to_id("<|bos|>")),
                    ("<|eos|>", tok2.token_to_id("<|eos|>"))])
before, after = len(tok.encode("The plan.").ids), len(tok2.encode("The plan.").ids)
print(f"template adds {after - before} tokens")
assert after == before + 2
assert tok2.encode("The plan.").special_tokens_mask == [1, 0, 0, 0, 1]
```

**Line by line:**

- Check 2 is the eval that can go red and it is the one that actually tests the claim of this part. A
  string round trip (`decode(encode(s)) == s`) tests the tokenizer; this tests the **file**, by comparing
  ids from a freshly loaded object against the original. If the file failed to capture some stage, this is
  where you find out.
- The probe deliberately includes `café` and `½` — the characters that broke things in parts 2.3 and 2.5.
  An ASCII probe would pass even if the normalizer were dropped on save, which is Silent Failure #5 again.
- `a + b in vocab` checks the structural invariant that every merge produces a token that exists. Only the
  first 50 are checked to keep it quick; drop the slice to check all 744.
- `assert stage in blob` uses `in`, not truthiness. `blob["normalizer"]` is `None` here, and `if
  blob["normalizer"]` would report it missing. The distinction between "absent" and "present and null" is
  the whole contract.
