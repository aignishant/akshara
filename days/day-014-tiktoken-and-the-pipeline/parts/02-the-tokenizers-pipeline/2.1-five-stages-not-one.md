# 2.1 — Five stages, not one

## One-line answer

What you have been calling "the tokenizer" is five separate, independently configurable objects — a
normalizer, a pre-tokenizer, a model, a post-processor and a decoder — and the reason to take them apart is
that **four of them have to match between training and serving, and nothing checks that they do**.

---

## The story

You order a coffee and it arrives. One thing happened, as far as you are concerned.

Behind the counter it was five things: somebody took the order, somebody ground the beans, somebody pulled
the shot, somebody added the milk, somebody wrote the name on the cup. When the coffee is right you never
think about the five. When it is wrong, "the coffee is bad" is not a useful sentence — the grind, the shot
and the milk fail differently and are fixed differently.

Nobody takes the machine apart because they enjoy it. They take it apart because at some point the coffee
is wrong and "the coffee" is not a thing you can fix.

---

## The idea in plain language

Over Days 11 to 13 you wrote a tokenizer as a handful of functions that called each other. It worked. It
also blurred five distinct jobs into one word.

The `tokenizers` library separates them, and the separation is not bureaucracy — it is the vocabulary you
need to describe a bug:

| Stage | Job | Yours (Day 13) | Changes the string? |
| --- | --- | --- | --- |
| **1. Normalizer** | rewrite the text before anything else | `NORM = "NFC"` on Day 11; nothing on Day 13 | **yes** |
| **2. Pre-tokenizer** | split into chunks that may never merge across | the `GPT_LIKE` regex + byte→unicode map | no |
| **3. Model** | apply the merges; produce ids | `encode_chunk` + the vocabulary | no |
| **4. Post-processor** | add the structural tokens | nothing yet — Day 16 | no |
| **5. Decoder** | ids back to a string | `from_symbols` + `bytes.decode` | inverse of 1–3 |

Two things about this table are the whole part.

**Only stage 1 changes the text.** Stages 2 and 3 re-describe it; they do not edit it. That is why the
round trip works at all, and it is why part [2.5](2.5-the-normalizer-that-broke-the-round-trip.md) — where
a normalizer is switched on — is the part where the round trip dies.

**Stage 5 is not derived from stages 1–3.** You configure the decoder separately, and **nothing verifies it
is their inverse**. Set a byte-level pre-tokenizer with no byte-level decoder and the library will
cheerfully hand you `Ġplan`. This is the single most surprising thing about the design, and once you have
seen it you stop trusting "it round-trips on my test string" as evidence.

---

## Why Akshara needs it

**Because this is the vocabulary for every tokenizer bug you will hit for the rest of the curriculum.**
"The tokenizer is wrong" is not diagnosable. "The pre-tokenizer disagrees between training and serving" is
a one-line fix, and part [3.3](../03-the-remaining-gap/3.3-the-mismatch-the-library-will-not-catch.md)
shows exactly that bug.

**Because Akshara's tokenizer will be assembled from these five stages on Day 16**, when the chat template
arrives. The post-processor — the one stage you have never written — is where a chat template lives, and
`TOK-17` is Silent Failure #2 by name.

**Because five configurable stages is five things to get wrong.** The plan's §6 says tokenizer mismatch is
one of the five silent failures. This part says *where* the mismatch can hide: four of these five stages
must be byte-identical between the machine that trained and the machine that serves, and the file format in
part [3.1](../03-the-remaining-gap/3.1-the-file-is-the-contract.md) exists to make that possible.

---

## The mechanism

Build the same byte-level BPE as part [1.1](../01-tiktoken/1.1-the-same-corpus-through-both.md), then run
one short string through it stage by stage instead of all at once.

### Step 1 — build it, naming each stage

```python
from tokenizers import Tokenizer, models, pre_tokenizers, decoders, trainers

tok = Tokenizer(models.BPE())                                           # stage 3
tok.pre_tokenizer = pre_tokenizers.ByteLevel(add_prefix_space=False,    # stage 2
                                             use_regex=True)
tok.decoder = decoders.ByteLevel()                                      # stage 5
tok.train_from_iterator([text], trainer=trainers.BpeTrainer(
    vocab_size=1000, show_progress=False,
    initial_alphabet=pre_tokenizers.ByteLevel.alphabet()))
```

**Line by line:**

- `Tokenizer(models.BPE())` — the `Tokenizer` object is a *container* for the five stages, and the model is
  the one you pass to the constructor because it is the only mandatory one. The other four default to
  "do nothing", which for the normalizer and post-processor is genuinely fine and for the decoder is a trap.
- Stages 1 and 4 are never assigned here. They will read as `None`, and that is a real configuration, not
  an incomplete one.
- Everything else is as part 1.1 explained it; this part changes nothing about the setup, only how it is
  inspected.

### Step 2 — run the stages one at a time

```python
s = "The plan costs 0 dollars."

print("1 normalizer     :", tok.normalizer)
normalized = tok.normalizer.normalize_str(s) if tok.normalizer else s
print("  output         :", repr(normalized))
print("2 pre-tokenizer  :", tok.pre_tokenizer.pre_tokenize_str(normalized))
out = tok.encode(s)
print("3 model tokens   :", out.tokens)
print("  ids            :", out.ids)
print("4 post-processor :", tok.post_processor)
print("5 decoder        :", repr(tok.decode(out.ids)))
```

**Line by line:**

- `tok.normalizer.normalize_str(s)` runs **only** stage 1 and hands back a string. Guarded with a
  conditional because `None` has no `normalize_str` — and the guard is the honest way to write it, since
  "no normalizer" is a legitimate configuration you should be able to see.
- `tok.pre_tokenizer.pre_tokenize_str(...)` runs **only** stage 2 and returns `(chunk, (start, end))`
  pairs. Those offsets are where part [2.3](2.3-offsets-are-the-product.md) begins — the pre-tokenizer is
  the stage that knows where things came from, and every later stage merely carries that knowledge forward.
- Note it is fed `normalized`, not `s`. Feeding it `s` would be wrong whenever a normalizer exists, and
  since the normalizer here is `None` the bug would be invisible on this example. That is the shape of
  every mistake in this section.
- `tok.encode(s)` runs all five. There is no public "run only stage 3" call — the model is not meaningfully
  runnable on its own, because it needs the chunking to know where merges may not cross.

Measured output, `tokenizers==0.23.1`:

```text
1 normalizer     : None
  output         : 'The plan costs 0 dollars.'
2 pre-tokenizer  : [('The', (0, 3)), ('Ġplan', (3, 8)), ('Ġcosts', (8, 14)),
                    ('Ġ0', (14, 16)), ('Ġdollars', (16, 24)), ('.', (24, 25))]
3 model tokens   : ['The', 'Ġplan', 'Ġc', 'ost', 's', 'Ġ', '0', 'Ġd', 'oll', 'ar', 's', '.']
  ids            : [629, 898, 269, 681, 82, 220, 15, 273, 746, 287, 82, 13]
4 post-processor : None
5 decoder        : 'The plan costs 0 dollars.'
```

### Step 3 — read what each stage did

**Stage 2 produced 6 chunks. Stage 3 turned them into 12 tokens.** That is the invariant worth carving into
your memory: *the model can only split chunks further, never join them.* `Ġcosts` became `Ġc` + `ost` +
`s` because this 744-merge vocabulary has no token for the whole word; but `Ġcosts` could never have merged
with `Ġ0`, no matter how often that pair occurred, because the pre-tokenizer put a wall between them. This
is Day 12 part [1.4](../../../day-012-bpe-the-merge-loop/parts/01-the-merge-loop/1.4-the-pre-tokenizer.md)
restated in library terms.

**`Ġ0` became `Ġ` + `0`.** Two tokens for a two-character chunk — no merge learned, so it falls back to
individual bytes. Day 13 part
[2.4](../../../day-013-bpe-encode-decode-bytes/parts/02-the-regex-pre-tokenizer/2.4-the-number-that-was-three-tokens.md)
is the day that explained why numbers are like this.

**Stages 1 and 4 are `None`, and the string survives.** With no normalizer the text reaching the
pre-tokenizer is exactly what you passed in — which is why `decode(encode(s)) == s` holds here and will
stop holding in part 2.5.

### Step 4 — the trap: the decoder is not checked

```python
tok_broken = build_the_same_way_but_never_assign_a_decoder()
ids = tok.encode(s).ids                       # the SAME ids as the working tokenizer
print("tokens          :", tok.encode(s).tokens)
print("with decoder    :", repr(tok.decode(ids)))
print("without decoder :", repr(tok_broken.decode(ids)))
```

Measured:

```text
tokens          : ['The', 'Ġplan', 'Ġc', 'ost', 's', 'Ġ', '0', 'Ġd', 'oll', 'ar', 's', '.']
with decoder    : 'The plan costs 0 dollars.'
without decoder : 'The Ġplan Ġc ost s Ġ 0 Ġd oll ar s .'
```

**Line by line:**

- The ids are *identical* in both cases. Stages 1–4 did the same work; only stage 5 differs. That is the
  point — this is not an encoding bug, it is a decoding bug, and no amount of checking the ids would find
  it.
- The default decoder does two wrong things at once, and both are visible above. It leaves the `Ġ` symbols
  in place — the unreadable vocabulary of Day 13 part
  [3.4](../../../day-013-bpe-encode-decode-bytes/parts/03-byte-level-bpe/3.4-the-vocabulary-you-cannot-read.md)
  leaking into user-facing text. And it joins tokens **with a space**, so `ost` and `s` become `ost s`.
  Neither is a guess the library should have to make, which is why the default does the literal thing
  rather than an inferred one.
- No exception. The library never asked whether stage 5 inverts stage 2, because it cannot — a decoder is
  an arbitrary object and inverse-checking is undecidable in general.

That is the design consequence to remember: **the five stages are independent, which means they are
independently wrong.**

## Shapes

| Name | Symbolic | Concrete | What the axis means |
| --- | --- | --- | --- |
| `s` | `(n_chars,)` | `(25,)` | input code points |
| after stage 1 | `(n_chars',)` | `(25,)` | may differ from `n_chars` — see part 2.5 |
| after stage 2 | `(n_chunks,)` | `(6,)` | chunks; merges may not cross these walls |
| after stage 3 | `(T,)` | `(12,)` | ids; `T >= n_chunks` always |
| after stage 4 | `(T + n_special,)` | `(12,)` | no post-processor here |
| after stage 5 | `(n_chars,)` | `(25,)` | equals the input **only if** stage 1 was lossless |

`T >= n_chunks` is a genuine invariant and worth asserting in tests: stage 3 can only subdivide.

## When it breaks

**Feeding the pre-tokenizer un-normalized text.** The most common way to get this section wrong, and on
this configuration it is invisible because the normalizer is `None`. Add an `NFKC` normalizer and
`pre_tokenize_str(s)` and `pre_tokenize_str(normalized)` diverge — with no error, because both are valid
calls on valid strings.

**Assigning a pre-tokenizer and forgetting the decoder** produces `'The Ġplan Ġc ost s Ġ 0 Ġd oll ar s .'`,
shown above. Two tells, and they point at different halves of the mistake: `Ġ` in user-visible output means
the byte map was never reversed, and spaces between word fragments mean the tokens were joined rather than
concatenated. If you ever see either in a served response, stage 5 is missing or wrong.

**Assuming `encode` is the inverse of `decode`.** It is the inverse of stages 1–4 composed, and only when
stage 1 is lossless. Day 13 part
[1.2](../../../day-013-bpe-encode-decode-bytes/parts/01-encode-and-decode/1.2-decode-is-a-lookup-not-a-search.md)
established that `encode(decode(y)) != y` in general; this part adds that `decode(encode(s)) != s` is also
reachable, and part 2.5 reaches it.

**Setting the model's `unk_token` on a byte-level tokenizer.** It will never fire — byte-level BPE has no
unknown tokens by construction (Day 13 part
[3.3](../../../day-013-bpe-encode-decode-bytes/parts/03-byte-level-bpe/3.3-zero-out-of-vocabulary.md)) —
but its presence in the file tells the next reader something false about how the tokenizer works.

## In production

**All five stages ship in one file.** That is the single most important practical consequence, and part
[3.1](../03-the-remaining-gap/3.1-the-file-is-the-contract.md) opens the file. Contrast with `gpt2`'s
format from part [1.3](../01-tiktoken/1.3-what-a-vocabulary-file-looks-like.md), which stores stage 3 and
leaves stages 1, 2, 4 and 5 as things you have to know. Most historical tokenizer mismatches are exactly
that: the merge list travelled and the pre-tokenizer did not.

**The stage names are industry-standard**, and knowing them changes how you read a bug report. "The
normalizer is `NFKC` but the model was trained with `NFC`" names a specific, findable, fixable problem.

**The post-processor is where the money is.** Every chat model wraps turns in special tokens, and that
wrapping is stage 4. It is also the stage most often reimplemented by hand in serving code — someone writes
the template as an f-string instead of loading it from the file — and then it drifts from the one used in
training. That is Silent Failure #2's most common real-world form and Day 16 (`TOK-17`) is where you build
the check for it.

**Stages 1 and 2 are the expensive ones.** Normalization and regex splitting dominate tokenization time,
which is why both are implemented in Rust here and why the pattern in part
[1.2](../01-tiktoken/1.2-the-published-pattern-verbatim.md) uses possessive quantifiers.

## Check yourself

```python
from tokenizers import Tokenizer, models, pre_tokenizers, decoders, trainers
from pathlib import Path

text = Path("docs/00_MASTER_PLAN.md").read_text(encoding="utf-8")
tok = Tokenizer(models.BPE())
tok.pre_tokenizer = pre_tokenizers.ByteLevel(add_prefix_space=False, use_regex=True)
tok.decoder = decoders.ByteLevel()
tok.train_from_iterator([text], trainer=trainers.BpeTrainer(
    vocab_size=1000, show_progress=False,
    initial_alphabet=pre_tokenizers.ByteLevel.alphabet()))

s = "The plan costs 0 dollars."
chunks = tok.pre_tokenizer.pre_tokenize_str(s)
out = tok.encode(s)

print(f"stage 2: {len(chunks):2d} chunks")
print(f"stage 3: {len(out.ids):2d} tokens")

# the eval that can go red: the model may subdivide, never join
assert len(out.ids) >= len(chunks), \
    "fewer tokens than chunks - a merge crossed a pre-tokenizer boundary"

# the pre-tokenizer must be lossless (Day 12 part 1.4)
rebuilt = "".join(c for c, _ in chunks)
assert len(rebuilt) == len(s), "pre-tokenizer changed the length"
assert chunks[-1][1][1] == len(s), "chunk offsets do not cover the whole string"

# every stage, named, so you see which are configured
for name in ("normalizer", "pre_tokenizer", "model", "post_processor", "decoder"):
    print(f"{name:15s}: {getattr(tok, name)}")
```

**Line by line:**

- `len(out.ids) >= len(chunks)` is the eval that can go red, and it encodes the invariant from the Shapes
  table. If it ever fails, a merge crossed a chunk boundary and your pre-tokenizer is not doing its job.
- `len(rebuilt) == len(s)` rather than `rebuilt == s`: the byte-level pre-tokenizer replaces spaces with
  `Ġ`, so the strings are deliberately *not* equal while the lengths must be. Asserting equality here is a
  mistake worth making once — it fails, and the failure teaches you what stage 2 actually did.
- The final loop prints all five stages including the two that are `None`. Get in the habit: when a
  tokenizer misbehaves, print this first. Two of the five being `None` is information, not absence.
