# 2.2 — The same vocabulary, trained twice

## One-line answer

Your Python trainer and a Rust one, on the same corpus at the same `V = 1000`, both learn 744 merges and
agree on 91.1% of them — but they diverge at **rank 24**, where two different pairs both occur exactly
**551** times, and neither tie-break is more correct than the other.

---

## The story

Two people count the same box of buttons and sort them into piles by colour, biggest pile first.

They agree on the order right down the list — until they get to two piles that both have 551 buttons in
them. One person puts the blue pile first because they picked it up first. The other puts the green pile
first because green comes earlier in their head.

Neither of them counted wrong. There is no fact about the buttons that settles it. But every pile after
that point is now numbered differently in the two lists, and if you compare the lists position by position
they will look like they disagree about almost everything.

---

## The idea in plain language

Day 12 part
[2.5](../../../day-012-bpe-the-merge-loop/parts/02-training-a-vocabulary/2.5-the-vocabulary-that-depended-on-the-order-of-the-corpus.md)
found that BPE training has a hidden decision in it. The algorithm says *merge the most frequent pair*, and
says nothing about what to do when two pairs are equally frequent. So every implementation invents a
tie-break, and the choice is arbitrary but permanent — it is baked into the merge list forever.

That part demonstrated it by changing the tie-break inside one program. This part is the stronger
experiment: **two programs written independently, in different languages, by different people, on identical
input.** Everything that could differ is held fixed except the implementation.

What you should expect if your Day 13 code is correct:

- **The same number of merges.** Both must learn 744, because `V = 256 + n_merges` is arithmetic.
- **Near-identical compression.** If both apply the algorithm faithfully, they should land within noise.
- **Different orderings.** Wherever counts tie, the lists fork.

All three happen. And the third one is the reason a merge list is not a canonical object: *there is no such
thing as "the" BPE vocabulary for a corpus.* There is only the one your implementation produced.

---

## Why Akshara needs it

**Because this is the strongest correctness evidence you will get for the code you wrote.** Your own tests
check that your code agrees with itself. Day 13's oracle test checked that your fast encoder agreed with
your slow one — better, but both were yours. An independent implementation agreeing to within 0.043% is
evidence of a different kind, and it is the closest thing to proof available here.

**Because it tells you what "reproducible" means for a tokenizer.** Principle 9 says seeds and configs are
committed. A tokenizer has no seed — training is deterministic. But it is deterministic *per
implementation*, which means "trained with `tokenizers==0.23.1`" is part of the config, and swapping the
library is not a refactor. Committing the merge list itself, not the code that generates it, is the only
thing that actually reproduces.

**Because you will be tempted to swap the implementation later** — for speed, after part
[1.1](../01-tiktoken/1.1-the-same-corpus-through-both.md)'s timings. This part is the reason you cannot
just re-train with a faster library and carry on: the new merge list will be *different*, and every
embedding indexed by the old ids becomes meaningless.

---

## The mechanism

### Step 1 — train both, compare the counts

Build the `tokenizers` BPE exactly as part [2.1](2.1-five-stages-not-one.md) did, then set it beside your
Day 13 output.

```python
import json
from pathlib import Path

their_merges = [tuple(m) for m in json.loads(tok.to_str())["model"]["merges"]]
my_merges = [tuple(m) for m in json.loads(
    Path("day13_merges_1000.json").read_text(encoding="utf-8"))["merges"]]

print("theirs:", len(their_merges), " mine:", len(my_merges))
same_rank = sum(1 for a, b in zip(their_merges, my_merges) if a == b)
first_diff = next((i for i, (a, b) in enumerate(zip(their_merges, my_merges)) if a != b), None)
overlap = len(set(their_merges) & set(my_merges))
print(f"identical at the same rank : {same_rank}")
print(f"first divergence at rank   : {first_diff}")
print(f"present in both, any rank  : {overlap} = {overlap / len(my_merges) * 100:.1f}%")
```

**Line by line:**

- `tok.to_str()` serializes the whole tokenizer to the JSON string that part
  [3.1](../03-the-remaining-gap/3.1-the-file-is-the-contract.md) dissects. Going through JSON rather than a
  Python accessor is deliberate: it reads the same bytes that would be written to disk, so what you compare
  is what would actually ship.
- `zip(their_merges, my_merges)` walks both lists in lockstep. This is a *position-by-position* comparison
  and it is the strict one — deliberately stricter than the set comparison in part
  [1.4](../01-tiktoken/1.4-your-merges-against-theirs.md), which asked a different question about two
  different corpora.
- `next((...), None)` finds the first index where they differ, returning `None` if they never do. The
  generator inside `next` stops at the first match rather than building the whole list.

Measured, corpus `9760f2b6d4340b97`, both at `V = 1000`:

```text
theirs: 744  mine: 744
identical at the same rank : 93
first divergence at rank   : 24
present in both, any rank  : 678 = 91.1%
```

91.1% of the pairs are in both lists. Only 93 sit at the same index. Both numbers are true and they measure
different things — the first says "we chose the same merges", the second says "we ordered them the same
way", and after one divergence the second number collapses even though nothing further went wrong.

### Step 2 — look at rank 24

```python
for i in range(22, 30):
    print(f"{i:4d} : {str(their_merges[i]):18s} {my_merges[i]}")
```

**Line by line:**

- `range(22, 30)` is a window **around** the divergence, not starting at it. Printing from rank 24 onward
  would show two lists that look wholly different; showing two ranks of agreement on either side is what
  reveals this is a transposition rather than a fork.
- `str(...)` before `:18s` for the same reason as part 1.4 — a tuple has no string format spec of its own.

```text
rank : theirs             mine
  22 : ('*', '*')         ('*', '*')
  23 : ('i', 'on')        ('i', 'on')
  24 : ('Ġ', 'p')         ('Ġan', 'd')
  25 : ('Ġan', 'd')       ('Ġ', 'p')
  26 : ('i', 's')         ('i', 's')
  27 : ('Ġ', 'w')         ('Ġ', 'w')
  28 : ('e', 'd')         ('e', 'd')
  29 : ('e', 's')         ('e', 's')
```

**They swapped two adjacent entries and then carried on agreeing.** Ranks 26 through 29 are identical
again. This is not a divergence in behaviour; it is a transposition.

### Step 3 — why they swapped

Replay your own trainer to the moment just before merge 24 and print the counts:

```python
words = bpe13.word_counts(text)
for i in range(24):
    words = {bpe13.merge_word(w, my_merges[i]): c for w, c in words.items()}

pairs = bpe13.pair_counts(words)
for pair, count in sorted(pairs.items(), key=lambda kv: -kv[1])[:6]:
    print(f"  {pair}  -> {count}")
```

**Line by line:**

- `bpe13.word_counts(text)` rebuilds the starting state — chunks counted, each as a tuple of byte symbols.
  Day 12 part [1.3](../../../day-012-bpe-the-merge-loop/parts/01-the-merge-loop/1.3-the-loop-and-where-it-stops.md)
  is where this state was defined.
- The loop applies **your** first 24 merges, so the state is exactly what your trainer saw when it chose
  merge 24. Replaying with their list would answer a different question.
- `sorted(..., key=lambda kv: -kv[1])[:6]` puts the most frequent pairs first. The negation sorts
  descending without `reverse=True`, which reads more directly here.

Measured:

```text
  ('Ġ', 'p')    -> 551
  ('Ġan', 'd')  -> 551
  ('i', 's')    -> 545
  ('Ġ', 'w')    -> 522
  ('e', 'd')    -> 518
  ('e', 's')    -> 495
```

**An exact tie at 551.** Both pairs occur 551 times. The algorithm has nothing left to say.

Your Day 13 trainer breaks the tie like this:

```python
best = max(pairs.items(), key=lambda kv: (kv[1], kv[0]))[0]
```

**Line by line:**

- `pairs.items()` rather than `pairs`, so the key function receives `(pair, count)` and can reach both.
- `key=lambda kv: (kv[1], kv[0])` builds a **tuple** key: count first, then the pair itself. Python
  compares tuples element by element, so this reads as "highest count wins; if counts tie, the
  lexicographically larger pair wins". The tie-break is the second element, and it exists only because
  the first can tie.
- `[0]` takes the pair back out of the `(pair, count)` tuple that `max` returned.

The key is `(count, pair)`, so when counts tie it compares the pairs themselves and takes the
lexicographically larger. `('Ġan', 'd')` beats `('Ġ', 'p')` because the string `'Ġan'` sorts after `'Ġ'`.
The Rust trainer resolves it the other way. Neither is wrong; the algorithm does not specify.

Note also that the tie-break you chose is at least *stable* — Day 12 part 2.5's point. Using
`max(pairs, key=pairs.get)` instead would break ties by whichever key `dict` iteration reached first, which
depends on insertion order, which depends on the corpus. That version produces different vocabularies from
the same text presented in a different order.

### Step 4 — does it matter?

```python
print(f"mine   ids={len(bpe13.tokenize(text, my_merges))}")
print(f"theirs ids={len(tok.encode(text).ids)}")
```

**Line by line:**

- Both encode **the whole corpus**, not a probe. The question is whether the ordering difference costs
  anything in aggregate, and a short string could easily show zero difference by luck.
- `len(...)` on both sides: this compares counts, not sequences. The sequences are certainly different —
  that was established two steps ago — and the point here is that the difference does not accumulate.

```text
mine   ids=46311
theirs ids=46291
```

**20 ids out of 46,000 — 0.043%.** A transposition at rank 24 and 651 further reorderings cost four
hundredths of one percent of compression. The ordering is arbitrary *and* it barely matters for the metric
you care about.

Which is the honest conclusion, and it cuts both ways: the tie-break is not worth agonising over, and it is
also not something you can change after the fact, because the ids move even though the compression does not.

## Shapes

| Name | Symbolic | Concrete | Meaning |
| --- | --- | --- | --- |
| `my_merges` | `(744, 2)` | `(744, 2)` | ordered pairs, Python trainer |
| `their_merges` | `(744, 2)` | `(744, 2)` | ordered pairs, Rust trainer |
| positional agreement | scalar | `93 / 744` | same pair at same index |
| set agreement | scalar | `678 / 744` | same pair anywhere |
| `ids` | `(T,)` | `(46311,)` vs `(46291,)` | the metric that barely moved |

## When it breaks

**Comparing merge lists position by position and concluding the code is broken.** After rank 24 the two
lists are offset, so a naive `zip` comparison reports 651 disagreements. It looks catastrophic. The set
comparison says 91.1% agreement and the token count says 0.043%. **When two views of the same data
disagree this violently, the question is which one answers your question** — and "does my implementation
work?" is answered by the token count, not by the index alignment.

**Assuming a tie is rare.** It is not: this corpus produced one within the first 24 merges. Small corpora
tie constantly, because counts are small and collisions are likely. A large corpus ties less often near the
top and constantly in the tail, where counts fall to single digits.

**Changing the tie-break and expecting compatibility.** If you swap `max(pairs.items(), key=lambda kv:
(kv[1], kv[0]))` for anything else, you get a different merge list, therefore different ids, therefore a
model whose embedding table is indexed by numbers that now mean different tokens. There is no error. The
model just gets quietly worse, in the way described in part
[3.3](../03-the-remaining-gap/3.3-the-mismatch-the-library-will-not-catch.md).

**Retraining "the same" tokenizer and expecting the same file.** Same code, same corpus, same version →
same file, because there is no randomness. Different library version → possibly a different file, with no
warning, if the tie-break implementation changed. This is why the merge list is committed and the training
script is not the artifact.

## In production

**The vocabulary is frozen before the model is trained, and never touched again.** Everything in this part
explains why. The merge list is an input to a run that costs real money, and its ids are baked into
`(V, C)` embedding weights. Retraining the tokenizer means retraining the model.

**Which is why the merge list is committed, not regenerated.** Principle 9 in its tokenizer form: commit
the artifact, not the recipe. A build step that regenerates `tokenizer.json` from a corpus is a build step
that can silently produce a different tokenizer when a dependency updates.

**Ties get more common as the vocabulary grows.** At `V = 50000` the last few thousand merges have counts
in the single digits, where ties are the norm rather than the exception. The tail of a large vocabulary is
therefore substantially arbitrary — which is a further reason not to read too much into any individual
low-rank token.

**Independent reimplementation is a real verification technique**, and this part is a small instance of it.
When two implementations of a spec agree on a large input, the spec is probably being followed. When they
disagree, one of three things is true: a bug, an ambiguity in the spec, or a tie. Here it was the third,
and finding that out took reading six numbers.

## Check yourself

```python
import json
from pathlib import Path
from tokenizers import Tokenizer, models, pre_tokenizers, decoders, trainers
import bpe13                                   # your Day 13 module

text = Path("docs/00_MASTER_PLAN.md").read_text(encoding="utf-8")
tok = Tokenizer(models.BPE())
tok.pre_tokenizer = pre_tokenizers.ByteLevel(add_prefix_space=False, use_regex=True)
tok.decoder = decoders.ByteLevel()
tok.train_from_iterator([text], trainer=trainers.BpeTrainer(
    vocab_size=1000, show_progress=False,
    initial_alphabet=pre_tokenizers.ByteLevel.alphabet()))

theirs = [tuple(m) for m in json.loads(tok.to_str())["model"]["merges"]]
mine = [tuple(m) for m in json.loads(
    Path("day13_merges_1000.json").read_text(encoding="utf-8"))["merges"]]

# the eval that can go red: arithmetic, not opinion
assert len(theirs) == len(mine) == 744, "V = 256 + n_merges is broken somewhere"

overlap = len(set(theirs) & set(mine)) / len(mine)
print(f"set agreement: {overlap * 100:.1f}%")
assert overlap > 0.85, "under 85% agreement is a bug, not a tie-break"

n_theirs, n_mine = len(tok.encode(text).ids), len(bpe13.tokenize(text, mine))
gap = abs(n_theirs - n_mine) / n_mine
print(f"compression gap: {gap * 100:.3f}%")
assert gap < 0.01, "over 1% apart means the implementations really do differ"

# now prove the divergence is a tie, not a mistake
d = next(i for i, (a, b) in enumerate(zip(theirs, mine)) if a != b)
words = bpe13.word_counts(text)
for i in range(d):
    words = {bpe13.merge_word(w, mine[i]): c for w, c in words.items()}
counts = bpe13.pair_counts(words)
print(f"rank {d}: theirs {theirs[d]} count={counts[theirs[d]]}, "
      f"mine {mine[d]} count={counts[mine[d]]}")
assert counts[theirs[d]] == counts[mine[d]], \
    "the divergence is NOT a tie - one trainer picked a less frequent pair, which is a real bug"
```

**Line by line:**

- Three thresholds, three different claims. `== 744` is arithmetic and must hold exactly. `> 0.85` and
  `< 0.01` are judgement calls, chosen loose enough not to be flaky and tight enough to catch a real
  difference — and stated as numbers you can argue with rather than hidden in prose.
- The final `assert` is the one that matters, and it is the difference between "I observed a difference"
  and "I explained the difference". It replays your trainer to the divergence point and asserts the two
  candidate pairs have *equal* counts. If they do not, one trainer chose a less frequent pair, and that is
  a genuine bug in somebody's code rather than a tie.
