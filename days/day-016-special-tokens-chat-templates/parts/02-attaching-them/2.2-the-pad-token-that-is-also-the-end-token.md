# 2.2 — The pad token that is also the end token

## One-line answer

A published model read here declares `pad_token_id: 2` and `eos_token_id: 2` — **the same integer** — which
is a deliberate, common and entirely workable choice that becomes a silent disaster the moment any code
downstream stops reading the attention mask.

---

## The story

A hostel canteen puts out a tray of steel tumblers at the start of every meal.

An upside-down tumbler means *nobody is sitting here*. It is also, by the same house rule, what you leave
when you have finished eating and gone. One position, two meanings, and everybody knows which is which
because the person who is actually there is obvious — you can see them.

Then the canteen starts taking a photograph of the hall each evening to count how many people ate.

The photograph shows upside-down tumblers. It does not show whether each one is an empty seat or a finished
meal, because the difference was never in the tumbler. It was in the room.

---

## The idea in plain language

Day 14 part
[2.4](../../../day-014-tiktoken-and-the-pipeline/parts/02-the-tokenizers-pipeline/2.4-padding-truncation-and-the-mask.md)
built the mechanics of padding: a batch has to be a rectangle, short rows are filled to the length of the
longest, and an **attention mask** — a `1` for every real position and a `0` for every filler — is what tells
the model which positions to ignore. That part measured a batch where 59.7% of the positions were fake.

This part is about a decision that sits on top of those mechanics: **which id to use as the filler.**

The obvious answer is a dedicated `<|pad|>` token, which is what section
[01](../01-special-tokens/1.1-four-jobs-four-tokens.md) added. But a great many shipped models do something
else — they reuse the end-of-sequence id as the padding id.

**Why anybody would do that,** and the reasons are good ones:

- It saves a vocabulary slot and an embedding row. Small, but free.
- Padding always sits *after* the content, and content always ends with EOS, so the padded region is a run
  of end markers rather than a run of some other symbol. In a causal model, everything after the first EOS is
  already meaningless, so filling it with more EOS is at least consistent.
- It removes a token that would otherwise appear in training data at a rate of exactly zero, since padding
  is masked out of the loss anyway. A row that never receives a gradient is a row that holds whatever its
  initialization gave it — which is part
  [3.4](../03-the-embedding-matrix/3.4-the-head-that-was-never-grown.md)'s subject.

**Why it is dangerous,** and the danger is precise rather than vague: the two meanings are now
indistinguishable **from the ids alone**. `[.., 2, 2, 2, 2]` might be one sequence that ended and then got
padded, or a sequence that emitted four end markers, or a padded row of a batch where the content itself
ended early. The only thing that can tell them apart is the attention mask — a *separate array*, travelling
alongside, that any refactor can drop.

That is the whole part. Reusing the id is fine. Reusing the id while relying on a second array to
disambiguate it is fine **until the second array is not there**.

---

## Why Akshara needs it

Day 57 writes the loss-masking code, and Silent Failure #3 — *the loss that counted padding* — lives there.
The standard defence is to set the label at every padded position to `-100` so the loss ignores it, and the
standard way to find the padded positions is to compare each id against the pad id.

If the pad id and the eos id are the same integer, that comparison masks out **every EOS in the batch**,
including the real ones at the end of real sequences. The model is then never trained to predict its own
stop token. It trains fine, the loss falls, and the model never learns to stop — which is precisely the
symptom part [1.1](../01-special-tokens/1.1-four-jobs-four-tokens.md) opened with, arrived at by a
completely different route.

The correct source of truth for "is this position padding?" is the attention mask, not an id comparison.
That sentence is the thing this part exists to install.

## The mechanism

Two measurements. First, a batch through the tokenizer built in part
[2.1](2.1-the-post-processor-adds-bos-and-eos.md), with a dedicated pad token, so the two masks can be seen
disagreeing:

```python
# lab/attach_02.py  -  T0, laptop CPU. Continues from lab/attach_01.py.
pad = tok.token_to_id("<|pad|>")
tok.enable_padding(pad_id=pad, pad_token="<|pad|>")

batch = tok.encode_batch(
    ["the merge list", "a", "byte-level BPE over the whole corpus"]
)
for e in batch:
    print("len", len(e.ids), "ids:", e.ids)
    print("     attention   :", e.attention_mask)
    print("     special mask:", e.special_tokens_mask)
```

**Line by line:**

- `enable_padding` takes **both** the id and the token string. They must agree, and the library does not
  check that they do — passing `pad_id=0` with `pad_token="<|pad|>"` gives you a tokenizer that pads with id
  0 and reports the string `<|pad|>` when decoding, which is a lie that survives every round-trip test you
  can write. Resolve both from the same `token_to_id` call, as here.
- No `length=` argument, so the batch pads to the longest member rather than to a fixed width. That is the
  right default for a demonstration and the wrong default for training, where a fixed width keeps tensor
  shapes stable across steps; Day 63 makes that choice deliberately.
- The three probe strings have deliberately unequal lengths, with one very short. The `"a"` row is what makes
  the padded fraction large enough to read at a glance.
- Both masks print for every row, one under the other, because the finding is that they differ. Printing
  either one alone would show nothing.

distinction part [2.1](2.1-the-post-processor-adds-bos-and-eos.md) drew and this is the batch that makes it
concrete.

**`vocab_size` is 49152**, which is 48 × 1024 exactly: a table sized to a round multiple rather than to the
tokenizer's count. Part [3.2](../03-the-embedding-matrix/3.2-growing-the-table.md) works that arithmetic.

## Shapes

`B` is batch, `T` is sequence position, `V` is vocabulary size.

| Tensor | Symbolic shape | Concrete here | What each axis means |
| --- | --- | --- | --- |
| `input_ids` | `(B, T)` | `(3, 16)` | row = one document in the batch; column = position, padded to the longest |
| `attention_mask` | `(B, T)` | `(3, 16)` | `1` = a real position, `0` = filler. **The only truthful source for "is this padding?"** |
| `special_tokens_mask` | `(B, T)` | `(3, 16)` | `1` = a position the post-processor inserted, filler included |
| `labels`, after masking | `(B, T)` | `(3, 16)` | `-100` wherever `attention_mask` is `0`; built on Day 57 |
| a real model's embedding | `(V, C)` | `(49152, 576)` | measured above from the pinned config |

The row that matters is `attention_mask`. It is a separate tensor, and it has to be threaded through every
function between the dataloader and the loss. Every hop is a chance to drop it, and dropping it is
undetectable from `input_ids` alone once pad and eos share an integer.

## When it breaks

**The loud version** is the one you get when the pad id is out of range of the model, and it is the same
error part [1.3](../01-special-tokens/1.3-added-tokens-sit-above-the-vocabulary.md) predicted:

```text
IndexError: list index out of range
```

Welcome, if unhelpful. The pad token was added after the config was written, and the embedding has no row
for it.

**The silent version, and this is the one this part exists for.** Somebody writes the loss mask by comparing
ids, which is the natural thing to write:

```text
labels = [-100 if i == pad_id else i for i in ids]
```

On a tokenizer where pad and eos are different, that is correct. On the published model measured above,
`pad_id == eos_id == 2`, so this line sets the label to `-100` at **every** end marker, including the real
one that terminates every real sequence. The model is never asked to predict its own stop token, not once,
in the entire run.

Nothing errors. The loss falls normally, because the tokens that remain are the ordinary ones and they are
learnable. Evaluation on perplexity looks fine, because perplexity is averaged over the unmasked positions
and those are all fine. The failure shows up only at generation time, as a model that produces good text and
runs to the length cap every time — and by then the run is spent.

**The check that catches it,** and it can go red:

```python
pad_id = 2
eos_id = 2
attention_mask = [1, 1, 1, 0, 0, 0]
ids = [1001, 64, eos_id, pad_id, pad_id, pad_id]

by_id = [i for i, t in enumerate(ids) if t == pad_id]
by_mask = [i for i, m in enumerate(attention_mask) if m == 0]
assert by_id == by_mask, (
    f"padding found at {by_id} by id but at {by_mask} by mask - pad_id and eos_id are the same "
    f"integer ({pad_id}), so an id comparison also masks every real end-of-sequence token"
)
```

**Line by line:**

- The check compares **two ways of finding the same thing** rather than asserting a value. That shape is
  worth stealing: when two independent derivations of one fact are cheap, disagreeing is a far stronger
  signal than either one being "wrong".
- `by_id` and `by_mask` are lists of positions rather than counts. A count comparison would pass when the
  two methods disagree about *which* positions in a way that happens to balance out; positions cannot.
- The message states the cause, not just the discrepancy. `[2, 3, 4, 5] != [3, 4, 5]` is a puzzle at three in
  the morning; "pad_id and eos_id are the same integer" is an instruction.
- Written against literals here so it runs on its own. In the real pipeline the three inputs come from the
  batch, and the assertion belongs in the dataloader's test, not in the training loop.

## In production

**Reusing the id is normal, and it is not the problem.** The measurement above is from a real, working,
widely used model. Do not read this part as "never share the ids". Read it as: the moment they are shared,
the attention mask stops being a convenience and becomes the *only* record of a distinction the ids can no
longer carry.

**The consequence for serving.** A batched inference server pads the requests in a batch to a common length.
If pad and eos share an id and the server truncates each output at the first eos, then a *padded* row
truncates at its first pad — which is right by accident. Change the padding side to the left, which is what
you do for efficient batched generation, and the first pad now comes *before* the content: every response
truncates to the empty string. That failure is instant, total and easy to fix, which makes it the good kind.

**What a research engineer does instead of arguing about it.** Writes the three ids into the run's config,
hashes the config into `docs/RUNS.md` (Principle 9), and adds the two-way check above to the dataloader's
test suite. The decision is then recorded rather than remembered, and Day 63 inherits a fact instead of a
convention.

**The review comment:** *"`labels[ids == pad_id] = -100` — are pad and eos distinct on this tokenizer?"* If
the author has to go and look, the check does not exist yet.

**The interview question:** *"Your model trains cleanly and never emits EOS at inference. Where do you
look?"* Naming this specific interaction — pad id equal to eos id, plus id-based loss masking — is an answer
that comes from having lost a run to it. Follow it with the fix: mask from the attention mask, and assert
the two agree.

## Check yourself

Run this — it prints a padded fraction and two mask disagreement counts, not a pass:

```text
uv run python -c "
from tokenizers import Tokenizer, models, pre_tokenizers, decoders, trainers, processors
import pathlib
t = Tokenizer(models.BPE()); t.pre_tokenizer = pre_tokenizers.ByteLevel(add_prefix_space=False)
t.decoder = decoders.ByteLevel()
t.train_from_iterator([pathlib.Path('docs/00_MASTER_PLAN.md').read_text(encoding='utf-8')],
  trainer=trainers.BpeTrainer(vocab_size=1000, show_progress=False,
                              initial_alphabet=pre_tokenizers.ByteLevel.alphabet()))
t.add_special_tokens(['<|pad|>','<|bos|>','<|eos|>','<|unk|>'])
b, e, p = (t.token_to_id(x) for x in ('<|bos|>','<|eos|>','<|pad|>'))
t.post_processor = processors.TemplateProcessing(single='<|bos|> \$A <|eos|>',
    special_tokens=[('<|bos|>', b), ('<|eos|>', e)])
t.enable_padding(pad_id=p, pad_token='<|pad|>')
batch = t.encode_batch(['the merge list', 'a', 'byte-level BPE over the whole corpus'])
total = sum(len(x.ids) for x in batch)
fake  = sum(m == 0 for x in batch for m in x.attention_mask)
print('positions        :', total)
print('padding positions:', fake, f'({100*fake/total:.1f}%)')
for x in batch:
    d = sum(a != s for a, s in zip(x.attention_mask, x.special_tokens_mask))
    print('  masks disagree at', d, 'of', len(x.ids), 'positions')
"
```

Expected: `48` positions, `21` padding (43.8%), and every one of the three rows disagreeing at **14 of 16**
positions. Three very differently shaped rows, the same disagreement count — worth a moment's thought before
you read on, because the coincidence is not one.
