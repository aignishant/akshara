# 1.1 — Four jobs, four tokens

## One-line answer

A model can only emit ids that are in its vocabulary, so every instruction you need to give it — *start
here*, *stop here*, *this position is empty*, *I have no id for this* — has to become an id too, and those
four jobs are what BOS, EOS, PAD and UNK are.

---

## The story

You are sitting an exam. The booklet has twelve ruled pages. You write four.

Before you hand it in, the invigilator reads out the rules from the front of the room. Write your roll
number at the top of the first page you used. Draw a line under your last answer and write *END* below it.
Cross out every page you did not use, corner to corner, so nobody can add anything later. And if a question
asks about something that was not on your syllabus, write *NOT COVERED* rather than leaving it blank.

None of those four marks are answers. Not one of them earns a mark. They are all instructions to the person
who will read the booklet, written in the same blue ink, on the same ruled lines, as the answers.

That is the whole problem. The reader is going to get a stack of pages covered in blue ink and will have to
work out which marks are the answer and which marks are the instructions about the answer. The rules only
work because everyone in the hall was told the same four marks, and because *END* is a word nobody would
write as part of an answer.

---

## The idea in plain language

Day 9 part
[1.1](../../../day-009-the-vocabulary-problem/parts/01-the-vocabulary-problem/1.1-a-model-can-only-emit-its-vocabulary.md)
established the rule this whole day is built on: **a model can only ever emit an id that is in its
vocabulary.** It has no other channel. There is no side band, no flag, no out-of-text signal. Every single
thing the model can tell you, and every single thing you can tell the model, has to be an id.

So look at the four things you need to say that are not text:

| Job | The usual name | What it means |
| --- | --- | --- |
| This is where a document begins | **BOS** — beginning of sequence | The model has no left context; do not treat what came before as part of this |
| This is where a document ends | **EOS** — end of sequence | Generation stops here; a serving loop watches for exactly this id |
| This position is not real | **PAD** — padding | A filler, so a batch of different-length rows is a rectangle |
| I have no id for this piece of text | **UNK** — unknown | The encoder met something it could not represent |

Each one is a **special token**: an entry in the vocabulary whose job is to carry a *control* meaning rather
than a piece of text.

**Why "special" and not just "a token".** Nothing about the id makes it special. Id 1002 is an integer like
any other. What makes it special is a set of promises the tokenizer keeps about it — it is never split into
smaller pieces, it can be hidden when you turn ids back into text, and it can be attached automatically at
the edges of a sequence. Parts [1.2](1.2-a-special-token-has-to-be-one-token.md),
[1.4](1.4-special-means-decode-drops-it.md) and
[2.1](../02-attaching-them/2.1-the-post-processor-adds-bos-and-eos.md) each take one of those promises
apart.

**Not every model uses all four.** UNK is the one that most often disappears. Day 13 part
[3.3](../../../day-013-bpe-encode-decode-bytes/parts/03-byte-level-bpe/3.3-zero-out-of-vocabulary.md) showed
why: once the alphabet is all 256 byte values, there is no text that cannot be represented, so there is
nothing for UNK to mean. A byte-level tokenizer that still carries an UNK token carries a token it can never
emit. Day 15 part
[1.4](../../../day-015-wordpiece-unigram-sentencepiece/parts/01-wordpiece/1.4-the-word-that-became-one-unk.md)
showed the other side of that: a WordPiece vocabulary that *does* need UNK, and what it costs when it fires.

**And PAD is often not a separate token at all.** Part
[2.2](../02-attaching-them/2.2-the-pad-token-that-is-also-the-end-token.md) measures a published model whose
pad id and eos id are the same integer, which is a deliberate choice with a specific danger attached.

---

## Why Akshara needs it

Akshara has to stop talking.

On Day 69 the curriculum builds a sampling loop: pick an id, append it, feed the sequence back, pick the
next id. That loop needs a halting condition, and there are only two candidates — a length cap, or an id
that means *stop*. A length cap alone gives you a model that always produces exactly 200 tokens, whatever
the question was.

The stop id has to exist in the vocabulary **before** the model is trained, because a model can only learn
to emit ids it has. Adding EOS afterwards means adding a row to a matrix that has never received a gradient,
which is section [03](../03-the-embedding-matrix/3.1-one-row-per-id.md)'s subject and part
[3.4](../03-the-embedding-matrix/3.4-the-head-that-was-never-grown.md)'s failure.

Every one of those four tokens is a decision made **today**, on Day 16, that the pretraining run on Day 67
cannot revisit.

## The mechanism

Start from a byte-level BPE tokenizer trained the way Day 14 trained one — same corpus, same settings — and
ask it what it currently knows.

```python
# lab/specials_01.py  -  T0, laptop CPU. No network: the corpus is this repo's own plan.
import hashlib
import pathlib

from tokenizers import Tokenizer, decoders, models, pre_tokenizers, trainers

CORPUS = pathlib.Path("docs/00_MASTER_PLAN.md")
raw = CORPUS.read_bytes()
print("corpus sha256:", hashlib.sha256(raw).hexdigest()[:16], "bytes:", len(raw))

tok = Tokenizer(models.BPE())
tok.pre_tokenizer = pre_tokenizers.ByteLevel(add_prefix_space=False)
tok.decoder = decoders.ByteLevel()
tok.train_from_iterator(
    [raw.decode("utf-8")],
    trainer=trainers.BpeTrainer(
        vocab_size=1000,
        show_progress=False,
        initial_alphabet=pre_tokenizers.ByteLevel.alphabet(),
    ),
)

print("trained vocabulary size:", tok.get_vocab_size(with_added_tokens=False))
print("is there a token that means 'stop'? ", tok.token_to_id("<|eos|>"))
print("is there a token that means 'empty'?", tok.token_to_id("<|pad|>"))
```

**Line by line:**

- `raw.decode("utf-8")` reads the corpus as text, but the hash is taken on the **bytes**. A hash of the
  decoded string would change if the file's line endings changed on checkout; a hash of the bytes is what
  Day 14 and Day 15 both quoted, so quoting it the same way keeps the three days comparable.
- `models.BPE()` with `pre_tokenizers.ByteLevel` and `decoders.ByteLevel` is the exact configuration Day 14
  part
  [2.1](../../../day-014-tiktoken-and-the-pipeline/parts/02-the-tokenizers-pipeline/2.1-five-stages-not-one.md)
  arrived at. Reusing it means every number today is comparable with every number on Day 14.
- `initial_alphabet=pre_tokenizers.ByteLevel.alphabet()` seeds all 256 byte symbols, which is what makes the
  tokenizer lossless (Day 13 part
  [3.1](../../../day-013-bpe-encode-decode-bytes/parts/03-byte-level-bpe/3.1-the-alphabet-becomes-256.md)).
  Without it, a byte absent from the corpus has no symbol at all.
- `get_vocab_size(with_added_tokens=False)` asks for the size of the **trained** vocabulary only. That
  argument matters enormously, and part [1.3](1.3-added-tokens-sit-above-the-vocabulary.md) is about nothing
  else.
- `token_to_id` returns `None` — not a `KeyError`, not `-1` — for a token the tokenizer has never heard of.
  A `None` that flows onward becomes a `TypeError` several frames away, which is why the *When it breaks*
  section below checks it at the source.

Measured on this machine on 2026-08-29, corpus `docs/00_MASTER_PLAN.md` sha256 `9760f2b6d4340b97`, 113,283
bytes:

```text
corpus sha256: 9760f2b6d4340b97 bytes: 113283
trained vocabulary size: 1000
is there a token that means 'stop'?  None
is there a token that means 'empty'? None
```

A tokenizer that trained perfectly, round-trips every byte, and cannot express a single one of the four
instructions. Nothing is wrong with it. It has simply not been told about the four jobs yet, and the rest of
this section is telling it.

## When it breaks

**The loud version.** Ask for the id of a token that does not exist, then use the answer:

```text
>>> ids = [tok.token_to_id("<|eos|>")]
>>> tok.decode(ids)
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
TypeError: argument 'ids': 'NoneType' object cannot be interpreted as an integer
```

The message means *you handed me a `None` where an id belongs*. Notice that the failure surfaces at
`decode`, not at `token_to_id` — the lookup returned `None` happily, one line earlier, and the `None`
travelled. The fix is to check `token_to_id` at the lookup, not at the crash.

**The silent version, and it is the one that costs a week.** There is no error at all when you simply never
add EOS. Training runs. The loss falls. The model generates fluent text — and it never stops, because there
is no id whose meaning is *stop*, so the sampling loop hits its length cap every single time. You see:

```text
prompt : What is a merge list?
output : An ordered table of byte pairs. An ordered table of byte pairs. An ordered
         table of byte pairs. An ordered table of byte pairs. An ordered table of by
```

Cut off mid-word at the length cap, with the answer repeated. Read as a model-quality problem, that looks
like undertrained, repetitive generation, and it invites a week of hyperparameter changes. It is not a
quality problem. It is a missing row in a table.

**The check that catches it before you train anything** asserts the ids exist, at the moment the tokenizer
is saved, rather than at the moment the model is served:

```python
specials = {"bos": "<|bos|>", "eos": "<|eos|>", "pad": "<|pad|>"}
ids = {name: tok.token_to_id(t) for name, t in specials.items()}
missing = [name for name, i in ids.items() if i is None]
assert not missing, f"tokenizer has no id for {missing} - a model trained on it cannot stop or pad"
print("special ids:", ids)
```

**Line by line:**

- The dictionary comprehension collects every answer before asserting on any of them, so one run tells you
  about all three missing tokens rather than only the first. An assertion that reports one problem per run
  turns one fix into three runs.
- `is None`, and not `not i`: id `0` is a perfectly legitimate id — part
  [4.5](../04-chat-templates/4.5-a-published-template-read-line-by-line.md) measures a real model whose UNK
  token is id 0 — and `not 0` is `True`, so a truthiness test would report a present token as missing.
- The message names the consequence, not just the fact. "Tokenizer has no id for `['eos']`" is a symptom; "a
  model trained on it cannot stop" is the thing that will actually happen to you.

## In production

**Nobody writes the four tokens as string literals in the training script.** They live in the tokenizer's
own saved file, and the model's config file records the *ids*. Part
[4.5](../04-chat-templates/4.5-a-published-template-read-line-by-line.md) reads both files from one
published model and finds the same facts written down twice, in two different formats — which is exactly
where they get their chance to disagree.

**The names are not standard, and that is a real cost.** `<|endoftext|>`, `</s>`, `<|im_end|>`, `[SEP]` and
`<|eot_id|>` have all served as an end marker on shipped models. Nothing enforces a convention, so code that
hardcodes one string works on one model family and silently does nothing on the next: `token_to_id` returns
`None`, the generation loop never matches, and the model runs to its length cap. The rule that survives —
**resolve the id from the tokenizer, never the string from your memory.**

**What degrades at scale.** Four tokens cost four rows in the embedding matrix. Measured in part
[3.2](../03-the-embedding-matrix/3.2-growing-the-table.md), that is 6,144 bytes on a `(1000, 384)` table in
fp32 — 0.400% of it. At production width the fraction is smaller still. Special tokens are the cheapest
thing in the model and the most expensive thing to get wrong, which is an unusual combination and worth
remembering.

**The review comment you will get:** *"Where does EOS come from at inference?"* If the answer is "the
generation config" and "the tokenizer", the reviewer will ask whether those two agree. Part
[5.2](../05-template-mismatch/5.2-the-check-the-round-trip-cannot-make.md) is the check that answers that
question with a number instead of a shrug.

**The interview question:** *"Your fine-tuned model never stops generating. Walk me through it."* The answer
that shows you have done this: check whether EOS is in the vocabulary at all; check whether the training
targets actually contained the EOS id, or whether the template appended it after the labels were built;
check whether the serving loop compares against the same integer. Three checks, all cheap, in that order. An
answer that starts with "lower the temperature" is an answer from someone who has read about the problem
rather than had it.
