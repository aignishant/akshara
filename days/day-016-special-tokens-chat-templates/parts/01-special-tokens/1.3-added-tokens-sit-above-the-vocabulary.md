# 1.3 — Added tokens sit above the vocabulary

## One-line answer

`add_special_tokens` does not change the trained vocabulary — measured here it stays at **1000** — it
appends to a second, separate list, so `get_vocab_size(with_added_tokens=True)` returns **1004** and the
largest id a model must be able to emit is 1003, not 999.

---

## The story

A library has a catalogue with ten thousand numbered slots. Every book has a number, the numbers run from 1
to 10,000, and the shelves are built to hold exactly that many.

Four new books arrive as a donation, after the catalogue was printed. Nobody wants to renumber ten thousand
books, so the librarian writes the four new ones on a card taped to the front of the catalogue: 10,001 to
10,004.

Everything works. Anyone who reads the catalogue *and* the card can find all 10,004 books.

Then a joiner comes to build a new set of shelves, and is handed the catalogue. Ten thousand slots. The card
is on the front cover, and the joiner is looking at the tables inside.

---

## The idea in plain language

When you call `add_special_tokens`, you might reasonably expect the vocabulary to grow. It does not — not
the trained one.

A `tokenizers` `Tokenizer` keeps two things:

| Store | What it holds | How it got there |
| --- | --- | --- |
| the **model** vocabulary | the entries the trainer produced | `train_from_iterator`, from your corpus |
| the **added tokens** list | entries bolted on afterwards | `add_tokens` and `add_special_tokens` |

The ids are drawn from one continuous number line, so there is no clash: a trained vocabulary of 1000 runs
`0 … 999`, and the first added token becomes `1000`. But the two stores are queried separately, and the
function that reports the size takes an argument saying which of them you meant.

```
get_vocab_size(with_added_tokens=False)  ->  1000   the trained vocabulary
get_vocab_size(with_added_tokens=True)   ->  1004   everything the tokenizer can emit
```

**That argument is the whole part.** One of those two numbers is the number of rows your embedding matrix
needs. The other one is a trap, and it is the default-looking one, and it is smaller — so the failure it
causes is an index that is out of range, or worse, a model that cannot emit a token it needs.

**Why the design is like this at all.** It is not carelessness. A tokenizer's trained vocabulary is the
learned artifact — Day 12 part
[2.1](../../../day-012-bpe-the-merge-loop/parts/01-the-merge-loop/1.1-merge-the-commonest-pair.md) called
the merge table the thing that was actually learned. Special tokens are not learned; they are declared. Two
stores keeps the learned thing separable from the declared thing, so you can add a marker to a shipped
tokenizer without touching a single merge. The price is that "how big is the vocabulary?" has two correct
answers.

---

## Why Akshara needs it

On Day 36 Akshara gets an embedding matrix, and its first dimension is a single integer written into a
config. On Day 67 that config drives a pretraining run that cannot be repeated on a free GPU session
without spending the whole budget again.

If that integer is `get_vocab_size(with_added_tokens=False)`, the model has 1000 rows and the tokenizer can
produce id 1003. What happens next depends on the framework and none of the outcomes are good: an index
error at the first document containing a marker, or — the case part
[3.4](../03-the-embedding-matrix/3.4-the-head-that-was-never-grown.md) measures — a model that runs
perfectly and simply cannot ever emit EOS.

The number to write into the config is `max(all ids) + 1`, and the honest way to get it is to ask the
tokenizer with the argument set to `True`.

## The mechanism

```python
# lab/specials_03.py  -  T0, laptop CPU.
import pathlib

from tokenizers import Tokenizer, decoders, models, pre_tokenizers, trainers

text = pathlib.Path("docs/00_MASTER_PLAN.md").read_text(encoding="utf-8")
tok = Tokenizer(models.BPE())
tok.pre_tokenizer = pre_tokenizers.ByteLevel(add_prefix_space=False)
tok.decoder = decoders.ByteLevel()
tok.train_from_iterator(
    [text],
    trainer=trainers.BpeTrainer(
        vocab_size=1000, show_progress=False,
        initial_alphabet=pre_tokenizers.ByteLevel.alphabet(),
    ),
)

print("trained    :", tok.get_vocab_size(with_added_tokens=False))
print("with added :", tok.get_vocab_size(with_added_tokens=True))

tok.add_special_tokens(["<|pad|>", "<|bos|>", "<|eos|>", "<|unk|>"])

print("trained    :", tok.get_vocab_size(with_added_tokens=False))
print("with added :", tok.get_vocab_size(with_added_tokens=True))
for t in ("<|pad|>", "<|bos|>", "<|eos|>", "<|unk|>"):
    print(f"  {t:9s} -> id {tok.token_to_id(t)}")

print("added tokens the tokenizer will report back:")
for i, t in sorted(tok.get_added_tokens_decoder().items()):
    print("   ", i, t)
```

**Line by line:**

- Both sizes are printed **before** anything is added, so the reader can see that the two numbers start
  equal. Printing them only afterwards would leave it ambiguous whether `with_added_tokens=True` had always
  been larger for some other reason.
- The four tokens are added in one call, in a fixed order, because `add_special_tokens` assigns ids in the
  order of the list. A set or a dict with a different iteration order would produce a different id for
  `<|eos|>` on a different run, and an id that moves between runs is Silent Failure #2 with a head start.
- `get_added_tokens_decoder()` returns a mapping from id to the `AddedToken` object, which is the tokenizer
  telling you what it believes about each one — including flags this part does not use and part
  [2.4](../02-attaching-them/2.4-lstrip-and-the-space-that-never-came-back.md) does. It is the honest way to
  ask "what did I actually add?" rather than trusting the list you passed in.
- Sorting by id rather than by insertion means the print order matches the number line, which is how you
  will read it when you are checking a config against a tokenizer at two in the morning.

Measured on this machine, 2026-08-29, corpus sha256 `9760f2b6d4340b97`:

```text
trained    : 1000
with added : 1000
trained    : 1000
with added : 1004
  <|pad|>   -> id 1000
  <|bos|>   -> id 1001
  <|eos|>   -> id 1002
  <|unk|>   -> id 1003
added tokens the tokenizer will report back:
    1000 AddedToken("<|pad|>", rstrip=False, lstrip=False, single_word=False, normalized=False, special=True)
    1001 AddedToken("<|bos|>", rstrip=False, lstrip=False, single_word=False, normalized=False, special=True)
    1002 AddedToken("<|eos|>", rstrip=False, lstrip=False, single_word=False, normalized=False, special=True)
    1003 AddedToken("<|unk|>", rstrip=False, lstrip=False, single_word=False, normalized=False, special=True)
```

The first two lines are equal. The next two differ by exactly four. **`trained` never moved.** That is the
finding: adding a special token is not an edit to the learned artifact, and any code reading the learned
artifact's size will not see it.

## Shapes

The embedding matrix built in section [03](../03-the-embedding-matrix/3.1-one-row-per-id.md) is sized from
one of these numbers, so it is worth writing both down next to it. `V` is the curriculum-wide symbol for
vocabulary size and `C` for the channel width (`d_model`).

| Tensor | Symbolic shape | Concrete here | What each axis means |
| --- | --- | --- | --- |
| embedding sized from the trained vocabulary | `(V, C)` | `(1000, 384)` | row = one id the **trainer** produced; column = one of `C` learned features |
| embedding sized from every emittable id | `(V, C)` | `(1004, 384)` | row = one id the **tokenizer** can produce, added tokens included |
| the four rows the difference buys | `(4, C)` | `(4, 384)` | one row each for `<\|pad\|>`, `<\|bos\|>`, `<\|eos\|>`, `<\|unk\|>` |

`C = 384` is a width chosen here so the arithmetic in part
[3.2](../03-the-embedding-matrix/3.2-growing-the-table.md) has concrete numbers to work with; nothing in
this part depends on its value. The axis that matters today is the first one, and the two candidate values
for it differ by four.

## When it breaks

**The loud version,** and you should hope for this one:

```text
Traceback (most recent call last):
  File "train.py", line 88, in forward
    x = self.wte[idx]
IndexError: list index out of range
```

Measured directly in part [3.4](../03-the-embedding-matrix/3.4-the-head-that-was-never-grown.md): a table
built with 1000 rows, asked for row 1000, raises exactly that. The message names neither the tokenizer nor
the config, so the temptation is to clamp the index — which is the wrong fix and creates the silent version
below.

**The silent version.** Python's negative indexing does not raise:

```text
>>> E[-1] is E[999]
True
>>> E[-4] is E[996]
True
```

So a sentinel of `-1` for "unknown token", or an id that arrived as a negative number from some upstream
subtraction, quietly reads the **last row of the table** and returns a perfectly well-formed vector. No
exception, no warning, and a model that has silently confused two tokens for the whole run.

**The check that catches both,** run at config-build time rather than at forward-pass time:

```python
tokenizer_max = tok.get_vocab_size(with_added_tokens=True)
config_vocab_size = 1000  # pretend this came out of configs/akshara-tiny.json
assert config_vocab_size >= tokenizer_max, (
    f"config says {config_vocab_size} rows but the tokenizer can emit id "
    f"{tokenizer_max - 1}; the model cannot represent every token it will be fed"
)
```

**Line by line:**

- `>=` rather than `==` on purpose. Part [3.2](../03-the-embedding-matrix/3.2-growing-the-table.md)'s
  production section describes deliberately sizing the table *larger* than the vocabulary, so an equality
  assertion would fail on a correct configuration. The property that actually matters is that no emittable
  id is out of range.
- `tokenizer_max - 1` in the message, not `tokenizer_max`, because the largest **id** is one less than the
  count. Off-by-one errors in an error message about off-by-one errors are a special kind of cruel.
- The assertion runs against the config value, not against a hardcoded number, so it keeps working when the
  config changes. A test that has to be edited whenever the thing it guards changes is not a guard.

## In production

**Published models do not all put their special tokens at the top.** The tokenizer configuration read in
part [4.5](../04-chat-templates/4.5-a-published-template-read-line-by-line.md) has its 17 special tokens at
ids **0 to 16** — at the *bottom* of the number line, with the trained vocabulary above them. Both
conventions ship. So "the special tokens are the last few ids" is a habit, not a fact, and code that assumes
it will be wrong on the next model it meets.

**The number written into the config is usually neither.** That same model's config declares
`vocab_size: 49152`. Note that 49152 is 48 × 1024 — a number chosen to be a round multiple, not a number
that fell out of a trainer. Part [3.2](../03-the-embedding-matrix/3.2-growing-the-table.md) works the
arithmetic on why a table is deliberately sized larger than the vocabulary it serves.

**The review comment:** *"Which `get_vocab_size` is this?"* If the code calls it with no argument, the
reviewer cannot tell from the call site what the author meant, and neither can the author six months later.
Pass the keyword explicitly, always, even when it matches the default. This is one of the few places where
spelling out a default earns its characters.

**The interview question:** *"You added four special tokens to a tokenizer and the model started throwing
index errors. What happened?"* The answer that lands: the trained vocabulary did not change, so anything
sized from it is now too small by exactly the number of tokens added; and the fix is to resize the embedding
and the output head together, not to clamp the index. If the interviewer follows up with *"and if it had not
thrown?"*, the answer is part
[3.4](../03-the-embedding-matrix/3.4-the-head-that-was-never-grown.md) — the model simply could never emit
them.
