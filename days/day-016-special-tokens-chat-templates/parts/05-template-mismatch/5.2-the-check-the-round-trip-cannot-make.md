# 5.2 — The check the round-trip cannot make

## One-line answer

The round-trip passes on every template because it only ever sees one string, so the check that actually
catches template drift is a **fingerprint**: render a fixed probe set through the template and hash the
output — measured here, `72176cff` for the training template against `1b43eeb0` for the one-newline variant
and `d87aff27` for the trailing-space one.

---

## The story

Two shops sell the same brand of rice from the same supplier.

Each shop weighs its own bags carefully and each shop's scale is accurate — every bag really is one
kilogram by that shop's scale. Both shops can prove it, and both proofs are honest.

Then somebody buys from each and puts the two bags on the same scale.

That was never a test either shop could have run on its own. Consistency with yourself is not the same
property as agreement with somebody else, and no amount of care in one shop produces the second property.

---

## The idea in plain language

Part [5.1](5.1-one-character-three-tokens-a-different-model.md) ended on an uncomfortable measurement: the
round-trip check that plan §6 prescribes for Silent Failure #2 **passes on all three templates**. That is
not a defect in the round-trip. It is a statement about what the round-trip asks.

| Check | The question it asks | Needs |
| --- | --- | --- |
| round-trip | does this tokenizer preserve *this* string? | one string, one tokenizer |
| `assert_same_tokenizer` (Day 14) | do these two tokenizers agree on these probes? | two tokenizers |
| **template fingerprint** | do these two *renderers* produce the same strings? | two renderers, or one renderer and a recorded value |

The first two are about the tokenizer. Template drift happens *upstream* of the tokenizer, on a byte-identical
tokenizer, so neither can see it. You need a check whose subject is the renderer.

**The check is a fingerprint.** Pick a fixed set of probe conversations, render every one of them through
the template, hash the concatenated output, and record the hash. Then:

- the training script records the fingerprint of the template it used, in the run's config;
- the serving path computes the fingerprint of the template it loaded, at startup;
- if they differ, the service refuses to start.

That is it. It is twelve lines and it converts an invisible failure into a startup error.

**Why a hash rather than a string comparison.** You will not always have both templates in the same process
— the training run happened last month on a machine you no longer have. A hash is a small value that
survives in a config file, a run ledger and a commit message, which is exactly the property Principle 9 asks
for: *a run without a config hash did not happen.*

**Why the probe set is the hard part.** A fingerprint is only as good as what it renders. Part
[4.5](../04-chat-templates/4.5-a-published-template-read-line-by-line.md) measured a template with a clause
that fires only when the first message is not a system message. A probe set of one well-formed conversation
would render identically through a template with that clause and one without it, and the fingerprints would
match on two templates that behave differently. **The probe set must contain the input shapes that turn each
clause on.**

## The mechanism

```python
# lab/mismatch_02.py  -  T0, laptop CPU. Requires jinja2==3.1.6.
import hashlib

import jinja2

#: Probe conversations chosen to exercise every clause a template might carry:
#: with and without a generation prompt, with and without a system message,
#: empty content, and a conversation ending on the assistant's turn.
PROBES: list[tuple[list[dict[str, str]], bool]] = [
    ([{"role": "user", "content": "hi"}], False),
    ([{"role": "user", "content": "hi"}], True),
    ([{"role": "system", "content": "s"}, {"role": "user", "content": "hi"}], True),
    ([{"role": "system", "content": "s"}, {"role": "user", "content": "hi"},
      {"role": "assistant", "content": "a"}], False),
    ([{"role": "user", "content": ""}], True),
    ([{"role": "user", "content": "a"}, {"role": "assistant", "content": "b"},
      {"role": "user", "content": "c"}], True),
]

env = jinja2.Environment(undefined=jinja2.StrictUndefined)


def fingerprint(template: str) -> str:
    """sha256 of every probe rendered through `template`, NUL-separated."""
    jt = env.from_string(template)
    h = hashlib.sha256()
    for messages, add_generation_prompt in PROBES:
        h.update(jt.render(messages=messages,
                           add_generation_prompt=add_generation_prompt).encode("utf-8"))
        h.update(b"\x00")
    return h.hexdigest()


for name, tmpl in (("A (training)", A), ("B (one newline moved)", B),
                   ("C (space, not newline)", C), ("published", published)):
    print(f"{name:24s} {fingerprint(tmpl)[:16]}")

print()
print("A == A :", fingerprint(A) == fingerprint(A))
print("A == B :", fingerprint(A) == fingerprint(B))
print("A == C :", fingerprint(A) == fingerprint(C))
print("probes :", len(PROBES))
```

**Line by line:**

- `PROBES` is a list of `(messages, add_generation_prompt)` pairs, and the flag is part of the probe rather
  than a separate loop. Both settings are part of the template's behaviour, and a fingerprint that covered
  only one of them would miss part [4.3](../04-chat-templates/4.3-the-generation-prompt.md)'s entire failure
  surface.
- The six probes are chosen against the clauses templates actually carry: **no system message** (fires part
  [4.5](../04-chat-templates/4.5-a-published-template-read-line-by-line.md)'s injection clause), **with a
  system message** (does not), **empty content** (catches a template that emits something for nothing), and
  **ending on an assistant turn** (the shape part [4.3](../04-chat-templates/4.3-the-generation-prompt.md)'s
  production section warned about). Each probe exists because a real template branches on it.
- `h.update(b"\x00")` writes a NUL byte between probes. Without a separator, hashing `["ab", "c"]` and
  `["a", "bc"]` gives the same digest — a real class of bug called length-extension confusion, and the fix
  is one byte that cannot appear in the rendered text.
- `.encode("utf-8")` is explicit. `hashlib` requires bytes, and letting the encoding be implicit is how the
  same template fingerprints differently on two machines, which would make the check worse than useless.
- `fingerprint(A) == fingerprint(A)` is checked first, and it is not a joke. It asserts that the function is
  **deterministic** — that nothing in the rendering path depends on dict ordering, a clock, or a random seed.
  A fingerprint that is not reproducible is a startup failure waiting to happen on a quiet Sunday.
- `[:16]` truncates for display only. The stored value is the full digest; sixteen hex characters is 64 bits,
  which is plenty for reading in a log and not what you would pin a config to.

Measured on this machine, 2026-08-29, `jinja2` 3.1.6:

```text
A (training)             72176cff468ded09
B (one newline moved)    1b43eeb027dd3f9b
C (space, not newline)   d87aff271ff8f676
published                32b8a5100eac2b9c

A == A : True
A == B : False
A == C : False
probes : 6
```

Four templates, four different fingerprints. **B and C are the two failures part
[5.1](5.1-one-character-three-tokens-a-different-model.md) measured**, and the one the round-trip could not
see — C, whose id sequence is the same length as A's and differs in one position — has a fingerprint as
plainly different as anything else. A hash does not care whether a difference is subtle.

Now the check as it would actually ship:

```python
TEMPLATE_FINGERPRINT = "72176cff468ded09"  # recorded in configs/ when the training set was built


def assert_template_matches(template: str, expected: str) -> None:
    """Refuse to serve a model with a template it was not trained on."""
    actual = fingerprint(template)[: len(expected)]
    if actual != expected:
        raise SystemExit(
            f"chat template mismatch: this template fingerprints {actual}, "
            f"the model was trained with {expected}. Serving it would feed the model a "
            f"format it has never seen. Load the template from the tokenizer, or retrain."
        )


assert_template_matches(A, TEMPLATE_FINGERPRINT)   # passes
assert_template_matches(B, TEMPLATE_FINGERPRINT)   # SystemExit
```

**Line by line:**

- `raise SystemExit` rather than `assert`. Assertions are stripped by `python -O`, and this is a check whose
  entire value is that it runs in production. An assertion that can be optimised out is a comment.
- `fingerprint(template)[: len(expected)]` truncates the computed digest to the length of the recorded one,
  so a config storing a short prefix and one storing the full digest both work. The comparison length is
  taken from the **stored** value, which means shortening it is a deliberate act by whoever wrote the config
  rather than an accident of this function.
- The message names three things: what was found, what was expected, and what to do. A startup failure at
  three in the morning is read by somebody who does not know this document exists.
- The two calls at the bottom are the test, and the second one is expected to raise. A check nobody has
  watched fail is a check nobody knows works.

## When it breaks

**The loud version is the whole point.** This is the one document in the day whose success condition is an
exception:

```text
SystemExit: chat template mismatch: this template fingerprints 1b43eeb027dd3f9b, the model
was trained with 72176cff468ded09. Serving it would feed the model a format it has never
seen. Load the template from the tokenizer, or retrain.
```

**The silent version — how this check itself fails.** Three ways, and all three are the probe set:

1. **Too few probes.** One well-formed conversation renders identically through a template with part
   [4.5](../04-chat-templates/4.5-a-published-template-read-line-by-line.md)'s injection clause and one
   without it, as long as that conversation starts with a system message. Identical fingerprints, different
   templates. The check reports green on a real mismatch.
2. **Probes that avoid the boundaries.** No empty content, no single-message conversation, no conversation
   ending on the assistant — and the clauses that branch on those shapes are unfingerprinted.
3. **The probe set changes.** Somebody adds a seventh probe, every fingerprint in every config becomes
   invalid at once, and the pressure is to update the recorded values rather than to investigate. The probe
   set has to be as versioned as the template, and the honest way to do that is to hash the probes into the
   fingerprint too.

**The check that catches the check,** and it can go red:

```python
probe_digest = hashlib.sha256(repr(PROBES).encode("utf-8")).hexdigest()[:8]
print("probe set:", probe_digest, f"({len(PROBES)} probes)")
assert probe_digest == "PIN_THIS", (
    f"the probe set changed to {probe_digest}; every recorded template fingerprint is now "
    "meaningless. Re-derive them deliberately, do not paste the new values in."
)

rendered = {fingerprint(t) for t in (A, B, C, published)}
assert len(rendered) == 4, (
    f"{4 - len(rendered)} template pair(s) share a fingerprint - the probe set does not "
    "distinguish templates that behave differently"
)
```

**Line by line:**

- `repr(PROBES)` is hashed rather than the list itself, because a list is unhashable and `repr` is stable for
  the plain nested lists and dicts used here. It would **not** be stable across Python versions for arbitrary
  objects, which is why the probes are deliberately restricted to strings, dicts and booleans.
- `"PIN_THIS"` is left as a placeholder on purpose — `TODO(me)`. Running the print gives you the value, and
  pasting it in is the reader's job, because a pinned value you did not derive yourself is a pinned value you
  will not question.
- The second assertion checks that the probe set **distinguishes** the four known-different templates. It is
  the direct test of failure mode 1: if two behaviourally different templates collide, the probe set is too
  weak, and this says so with a count instead of a hunch.
- Using a `set` for the collision test is the whole trick — four templates should give four digests, and
  `len` says how many collided without needing a pairwise loop.

## In production

**Where the fingerprint is recorded.** In the run's config, hashed into `docs/RUNS.md` alongside the seed
and the hardware (Principle 9). It travels with the run, not with the code, because the question it answers
is *"what did this run train on?"* and the code moves on.

**Where it is checked.** At service startup, before the first request, and in CI on every change to the
template or the probe set. Not per request — it is a fixed value, and computing a hash of six renders on
every inference call is real latency for no additional information.

**What a research engineer does that this document has not shown.** Extends the same idea past the template.
The pipeline from a conversation to a training batch has more stages than rendering — tokenization, the
post-processor from part [2.1](../02-attaching-them/2.1-the-post-processor-adds-bos-and-eos.md), truncation,
label masking — and each one can drift. The mature version fingerprints the **ids**, not the string, over the
same probe set, which pins the tokenizer and the template together in one value. That is the check this
day's whole content builds toward, and it is left as a `TODO(me)` in the hub's §4 rather than solved here.

**The failure this does not catch.** A template that is *correct* and a model that was trained badly. A
fingerprint proves that two paths agree; it says nothing about whether what they agree on is any good. It
is a consistency check, and consistency checks are exactly as valuable as their reputation for being green.

**Which of the five silent failures this closes.** Number 2 — tokenizer/template mismatch — for the template
half. The tokenizer half is Day 14 part
[3.3](../../../day-014-tiktoken-and-the-pipeline/parts/03-the-remaining-gap/3.3-the-mismatch-the-library-will-not-catch.md)'s
`assert_same_tokenizer`, and the two together are what §6 means by "round-trip the exact training string
through the inference path". This part is what that instruction turns into when you write it down properly:
not one round-trip, but a fingerprint over a probe set that covers the branches.

**The review comment:** *"What is the recorded template fingerprint for this checkpoint?"* If there is not
one, the answer to "what format was this trained on?" is somebody's memory.

**The interview question:** *"How would you prevent a chat template mismatch?"* The structural answer is one
template loaded from the tokenizer everywhere. The answer that shows you have shipped something adds the
verification: a fingerprint over a probe set, recorded at training time and checked at startup — and then
names the probe set as the hard part, because that is where this check quietly stops working.
