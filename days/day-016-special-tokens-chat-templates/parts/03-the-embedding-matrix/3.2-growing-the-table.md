# 3.2 — Growing the table, and what goes in the new rows

## One-line answer

Adding four special tokens costs **6,144 bytes on a `(1000, 384)` fp32 table — 0.400% of it** — and the hard
part is not the resize but what goes in the new rows: measured here, the popular "average of every existing
row" trick produces a vector of norm **0.0132** where a typical row has norm **0.3917**, which is 3.4% of
one, so it is very nearly a row of zeros wearing a clever name.

---

## The story

A school hall has 240 chairs set out in rows for a prize-giving. Four more guests arrive.

Adding four chairs is easy — they are stacked at the back, somebody carries four out and puts them at the
end of the last row. Two minutes.

The awkward part is nothing to do with the chairs. It is that the seating list, the printed programme and
the photographer's plan all say 240, and each of those is held by a different person, and the person with
the programme has gone to get tea.

---

## The idea in plain language

**Resizing an embedding matrix** means changing `V` — the first dimension of the `(V, C)` table part
[3.1](3.1-one-row-per-id.md) built — while keeping every existing row exactly where it was.

The "keeping every existing row exactly where it was" clause is the whole safety property. Row 471 must
still be row 471 afterwards, because the model has spent its entire training run learning that row 471 means
`end`. A resize that reorders is not a resize; it is a different model with the same weights.

So the operation is simple: append. And because ids are assigned above the trained vocabulary (part
[1.3](../01-special-tokens/1.3-added-tokens-sit-above-the-vocabulary.md)), appending is exactly right — the
new ids are the new rows, in order.

**What goes in the new rows is the interesting question,** and there are three candidate answers:

| Choice | Argument for it | What it actually does |
| --- | --- | --- |
| zeros | neutral; adds nothing | the vector has no direction; every new token embeds identically |
| a fresh random draw | matches how the table was initialised | a row statistically like the others |
| the mean of all existing rows | "start it where the average token is" | measured below, and it is not what people think |

The third one has a real intuition behind it: put the new token somewhere sensible so it starts closer to
useful than random noise. On a **trained** table that intuition can hold, because the rows of a trained
table are not centred on zero and their mean points somewhere.

On a table that has just been initialised from a zero-centred distribution, the mean of `V` rows is the mean
of `V` independent zero-mean samples, which is close to zero — closer, the more rows you have. The
measurement below puts a number on "close". It is a good example of a technique whose correctness depends
entirely on a precondition nobody states.

---

## Why Akshara needs it

Day 88 fine-tunes Akshara for chat, and a chat template needs turn markers that the pretrained tokenizer
does not have. That is the canonical resize: a model trained on plain text, given new control tokens, then
trained further.

At that point the new rows are the only part of the model with no history. Every other row has been shaped
by 67 days of gradient. If the new rows start as zeros, then part
[3.4](3.4-the-head-that-was-never-grown.md)'s failure is waiting, and if they start too large they dominate
the first steps of the fine-tune. The choice made here is one of a small number of decisions on Day 88 that
cannot be undone by training longer.

---

## The mechanism

Two measurements. First the cost, which is arithmetic; then the initialisation, which is not.

```python
# lab/embed_02.py  -  T0, laptop CPU. Plain Python.
V, C = 1000, 384
before = V * C * 4                 # fp32: 4 bytes per number
after = (V + 4) * C * 4
print(f"before: {before:,} bytes ({before / 2**20:.3f} MiB)")
print(f"after : {after:,} bytes ({after / 2**20:.3f} MiB)")
print(f"delta : {after - before:,} bytes = {(after - before) / 1024:.1f} KiB "
      f"= {100 * (after - before) / before:.3f}% of the table")
```

**Line by line:**

- `* 4` is fp32 — four bytes per number. It is written as a literal with a comment rather than a named
  constant because the whole point is that the reader can see where the factor enters; a `BYTES_PER_PARAM`
  name would hide the one assumption in the calculation.
- `2**20` rather than `1e6`: a MiB is 1,048,576 bytes, and mixing MiB with MB is how two people comparing
  memory figures end up 4.9% apart and blaming each other's hardware.
- The percentage is printed to three decimal places because it is going to be small, and a percentage
  rounded to `0.4%` and one rounded to `0%` are different arguments.

Measured on this machine, 2026-08-29:

```text
before: 1,536,000 bytes (1.465 MiB)
after : 1,542,144 bytes (1.471 MiB)
delta : 6,144 bytes = 6.0 KiB = 0.400% of the table
```

Now the initialisation, which is where the surprise is.

```python
import math
import random

V, C = 1000, 384
rng = random.Random(1337)
E = [[rng.gauss(0.0, 0.02) for _ in range(C)] for _ in range(V)]     # (V, C)


def l2(v: list[float]) -> float:
    """Euclidean length of a vector."""
    return math.sqrt(sum(x * x for x in v))


norms = [l2(r) for r in E]
mean_norm = sum(norms) / len(norms)
mean_row = [sum(E[i][j] for i in range(V)) / V for j in range(C)]     # (C,)
fresh = [rng.gauss(0.0, 0.02) for _ in range(C)]                      # (C,)

print(f"seed 1337, init N(0, 0.02), V={V}, C={C}")
print(f"  mean row-norm of the table  : {mean_norm:.4f}")
print(f"  norm of the MEAN row        : {l2(mean_row):.4f}")
print(f"  norm of a ZERO row          : {l2([0.0] * C):.4f}")
print(f"  norm of a fresh N(0, 0.02)  : {l2(fresh):.4f}")
print(f"  ratio mean-row / typical row: {l2(mean_row) / mean_norm:.4f}")
```

**Line by line:**

- `l2` is the Euclidean length — the square root of the sum of squares. It is defined here rather than
  imported because the comparison in this part is *entirely* about lengths, and a reader who is not certain
  what is being compared cannot read the result.
- `mean_row` averages **down each column**: `sum(E[i][j] for i in range(V)) / V` fixes the column `j` and
  runs over rows `i`. Averaging the other way round would produce `V` numbers, one per token, which is a
  different and meaningless object.
- `fresh` is drawn from the *same* generator after the table, so it uses the same distribution and a
  different draw. Comparing against a re-seeded draw would risk comparing against a row already in the
  table.
- Four norms are printed, not two. The zero row and the fresh row are the reference points that turn "0.0132"
  from a number into a verdict.

Measured on this machine, 2026-08-29, seed 1337:

```text
seed 1337, init N(0, 0.02), V=1000, C=384
  mean row-norm of the table  : 0.3917
  norm of the MEAN row        : 0.0132
  norm of a ZERO row          : 0.0000
  norm of a fresh N(0, 0.02)  : 0.3803
  ratio mean-row / typical row: 0.0336
```

A typical row has length 0.3917. A fresh draw has length 0.3803 — near enough the same, as it should be. And
the mean row has length **0.0132**, which is 3.4% of a typical row. On the scale of this table, the "average
of all rows" is almost the origin.

**Say precisely what this does and does not show.** The table here is freshly initialised from a zero-mean
distribution, so its column means are `V`-sample estimates of zero and shrink roughly like `1/√V`. That is
the whole mechanism. On a **trained** embedding table the rows are not zero-mean, the mean row genuinely
points somewhere, and mean-initialisation is a different and more defensible proposal. This part has not
measured that case, because Akshara has no trained embedding table until Day 67, and quoting a number for it
would be exactly the rumour Principle 8 forbids. What is established here is narrower and still useful:
**mean-initialisation is only meaningfully different from zero-initialisation if the table it averages is
already trained**, and the check for that takes four lines.

---

## Shapes

| Tensor | Symbolic shape | Concrete here | What each axis means |
| --- | --- | --- | --- |
| `E`, before the resize | `(V, C)` | `(1000, 384)` | row = a trained-vocabulary id; column = a learned feature |
| `E`, after the resize | `(V + 4, C)` | `(1004, 384)` | the same rows 0–999, plus four appended |
| `mean_row` | `(C,)` | `(384,)` | one number per feature: the column-wise average over all `V` rows |
| a new row | `(C,)` | `(384,)` | whatever the initialisation put there |
| `norms` | `(V,)` | `(1000,)` | one number per row: that row's Euclidean length |

`mean_row` and `norms` are the two summaries, and they run along **different axes** of the same table —
`mean_row` collapses the row axis and keeps the feature axis; `norms` collapses the feature axis and keeps
the row axis. Getting them the wrong way round produces an array of the wrong length, which is the good
case, or an array of the right length on a square table, which is not.

## When it breaks

**The loud version.** Resize the embedding and not the config:

```text
IndexError: list index out of range
```

Measured in part [3.1](3.1-one-row-per-id.md). The table has 1,004 rows, some other component believes 1,000,
and whichever one is asked for row 1,000 first is where it surfaces.

**The silent version.** Initialise the new rows with zeros, and then look at what the model does with two of
them:

```text
>>> new_bos = [0.0] * C
>>> new_eos = [0.0] * C
>>> new_bos == new_eos
True
```

Every zero-initialised token has the **identical** embedding, so before any training the model cannot
distinguish BOS from EOS from PAD — they are the same vector. Nothing errors; the forward pass runs; the
loss is finite. The tokens become distinguishable only once gradients separate them, which requires that
they appear in the training data, which for PAD they deliberately never do. A PAD row initialised to zeros
stays exactly zero forever, and that is fine — right up until somebody feeds a padded sequence without an
attention mask, at which point the model is attending to a vector it has no information about.

**The check that catches it,** and it can go red:

```python
new_rows = E[V:]
assert len(new_rows) == 4, f"expected 4 new rows, found {len(new_rows)}"
assert all(l2(r) > 0 for r in new_rows), "a new row is all zeros - it has no direction to learn from"
assert len({tuple(r) for r in new_rows}) == len(new_rows), (
    "two new rows are identical - the tokens are indistinguishable before training"
)
lo, hi = 0.5 * mean_norm, 1.5 * mean_norm
for i, r in enumerate(new_rows):
    n = l2(r)
    assert lo < n < hi, (
        f"new row {V + i} has norm {n:.4f}; existing rows average {mean_norm:.4f}. "
        "A row far off that scale either dominates or is ignored in the first steps."
    )
print(f"{len(new_rows)} new rows, norms in [{lo:.4f}, {hi:.4f}]")
```

**Line by line:**

- `E[V:]` slices the appended rows using the **old** `V`, which is why the old value has to still be in scope.
  A resize function that overwrites `V` before the check has thrown away the only handle on which rows are
  new.
- The identical-rows check uses a set of **tuples**, because lists are unhashable. It is the assertion that
  catches zero-initialisation directly, and it catches it as *"these tokens are the same"* rather than as
  *"this number is zero"*, which is the failure in the terms that matter.
- The band is `0.5×` to `1.5×` the existing mean norm. Those factors are a judgement, not a measurement, and
  the message says what the band is *for* — a row far off scale is either dominant or invisible in the early
  steps. A tolerance with a stated purpose can be argued with; a bare `0.5` cannot.
- The mean-row initialisation measured above would **fail** this check, at norm 0.0132 against a band
  starting at 0.1959. That is the check working, not the check being wrong.

## In production

**What a research engineer writes instead.** Not this loop. Model libraries ship a resize helper —
`transformers` has one named `resize_token_embeddings` — and a one-line call replaces the whole of *The
mechanism* above.

**This part will not tell you what that call does**, and the reason is Principle 7 rather than coyness.
`transformers` is not pinned in this repository — `docs/PACKAGES.md` has no row for it, and Day 16 does not
add one — so any statement here about which tensors it updates, how it initialises the new rows, or what it
does about tied weights would be recalled rather than verified. The lookup, on the day you pin it, is:

```text
uv run python -c "
import inspect, transformers
print(transformers.__version__)
print(inspect.getsource(transformers.PreTrainedModel.resize_token_embeddings))
"
```

Read the source, for the version you actually pinned, and write down the three answers: which tensors it
touches, what goes in the new rows, and whether the output head comes along. Part
[3.3](3.3-the-second-matrix.md) is about why that third answer is the one that bites.

That is also the argument for hand-rolling the append first (Principle 3). A one-line call that does three
things is a convenience once you know which three; before that it is a mystery with a good name.

**Sizing the table larger than the vocabulary, on purpose.** The pinned model config read in part
[2.2](../02-attaching-them/2.2-the-pad-token-that-is-also-the-end-token.md) declares `vocab_size: 49152`.
That number is 48 × 1024 exactly — a round multiple rather than a count that fell out of a trainer. Sizing a
vocabulary dimension to a multiple of a power of two is a common production practice, and the arithmetic of
what it costs is worth doing here even though this day has no GPU to measure the benefit on:

| `V` | `C` | Parameters | fp32 | bf16 |
| --- | --- | --- | --- | --- |
| 49,152 | 576 | 28,311,552 | 108.00 MiB | 54.00 MiB |
| 49,157 (five more tokens) | 576 | 28,314,432 | 108.01 MiB | 54.01 MiB |

Five extra rows cost 2,880 parameters, or 5.6 KiB in bf16 — 0.010% of the table. **Whether padding the
vocabulary to a round multiple also makes the matmul faster is a claim this day cannot test**, because it
needs a GPU and a benchmark; it is T2 🅿️ here. The command that would measure it, on the day a GPU is
available, is a timed forward pass at both widths with a fixed seed and a fixed batch — `TODO(measure: time
100 forward passes at V=49152 and V=49157, same seed, same batch, report the spread over 3 runs)`. Until
that number exists, the honest statement is the memory one, and the memory cost is negligible.

**The failure that only shows with real data.** Resize, fine-tune on a small dataset, and the new rows are
updated only when their tokens appear. Turn markers appear in every example, so they train. A rarely used
marker — a tool-call token that occurs in 2% of examples — barely moves, and the model's behaviour around it
is close to whatever the initialisation was. That is not fixed by training longer at the same data mix; it
is fixed by the data mix.

**The review comment:** *"How are the new embeddings initialised, and did you check their norm against the
existing rows?"* The second half is what turns a preference into a measurement, and it is one line.

**The interview question:** *"You add tokens to a pretrained model. How do you initialise the new
embeddings?"* An answer that says "the mean of the existing embeddings" and stops is repeating a recipe. An
answer that says "the mean, **because on a trained table the rows are not zero-centred** — and I check the
new row's norm against the existing mean, because on a freshly initialised table the mean is essentially
zero" is an answer with the precondition attached. That precondition is the whole content of this part.
