# 3.3 — The second matrix, and weight tying

## One-line answer

`V` appears **twice** in a language model — once as the rows of the input embedding and once as the columns
of the output head that produces one logit per vocabulary entry — so resizing a vocabulary is two edits, not
one, unless the two matrices are *tied* to be the same numbers, which the pinned model config read here
declares with `tie_word_embeddings: True` and which halves 108.00 MiB to 54.00 MiB at `(49152, 576)`.

---

## The story

A cloakroom at a wedding hall has 300 numbered hooks and a book of 300 numbered paper tickets.

You hand over a coat, you get ticket 148, the coat goes on hook 148. Later you hand back ticket 148 and the
coat comes off hook 148. Two objects — hooks and tickets — and the system only works because they are
numbered identically.

Somebody adds 20 hooks for a busy weekend. If nobody prints 20 more tickets, the last 20 hooks can hold
coats that can never be claimed. The hooks are not broken. There is simply no way to ask for them.

---

## The idea in plain language

Day 5 part
[1.1](../../../day-005-logits-softmax-sampling/parts/01-logits-and-probabilities/1.1-a-distribution-over-a-vocabulary.md)
established what a language model's output is: one number per vocabulary entry, called a **logit**, turned
into a probability distribution by softmax. `V` numbers out, for a vocabulary of `V`.

Part [3.1](3.1-one-row-per-id.md) established what its input is: a lookup into a `(V, C)` table.

So `V` is in the model twice, at opposite ends:

| Matrix | Shape | What it does | Indexed by |
| --- | --- | --- | --- |
| the input embedding `E` | `(V, C)` | id → vector | a row per **id you feed in** |
| the output head `W_out` | `(C, V)` | vector → one logit per id | a column per **id it can emit** |

Between them sits the model. Everything Days 29 to 50 build lives in the `C`-dimensional space in the
middle, and neither end of it cares how big `V` is — which is exactly why a `V` change is easy to make
incompletely.

**Weight tying** is the observation that these two matrices are transposes of the same thing. Both map
between "a vocabulary entry" and "a point in `C`-dimensional space", one in each direction. So you can use
one array for both: `W_out = Eᵀ`. The logit for token `v` becomes the dot product of the hidden state with
row `v` of the embedding — literally "how much does this hidden state look like the vector for token `v`?",
which is a satisfying thing for a logit to be.

Two consequences follow, and both are why this matters today:

1. **Tying halves the vocabulary-dependent parameters.** One `(V, C)` array instead of two.
2. **Tying makes resizing atomic.** There is one array, so growing it grows both ends, and the failure part
   [3.4](3.4-the-head-that-was-never-grown.md) measures becomes impossible by construction.

Untied models exist and are a legitimate choice — the two directions are not obliged to use the same
representation. But untied means two resizes, and two of anything is where one gets forgotten.

## Why Akshara needs it

Day 39 assembles Akshara, and one of its config fields will be whether the output head is tied. Day 78 opens
the efficiency curriculum, where the memory equation decides how large a model can be trained on one free
GPU session — and at small model sizes the vocabulary matrices are a startling fraction of the total, so
tying is not a micro-optimisation there, it is the difference between fitting and not.

## The mechanism

The tying arithmetic first, because it is the argument for the design:

```python
# lab/embed_03.py  -  T0, laptop CPU. Plain Python arithmetic.
rows = [
    ("this day's toy tokenizer", 1004, 384),
    ("the pinned model config", 49152, 576),
    ("o200k_base vocabulary", 200019, 768),
]
for label, V, C in rows:
    tied = V * C
    untied = 2 * V * C
    print(f"{label}: V={V:,} C={C}")
    print(f"    tied  : {tied:>12,} params  {tied * 4 / 2**20:8.2f} MiB fp32"
          f"  {tied * 2 / 2**20:8.2f} MiB bf16")
    print(f"    untied: {untied:>12,} params  {untied * 4 / 2**20:8.2f} MiB fp32"
          f"  {untied * 2 / 2**20:8.2f} MiB bf16")
```

**Line by line:**

- The three `(V, C)` pairs are not invented. `1004` is measured in part
  [1.3](../01-special-tokens/1.3-added-tokens-sit-above-the-vocabulary.md); `49152` and `576` are read from
  the model config pinned in part
  [2.2](../02-attaching-them/2.2-the-pad-token-that-is-also-the-end-token.md); `200019` is what
  `tiktoken.get_encoding("o200k_base").n_vocab` printed at version 0.14.0 on 2026-08-29. The `384` and `768`
  widths are chosen for the arithmetic and are claims about nothing.
- `2 * V * C` for untied assumes the head is exactly the transpose shape. It is: `(C, V)` has the same
  element count as `(V, C)`. Any bias vector on the head adds `V` more, which is under 0.2% at these sizes
  and is left out rather than smuggled in.
- Both fp32 and bf16 are printed, because the pinned config declares `torch_dtype: bfloat16` and quoting
  only fp32 would double every number relative to how that model actually ships.
- `:>12,` right-aligns with thousands separators. Parameter counts are read by comparing digit positions,
  and unaligned numbers make a reader count zeros.

Measured on this machine, 2026-08-29:

```text

o200k_base vocabulary: V=200,019 C=768
    tied  :  153,614,592 params    585.99 MiB fp32    293.00 MiB bf16
    untied:  307,229,184 params   1171.99 MiB fp32    585.99 MiB bf16
```

And the config that decides it, from the file pinned at revision
`12fd25f77366fa6b3b4b768ec3050bf629380bac`:

```text
config  vocab_size             = 49152
config  hidden_size            = 576
config  tie_word_embeddings    = True
config  num_hidden_layers      = 30
config  torch_dtype            = bfloat16
```

`tie_word_embeddings: True`. That model carries 28,311,552 vocabulary parameters rather than 56,623,104 —
54.00 MiB in bf16 rather than 108.00 MiB. The model's own name puts it at roughly 135 million parameters
total, so the vocabulary side, tied, is on the order of a fifth of the whole model, and untying it would
have added another fifth.

Now the mechanism itself, hand-rolled, so the tie is visible as a fact about references rather than as a
config flag:

```python
import random

V, C = 1004, 384
rng = random.Random(1337)
E = [[rng.gauss(0.0, 0.02) for _ in range(C)] for _ in range(V)]      # (V, C)

h = [rng.gauss(0.0, 1.0) for _ in range(C)]                           # (C,) one hidden state


def logits_tied(h: list[float], E: list[list[float]]) -> list[float]:
    """One logit per vocabulary entry, using the embedding table as the head."""
    return [sum(h[c] * E[v][c] for c in range(C)) for v in range(len(E))]   # (V,)


lo = logits_tied(h, E)
print("hidden state :", len(h))
print("logits       :", len(lo))
print("argmax id    :", max(range(len(lo)), key=lo.__getitem__))
E.append([rng.gauss(0.0, 0.02) for _ in range(C)])                    # (V+1, C)
print("after appending one row, logits:", len(logits_tied(h, E)))
```

**Line by line:**

- `logits_tied` takes `E` — the **embedding table** — as the output head. That single fact is what tying
  means, and writing it as a parameter rather than a global makes it something the reader can see rather
  than infer.
- The inner sum is a dot product of the hidden state with row `v`. Read it as the sentence it is: the logit
  for token `v` is how much `h` points along the direction that token `v` embeds to.
- `range(len(E))` rather than `range(V)`. That is what makes the last two lines work: append a row and the
  output width follows automatically, with nothing else edited. On an untied model those two numbers come
  from two places and one of them stays behind.
- The append is the point of the whole listing. One `list.append` and the model can both consume and emit
  the new id. Part [3.4](3.4-the-head-that-was-never-grown.md) is what the same append looks like when there
  are two arrays.

Measured on this machine, 2026-08-29, seed 1337:

```text
hidden state : 384
logits       : 1004
argmax id    : 681
after appending one row, logits: 1005
```

## Shapes

| Tensor | Symbolic shape | Concrete here | What each axis means |
| --- | --- | --- | --- |
| `E`, input embedding | `(V, C)` | `(1004, 384)` | row = vocabulary id; column = learned feature |
| `h`, one hidden state | `(C,)` | `(384,)` | the model's output at one position, before the head |
| `W_out`, untied head | `(C, V)` | `(384, 1004)` | column = vocabulary id; row = learned feature |
| `logits` | `(V,)` | `(1004,)` | one score per vocabulary id — Day 5's distribution, before softmax |
| `h` for a whole batch | `(B, T, C)` | `(3, 16, 384)` | the shape the head is actually applied to, from Day 39 |
| `logits` for a whole batch | `(B, T, V)` | `(3, 16, 1004)` | **the largest tensor in a training step** |

That last row deserves a stare. `(B, T, V)` at production scale is enormous — batch times sequence times
vocabulary — and it is why Day 78's memory equation treats the logits tensor as a first-class term rather
than an afterthought. At `B=3, T=16, V=1004` it is 48,192 numbers; at `B=8, T=1024, V=49152` it is
402,653,184, which in fp32 is 1.50 GiB for a single forward pass.

Note also that `E` is `(V, C)` and the untied head is `(C, V)`. They hold the same number of elements in
the opposite arrangement, which is precisely why tying is possible and precisely why a transposition bug
here is silent — both shapes are "valid".

## When it breaks

**The loud version.** Untied, only the embedding resized, and something asks the head for the new column:

```text
>>> W_out = [[0.0] * 1000 for _ in range(C)]   # (C, V_old) - never grew
>>> sum(h[c] * W_out[c][1002] for c in range(C))
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
IndexError: list index out of range
```

That is the exact message, measured on this machine on 2026-08-29 in the hand-rolled version. It is the same
`IndexError` part [3.1](3.1-one-row-per-id.md) got from the embedding side, arriving from the other end, and
it is just as unhelpful about *which* array was too small.

**A tensor library reports this differently**, as a shape mismatch naming both operands rather than an index
error, and the message is far more useful. This day cannot quote that message: `torch` is not pinned in this
repository — `docs/PACKAGES.md` has no row for it — so its exact wording would be recalled rather than
observed, which Principle 8 forbids. On the day Akshara pins it, the command that produces the real text is:

```text
uv run python -c "
import torch
h = torch.randn(48, 384); W = torch.randn(384, 1000)
print(torch.__version__); h @ W.new_zeros(383, 1000)
"
```

Write the message it prints into your notes then. Until it exists, the honest statement is that the loud
failure is loud in both worlds and names a size in neither.

**The silent version** is the one part [3.4](3.4-the-head-that-was-never-grown.md) measures in full, and it
is the reason that part exists: when the head is not resized but the *ids never reach it*, there is no shape
error at all. The head produces 1,000 logits, softmax normalises them to sum to 1.0, sampling works, and the
four new tokens are simply unreachable. Every operation is valid. The model is missing four words and cannot
tell you.

**A third failure, specific to tying.** Tie two matrices by *copying* rather than by *reference* and you get
a model that is tied at initialisation and untied thereafter:

```text
>>> W_out = [row[:] for row in E]     # a copy, not a reference
>>> E[0][0] = 99.0
>>> W_out[0][0]
0.019...
```

The gradients then update `E` and `W_out` independently, the two drift apart over training, and the model
still works — it is simply an untied model that the config claims is tied. Nothing errors, the parameter
count reported at startup is wrong by `V × C`, and the checkpoint is a different architecture from the one
in the config.

**The check that catches it,** and it can go red:

```python
V_now = len(E)
assert len(logits_tied(h, E)) == V_now, "the head does not produce one logit per row of E"
assert E is not None and W_out_is_E, "tying claimed but the head is a separate array"
tokenizer_max = 1004
assert V_now >= tokenizer_max, (
    f"model has {V_now} rows, tokenizer can emit id {tokenizer_max - 1}"
)
print(f"V={V_now}, logits={len(logits_tied(h, E))}, tokenizer max id={tokenizer_max - 1}")
```

**Line by line:**

- The first assertion checks the property rather than the plumbing: whatever the head is, it must produce
  exactly one number per vocabulary row. That holds for tied and untied models alike, which is what makes it
  the right assertion to write once.
- `W_out_is_E` stands for the identity test — in a real framework, `model.lm_head.weight is
  model.embed_tokens.weight`. Identity, not equality: two arrays that are equal today and separate objects
  will diverge by the first optimizer step, which is the third failure above.
- The `tokenizer_max` comparison repeats part
  [1.3](../01-special-tokens/1.3-added-tokens-sit-above-the-vocabulary.md)'s assertion deliberately. It is
  the same check from the other side — there, "does the model have enough rows?"; here, "does the head have
  enough columns?" — and on an untied model those are genuinely two questions.

## In production

**When untying is the right call.** The two directions really do have different jobs: the input side wants
tokens that appear in similar contexts to be nearby, and the output side wants tokens that are *confusable*
to be separable. Those objectives are related but not identical, and a model with parameters to spare can
afford to learn both. Untying is a considered choice at scale and a false economy at small scale, where the
vocabulary matrices dominate.

**The number that decides it.** Vocabulary parameters as a fraction of the whole model. At the pinned
config's `(49152, 576)` with 30 layers, the tied vocabulary side is 28.3 M parameters against a model of
roughly 135 M — around a fifth. Untying would put the vocabulary at about a third of a larger model. On a
7-billion-parameter model the same `(V, C)` is a rounding error and untying costs nothing anyone notices.
**Model size decides this, not taste**, and the arithmetic is two multiplications.

**What a research engineer checks on a checkpoint they did not make.** Whether the two tensors are the same
object, by identity, and whether that matches what the config claims. A config saying `tie_word_embeddings:
True` over a checkpoint holding two distinct arrays is a checkpoint whose parameter count and whose
behaviour both disagree with its own description — and it loads without complaint.

**The review comment:** *"You resized the embedding — did the head come with it?"* On a tied model the
answer is "by construction". On an untied model the answer needs a line of code to point at.

**The interview question:** *"What is weight tying and why would you use it?"* The answer that shows
understanding gives the *reason* the tie is sensible — both matrices map between vocabulary and the same
`C`-dimensional space, so a logit becomes a similarity between the hidden state and a token's embedding —
before it gives the parameter saving. Anyone can recite "it saves memory". The follow-up is usually "when
would you not?", and the answer is a size argument with numbers in it.
