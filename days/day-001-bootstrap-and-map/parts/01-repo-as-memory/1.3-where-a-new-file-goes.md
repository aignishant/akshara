# 1.3 — Where a new file goes, and who decides when the rules disagree

## One-line answer

Most files have an obvious home; the ones that do not are the ones that damage a layout, so the
useful artifact is not a folder diagram but a short **decision procedure** — plus an agreement about
what to do when the procedure genuinely has no answer.

---

## The story

A project has a clean layout with clear rules. It holds for months.

Then something arrives that does not fit. It is a piece of code that reads the configuration, checks
a few things about the data, and prints a report. It is not the model. It is not really tooling —
it knows about the model's internals. It is not a test, because it does not assert anything. It is
not a notebook, because it runs in the pipeline.

Somebody has to put it somewhere, and there is no correct answer. So it goes wherever seems least
bad, and — this is the part that matters — **no note is left saying it was a close call.** Later,
somebody sees it there and reasonably concludes that is where such things go. The next one joins it.
Within a year there is a category of file living in a place nobody would have chosen, established by
a decision that was never made.

The layout did not fail because the rules were wrong. It failed at the one point where the rules
were *silent*, and it failed quietly, because a hard case handled without comment is indistinguishable
from an easy case.

---

## The idea in plain language

Any set of rules covers most cases and leaves a residue. What separates a layout that survives from
one that erodes is not the rules; it is what happens at the edges.

Three things make the difference.

**A procedure, not a diagram.** A diagram shows where things are. A procedure tells you where a *new*
thing goes, which is the question people actually have. It is a short ordered list of questions, and
the order matters — the first question that gives an answer wins.

**The residue is named.** Some files genuinely do not fit, and pretending otherwise is how `utils/`
gets born. A layout that admits a residue can handle it deliberately; one that claims total coverage
handles it by accident.

**Close calls leave a trace.** The failure in the story is not the placement — it is the silence. A
one-line comment at the top of the file (*"this could equally have gone in `scripts/`; it lives here
because it imports the model"*) costs nothing and stops a coincidence hardening into a convention.

That third point generalises well beyond directories, and it is the transferable idea here: **the
cost of an arbitrary decision is not the decision, it is that later readers cannot tell it was
arbitrary.** They assume intent, and build on it.

---

## Why Akshara needs it

This project produces an unusually large amount of residue, because it holds several kinds of thing
that most repositories do not hold together.

Real cases that arrive on scheduled days:

- **Day 62** writes a corpus deduplication routine. It is one-shot data preparation. Not model code —
  the model never imports it. Not repo tooling — it knows about tokenizers. Not a test. It genuinely
  sits between `akshara/` and `scripts/`.
- **Day 67** writes a training launcher: reads a config, sets seeds, calls into `akshara/train/`,
  writes a `RUNS.md` row. It imports the model, which by the rule from
  [1.2](1.2-the-layout-as-argument.md) means it cannot be in `scripts/`.
- **Day 116** builds an LLM judge. It is evaluation, so `akshara/eval/` — but it also calls an
  external model, which makes it non-deterministic and therefore something `tests/` must never import.

None of these is a crisis. All three are exactly the shape of the file in the story, and each will be
placed by somebody at the end of a long day. The procedure below is what makes those three placements
consistent rather than three separate improvisations.

---

## The mechanism

The procedure. Ask these in order and stop at the first that answers:

```text
1. Is it typed by the learner from a day document, and imported by other code?
   → akshara/<stage>/          (tokenizer · model · train · infer · eval · serve)

2. Does it assert something and run offline on CPU?
   → tests/

3. Does it operate on the repository itself — markdown, ledgers, structure —
   and NOT import akshara?
   → scripts/

4. Is it a run's parameters rather than its logic?
   → configs/

5. Is it exploratory, and is the logic already committed elsewhere?
   → notebooks/

6. Is it teaching — prose a reader reads?
   → days/  (or docs/ if it is a decision, a ledger, or the plan)

7. None of the above?
   → STOP. It is residue. See below — do not improvise.
```

**Line by line:**
- The order is not arbitrary: it runs from **most constrained to least**. `akshara/` has the
  strictest membership test, so it is asked first; `notebooks/` is the most permissive, so it is
  asked late. Ordering loosest-first would put everything in the first permissive bucket that
  accepted it — which is how `utils/` wins.
- Question 3 encodes the dependency arrow from [1.2](1.2-the-layout-as-argument.md) as a *membership
  test*, which is what makes it enforceable by `grep` rather than by judgement.
- Question 5's second clause is doing the real work. "Is it exploratory" alone would let a notebook
  become the only home for logic — the failure part
  [4.3](../04-free-compute/4.3-notebook-module-discipline.md) is about. The clause makes the refusal
  from [1.2](1.2-the-layout-as-argument.md) operational.
- Question 7 is the point of the whole list. Most procedures pretend to be total; this one names its
  residue, which is what stops the residue being handled silently.

For the residue, the rule is: **place it, then say that you placed it.**

```python
"""Corpus deduplication (Day 62).

Placement note: this is a close call. It imports `akshara.tokenizer`, so by the
`scripts/` refusal (Day 1, part 1.2) it cannot live there. It is one-shot data
preparation rather than library code, so `akshara/train/` is imperfect too.
Chosen: `akshara/train/data/`, because everything that reads the corpus lives there
and the import direction stays clean.

If a third file like this appears, that is the signal to add a directory rather than
keep stretching this one.
"""
```

**Line by line:**
- The note lives **in the file**, not in a wiki. It is read by the next person to open it, which is
  the only place a placement note is ever read.
- It names the rule that was applied and the rule that was strained. A future reader can tell this
  was a judgement rather than an obvious fit — which is precisely the information the story's project
  lost.
- The last sentence is the important one: **a threshold for revisiting.** "If a third file like this
  appears, add a directory." Without a threshold, the exception is permanent by default; with one,
  the layout is allowed to learn.

---

## When it breaks

There is no error message for a misplaced file, which is exactly why this is a `production` part.

The nearest thing to a loud failure is the dependency arrow being violated:

```console
$ grep -rn "^from akshara\|^import akshara" scripts/
scripts/prepare_corpus.py:8:from akshara.tokenizer import BPETokenizer
```

One line, and it tells you a placement decision went wrong: something in `scripts/` needed the model.
The fix is to move the file, not to relax the rule.

**The silent version is the normal one.** A file goes somewhere plausible. Nothing breaks. Nothing
warns. Six months later there are four files of the same kind in three directories, and the layout
now requires a paragraph of explanation instead of a procedure.

The detection is a periodic read rather than a check, and it is worth actually doing:

```bash
find akshara scripts tests -name '*.py' -newer pyproject.toml \
  | head -20
```

**Line by line:**
- `-newer pyproject.toml` selects files added since the layout was last deliberately changed — a
  rough proxy for "everything placed since anyone last thought about placement".
- Read the list and ask of each: *would the procedure have put it here?* Any disagreement is either a
  file to move or a procedure to amend, and deciding which is the whole exercise.
- **This is not automatable**, and pretending otherwise would be the mistake part
  [5.2](../../../day-000-toolchain-skeleton-driver/parts/05-the-depth-check/5.2-what-depth-check-cannot-catch.md)
  warns about on Day 0: rules that need judgement get a reviewer, not a regex.

---

## In production

**What a research engineer does instead of the teaching version.** They let the layout change. A
directory structure fixed on day one and defended for three years is a structure that fits nothing
by the end. The procedure has a threshold — *"if a third file like this appears, add a directory"* —
and reaching it is a **success**, not a failure: it means the project learned something about its own
shape. What kills layouts is not restructuring, it is restructuring without recording why, which is
what ADRs are for (part [1.1](1.1-the-repo-is-the-memory.md)).

**What degrades at scale.** The procedure gets longer, and a procedure nobody can hold in their head
is one nobody consults. Past six or seven questions, the fix is not more questions but **fewer, more
orthogonal** directories. If deciding between two folders requires a subtle argument, the two folders
are probably one folder — and the difficulty of the decision is evidence about the layout, not about
the file.

**The failure that only shows with real data.** Placement pressure spikes at exactly the wrong
moments. Day 67 produces a launcher at the end of a metered GPU session; Day 116 produces a judge in
the middle of an evaluation push. Nobody consults a procedure at those moments. What actually saves
you is that the procedure is **short enough to remember** and that its first question is unambiguous —
which is why "is it imported by other code?" comes first, since that one is answerable without
thinking.

**The review comment.** *"Why here rather than `scripts/`?"* If the file has a placement note, this is
answered before it is asked. If the answer is "it seemed fine", the reviewer has found a decision
that was never made — and that is worth a comment even when the placement turns out to be right.

**The interview question.** *"A new file doesn't fit any of your existing directories. What do you
do?"* The weak answer creates `utils/`. The strong answer places it deliberately, leaves a note
saying it was a close call and which rule was strained, and sets a threshold for when the layout
should change instead — because the real risk is not the file, it is the precedent it silently sets.

**Compute tier: T0.** Laptop CPU. Nothing here runs; the cost is thinking, and the payoff is a layout
that still means something on Day 161.

## Check yourself

Run this. It prints the **number** of Python files currently placed, and how many carry a placement
note — the second is small today and should grow only when placements are genuinely hard:

```bash
find akshara scripts tests -name '*.py' 2>/dev/null | wc -l
grep -rln "Placement note" akshara scripts tests 2>/dev/null | wc -l
```

**Line by line:**
- The first is the size of the layout so far. On Day 1 it is mostly empty `__init__.py` files, and
  that is the baseline.
- The second counts files that admitted a close call. **A zero here is fine and a large number is
  also fine** — what would be worrying is a project with many files, none of which was ever a close
  call, because that means the notes are not being written rather than that every placement was
  obvious.
- Re-run both on Day 67 and Day 116, the two days the procedure is predicted to strain.

**Say this out loud, without scrolling up:** why is the placement procedure ordered from most
constrained to least — and what specific information is lost when a close call is placed without a
note?
