# 2.1 — The token that lives in exactly one place

## One-line answer

A credential should exist in exactly one file, that file must be ignored by git **before** it is
created, and every piece of code that needs the credential reads it from the environment — because a
secret's danger is proportional to the number of copies of it, and copies are made by accident.

---

## The story

Somebody needs a credential to get something working. They paste it into the file they are editing,
because that is the fastest way to find out whether the rest of the code is correct. It works. They
mean to move it somewhere proper afterwards.

Afterwards does not arrive in the way they expected. The code gets tidied, the function gets moved
into a module, the module gets committed. The credential travels with it, because it is now just a
string in a line of code and nothing about it looks different from any other string.

Months later the repository is shared — made public, or handed to a contractor, or simply cloned onto
a laptop that later gets sold. The credential is in it, and it has been in every clone since the day
it was pasted.

The part worth sitting with: **at no point did anybody make a mistake they would recognise as one.**
Pasting a credential to test something is reasonable. Tidying code is good. Committing work is
correct. The failure is that the credential was allowed to become an ordinary string, and ordinary
strings travel.

---

## The idea in plain language

Three terms first, because they are used loosely everywhere and the differences matter.

A **credential** is anything that proves you are allowed to do something — an API token, a password,
a signing key. It is not data. It is *authority*, which is why a copy of it is as good as the
original.

An **environment variable** is a name-value pair a process is given when it starts. It lives in
memory for that process. Nothing about it is inherently secure; what it is, is **outside the source
code**, which is the property you want.

A **`.env` file** is a plain text file of `NAME=value` lines that a program loads into environment
variables at startup. It is a convenience so you do not have to set variables by hand every time.

The rule these three combine into:

> The credential lives in `.env`. `.env` is ignored by git. Code reads
> `os.environ["HF_TOKEN"]` and never contains the value.

The reason this works is not that environment variables are secure — they are readable by any process
running as you. It is **separation**: the secret and the code have different lifecycles. Code is
copied, forked, shared, published, and pasted into issues. The secret stays on the machine.

Two consequences people miss.

**The order of operations is the whole thing.** `.gitignore` must contain `.env` *before* `.env`
exists. If the file is created first and ignored second, there is a window — usually one commit long
— where it is trackable, and part
[3.1](../../../day-000-toolchain-skeleton-driver/parts/03-gitignore-first/3.1-ignore-before-it-exists.md)
of Day 0 showed that ignore rules do not apply to files git already tracks.

**A committed secret is compromised, not retrievable.** Once it is in history it is in every clone
(Day 0, part
[3.2](../../../day-000-toolchain-skeleton-driver/parts/03-gitignore-first/3.2-the-checkpoint-that-cannot-be-removed.md)),
and rewriting history does not un-copy it. The response is never "remove it" — it is **rotate it**:
invalidate the old credential so the copies are worthless.

## Why Akshara needs it

One credential arrives today, and its scope is a real decision rather than a formality.

The **Hugging Face token** is needed to download gated datasets and models, and later to push your
own. Tokens come with a permission level, and the plan's Principle 13 — *blast radius before
capability* — applies directly: **create a read-only token today.** A read token cannot delete your
repositories. A write token can, and today nothing needs to write.

Where it gets used:

- **Day 61–62** download and filter a pretraining corpus, with licence and revision SHA recorded in
  `docs/DATASETS.md` before the download.
- **Day 105** pulls an embedding model for retrieval; **Day 122** pulls CLIP weights.
- **Day 67** runs in a free notebook — a machine that is **not yours**, rebuilt from nothing, shared
  infrastructure. The token has to get there somehow, and that is the interesting case, handled in
  part [2.3](2.3-the-token-that-leaked.md).

The other reason this is Day 1: on Day 149 the repository is expected to be publishable. A repository
whose history has never contained a secret can be published. One whose history contains a secret
cannot be published safely no matter how it looks today — and that property is decided now, by the
order in which two files are created.

## The mechanism

The order matters more than the content. `.gitignore` first, **then** the file.

```bash
# 1 — the rule, before the file it protects
printf '\n# Secrets (OPS-02) — the rule exists before the file does\n.env\n.env.*\n!.env.example\n*.key\n*.pem\n' >> .gitignore
git check-ignore -v .env; echo "ignored? exit=$?"
```

**Line by line:**
- The patterns are appended to the `.gitignore` written on Day 0, which already covers artifacts.
  Today adds the **secret** half — two different reasons to exclude a file, as part 3.1 explained.
- `.env.*` catches `.env.local`, `.env.production` and the variants people invent.
- `!.env.example` un-ignores the template. The `!` prefix reverses a previous match, and **order
  matters**: it must come after the pattern it is excepting. This file is committed on purpose — it
  is how somebody else learns which variables exist without learning their values.
- `git check-ignore -v .env` asks git to name the rule that matches, **before the file exists**. Exit
  `0` and a printed rule means the guard is live. This is the Day 0 habit: prove the rule rather than
  assume it.

Now the template — committed — and the real file, which is not:

```bash
cat > .env.example <<'EOF'
# Copy to .env and fill in. .env is gitignored and never committed.
# Everything here is FREE-TIER ONLY (plan §4). No key may bill you.

# Hugging Face — gated datasets and models.
# Create a READ token: https://huggingface.co/settings/tokens
# Read cannot delete your repos. Use write only on the day you actually push.
HF_TOKEN=

# Where large artifacts live — outside the repo tree (Principle 9).
AKSHARA_DATA_DIR=./data
AKSHARA_CHECKPOINT_DIR=./checkpoints
EOF

cp .env.example .env
# now edit .env and paste your token into HF_TOKEN=
```

**Line by line:**
- `.env.example` carries **names and instructions, never values**. It is the answer to "what does
  this project need?" for anyone who clones it, and it is why the `!.env.example` exception exists.
- The comment naming the *read* token is doing security work: the default when creating a token is
  often broader than needed, and a note at the point of creation is worth more than a policy
  document.
- `cp .env.example .env` then editing means the real file starts from the documented shape, so a
  variable added to the template does not get silently missed.
- The two `AKSHARA_*_DIR` variables are not secrets. They are here because they belong to the same
  category — *machine-specific configuration that must not be hard-coded* — and because pointing
  artifacts outside the tree is the strongest form of Day 0's Principle 9 guard.

Verify, and note that "no output" is not proof:

```bash
git status --short | grep -c '\.env$'
git ls-files | grep -c '^\.env$'
```

**Line by line:**
- The first counts `.env` appearing as an untracked file. It must be `0` — meaning git does not even
  see it.
- The second counts `.env` among **tracked** files. It must be `0`, and this is the one that matters:
  `git ls-files` is unaffected by `.gitignore`, so it is the ground truth about what is in the
  repository.
- `grep -c` prints a number rather than nothing, which is the point — a check whose success is
  silence is a check you cannot distinguish from a check that did not run.

## When it breaks

The loud failure, when code expects a variable that is not set:

```console
$ uv run python -c "import os; print(os.environ['HF_TOKEN'])"
Traceback (most recent call last):
  File "<string>", line 1, in <module>
KeyError: 'HF_TOKEN'
```

`KeyError` on an environment variable means the process did not receive it. Usually one of three
things: `.env` exists but nothing loaded it (part [2.2](2.2-reading-env-without-a-dependency.md)), the
name is misspelled, or you are on a machine where you never created it — which on Day 67 will be the
notebook.

This is the **good** failure. It stops, it names the variable, and nothing proceeds without
authority.

**The silent version, which is why this part exists.** The code does not use `os.environ`. Somebody
pasted the token directly to test something, and it works perfectly:

```console
$ uv run python scripts/fetch_corpus.py
Downloading... done. 4,213 documents.
```

Nothing warns. Nothing fails. The download works *better* than the correct version, because it cannot
be affected by a missing variable. The token is now in a source file, and every subsequent commit
carries it.

Detect it by searching for the shape of a credential in tracked files:

```bash
git ls-files -z | xargs -0 grep -nE "hf_[A-Za-z0-9]{20,}|sk-[A-Za-z0-9]{20,}|AKIA[0-9A-Z]{16}" 2>/dev/null \
  || echo "OK no credential-shaped strings in tracked files"
```

**Line by line:**
- `git ls-files -z | xargs -0` searches **tracked** files only, which is the set that gets published.
  Untracked files are not the risk; committed ones are.
- The patterns match the prefixes real tokens use — `hf_` for Hugging Face, `sk-` for several
  providers, `AKIA` for AWS keys. This is a crude net and it catches the common case.
- The `|| echo` makes success say something. Any output at all means **rotate the credential first**,
  then clean the repository — in that order, because rotation is what makes the copies worthless and
  cleaning is only tidying.
- This is a good candidate for the `TODO(me)` in today's build brief: wire it into `./m check` so it
  runs before every commit rather than when somebody remembers.

## In production

**What a research engineer does instead of the teaching version.** They do not distribute `.env`
files at all. A secret manager issues short-lived credentials to a process at startup, so a leaked
value expires on its own and there is no long-lived string to leak in the first place. `.env` is the
single-developer version of that idea, and it keeps the property that matters — the secret and the
code have different lifecycles — while giving up the one that matters most at scale, which is
expiry.

**What degrades at scale.** Copies multiply, and every copy is a full-strength credential: one in
`.env`, one in a notebook cell, one in a CI secret, one in a message where somebody was helping a
colleague, one in a shell history file. The number of places a secret exists only ever grows, which
is why the professional answer is **rotation on a schedule** rather than protection — you assume
leakage and make it expire. The practical version of that here is Principle 13: a read-only token
limits what a leak *does*, which is the only variable you control once the value is out.

**The failure that only shows with real data.** Notebooks. Part [2.3](2.3-the-token-that-leaked.md) is
about it in full, but the shape is worth flagging now: a notebook stores its **outputs** in the file,
so a cell that prints or errors on a token embeds it in the committed JSON. It does not look like a
credential in a source file. It looks like a stack trace.

**The review comment.** *"This reads `HF_TOKEN` — is it in `.env.example` with a note about which
scope?"* The scope half is the part people skip, and it is the part that decides what a leak costs.

**The interview question.** *"You discover a token was committed six months ago. What do you do
first?"* The answer that shows experience is **rotate it**, immediately, before anything else. Cleaning
history is second and is mostly hygiene: every clone made in those six months still has the old value,
and no amount of rewriting reaches them. What is being probed is whether you understand that a leaked
secret is not a file problem, it is an authority problem.

**Compute tier: T0.** Laptop CPU, no GPU. Creating a token needs a browser and a free account, and
nothing today spends any quota.

## Check yourself

Run this. It prints three **numbers**, and all three must be `0`:

```bash
echo "tracked .env:        $(git ls-files | grep -c '^\.env$')"
echo "untracked .env seen: $(git status --short | grep -c '\.env$')"
echo "token-shaped strings: $(git ls-files -z | xargs -0 grep -lE 'hf_[A-Za-z0-9]{20,}' 2>/dev/null | wc -l)"
```

**Line by line:**
- The first is the one that would be catastrophic: `.env` among tracked files. `git ls-files` ignores
  `.gitignore`, so this is ground truth rather than a guess.
- The second confirms git does not even see the file — the ignore rule is doing its job.
- The third scans every tracked file for a Hugging Face token shape. **A non-zero here means rotate
  the token before you do anything else**, including before you finish reading this part.

**Say this out loud, without scrolling up:** why must `.gitignore` contain `.env` *before* `.env` is
created — and why is "remove it from history" the wrong first response to a committed credential?
