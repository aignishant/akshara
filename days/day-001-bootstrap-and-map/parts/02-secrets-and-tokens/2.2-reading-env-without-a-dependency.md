# 2.2 — Reading `.env` without a dependency: twelve lines you can audit

## One-line answer

Loading a `.env` file is a dozen lines of parsing, and writing them yourself — rather than installing
a package on day one — is the first application of *build first, compare after*, on the one code path
in the project that handles a credential.

---

## The story

A team audits their dependencies after an incident elsewhere in the industry. The question is simple:
what code runs in this project that we did not write?

The direct dependency list is short and defensible. Then somebody expands the full tree. It is
several hundred packages. Almost all arrived transitively — pulled in by something pulled in by
something someone added for one small convenience.

One of them, four levels down, is a package whose entire job is to turn a text file into
name-value pairs. Perhaps forty lines of real logic. It is depended on by something that is depended
on by something the team added deliberately, and it runs in every process, and nobody has read it,
and it handles the file where the credentials live.

Nothing was wrong. The package is fine. The point is narrower and more uncomfortable: **a convenience
worth forty lines had been accepted without anyone deciding to accept it**, and the code path it sat
on was the one carrying secrets.

---

## The idea in plain language

Every dependency is a trade. You get code you did not write; you accept code you have not read,
plus everything *it* depends on, forever, on every machine that runs the project.

For most things the trade is obviously good. Nobody should hand-roll a numerical library.

The trade gets worse as three things go up: **how small the thing is**, **how deep in the tree it
sits**, and **how sensitive the code path is**. A `.env` loader scores badly on all three. It is
small enough to read in a minute, and it sits on the path that handles credentials.

There is a second reason specific to this curriculum. Principle 3 says: hand-roll the mechanism once,
then open the library. This is its smallest possible instance — twelve lines, on Day 1, before
anything is at stake — and it establishes the habit that later pays for itself on tokenizers,
attention and LoRA. The point is not that a `.env` parser is hard. **The point is that you now know
what one does**, so when you meet a real one you can read it instead of trusting it.

What the parser has to handle, and each one is a real file people write:

| Case | Line | Why it matters |
| --- | --- | --- |
| a comment | `# Hugging Face` | must not become a variable named `# Hugging Face` |
| a blank line | | must not crash the split |
| an empty value | `HF_TOKEN=` | the template state — must not set a bogus empty token |
| `=` in the value | `URL=a=b` | split on the **first** `=` only |
| quotes | `NAME="value"` | people copy quoted values from documentation |
| `export` prefix | `export HF_TOKEN=x` | people copy lines from shell scripts |
| already set | | an existing environment variable **wins** — see below |

That last row is the one with real consequences. If `.env` overwrote existing variables, then on
Day 67 a notebook that sets `HF_TOKEN` through its own secret mechanism would be silently overridden
by a stale committed default. **The file is a fallback, not an authority.**

---

## Why Akshara needs it

- **Every day from 61 onward** that touches a dataset or a model needs `HF_TOKEN` present, and needs
  a clear failure when it is not.
- **Day 67** runs on a notebook where the token arrives through a completely different route than a
  `.env` file. The "already set wins" rule is what makes the same code work in both places without a
  conditional.
- **Day 145** studies supply-chain attacks — malicious packages, poisoned artifacts. The habit being
  built today is the one that day depends on: *read what runs on your sensitive paths*. Twelve lines
  you have read beat forty you have not.
- **Principle 3**, immediately. The library version arrives when there is a reason for it, and the
  comparison is honest because the hand-rolled version already exists.

---

## The mechanism

The whole loader. It goes in `akshara/config.py` — it is library code, imported by other code, so by
the procedure in part [1.3](../01-repo-as-memory/1.3-where-a-new-file-goes.md) it belongs in the
package rather than in `scripts/`:

```python
"""Environment loading. No dependency: twelve lines you can audit (Day 1, part 2.2)."""

import os
from pathlib import Path


def load_env(path: str | Path = ".env") -> int:
    """Load NAME=value pairs from `path` into os.environ. Returns how many were set.

    An existing environment variable always wins: the file is a fallback, not an
    authority. That is what lets the same code work on a notebook where the token
    arrives by another route (Day 67).
    """
    p = Path(path)
    if not p.exists():
        return 0
    loaded = 0
    for raw in p.read_text(encoding="utf-8").splitlines():
        line = raw.strip()
        if not line or line.startswith("#") or "=" not in line:
            continue
        if line.startswith("export "):
            line = line[len("export ") :]
        name, _, value = line.partition("=")
        name, value = name.strip(), value.strip().strip("\"'")
        if not name or not value or name in os.environ:
            continue
        os.environ[name] = value
        loaded += 1
    return loaded
```

**Line by line:**
- `path: str | Path = ".env"` — a default that covers every normal call, and a parameter so tests can
  point it at a fixture instead of the real file. A function that can only read one hard-coded path
  is a function you cannot test.
- `if not p.exists(): return 0` — a missing file is **not an error**. On Day 67 the notebook has no
  `.env` and gets its token another way; raising here would break the machine this has to work on.
  Returning `0` rather than `None` makes "how many did you load?" answerable by the caller.
- `line.startswith("#")` skips comments. Checking *after* `strip()` means an indented comment is
  handled too.
- `"=" not in line` skips anything that is not a pair, rather than crashing on it. Tolerating junk
  matters here because this file is edited by hand.
- `line[len("export ") :]` strips a shell-script prefix. This exists because people copy lines out of
  documentation, and a loader that rejects the format the docs use will be worked around.
- `partition("=")` splits on the **first** `=` only and always returns three parts, so a value
  containing `=` survives intact. `split("=")` would return a variable-length list and mangle it —
  this is the single most common bug in a hand-rolled loader.
- `.strip("\"'")` removes surrounding quotes. Documentation examples are frequently quoted and the
  quotes are not part of the value.
- `if not name or not value or name in os.environ: continue` — three refusals in one line, and each
  earns its place. An empty `name` is malformed. An empty `value` is the `.env.example` template
  state, and setting `HF_TOKEN=""` would turn a clear `KeyError` into a confusing authentication
  failure much later. And `name in os.environ` is the fallback rule: **the real environment wins.**
- `return loaded` gives the caller a number. Silence would be indistinguishable from a file that
  parsed to nothing.

Using it — note the order, which is the part people get wrong:

```python
from akshara.config import load_env
import os

load_env()                      # must run BEFORE anything reads os.environ
token = os.environ["HF_TOKEN"]  # KeyError here is the good failure
```

**Line by line:**
- `load_env()` first. A module that reads `os.environ` at **import time** will read it before this
  runs, which is why credentials are fetched inside functions rather than at module level.
- `os.environ["HF_TOKEN"]` with square brackets, deliberately — **not** `os.environ.get("HF_TOKEN")`.
  `.get()` returns `None` on a missing variable, which then travels into an HTTP header and produces a
  `401` several layers away from the actual cause. The bracket form fails immediately and names the
  variable. This is Principle 10 — fail honestly — in one character of syntax.

## When it breaks

The loud failure, and the one you want:

```console
$ uv run python -c "from akshara.config import load_env; import os; load_env(); print(os.environ['HF_TOKEN'])"
Traceback (most recent call last):
  File "<string>", line 1, in <module>
KeyError: 'HF_TOKEN'
```

Three causes, in order of likelihood: `.env` has `HF_TOKEN=` with no value (the template state, which
`not value` deliberately skips); the file does not exist; the name is misspelled. All three are one
`cat .env` away from being obvious, and the error named the variable.

The failure you get with `.get()` instead, several layers away:

```console
requests.exceptions.HTTPError: 401 Client Error: Unauthorized for url: https://huggingface.co/api/...
```

Same root cause, reported by a different system, after a network round trip, with no mention of
`HF_TOKEN`. This is why the bracket form is not a style preference.

**The silent version, which is what "already set wins" prevents.** Suppose the loader overwrote
existing variables. On the Day 67 notebook, the platform injects `HF_TOKEN` through its own secret
mechanism. Your code then loads a `.env` that somebody committed a stale value into, or an empty one,
and overwrites the good token with a bad one. The download fails with a `401` and the notebook's
secret panel shows the token present and correct. Nothing anywhere reports that a file overrode it.

Detect it by asking **where a value came from**, not just what it is:

```python
import os
from akshara.config import load_env

before = set(os.environ)
n = load_env()
print(f"loaded {n} new; HF_TOKEN came from {'the file' if 'HF_TOKEN' in set(os.environ) - before else 'the real environment'}")
```

**Line by line:**
- Snapshotting `os.environ` before and after turns "is it set?" into "**who set it?**" — the same
  observation habit as Day 0 part
  [1.3](../../../day-000-toolchain-skeleton-driver/parts/01-the-toolchain/1.3-observed-is-not-available.md),
  applied to configuration.
- The count `n` distinguishes "the file was read and everything was already set" from "the file was
  not read at all", which otherwise look identical.
- Print this once at the start of any run that behaves oddly on a machine that is not yours. It
  answers the question you will actually have on Day 67.

## In production

**What a research engineer does instead of the teaching version.** They use a settings object rather
than scattered `os.environ` reads — one class, validated once at startup, that fails immediately with
a list of everything missing instead of one `KeyError` per attempt. `pydantic-settings` is the common
choice. The upgrade that matters is not the library, it is **validate-at-startup**: a long training
run that fails forty minutes in because a variable needed for the checkpoint upload was unset has
wasted a metered GPU session for a reason that was knowable at second zero.

**What degrades at scale.** `.env` files stop being the mechanism. Deployed processes get their
configuration from a secret manager or an orchestrator, and the file becomes local-development-only.
The property this part is really teaching survives that transition unchanged: **the real environment
outranks any file**, which is exactly what makes the same code work on a laptop, in a notebook and in
a container without a conditional.

**The failure that only shows with real data.** Precedence bugs are invisible until two sources
disagree, and two sources only disagree on a machine that is not yours. That is why the "already set
wins" line is written on Day 1 for a problem that first appears on Day 67 — by then the code is
established and nobody is thinking about `.env` semantics.

**The review comment.** *"`os.environ.get()` here — what happens downstream if it's `None`?"* The
answer is almost always "a confusing error somewhere else", and the fix is one character.

**The interview question.** *"How does configuration reach your training job?"* The strong answer names
a precedence order — real environment, then file, then default — and says what happens when a required
value is missing: **fail at startup with everything that is missing, not on first use with one thing.**
What is being probed is whether you have ever lost a long run to a missing variable.

**Compute tier: T0.** Laptop CPU. Twelve lines of string handling; the reason it is here rather than
in a package is auditability, not performance.

## Check yourself

Run this. It prints a **number** — how many variables the loader set — and where the token came from:

```bash
uv run python -c "
from akshara.config import load_env
import os
before = set(os.environ)
n = load_env()
src = 'the file' if 'HF_TOKEN' in set(os.environ) - before else ('the real environment' if 'HF_TOKEN' in os.environ else 'NOWHERE')
print(f'loaded={n} token_source={src}')
"
```

**Line by line:**
- `loaded=` is the count of variables the file actually contributed. **A `0` with a populated `.env`
  means everything was already set** — which is correct behaviour, not a bug, and is exactly the
  distinction the count exists to make visible.
- `token_source=NOWHERE` means neither route supplied it, and every download from Day 61 onward will
  fail. Better to learn that now than in the middle of a corpus fetch.
- Run this again on Day 67 inside the notebook. The expected answer there is
  `the real environment` — and if it says `the file`, something has committed a token.

**Say this out loud, without scrolling up:** why does an existing environment variable win over the
file — and why is `os.environ["X"]` the right call rather than `os.environ.get("X")`?
