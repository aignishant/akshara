# 2.3 — 💥 The token that leaked through a notebook output

## One-line answer

A notebook stores its **outputs inside the file**, so a credential that was never written in any cell
can still be committed — printed by a debug line, or embedded in a traceback — and this is the leak
route that `.gitignore` cannot see.

---

## The story

🎬 **The scene.** Somebody is debugging an authentication problem in a notebook on a free GPU. The
download keeps failing. They add the obvious diagnostic line — print the token, or at least its first
few characters — and run the cell. Now they can see it is present and correct, and the real problem
turns out to be somewhere else. They fix that, delete the debug line, and commit the notebook.

😬 **The naive fix.** Deleting the line is the fix. The cell is gone; the notebook no longer contains
any code that prints a credential. Every visible signal agrees: open the file in a browser and there
is nothing there.

💥 **Why it fails.** A notebook is a JSON document, and it stores the **output** of every cell
alongside the source. Deleting the source of a cell you already ran does not necessarily remove the
recorded output, and even where it does, the output of *other* cells persists — including any
traceback that happened to include a request header. The token is sitting in the JSON, in an
`"outputs"` array, in a file that is fully tracked and about to be committed. It is not in any line of
code. `grep`ping the source finds nothing.

💡 **The insight.** Every rule from part [2.1](2.1-the-token-in-one-place.md) held perfectly. The
token lived in one place, `.env` was ignored, the code read `os.environ`. **None of it protects
against a file format that records what your program said.** The leak route is not the code; it is
the artifact the code produced, and defending it needs a different mechanism — stripping outputs
before commit — rather than a stricter version of the same one.

---

## The idea in plain language

A `.ipynb` file is JSON with three things per cell: the source, the metadata, and the **outputs** —
everything the cell printed, returned, or raised, saved verbatim.

That third one is the whole problem, and it is genuinely different from a source file:

| | source file | notebook |
| --- | --- | --- |
| what is committed | what you wrote | what you wrote **and what it printed** |
| leak route | writing a secret in the code | writing a secret, **or printing one, or raising on one** |
| visible in a diff | yes | outputs are base64 and JSON — technically visible, practically not |
| caught by reading the code | yes | **no** |

Three ways a credential reaches an output without ever appearing in source:

- **A print.** `print(os.environ["HF_TOKEN"][:8])` — even a truncated token is a real prefix, and
  people print truncations precisely because they feel safe.
- **A traceback.** An exception raised inside an HTTP library frequently includes the request object,
  and the request object carries the `Authorization` header. Nobody wrote a print statement at all.
- **A repr.** Displaying a client or config object at the end of a cell calls its `__repr__`, and
  plenty of libraries put credentials in theirs.

The second and third are the dangerous ones because there is no line to delete. The mechanism has to
be **strip outputs before the file is committed**, applied automatically, because a human deciding
each time will be right until the evening they are not.

---

## Why Akshara needs it

The plan has notebooks for one reason: **T1 compute** (§4). Days 67, 89, 94, 123 and 134 all run on a
free notebook GPU, and the token has to be present on a machine that is not yours, shared, and
rebuilt from nothing every session.

That is the maximally risky combination for this exact failure:

- The token is on a machine you do not control.
- The work is exploratory, so debug prints are normal and correct.
- The session is metered, so people move fast and commit at the end.
- The output is a file format that records everything.

And the constraint that makes it matter beyond your own account: the plan expects this repository to
be publishable by Day 149. A notebook with a token in its `outputs` is a permanent, published
credential — a Day 0 part
[3.2](../../../day-000-toolchain-skeleton-driver/parts/03-gitignore-first/3.2-the-checkpoint-that-cannot-be-removed.md)
problem with an authority attached.

There is a second, quieter reason. Notebook outputs also record **data samples**. On Day 61 you will
handle a pretraining corpus; a cell displaying a dataframe of examples embeds those examples in a
committed file. That is a licensing and privacy question (SAFE-09, SAFE-14) with the same mechanism
and the same fix.

## The mechanism

Do it on purpose, on a fake token, and see it in the file.

```bash
mkdir -p notebooks
uv run python - <<'PY'
import json, pathlib
nb = {"cells": [{"cell_type": "code", "execution_count": 1, "metadata": {},
                 "source": ["import os\n", "print(os.environ['FAKE_TOKEN'][:12])\n"],
                 "outputs": [{"output_type": "stream", "name": "stdout",
                              "text": ["hf_ABCDEFGHIJKLMNOPQRSTUVWXYZ012345\n"]}]}],
      "metadata": {}, "nbformat": 4, "nbformat_minor": 5}
pathlib.Path("notebooks/leak_demo.ipynb").write_text(json.dumps(nb, indent=1), encoding="utf-8")
print("wrote notebooks/leak_demo.ipynb")
PY
```

**Line by line:**
- This builds a minimal notebook by hand rather than asking you to run one, so the demonstration works
  identically whether or not Jupyter is installed. The structure is the real `nbformat` 4 shape.
- The `"source"` array is the code. The `"outputs"` array is what the cell printed — **a separate
  field**, which is the entire point of this part.
- The token here is fabricated and begins with the real `hf_` prefix so the detection below matches
  the same shape a genuine one would.

Now look for it the two ways people actually look:

```bash
grep -c "hf_ABCDEF" notebooks/leak_demo.ipynb
python - <<'PY'
import json
nb = json.load(open("notebooks/leak_demo.ipynb", encoding="utf-8"))
src = "".join("".join(c["source"]) for c in nb["cells"])
print("in source code?", "hf_ABCDEF" in src)
PY
```

**Line by line:**
- The `grep` searches the **raw file** and finds it — the token is there.
- The Python block reconstructs only the **source** of every cell, which is what a person reviewing
  the notebook in a browser reads, and reports `False`. The credential is in the file and not in the
  code, and those are different things.
- That gap between the two answers is the failure this part exists to show. A review that reads the
  code passes. A review that reads the file does not.

The fix — strip outputs before the file is ever committed:

```bash
uv add --dev nbstripout==<the version your lookup printed>
uv run nbstripout --install --attributes .gitattributes
grep nbstripout .gitattributes
```

**Line by line:**
- Pin the version from a live lookup (`curl -s https://pypi.org/pypi/nbstripout/json`) and record it
  in `docs/PACKAGES.md` — Principle 6, and Day 0 part
  [1.3](../../../day-000-toolchain-skeleton-driver/parts/01-the-toolchain/1.3-observed-is-not-available.md)
  on why the observed version is the only one you may write down.
- `--install` registers a **git filter**: a program git runs on a file on its way into the index. The
  working copy on disk keeps its outputs, so the notebook stays useful to you; what gets committed has
  them removed. That split is what makes the fix survivable — a tool that wiped your outputs on disk
  would be uninstalled within a week.
- `--attributes .gitattributes` writes the rule into a **committed** file, so the protection follows
  the repository to other machines rather than living only in your local git config.
- The `grep` confirms the rule landed. Verify the artifact, not the exit code.

Verify the filter actually filters:

```bash
git add notebooks/leak_demo.ipynb
git show :notebooks/leak_demo.ipynb | grep -c "hf_ABCDEF"
git reset -q HEAD notebooks/leak_demo.ipynb
```

**Line by line:**
- `git show :<path>` prints the **staged** content — the bytes that would be committed, after filters
  have run. This is the only view that answers the question.
- The count must be `0` while the file on disk still contains the token. Working copy dirty, index
  clean: exactly the intended split.
- If it prints anything above `0`, the filter is not installed for this repository, and the notebook
  guard you believe in does not exist — the same lesson as Day 0's failure lab.

## When it breaks

The loud failure, once a provider's scanner sees a pushed credential:

```console
$ git push
remote: error: GH013: Repository rule violations found for refs/heads/main.
remote:   - GITHUB PUSH PROTECTION
remote:     —— Hugging Face User Access Token ——————————————————
remote:      locations:
remote:        - commit: 9f2c1a4
remote:          path: notebooks/pretrain.ipynb:1:  <-- in the outputs, not the source
```

This is the **good** outcome: the push is refused and the credential never becomes public. It is also
luck — it depends on the provider recognising that token format, and it does not fire for data
samples or for formats nobody scans.

**The silent version, which is the normal one.** The push succeeds. Nothing warns. The token is in a
committed notebook's `outputs`, in every clone, and it will remain valid until somebody rotates it —
which nobody will, because nobody knows. There is no error, no scanner hit, and no visible difference
between this notebook and a clean one when you open it.

Detect it by searching the **file**, not the code, across all of history:

```bash
git grep -nE "hf_[A-Za-z0-9]{20,}|sk-[A-Za-z0-9]{20,}" $(git rev-list --all) -- '*.ipynb' 2>/dev/null | head \
  || echo "OK no token-shaped strings in any committed notebook"
```

**Line by line:**
- `git grep ... $(git rev-list --all)` searches **every commit**, not just the current checkout. A
  token removed last week is still in last month's commit and still in every clone.
- Restricting to `-- '*.ipynb'` targets the format where the leak hides in a field nobody reads.
- Any hit means the same order as part [2.1](2.1-the-token-in-one-place.md): **rotate first**, clean
  second. Rotation makes the copies worthless; cleaning is housekeeping that never reaches the clones
  anyone already made.

## In production

**What a research engineer does instead of the teaching version.** Two layers, because one is never
enough. The mechanical layer is a pre-commit hook — `nbstripout` plus a secret scanner — that runs on
every commit regardless of which command was typed. The architectural layer is that notebooks stop
being where anything important happens: logic lives in `akshara/`, the notebook imports it, and a cell
that produces a two-line output has almost nothing to leak. Part
[4.3](../04-free-compute/4.3-notebook-module-discipline.md) is that discipline, and this leak is one
of its two motivations.

**What degrades at scale.** Scanners are denylists and lag every new credential format. They also do
nothing about the *other* payload in outputs: rows of real data, a customer record in a dataframe
preview, an internal URL. Stripping outputs unconditionally is stronger than scanning for known
patterns, because it does not need to know what it is protecting you from — the same argument as
Day 0's preference for directory rules over extension rules.

**The failure that only shows with real data.** On a free notebook the token often arrives through the
platform's own secret mechanism, and the platform may display it in a widget, or a helper may echo a
confirmation containing it. You did not write that cell; the environment did. This is why the defence
has to be at the **commit boundary** rather than in your coding habits — you cannot audit code you
did not write on a machine you do not control.

**The review comment.** *"This notebook has outputs — is `nbstripout` installed on this repo?"* Any
diff showing an `outputs` array with content is a diff where the filter is not running, and that is
visible at a glance without reading the content.

**The interview question.** *"How do you keep secrets out of a repository?"* The weak answer is
`.gitignore` and environment variables. The strong answer adds the artifact channels — notebook
outputs, log files, test fixtures, error reports — and observes that **`.gitignore` protects files you
know about, while the leak comes through a file you meant to commit.**

**Compute tier: T0.** Laptop CPU, no GPU, a fabricated token. The whole failure is reproduced with a
JSON file — and reproducing it here, on Day 1, is what makes the Day 67 notebook safe.

## Check yourself

Run this. It prints two **numbers**: the token count in the file on disk, and in what git would
actually commit. They must differ:

```bash
git add notebooks/leak_demo.ipynb 2>/dev/null
echo "on disk:  $(grep -c 'hf_ABCDEF' notebooks/leak_demo.ipynb)"
echo "in index: $(git show :notebooks/leak_demo.ipynb 2>/dev/null | grep -c 'hf_ABCDEF')"
git reset -q HEAD notebooks/leak_demo.ipynb 2>/dev/null; rm -f notebooks/leak_demo.ipynb
```

**Line by line:**
- `on disk: 1` and `in index: 0` is the passing result — the filter stripped the output on the way
  into git while leaving your working copy intact.
- **`in index: 1` means the filter is not installed for this repository**, and every notebook you
  commit from here is carrying whatever it printed.
- The last line removes the demo. Leaving a file with a token-shaped string in the tree, even a fake
  one, trains you to ignore exactly the thing you should never ignore.

**Say this out loud, without scrolling up:** name two ways a credential reaches a notebook's output
without appearing in any cell's source — and why does stripping outputs beat scanning for known token
formats?
