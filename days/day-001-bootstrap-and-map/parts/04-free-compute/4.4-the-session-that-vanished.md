# 4.4 — 💥 The session that vanished: rehearsing pre-emption before it costs anything

## One-line answer

A free GPU session ends without warning, and the only way to find out whether your work survives that
is to **kill it on purpose** — today, on a laptop, with a toy job, rather than on Day 67 with a
pretraining run inside a session you cannot get back.

---

## The story

🎬 **The scene.** A long job has been running for a couple of hours. The loss is coming down nicely.
The cell is still executing, the progress output is scrolling, and there is nothing to do but let it
finish.

😬 **The naive fix.** There is nothing to fix. It is working. Interrupting it to add checkpointing
would waste the hours already spent, and the job is nearly done. The rational move is to let it run.

💥 **Why it fails.** The session is reclaimed. Not crashed — reclaimed, which is quieter: the kernel
disconnects, the cell stops, and the machine that held everything is gone. There is no traceback,
because nothing raised. There is no partial result, because nothing was written. There is no record
that the run happened, because the ledger row was going to be written at the end. Two hours of GPU
time produced **nothing at all** — not a bad model, not a failed experiment you can learn from, but
an absence.

💡 **The insight.** The job was not risky because it was long. It was risky because it was **one
indivisible unit of work whose only output arrived at the end.** Any process with that shape loses
everything to any interruption, and on infrastructure that can interrupt you at will, that is not a
risk, it is a **scheduled outcome**. The fix is not to hope; it is to make progress durable at
intervals, so that an interruption costs one interval instead of everything.

---

## The idea in plain language

Two concepts, and the second is the one people skip.

**Checkpointing** is periodically writing enough state to disk that the job could be restarted from
that point. Crucially, "enough state" is more than the model weights: it is the optimizer state, the
step counter, the learning-rate schedule position, and the data iterator's position. A checkpoint
containing only weights produces a resume that silently restarts the schedule and re-reads the same
data — which trains a **different model** than the uninterrupted run would have, with nothing red
anywhere.

**Resume** is the code path that loads that state and continues. It is a distinct path from a fresh
start, and — this is the part that gets skipped — **it is exercised only when something goes wrong**,
which means it is the least-tested code in the project and it runs at the worst possible moment.

So the discipline has three parts, and only the third one is unusual:

1. Write a checkpoint every *N* steps, not every epoch. On a pre-emptible machine, `N` is chosen so
   that losing `N` steps is tolerable.
2. Write a `RUNS.md` row **at launch**, not at exit (part
   [3.2](../03-the-ledgers/3.2-runs-md-turns-anecdote-into-result.md)), so an interrupted run still
   leaves a record.
3. **Rehearse the interruption.** Kill the job on purpose, resume it, and verify the resumed run
   matches what an uninterrupted run would have produced. A resume path that has never been run is a
   resume path that does not work — the same argument as Day 0's failure lab, applied to the one
   scenario that will definitely happen.

## Why Akshara needs it

Pre-emption is not an edge case in this plan. It is the **expected operating condition** of every T1
day: 67, 89, 94, 123 and 134.

The plan sequences the mechanism deliberately: **Day 58 teaches checkpoint-and-resume (TRAIN-15,
TRAIN-16), and Day 67 is the first real run.** That ordering is the whole point — the machinery
exists before the session that needs it, rather than being added after the first loss.

Today's job is smaller and comes first: **establish the reflex.** Before Day 58 builds the real
thing, you should already believe, from having done it, that a job which cannot be killed and resumed
is a job that will eventually be killed and not resumed.

There is a second reason specific to this project's honesty rules. Principle 10 says fail honestly,
and `docs/RUNS.md` has an `Outcome` column including `preempted`. That column can only be filled in
if the row exists **before** the outcome is known. A ledger written at exit records only runs that
exited.

## The mechanism

Rehearse it. On the laptop, with a toy job, where the cost is nothing.

**Step 1 — a job with the dangerous shape: all output at the end.**

```bash
mkdir -p /tmp/preempt && cat > /tmp/preempt/fragile.py <<'PY'
import time, pathlib
total = 0
for step in range(1, 31):
    total += step
    time.sleep(0.2)
    print(f"step {step} total {total}", flush=True)
pathlib.Path("/tmp/preempt/result.txt").write_text(str(total))
print("done")
PY
```

**Line by line:**
- The loop stands in for a training run: it accumulates state (`total` is the model) and prints
  progress.
- `flush=True` forces output immediately rather than buffering it. Without this the progress looks
  fine right up to the moment it is lost, which is realistic but makes the demonstration harder to
  read.
- **The only write happens after the loop.** This is the shape from the story, and it is what makes
  the job all-or-nothing.

**Step 2 — kill it partway through, exactly as a platform would.**

```bash
cd /tmp/preempt && uv run python fragile.py & PID=$!
sleep 3; kill -9 $PID 2>/dev/null; wait $PID 2>/dev/null
echo "--- what survived? ---"; ls /tmp/preempt/; cat /tmp/preempt/result.txt 2>/dev/null || echo "result.txt: DOES NOT EXIST"
```

**Line by line:**
- `& PID=$!` runs the job in the background and captures its process id.
- `kill -9` is deliberately the un-catchable signal. A platform reclaiming a machine does not send a
  polite request your code can handle — modelling it with something catchable would rehearse an
  easier problem than the real one.
- `wait ... 2>/dev/null` suppresses the shell's job-killed notice so the output stays readable.
- **`result.txt` does not exist.** Fifteen steps of work, entirely gone, with no error and no partial
  output. That absence is the thing this part is about.

**Step 3 — the same job, made durable.**

```bash
cat > /tmp/preempt/durable.py <<'PY'
import json, pathlib, time
CKPT = pathlib.Path("/tmp/preempt/ckpt.json")
state = json.loads(CKPT.read_text()) if CKPT.exists() else {"step": 0, "total": 0}
print(f"resuming from step {state['step']}", flush=True)
for step in range(state["step"] + 1, 31):
    state["total"] += step
    state["step"] = step
    time.sleep(0.2)
    if step % 5 == 0:                      # checkpoint every N steps, not every epoch
        CKPT.write_text(json.dumps(state))
        print(f"step {step} total {state['total']}  [checkpointed]", flush=True)
print("done", state["total"])
PY
cd /tmp/preempt && uv run python durable.py & PID=$!
sleep 3; kill -9 $PID 2>/dev/null; wait $PID 2>/dev/null
echo "--- resuming ---"; uv run python /tmp/preempt/durable.py
```

**Line by line:**
- The first three lines are the **resume path**: if a checkpoint exists, load it; otherwise start
  fresh. Resume is not a special mode — it is the normal startup path, which is what keeps it tested
  every single run rather than only after a failure.
- `range(state["step"] + 1, 31)` continues from where the checkpoint stopped. Off-by-one here is the
  classic bug: `state["step"]` without the `+ 1` silently re-runs one step, which in a real trainer
  means one batch seen twice and a step counter that disagrees with the schedule.
- `if step % 5 == 0` checkpoints **every N steps**, not at the end and not per epoch. On pre-emptible
  hardware the interval is a risk decision: it is how much work you are willing to lose.
- **`state` holds the step counter, not just the value.** In a real trainer this is where the
  optimizer state and the schedule position go — the things a weights-only checkpoint omits and whose
  absence produces a silently different model.
- The resumed run prints `resuming from step 10` and finishes at the same total an uninterrupted run
  would reach. That equality is the property being verified.

**Step 4 — verify the resumed result is the *right* result.**

```bash
rm -f /tmp/preempt/ckpt.json
uv run python /tmp/preempt/durable.py | tail -1
```

**Line by line:**
- Deleting the checkpoint forces a clean, uninterrupted run.
- Its final line must **match** the interrupted-then-resumed run's final line. If they differ, the
  resume path is losing or duplicating work — which is the bug that matters, and it is invisible
  without this comparison.
- **This is the step people skip.** Confirming that a resume *runs* is easy; confirming it produces
  the same answer is the actual requirement.

## When it breaks

The loud failure, when a resume path has a bug:

```console
$ uv run python durable.py
resuming from step 10
Traceback (most recent call last):
  File "durable.py", line 4, in <module>
    state = json.loads(CKPT.read_text())
json.decoder.JSONDecodeError: Unterminated string starting at: line 1 column 1 (char 0)
```

The process was killed **mid-write**, leaving a truncated checkpoint. This is a real hazard on
pre-emptible hardware and it is why production checkpointing writes to a temporary file and renames
it — a rename is atomic, so a checkpoint is either complete or absent, never half-written.

**The silent version, which is the expensive one.** The resume works and is wrong. The weights are
restored but the optimizer state is not, so momentum restarts from zero. Or the schedule position is
not restored, so the learning rate jumps back up. Or the data iterator restarts, so the model sees
the same first ten thousand examples twice.

Every one of those **runs to completion and produces a model**. The loss curve has a small bump at
the resume point that looks like noise. Nothing is red. You have trained something other than what
you intended, and the only evidence is a discontinuity you will not notice.

Detect it by comparing an interrupted run against a clean one:

```bash
rm -f /tmp/preempt/ckpt.json && uv run python /tmp/preempt/durable.py | tail -1 > /tmp/preempt/clean.txt
rm -f /tmp/preempt/ckpt.json
(cd /tmp/preempt && uv run python durable.py & P=$!; sleep 2; kill -9 $P 2>/dev/null; wait $P 2>/dev/null)
uv run python /tmp/preempt/durable.py | tail -1 > /tmp/preempt/resumed.txt
diff /tmp/preempt/clean.txt /tmp/preempt/resumed.txt && echo "IDENTICAL — resume is correct"
```

**Line by line:**
- Run clean, record the answer. Run interrupted, resume, record the answer. `diff` them.
- **`IDENTICAL` is the only acceptable result.** Anything else means the resume path is not
  equivalent to an uninterrupted run, which is a correctness bug that will express itself as a
  slightly worse model rather than as an error.
- On Day 58 this becomes a real test with a real trainer, comparing loss after a fixed number of
  steps with a fixed seed. The structure is identical; only the thing being compared changes.

## In production

**What a research engineer does instead of the teaching version.** Checkpoints are written
atomically — to a temporary path, then renamed — so a kill during a write cannot corrupt the previous
good one. Several are kept, not one, because the most recent may be the truncated one. Resume is the
**default** startup path rather than a flag, so it is exercised on every run and cannot rot. And the
checkpoint carries everything: weights, optimizer state, scheduler state, dataloader position, RNG
state, and the step count. That last group is what makes a resumed run equal to an uninterrupted one
rather than merely similar.

**What degrades at scale.** Checkpoints get large and frequent writing becomes a throughput cost, so
the interval becomes a real trade: write often and lose less time to pre-emption, write rarely and
spend less time writing. The number is chosen from measured pre-emption frequency, which is why part
[4.2](4.2-the-accounts-and-what-they-cost.md) insists on measuring the session's actual limits rather
than assuming them. On this project's free tier the answer leans toward frequent, because a lost
session cannot be bought back.

**The failure that only shows with real data.** Non-determinism across the resume boundary. Even with
everything restored, resuming can diverge slightly from an uninterrupted run because of nondeterministic
kernels and reduction orders. That is expected and acceptable — but you have to know the **size** of
the acceptable difference in advance, or you cannot distinguish "hardware noise" from "my resume path
is broken". This is Silent Failure #4 from the plan's §6 arriving through infrastructure, and it is
why the `RUNS.md` row records the hardware.

**The review comment.** *"This checkpoints the model — does it also save the optimizer and the
scheduler?"* The most common incomplete-checkpoint bug, and it produces a model that is worse for
reasons nobody traces back to the interruption.

**The interview question.** *"Your training job gets killed at hour six of eight. What happens?"* The
weak answer describes restarting. The strong answer names what is in the checkpoint, how often it is
written, and — the part that shows real experience — **how you verified the resume produces the same
result as an uninterrupted run**, because nearly everyone has a resume path and far fewer have
checked it.

**Compute tier: T0.** Laptop CPU, two toy scripts, no GPU. Rehearsing pre-emption costs nothing here
and is what makes the first T1 session on Day 67 survivable.

## Check yourself

Run this. It prints whether an interrupted-and-resumed run produces the **same number** as a clean
one:

```bash
rm -f /tmp/preempt/ckpt.json; uv run python /tmp/preempt/durable.py | tail -1
rm -f /tmp/preempt/ckpt.json
(cd /tmp/preempt && uv run python durable.py & P=$!; sleep 2; kill -9 $P 2>/dev/null; wait $P 2>/dev/null) 2>/dev/null
uv run python /tmp/preempt/durable.py | tail -1
```

**Line by line:**
- The first line is the clean run's final total. The last is the resumed run's.
- **Both must print `done 465`** — the sum of 1 to 30. A different number means the resume path lost
  or repeated work, and you have found it on a toy script rather than in a checkpoint.
- Clean up with `rm -rf /tmp/preempt` when the numbers match.

**Say this out loud, without scrolling up:** name three things besides the weights that a checkpoint
must contain — and say why "the resume ran successfully" is not evidence that the resume is correct.
