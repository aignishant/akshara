# 3.1 — What a ledger is for: append-only, dated, and never edited

## One-line answer

A ledger records **what was true at a moment**, one dated row at a time, and is never rewritten —
which is a different job from documentation, and the difference is why a ledger can still be trusted
six months later when documentation cannot.

---

## The story

A project keeps a page describing its setup: which versions, which data, which decisions. It is
maintained conscientiously. When something changes, somebody updates the page so it stays accurate.

A year later a question arrives: this result from March — what was it produced with?

The page cannot answer. It describes **now**. Every update overwrote the previous state, so the page
has always been correct and has never been able to say anything about the past. The information was
not lost in a crash; it was deliberately replaced, each time, by somebody being diligent.

Somebody suggests the page's history in version control will have it. It does, in a sense — a diff
showing a version number changing on some date. But the date the page was *edited* is not the date
the change *happened*, and a diff does not say which experiments ran on which side of it.

**The page was maintained. It was just answering a different question than the one that mattered.**

---

## The idea in plain language

Two kinds of document, and conflating them is the mistake:

| | Documentation | Ledger |
| --- | --- | --- |
| Answers | "What is true now?" | "What was true then?" |
| On change | **overwrite** | **append a new row** |
| Rows carry a date | no | **always** |
| Editing an old entry | normal | **a corruption** |
| Goes stale | yes, silently | no — staleness is visible as an old date |

A ledger is append-only. When something changes you add a row; you never edit the old one. The old row
was not wrong — it was true then, and the whole value of the artifact is that it can say so.

Three properties follow, and each is doing real work:

**Every row has a date.** Without one, a ledger is a list of claims with no time attached, which
quietly means "still true" and is exactly the assumption that fails. With one, a stale row is
*visibly* stale — you can see it is from March and ask whether it still holds. **Dates do not prevent
staleness; they make staleness detectable**, which is the achievable goal.

**Corrections are appended, not applied.** If a row turns out to be wrong, the fix is a new row saying
so, referring to the old one. The wrong row stays. This feels untidy and it is the point: the record
of what you *believed* is often more useful than the record of what was true, particularly when
tracking down why a decision was made.

**Rows are small.** A ledger row is written at the end of a working day by somebody tired. A format
that demands a paragraph will be skipped; one that demands seven short columns will be filled in.
This is a real design constraint, not a compromise — a ledger nobody fills in records nothing.

---

## Why Akshara needs it

The plan (§27) has **ten** ledgers: seven written by hand, three regenerated. That is more than most
projects and there is a specific reason.

Ordinary software can reconstruct its own past. The code is the artifact, the tests describe the
behaviour, and git history holds every version. Generative work cannot. A trained model is a file of
numbers that does not record how it was made — the corpus, the seed, the hyperparameters, the
hardware, the library versions. **None of that is recoverable from the checkpoint**, and the
checkpoint is not even in the repository (Principle 9). If it was not written down at the time, it is
gone.

The seven hand-written ones, and the question each answers about a moment in the past:

| Ledger | The question, six months later |
| --- | --- |
| `PROGRESS.md` | which days were finished, and were their gates green? |
| `PACKAGES.md` | what version of this library was installed **then**? |
| `DATASETS.md` | which revision of this corpus, under what licence, and was it decontaminated? |
| `MODELS.md` | which checkpoint revision did we load, and was it safetensors? |
| `RUNS.md` | what produced this result — seed, config, hardware, outcome? |
| `PAPERS.md` | which paper did we read, when, and at which URL? |
| `CHANGELOG_PLAN.md` | when did the plan change, and why? |

Every one of those is a question with a *timestamp built into it*. That is the tell for when a ledger
is the right artifact rather than a documentation page.

---

## The mechanism

Every ledger in this project has the same shape, and the header is not decoration — it is where the
rules live, next to the thing they govern:

```text
# Package Ledger — Project Akshara

Append-only. Principle 6: **never invent a version number.** Every install gets a row here
with the version actually observed, the date it was observed, the day that added it, and why.
If a version could not be looked up, the row says `TODO(<the exact lookup command>)` — never
a guess.

| Package | Version | Date | Day | Why |
| ------- | ------- | ---- | --- | --- |
| uv | 0.12.3 | 2026-08-25 | 0 | One binary owns the environment. Observed with `uv --version`. |
```

**Line by line:**
- The word **Append-only** is the first thing in the file, because the rule has to be visible to
  somebody about to edit a row.
- The header states the *principle* the ledger serves, so a reader knows why the discipline exists
  rather than just that it does. A rule without its reason gets overridden by whoever is in a hurry.
- The `TODO(<command>)` convention is stated in the header rather than left to judgement — it is the
  escape hatch that keeps a failed lookup from becoming a guess. **Naming the escape hatch is what
  stops people inventing worse ones.**
- The `Why` column is the one people want to drop and the one that pays off. In six months "what
  version" is answerable from the lockfile; "why is this here at all, and what breaks if I remove
  it?" is not answerable from anywhere else.

A correction is a **new row**, not an edit:

```text
| python | 3.12.13 | 2026-08-25 | 0 | Runtime per plan §5. Read from `uv python list`. |
| python | 3.12.12 | 2026-08-26 | 0 | **Correction to the row above.** `uv python list` *offers* 3.12.13 but it is `<download available>`, not installed; the interpreter this venv runs is 3.12.12 (`sys.version`). Principle 6 records the version observed, not the version available. |
```

**Line by line:**
- The first row stays. It is a true record of what somebody believed on the 25th, and any experiment
  run that day was run under that belief.
- The second row is dated the 26th and says **Correction to the row above** explicitly. A reader
  scanning for `python` sees both and reads them in order.
- The correction states *how* the mistake happened — offered versus observed — which is worth more
  than the corrected number, because it stops the same mistake recurring. This is the Day 0 lesson
  from part
  [1.3](../../../day-000-toolchain-skeleton-driver/parts/01-the-toolchain/1.3-observed-is-not-available.md),
  recorded where it will be met again.
- Had the first row simply been edited, the repository would now claim nobody was ever confused about
  this, which is false and also less useful.

Create the ledgers, all seven, with their headers:

```bash
ls docs/*.md
head -6 docs/RUNS.md
```

**Line by line:**
- The files were created as part of the repository bootstrap; today is about understanding what each
  is for rather than typing seven headers.
- `head -6 docs/RUNS.md` shows the rules at the top of the one that matters most. Read it now — part
  [3.2](3.2-runs-md-turns-anecdote-into-result.md) is entirely about that file.

## When it breaks

There is no error message for a ledger. That is the defining difficulty and it is why the discipline
has to be ritual rather than judgement.

The nearest thing to a loud failure is a question you cannot answer:

```console
$ grep "gemma" docs/MODELS.md
$ echo $?
1
```

Nothing. A model was used and never recorded, so its revision and licence are unknown — and on Day
147, when the corpus and model licences get audited (SAFE-14), this is a gap that cannot be filled
retroactively because the repository may have been force-pushed since.

**The silent version, and it is the normal decay.** Rows stop being added. The ledger still exists,
still looks authoritative, still has rows in it — and it is now describing a subset of reality that
nobody has flagged as a subset. Somebody reads it, concludes those are all the datasets used, and is
wrong.

This is worse than an empty ledger, because an empty one is obviously empty. **A partial ledger
invites confident wrong conclusions**, which is precisely the failure mode a record is supposed to
prevent.

Detect it by comparing the ledger against reality rather than reading it:

```bash
echo "days finished (PROGRESS): $(grep -c '^| [0-9]' docs/PROGRESS.md)"
echo "day folders on disk:      $(ls -d days/day-* 2>/dev/null | wc -l)"
echo "newest ledger date:       $(grep -ohE '20[0-9]{2}-[0-9]{2}-[0-9]{2}' docs/*.md | sort | tail -1)"
```

**Line by line:**
- The first two numbers should track each other. Folders far ahead of `PROGRESS.md` rows means days
  are being written and not finished — the ledger has fallen behind the work.
- The third is the **staleness check** and it is the one worth running periodically. A newest date of
  three months ago on an active project means the ritual has quietly stopped, and no single row looks
  wrong.
- This is a manual read, not an automated check, and that is honest: part
  [5.2](../../../day-000-toolchain-skeleton-driver/parts/05-the-depth-check/5.2-what-depth-check-cannot-catch.md)
  of Day 0 argued that rules needing judgement get a reviewer rather than a regex.

## In production

**What a research engineer does instead of the teaching version.** They make the ledger a by-product.
The training script writes its own row — config hash, seed, git commit, hardware, final loss — into a
structured log at launch and at exit, so the record cannot be forgotten because it is not a separate
act. Experiment trackers are the hosted version of the same idea. What survives the switch to a tool
is the **discipline**: append-only, dated, corrections as new entries. What is given up if you rely on
a hosted tool alone is that it is not in the repository, which means it is not clonable and not
guaranteed to outlive an account (§4 forbids depending on a paid quota for anything load-bearing).

**What degrades at scale.** Hand-written ledgers rot in proportion to how many people write to them
and how far the row is from the work. The countermeasures used here are the ones that generalise:
generate what can be generated (three of ten, part [3.3](3.3-the-generated-three.md)), keep rows
small enough to write when tired, and put the exact row to paste at the end of every day document so
that filling it in requires no thought. **A ritual survives on being cheap, not on being important.**

**The failure that only shows with real data.** The rows you most need are the ones nobody wants to
write: the run that diverged, the dataset that turned out to be contaminated, the model that could
not be used because of its licence. Those are the expensive knowledge, and they have no artifact to
attach themselves to — nothing shipped. `RUNS.md` therefore requires an `Outcome` column that includes
`diverged` and `oom`, because **a ledger with no failures in it is a ledger someone has been editing.**

**The review comment.** *"This uses a new dataset — is there a `DATASETS.md` row with the revision and
the licence, dated before the download?"* The word *before* is the whole question: a row written
afterwards is a description, while a row written first is a decision.

**The interview question.** *"How do you know what produced a model you trained six months ago?"* The
weak answer is "it's in the code". The strong answer distinguishes what code can tell you
(architecture) from what only a record can (data revision, seed, hardware, library versions) — and
observes that the checkpoint itself contains none of it.

**Compute tier: T0.** Laptop CPU. Writing a row costs nothing, which is exactly why there is no
defensible reason to skip it and exactly why it gets skipped.

## Check yourself

Run this. It prints three **numbers**: how many hand-written ledgers exist, how many rows they hold
between them, and the date of the most recent row:

```bash
echo "ledgers:  $(ls docs/PROGRESS.md docs/PACKAGES.md docs/DATASETS.md docs/MODELS.md docs/RUNS.md docs/PAPERS.md docs/CHANGELOG_PLAN.md 2>/dev/null | wc -l)"
echo "rows:     $(grep -ch '^| [^-|]' docs/PROGRESS.md docs/PACKAGES.md docs/DATASETS.md docs/MODELS.md docs/RUNS.md docs/PAPERS.md 2>/dev/null | paste -sd+ | bc)"
echo "newest:   $(grep -ohE '20[0-9]{2}-[0-9]{2}-[0-9]{2}' docs/*.md | sort | tail -1)"
```

**Line by line:**
- The first must be **7**. A missing ledger is a category of fact this project has decided not to
  record, and that should be a decision rather than an oversight.
- The second counts data rows across all of them — small today, and that is the baseline.
- The third is the staleness signal. **Today it should be today's date.** Re-run this on Day 67; if
  the newest row is weeks old on a project that has been training models, the ritual has stopped.

**Say this out loud, without scrolling up:** why is a correction appended as a new row rather than
applied to the old one — and why is a partially-maintained ledger more dangerous than an empty one?
