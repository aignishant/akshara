# 6.1 — 💥 Four ways to break the gate, and watching each one get caught

## One-line answer

A guard that has never been triggered is a guard nobody has tested — so today you break the gate four
different ways on purpose, watch each refusal, and end the day knowing the difference between a
mechanism and a decoration.

---

## The story

🎬 **The scene.** A building has a fire alarm. It has been installed for years. It has never gone off,
which everybody takes as good news.

😬 **The naive fix.** Nothing needs fixing. The alarm is present, it is wired in, it was working when
it was installed. Testing it would be disruptive and would find nothing, because there is no reason
to think it is broken.

💥 **Why it fails.** The alarm was disconnected during building work two years ago. Nobody noticed,
because the signal it emits when it is working is identical to the signal it emits when it is
disconnected: **silence**. Every day of quiet was read as evidence the alarm was fine, and every one
of those days was equally consistent with it being dead.

💡 **The insight.** A guard that never fires produces no information. You cannot distinguish "nothing
bad happened" from "the guard is broken", and the two look the same for as long as it takes for
something bad to happen. **The only way to learn which one you have is to cause the bad thing on
purpose, somewhere it is cheap.**

Today is the cheap place. The repository has no history, no checkpoints, no work to lose. Every guard
this project relies on for the next hundred and sixty-one days gets triggered here, once, deliberately
— which is the only moment where triggering it costs nothing.

---

## The idea in plain language

Four independent guards were built today. Each one protects against a different mistake, each fails
differently, and **none of them has been observed doing its job**.

| # | Guard | Built in | Protects against | Consequence if it is dead |
| --- | --- | --- | --- | --- |
| 1 | `.gitignore` artifact patterns | [3.1](../03-gitignore-first/3.1-ignore-before-it-exists.md) | a checkpoint entering git | permanent, unfixable without a history rewrite |
| 2 | `./m done` staged-artifact check | [4.3](../04-the-driver/4.3-the-gate-that-refuses.md) | the same thing, past `git add -f` | permanent |
| 3 | `./m done` unticked-checklist check | [4.3](../04-the-driver/4.3-the-gate-that-refuses.md) | a day recorded as done that is not | a history that lies |
| 4 | `depth_check.py` | [5.1](../05-the-depth-check/5.1-a-contract-nobody-checks.md) | a day document missing required sections | the contract decays quietly |

The thing worth noticing before you start: **guards 1 and 2 protect against the same mistake.** That
is not redundancy by accident. Guard 1 is one character deep — `git add -f` walks straight past it —
so guard 2 exists to catch exactly the case where guard 1 was overridden by somebody in a hurry. A
layered defence is only worth building if you know which layer catches what, and the way to find out
is to defeat them one at a time.

There is also a fifth thing being tested here, which is not in the table: **whether the failure
messages are usable.** A refusal that does not say what to fix is a refusal people learn to route
around. Read each message as it appears and ask whether it would have been enough at eleven at night.

## Why Akshara needs it

Every one of these four fires on a real day, at a predictable moment:

- **Guard 1 and 2** fire on **Day 67**, at the end of the pretraining session, when there is a
  checkpoint on disk that cost a whole free GPU session and the instinct is to put it somewhere safe.
  They fire again on Day 80 (`.gguf`), Day 89 (LoRA adapters, small enough to feel harmless) and Day
  134 (diffusion).
- **Guard 3** fires on any day where the building went well and the verifying got skipped — which is
  most of the interesting days, because that is exactly when the result feels like the finish line.
- **Guard 4** fires while writing any day, and it is the one that keeps the depth contract from
  becoming a preference (part [5.1](../05-the-depth-check/5.1-a-contract-nobody-checks.md)).

Principle 11 says every day ends with at least one check that can go red. Today that check is
**four checks, each verified red on purpose**, which is the strongest form of it in the whole plan and
the only day where it costs nothing to do.

## The mechanism

Four experiments. Run them in order, read each message, and note the exit code each time.

**Break 1 — commit an artifact past `.gitignore`.**

```bash
mkdir -p checkpoints
uv run python -c "open('checkpoints/probe.safetensors','wb').write(b'0'*2048)"
git check-ignore -v checkpoints/probe.safetensors; echo "ignored? exit=$?"
git add -f checkpoints/probe.safetensors
./m done 0 > /tmp/g1.txt 2>&1; echo "guard 2 exit=$?"; tail -3 /tmp/g1.txt
git reset -q HEAD checkpoints/probe.safetensors; rm -rf checkpoints
```

**Line by line:**
- `git check-ignore -v` prints the `.gitignore` line that matched and exits `0` — that is **guard 1
  confirmed alive**, and it names the rule rather than just agreeing with you.
- `git add -f` then deliberately overrides it. This is the realistic mistake: not somebody ignoring a
  rule, but somebody hitting a refusal and adding the flag that makes it go away.
- `./m done 0` must print `FAIL a weight/dataset file is staged` and exit `1`. **That is guard 2
  catching what guard 1 could not**, and it is the reason two guards exist for one mistake.
- The `git reset` unstages the bait; `rm -rf` removes it. Note `;` rather than `&&` so cleanup happens
  even if the reset finds nothing to do.

**Break 2 — finish a day whose checklist is not finished.**

```bash
printf '# Day 0 — CHECKLIST\n\n- [x] done thing\n- [ ] not done thing\n' \
  > days/day-000-toolchain-skeleton-driver/CHECKLIST.md
./m done 0 > /tmp/g3.txt 2>&1; echo "guard 3 exit=$?"; tail -3 /tmp/g3.txt
```

**Line by line:**
- One ticked box and one unticked box is the realistic state of a day in progress, not an artificial
  one.
- The refusal must name the file **and print the offending line with its number**. A gate that says
  only `FAIL` is a gate you argue with; one that points at line 4 is one you fix.
- Leave the file in this state for now — the real checklist is written at the end of the day, and you
  want the gate refusing until it genuinely is.

**Break 3 — smuggle a clock into a day document.**

```bash
mkdir -p /tmp/probe && cp -r days/day-000-toolchain-skeleton-driver /tmp/probe/backup
printf '\n\nThis section should take about 90 minutes.\n' \
  >> days/day-000-toolchain-skeleton-driver/parts/01-the-toolchain/1.1-the-four-pythons.md
uv run python scripts/depth_check.py 0 > /tmp/g4.txt 2>&1; echo "guard 4 exit=$?"; grep -i "principle 17" /tmp/g4.txt
```

**Line by line:**
- The backup is taken first because this experiment edits a real document. Verify a guard on a copy
  you can restore, not on the only copy.
- The added sentence is exactly the kind of thing that gets written with good intentions — it sounds
  helpful. Principle 17 bans it because a duration at the top of a document is a standing instruction
  to cut the explanation when the document runs long.
- The failure message must name the line and cite Principle 17. Restore immediately after:
  `cp -r /tmp/probe/backup/. days/day-000-toolchain-skeleton-driver/`.

**Break 4 — remove a required section from a part.**

```bash
python - <<'PY'
from pathlib import Path
p = Path('days/day-000-toolchain-skeleton-driver/parts/01-the-toolchain/1.1-the-four-pythons.md')
t = p.read_text(encoding='utf-8')
i = t.index('## In production'); j = t.index('## Check yourself')
Path('/tmp/section.bak').write_text(t[i:j], encoding='utf-8')
p.write_text(t[:i] + t[j:], encoding='utf-8')
print("removed In production")
PY
uv run python scripts/depth_check.py 0 > /tmp/g5.txt 2>&1; echo "guard 4 exit=$?"; grep -i "missing required" /tmp/g5.txt
```

**Line by line:**
- This deletes the `In production` section — §25.4's most-skipped requirement and the one §25.8 names
  as the difference between a professional document and an introductory one.
- The section is saved to `/tmp/section.bak` first, because the point is to observe a refusal, not to
  damage the day.
- The refusal must name the file and the missing section. Restore by splicing the backup back in
  before `## Check yourself`, then re-run the check and confirm it goes green.

## When it breaks

The four refusals you should see, verbatim:

```console
$ ./m done 0
FAIL a weight/dataset file is staged - Principle 9: the repo holds what reproduces a model, never the model
checkpoints/probe.safetensors

$ ./m done 0
FAIL unticked boxes remain in days/day-000-toolchain-skeleton-driver/CHECKLIST.md
4:- [ ] not done thing

$ uv run python scripts/depth_check.py 0
depth: FAIL — 1 problem(s) across 1 day(s)
  days/day-000-.../parts/01-the-toolchain/1.1-the-four-pythons.md: line 218: a 'should take N' estimate — 'should take about 9' (Principle 17)

$ uv run python scripts/depth_check.py 0
depth: FAIL — 1 problem(s) across 1 day(s)
  days/day-000-.../parts/01-the-toolchain/1.1-the-four-pythons.md: missing required section(s): In production (§25.4)
```

Each names the file, the rule and the principle. **Read them as a user, not as the author** — the
question is whether this message would be enough when you meet it in nine weeks having forgotten
everything about today.

**The silent version, which is the one this whole part exists to expose.** A guard that is present and
dead:

```console
$ ./m done 0
OK day 0 committed
```

after staging a checkpoint. Nothing failed. The message is confident and wrong. If you see this, one
of three things is true and all three are worth knowing about:

1. `set -euo pipefail` is missing from `m`, so a failing check printed and the script carried on
   (part [4.1](../04-the-driver/4.1-why-a-driver.md)).
2. The staged-file check's pattern does not match your filename — a format not in the list.
3. `./m done` is not calling `./m check` at all.

The detection is the experiment itself. **This is the only part of the day where a passing result is
a failing result**, and it is worth sitting with that inversion for a moment: for every guard you ever
build, the test that matters is the one where it says no.

```bash
for f in /tmp/g1.txt /tmp/g3.txt /tmp/g4.txt /tmp/g5.txt; do
  grep -qiE 'FAIL|depth: FAIL' "$f" && echo "$f: refused (good)" || echo "$f: DID NOT REFUSE - guard is decorative"
done
```

**Line by line:**
- Each captured output is checked for a refusal. Four `refused (good)` lines mean four live guards.
- Any `DID NOT REFUSE` is a guard you believed in and do not have — found today, on a repository
  containing nothing, rather than on Day 67 with a checkpoint you cannot un-commit.

## In production

**What a research engineer does instead of the teaching version.** They write the negative test — a
test asserting that the guard **refuses** — and put it in the suite so it runs forever, not once. A
guard verified by hand on the day it was built is a guard verified once; a guard with a test is one
verified on every change to the code around it. That test is the difference between "we have a check"
and "we know the check works", and it is the most commonly skipped test in any codebase because it
tests something not happening.

**What degrades at scale.** Guards accumulate and nobody knows which are live. A repository ends up
with six checks, two of which were broken by an unrelated refactor months ago and are silently
passing everything. The countermeasure is the same one used here: a small suite of deliberate
violations, run regularly, that must all be caught. Some teams call this a canary or a mutation test;
the name matters less than the property, which is that **every guard has a case that proves it is
alive.**

**The failure that only shows with real data.** Denylists lag reality. The staged-file check knows
about `.safetensors`, `.gguf`, `.pt` and a handful more, and a future format will not be in it. The
honest complement is a size rule — refuse any staged file over a few megabytes regardless of
extension, since source files are not that large. Denylists catch what you predicted; a size rule
catches what you did not, and the two together are much stronger than either.

**The review comment.** *"Is there a test that this actually refuses?"* Asked about any new guard, it
separates the guards that work from the guards that are believed in.

**The interview question.** *"How do you know your safety checks work?"* The weak answer describes what
they check. The strong answer describes the last time each one fired, or the test that makes it fire
on purpose — and mentions the alarm problem: a guard that never fires and a guard that is broken emit
exactly the same signal.

**Compute tier: T0.** Laptop CPU, four small files, no network. Every guard this curriculum depends on
is verified on hardware everybody has, which is what makes it reasonable to depend on them on Day 67.

## Check yourself

Run this. It prints the **number of guards that refused** — and it must be `4`:

```bash
grep -qiE 'FAIL|depth: FAIL' /tmp/g1.txt /tmp/g3.txt /tmp/g4.txt /tmp/g5.txt 2>/dev/null
ls /tmp/g1.txt /tmp/g3.txt /tmp/g4.txt /tmp/g5.txt 2>/dev/null | while read f; do
  grep -qiE 'FAIL' "$f" && echo live
done | wc -l
```

**Line by line:**
- The loop reads each captured refusal and prints `live` for every guard that actually said no.
- `wc -l` turns that into the number this part is about. **Anything less than `4` means you have a
  guard you believe in and do not have**, and today is the cheapest day of the entire hundred and
  sixty-two to find that out.
- Once you have your `4`, restore everything you broke — the `In production` section, the clock
  sentence, the checklist — and confirm `uv run python scripts/depth_check.py 0` goes green again. A
  failure lab that leaves the repository broken has taught only half its lesson.

**Say this out loud, without scrolling up:** why do guards 1 and 2 protect against the same mistake —
and why is a guard that has never fired indistinguishable from a guard that is broken?
