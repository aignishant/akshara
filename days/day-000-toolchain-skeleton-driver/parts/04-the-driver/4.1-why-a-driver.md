# 4.1 — Why a driver: one place to look up how to do anything in this repo

## One-line answer

A driver script is a single file listing every operation a repository supports, so that the answer to
"how do I run the checks here?" lives in the repository rather than in the memory of whoever set it
up — which matters most on the day that person is you, six months later.

---

## The story

Somebody returns to a project after a long gap. They want to do the most ordinary thing possible: run
the tests, confirm nothing is broken, then start work.

The README says `pytest`. That fails — wrong environment. There is a note in a chat log about a
different command with a flag, but the flag no longer exists. There is a config file that mentions a
test path that has since moved. Eventually the right invocation is reconstructed from a combination
of the config, a half-remembered detail, and trial and error.

Forty minutes to reach the starting line. Nothing was broken. Every piece of information needed was
present somewhere in the repository. **What was missing was a single place where the answer lived**,
so the answer had to be reassembled from evidence each time.

The tell is that the person doing the reassembling is usually the same person who built it. This is
not a handover problem. It is a memory problem, and memory is the thing this repository exists to
replace.

---

## The idea in plain language

A **driver** is one executable file at the root of a project that exposes the project's operations as
named commands: `./m check`, `./m start 3`, `./m done 3`.

It is not automation in the interesting sense. It runs the same commands you would have typed. The
value is in three properties that have nothing to do with saving keystrokes:

**It is discoverable.** Running `./m` with no arguments prints what the project can do. A newcomer —
including future you — learns the repository's vocabulary by running one thing, rather than by
reading documentation that may have drifted from reality.

**It is the single definition.** When `./m check` is what CI runs and what you run, there is exactly
one meaning of "the checks pass". The moment they are two separate lists, they drift, and the drift
is silent until CI fails on something that passes locally.

**It can refuse.** A command that only runs things is a convenience. A command that *declines* to
proceed — because a checklist is unticked, or a checkpoint is staged — is a mechanism. This is the
property that makes a driver worth having, and part
[4.3](4.3-the-gate-that-refuses.md) is entirely about it.

There is a fourth property, quieter and more valuable: **the driver is documentation that cannot go
stale**, because if it is wrong, it fails. Prose describing a command can be wrong for a year without
anyone noticing.

---

## Why Akshara needs it

This curriculum has one hundred and sixty-two days, and the ritual at the end of every one of them is
identical: verify the whole project, regenerate the ledgers, refuse if the day is not actually
finished, commit. A ritual repeated a hundred and sixty-two times has to be one command, or it will
be performed differently on the days it matters most — which are the tired ones.

More concretely:

- **Every day** ends with `./m done N`, which will not commit while `CHECKLIST.md` has an unticked
  box or an artifact is staged (Principle 9 and part
  [3.2](../03-gitignore-first/3.2-the-checkpoint-that-cannot-be-removed.md)).
- **The depth contract** (plan §25) is checked by `./m depth N`. A contract that is checked by
  reading is a preference; part [5.1](../05-the-depth-check/5.1-a-contract-nobody-checks.md) is about
  that difference.
- **The ledgers** are regenerated by `./m trace` and `./m tracker`. Three of the ten are outputs, and
  a human editing an output loses the edit silently on the next run.
- **Day 67** happens on a machine that is not this one. `./m check` there means what it means here,
  because it is the same file.

And a plain constraint: `make` is not installed on a default Windows machine, and this curriculum is
written for Git Bash on Windows. A driver written in the shell everything else uses is one fewer tool
to install and one fewer thing that behaves differently on the notebook.

## The mechanism

The interface first — decide what the repository can do before writing how:

| Command | What it answers |
| --- | --- |
| `./m status` | Where am I? One line. |
| `./m start N` | Open day N's hub and list its parts. |
| `./m parts N` | What subtopics does day N have? |
| `./m depth [N]` | Does day N satisfy the depth contract (plan §25)? |
| `./m trace` | Regenerate the traceability ledgers from the hubs vs plan §24. |
| `./m tracker` | Regenerate the progress table. |
| `./m scaffold N` | Create day N's `lab/` for my own code. |
| `./m check` | Is the **whole project** green? |
| `./m done N` | Finish day N — **refuse** unless it is genuinely done. |

Two design decisions in that table are worth stating, because they are the difference between a
driver and a pile of aliases.

**Verbs, not tools.** `./m check` rather than `./m ruff`. The name says what you want, not what
implements it. When the linter is replaced on some future day, the command does not change and
neither does anything that calls it — including a hundred and sixty-two day documents.

**One command is the gate.** `./m check` runs everything. Not `./m lint && ./m test && ./m depth` — a
composite that people assemble by hand is a composite that gets assembled differently.

Here is the skeleton, which part [4.2](4.2-building-the-driver.md) fills in:

```bash
#!/usr/bin/env bash
set -euo pipefail

case "${1:-help}" in
  status)  ;;
  check)   ;;
  done)    ;;
  *)
    cat <<'USAGE'
usage: ./m <command> [day]
  status         one line: how many days are written / complete
  check          the whole-project gate
  done N         refuse unless the day is genuinely finished, then commit
USAGE
    ;;
esac
```

**Line by line:**
- `#!/usr/bin/env bash` finds bash via the environment rather than assuming a fixed path — which is
  what makes the same file work on Windows Git Bash, macOS and the Linux notebook on Day 67.
- `set -euo pipefail` is four safety behaviours in one line, and it is the difference between a
  script and a hazard:
  - `-e` exits on the first failing command. Without it a failed lint step is *printed* and the
    script continues to the commit, which is the exact opposite of a gate.
  - `-u` errors on an undefined variable rather than substituting an empty string. Without it a typo
    in a variable name becomes an empty path, and `rm -rf "$TYPO/"` becomes `rm -rf /`.
  - `-o pipefail` makes a pipeline fail if **any** stage fails, not just the last. Without it,
    `failing_command | tee log` reports success.
- `"${1:-help}"` uses the first argument, defaulting to `help` when there is none — so bare `./m`
  prints usage instead of erroring. Discoverability is a feature you have to actually implement.
- `case` rather than a chain of `if`s: adding a command is one clause, and the `*)` fallback means an
  unknown command prints the usage rather than silently doing nothing.
- The `<<'USAGE'` here-document is **quoted**, so `$` and backticks inside are literal. Usage text is
  full of them.

## When it breaks

The loud failure, on the first run, on every machine:

```console
$ ./m check
bash: ./m: Permission denied
```

The file is not executable. Git tracks that bit, so fixing it once fixes it for everyone:

```bash
chmod +x m
git update-index --chmod=+x m
```

**Line by line:**
- `chmod +x` sets the bit locally.
- `git update-index --chmod=+x` records it **in git**, so a fresh clone is executable too. Without
  the second line, every new clone hits `Permission denied` and every new person concludes the
  repository is broken. On Windows the local bit is largely notional, which is exactly why the git
  half matters — the Day 67 notebook is Linux and will honour it.

The second loud one, on a file edited by a Windows editor:

```console
$ ./m status
bash: ./m: cannot execute: required file not found
```

Bewildering, because the file is plainly there. The cause is `\r\n` line endings: the kernel reads
the shebang as `/usr/bin/env bash\r` and looks for an interpreter whose name ends in a carriage
return. Fix and prevent:

```bash
sed -i 's/\r$//' m
printf 'm text eol=lf\n' >> .gitattributes
```

**Line by line:**
- `sed -i 's/\r$//'` strips the carriage return from the end of every line, in place.
- `.gitattributes` with `eol=lf` tells git to keep this file's line endings as LF regardless of
  platform settings — the durable fix, since the `sed` only repairs today's copy.

**The silent version.** `set -euo pipefail` is omitted. `./m check` runs the linter, the linter fails,
the failure scrolls past, the script continues, the tests run, they pass, and the last line prints
`OK all green`. The gate reported success on a repository that does not lint. Nothing is broken —
`bash` continued after a failing command because that is what `bash` does by default.

Detect it by asking the shell what the script actually returned, rather than reading what it printed:

```bash
./m check; echo "exit=$?"
```

**Line by line:**
- `$?` is the exit status of the previous command: `0` means success and anything else means failure.
- **The printed word is not the result; the exit code is.** Any automation — CI, `./m done` calling
  `./m check` — branches on the code, so a script whose text says "green" and whose code says `1` will
  behave one way for a human and another way for a machine.
- This is Silent Failure #4's shape from the plan's §6 arriving through tooling rather than through a
  seed: a green signal that measured nothing.

## In production

**What a research engineer does instead of the teaching version.** The driver stays thin and calls
real tools; it never grows logic of its own. The moment it wants a conditional, a loop over
directories or an argument parser, that part moves into `scripts/*.py` where it can be tested — which
is exactly what happens here with `depth_check.py`, `trace.py` and `tracker.py`. A driver that
accumulates business logic becomes an untested program at the root of the repository that everything
depends on and nobody reads. The rule of thumb: **the driver dispatches, the scripts decide.**

**What degrades at scale.** Two things. Commands multiply until nobody knows which are current, which
is why `./m` with no arguments prints the list — the usage text is the inventory, and a command
missing from it is effectively deleted. And the local gate drifts from CI, which is prevented by CI
running `./m check` rather than its own list of steps. That is the single highest-value line in a
pipeline configuration.

**The failure that only shows with real traffic.** Day 67's notebook is a different operating system
with a different shell and a different filesystem. A driver that quietly depends on a
platform-specific tool works for two months and then fails on the one day it is needed most. The
defence is boring: POSIX shell, no non-portable flags, and a `find` invocation that behaves the same
in both places.

**The review comment.** *"Does CI run this same command, or its own copy of the steps?"* If the answer
is "its own copy", the two lists have already begun to diverge and nobody has noticed yet.

**The interview question.** *"How does a new engineer find out how to run your project's tests?"* The
weak answer points at a README. The strong answer points at something **executable**, and explains
that prose can be wrong for a year while a script that is wrong fails today.

**Compute tier: T0.** Laptop CPU. The driver runs nothing that needs a GPU, and `./m check` is
required to stay that way — that constraint is what makes the gate runnable on the machine you
actually have.

## Check yourself

Run this. It prints the **number** of commands your repository currently advertises:

```bash
./m | grep -cE '^\s{2}[a-z]+'
```

**Line by line:**
- `./m` with no arguments hits the `*)` fallback and prints the usage block — which is the
  discoverability property being tested, not just a way of counting.
- `grep -cE '^\s{2}[a-z]+'` counts the indented command lines in that block.
- Compare the number against the table in *The mechanism*. **A command that exists in the `case` but
  not in the usage text is invisible**, and invisible is the same as absent for anyone who did not
  write it.

**Say this out loud, without scrolling up:** what does `set -e` prevent — and why is a driver that can
*refuse* to run more valuable than one that merely runs things?
