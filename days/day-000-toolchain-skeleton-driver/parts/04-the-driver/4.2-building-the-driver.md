# 4.2 — Building `./m`: resolving a day by number, and one gate that runs everything

## One-line answer

`./m` resolves a day by its **number** and accepts whatever slug follows, so folders can be renamed
freely — and `./m check` is a single command that runs lint, format, tests, the depth contract and
traceability, in that order, stopping at the first failure.

---

## The story

A project names its folders after their contents, which is a good decision. Two months in, somebody
finds a better name for one of them and renames it.

Six things break. A script constructed a path by joining a hard-coded folder name. A configuration
file listed the old name. Two documents linked to it. A test fixture pointed at it. None of these
failures are related to each other and none of them are interesting; they are all the same mistake
repeated, which is that the *name* was treated as the *identity*.

The person renames it back. The better name never happens, and neither does the next one, because
everyone has learned that renaming is expensive. Six months later the folder names are all slightly
wrong and nobody will touch them.

The fix is not to stop renaming. It is to decide, once, which part of a name is the identity and
which part is a label — and then make every tool respect that distinction.

---

## The idea in plain language

A day folder is `day-NNN-<slug>`: `day-000-toolchain-skeleton-driver`, `day-043-rope-and-alibi`.

- The **number** is the identity. It never changes. It comes from the plan's day map (§24).
- The **slug** is a label on it, for humans reading a file tree. It should change whenever a better
  one is found.

For that to be true rather than aspirational, every tool has to **resolve a day by its number and
tolerate any slug**. That means globbing `days/day-043-*` rather than constructing
`days/day-043-rope-and-alibi`. It is a small implementation detail with a large consequence:
renaming becomes free, so the names get better over time instead of worse.

Two related decisions from the plan, both of which show up in the code below:

**Three digits, zero-padded.** The plan runs to Day 161. With two digits, `day-9` sorts after
`day-100` in every listing, every editor tab bar and every glob — a papercut paid a hundred and
sixty-two times.

**One gate, ordered cheapest-first.** `./m check` runs five things. The order is deliberate: the fast
checks run first so that a formatting error is reported in a second rather than after the test suite.

---

## Why Akshara needs it

- **`./m start N`** is how you open a day, every day, for a hundred and sixty-one days. It has to
  work when the folder is called something you have forgotten.
- **`./m check`** is what CI will run and what `./m done` calls internally, so "the checks pass" has
  exactly one meaning (part [4.1](4.1-why-a-driver.md)).
- **The test step must survive an empty suite.** There are no tests until Day 59, and a gate that
  fails for fifty-nine days because there is nothing to test is a gate that gets bypassed and then
  ignored.
- **The test step must exclude GPU tests.** `CLAUDE.md` requires the gate to run on a laptop with no
  CUDA and no network. That is what makes T0 a guarantee.

---

## The mechanism

The day resolver first, because everything else uses it:

```bash
DAY="${2:-}"
pad() { printf "%03d" "$1"; }

daydir() {
  local n d
  n="$1"
  for d in "days/day-$(pad "$n")-"*; do
    [ -d "$d" ] && { echo "$d"; return; }
  done
  echo ""
}
```

**Line by line:**
- `DAY="${2:-}"` takes the second argument — `./m depth 43` — defaulting to empty. The `:-` is
  required because `set -u` from part [4.1](4.1-why-a-driver.md) would otherwise abort on an
  unset `$2` for commands like `./m check` that take no day.
- `pad()` turns `43` into `043` with `printf "%03d"`. This is why you can type `./m start 3` rather
  than `./m start 003` — the human types the number they think in, and the tool converts.
- `local n d` scopes the variables to the function. Without `local`, a variable named `d` leaks into
  the rest of the script and collides with whatever else uses that name — a bug that appears only
  when the script grows.
- The `for d in "days/day-043-"*` glob is the whole idea of this part: it matches **whatever slug
  follows the number**. Rename the folder and this keeps working.
- `[ -d "$d" ] &&` guards the case where nothing matches. An unmatched glob in bash expands to the
  literal pattern text, so without the directory test you would return the string
  `days/day-043-*` as if it were a path.
- `echo ""` on failure lets the caller test for an empty result, which is simpler to handle than an
  exit code in a function whose output you are capturing.

Now the gate:

```bash
check)
  uv run ruff check .
  uv run ruff format --check .
  uv run python -m pytest -q -m "not gpu" || [ $? -eq 5 ]
  uv run python scripts/depth_check.py
  uv run python scripts/trace.py
  echo "OK all green"
  ;;
```

**Line by line:**
- Every command starts with `uv run`, per part
  [1.2](../01-the-toolchain/1.2-uv-owns-the-environment.md). The gate must use the project's
  environment, not whatever the shell resolves to.
- `ruff check` is the linter; `ruff format --check` verifies formatting **without rewriting**. The
  `--check` matters: a gate that silently reformats your files is a gate that changes the thing it is
  measuring.
- Lint before tests because it is faster. With `set -e` the script stops at the first failure, so
  ordering by speed means the common failure is reported quickly.
- `-m "not gpu"` excludes tests marked `gpu`, which is what keeps the gate honest on a laptop. The
  marker is declared in `pyproject.toml`
  ([2.2](../02-the-skeleton/2.2-one-file-owns-the-config.md)) with `--strict-markers`, so a
  misspelled marker is an error rather than a silent inclusion.
- `|| [ $? -eq 5 ]` is the empty-suite escape hatch and it deserves its own explanation. **pytest
  exits `5` when it collected no tests.** Before Day 59 that is the correct and expected state. This
  clause says: succeed on `0`, succeed on `5`, fail on everything else. Writing `|| true` instead
  would have swallowed *every* test failure for the rest of the project — the difference between a
  precise exception and a disabled check.
- `depth_check.py` and `trace.py` come last because they are the slowest and the most likely to be
  green.
- `echo "OK all green"` only runs if everything before it succeeded, because `set -e` aborts
  otherwise. The message is a consequence of success, not a claim about it.

And the dispatch for the day-based commands:

```bash
start)
  [ -z "$DAY" ] && { echo "usage: ./m start <day>"; exit 1; }
  D="$(daydir "$DAY")"
  [ -n "$D" ] || { echo "no day $DAY yet - see docs/TRACKER.md"; exit 1; }
  if [ -f "$D/LESSON.md" ] && [ -d "$D/parts" ]; then
    echo "-> open $D/LESSON.md   (the hub - read its §2 map, then the parts in order)"
    find "$D/parts" -name '*.md' | sort | sed "s|^$D/|     |"
  else
    echo "day $DAY has no hub + parts/ - it is not written (plan §25.2)"; exit 1
  fi
  ;;
```

**Line by line:**
- `[ -z "$DAY" ]` catches `./m start` with no number and prints usage rather than failing obscurely
  three lines later.
- `[ -n "$D" ] ||` handles a day that does not exist yet, and points at the tracker rather than just
  saying no — an error message that tells you where to look is worth the extra words.
- The `if [ -f ... ] && [ -d ... ]` test encodes the plan's §25.2 rule that **a day without `parts/`
  is not written.** The driver refuses to open a folder that only looks like a day, which is a small
  instance of the "it can refuse" property from part [4.1](4.1-why-a-driver.md).
- `find | sort` lists the parts in numerical order; the `sed` strips the directory prefix and indents,
  so the output is a readable table of contents rather than a wall of paths.

## When it breaks

The loud failure that catches everyone once:

```console
$ ./m start 3
no day 3 yet - see docs/TRACKER.md for what is written
```

Two very different causes, one message. Either the day genuinely is not written, or it **is** written
and the folder is named `day-03-...` with two digits instead of three, so the `day-003-*` glob misses
it. Distinguish them without guessing:

```bash
ls -d days/day-*3* 2>/dev/null
```

**Line by line:**
- A loose glob shows what is actually on disk regardless of padding.
- If a two-digit folder appears, rename it to three digits. `./m depth` rejects two-digit folders on
  purpose (plan §25.9), so this fails fast rather than sorting wrongly forever.

The second loud one, on a day that was created by hand:

```console
$ ./m start 5
day 5 has no hub + parts/ - it is not written (plan §25.2)
```

This is the driver enforcing the depth contract's most basic rule, and it is doing its job.

**The silent version, which is why `|| [ $? -eq 5 ]` is written the way it is.** Replace that clause
with `|| true` and the gate reports success no matter what the tests did:

```console
$ ./m check
1 failed, 3 passed
OK all green
```

Both lines are printed. The failure is visible to a human reading the scroll-back and invisible to
everything else — `./m done` calls `./m check` and branches on the **exit code**, which is now `0`.
The day commits with a failing test. Detect it by checking the code, not the text:

```bash
./m check > /dev/null 2>&1; echo "exit=$?"
```

**Line by line:**
- Discarding the output forces you to judge by the exit status alone, which is exactly how every
  automated caller judges it.
- `exit=0` with a failing test underneath is Silent Failure #4's shape from the plan's §6: a green
  signal that measured nothing. **The word is not the result. The code is.**

## In production

**What a research engineer does instead of the teaching version.** They keep the driver dispatch-only
and push anything with logic into `scripts/*.py`, where it can be unit-tested. Shell is excellent at
"run these five things in order and stop on failure" and poor at anything with branching, because
shell has no tests and its failure modes are quiet. The line in this project sits exactly where
`depth_check.py` starts: the driver decides *what* runs, the Python decides *whether it passed*.

**What degrades at scale.** The gate gets slower and people stop running it locally, which is the
beginning of the end — a gate only runs before every commit if it is fast enough to tolerate. The
standard remedy is tiering: a fast gate on every commit, a full one in CI. This project keeps one gate
and pays for it by keeping the test suite CPU-only and offline, which is a constraint doing double
duty: it also makes the suite runnable on the Day 67 notebook.

**The failure that only shows with real traffic.** `find`, `sed` and `printf` differ between GNU and
BSD userlands, so a driver written on Linux can break on macOS and vice versa. This one sticks to
flags that behave identically on both, which is why the `find` call has no `-printf` and the `sed`
uses `|` as its delimiter — paths contain slashes, and a `/`-delimited `sed` on a path is a bug
waiting for the first directory with a slash in the wrong place.

**The review comment.** *"Why `|| [ $? -eq 5 ]` and not `|| true`?"* The answer is the whole
difference between an exception and a disabled check, and it is worth a comment in the file itself —
which is why the real `m` in this repository has one.

**The interview question.** *"Your CI is green but production is broken. Where do you look first?"* A
strong answer includes: whether the gate actually ran anything. Empty test suites, filters matching
nothing, and swallowed exit codes all report green, and all three are more common than a genuinely
undetected bug.

**Compute tier: T0.** Laptop CPU. `-m "not gpu"` in the gate is precisely the line that guarantees it.

## Check yourself

Run this. It prints the **exit code** of the gate — the number every automated caller actually reads:

```bash
./m check; echo "exit=$?"
```

**Line by line:**
- `0` means genuinely green: lint clean, format clean, tests passed or collected nothing, depth
  contract satisfied, traceability consistent.
- Anything else is a real failure, and `set -e` means the script stopped at it — so the last thing
  printed before the code is the thing that failed.
- Today the test step contributes exit `5` internally, converted to success by the clause above.
  **Know that this is happening**, because from Day 59 it will not be, and a gate whose behaviour you
  cannot predict is not a gate.

**Say this out loud, without scrolling up:** why does `./m` glob `days/day-043-*` instead of building
the full folder name — and what exactly would `|| true` have broken?
