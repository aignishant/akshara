# 2.2 — pyproject.toml: one file owns the dependencies and the tool settings

## One-line answer

`pyproject.toml` is the single file that declares what this project is, what it depends on, and how
every tool that touches it should behave — so that "what are the rules here?" has one answer stored
in git rather than several answers stored in people's habits.

---

## The story

A project accumulates configuration the way a coat accumulates receipts.

The linter's settings live in a dotfile at the root. The formatter has its own dotfile, with a line
length that disagrees with the linter's by two characters, which nobody notices until a tool
reformats a file and the other tool objects to the result. The test runner reads a third file. The
line length is also hard-coded in the editor settings of three people, differently.

Then someone joins, runs the linter, and gets four hundred errors on code that passes in the
project's own automation — because their editor is applying its own defaults and the project's
config file is not where their tool looks.

Nothing here is broken. Every tool is correctly reading its own configuration. **The problem is that
"the project's rules" is not a thing that exists** — there are only several tools' opinions, stored
separately, agreeing by coincidence and drifting without a sound.

---

## The idea in plain language

`pyproject.toml` is a standard file at the root of a Python project. It has two jobs, and it is worth
keeping them separate in your head because they fail differently.

**Job one: declare the project.** Its name, its Python requirement, and its dependencies. This is
what `uv sync` reads to decide what to install (see
[1.2](../01-the-toolchain/1.2-uv-owns-the-environment.md)).

**Job two: hold every tool's settings**, in `[tool.<name>]` sections. The linter, the formatter and
the test runner all agreed to look here, which means one file can be the answer to "what are the
rules?" instead of four.

`toml` is the format — a config format built for exactly this: sections in square brackets,
`key = value` inside them, lists in square brackets, comments after `#`. You do not need to learn it
beyond that.

One distinction matters for the rest of this curriculum. A dependency belongs in one of two places:

- **`dependencies`** — the project genuinely cannot run without it. `torch` will live here.
- **`[dependency-groups] dev`** — needed to *develop* the project, not to run it. The linter and the
  test runner live here.

The difference is not bookkeeping. On Day 156 the model gets containerized, and the container
installs the first list and not the second. A test runner that crept into `dependencies` ships to
production inside your image; a `torch` that crept into `dev` produces a container that cannot run
the model.

---

## Why Akshara needs it

Three specific things this file has to be true for, all of them later:

- **Day 59** introduces unit tests for numerical code and the plan requires the default gate to run
  **CPU-only, offline, deterministically** (`CLAUDE.md`). That is enforced by pytest *markers*
  declared in this file: a test that needs a GPU is marked, and the gate excludes it. Without the
  declaration, `-m "not gpu"` silently matches nothing and the gate quietly stops excluding anything
  — a check that passes because it tested nothing.
- **Day 67** runs on a free notebook that rebuilds from zero. `uv sync` there reads this file plus
  the lockfile, and nothing else. Any rule that lives in your editor rather than in this file does
  not exist on that machine.
- **Every day from 2 onward** adds at most one or two packages, pinned with `==`, on the day they
  are first used and only after the hand-rolled version exists (Principle 3). This file is where the
  pin goes, and `docs/PACKAGES.md` is where the observation goes
  ([1.3](../01-the-toolchain/1.3-observed-is-not-available.md)).

---

## The mechanism

Write the file. It is longer than it needs to be today and every line will earn its place:

```toml
[project]
name = "akshara"
version = "0.1.0"
description = "Generative AI from the byte up"
requires-python = "==3.12.*"

# Principle 6: never invent a version. Every dependency arrives on the day it is first
# used, after the hand-rolled version exists (Principle 3), pinned with `==` to the
# version actually observed, with a dated row in docs/PACKAGES.md.
# This list starts EMPTY on purpose.
dependencies = []

[dependency-groups]
dev = []

[tool.uv]
package = true
```

**Line by line:**
- `name` and `version` are what make this an installable package rather than a folder of scripts.
  `[tool.uv] package = true` then tells `uv` to install `akshara/` **into the environment**, which is
  what lets `from akshara.model import GPT` work from a test, a script or a notebook without anyone
  fiddling with `sys.path`. That fiddling is the usual reason a notebook and a test import different
  copies of the same file.
- `requires-python = "==3.12.*"` pins the minor version and accepts any patch. `==3.12.*` rather than
  `>=3.12` is deliberate: a floating upper bound means a future 3.13 silently becomes eligible, and
  a changed interpreter is a changed experiment (Principle 14 — that would be an amendment, not an
  upgrade).
- `dependencies = []` is **the most important line in the file today.** Empty is a decision. Packages
  arrive one at a time, each on the day its hand-rolled version has already been built, which is what
  keeps the comparison days honest. A project that installs `torch` on day zero has already skipped
  the argument.
- `dev = []` is the same decision for tooling, and it fills in below.
- The comment is in the file rather than in this document because the rule has to be visible at the
  moment somebody is tempted to break it.

Now the tool sections. Add them to the same file:

```toml
[tool.ruff]
line-length = 100
target-version = "py312"
extend-exclude = ["notebooks", "days"]

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "SIM", "PTH", "RUF"]
ignore = ["E501"]

[tool.ruff.lint.per-file-ignores]
"days/**/lab/*.py" = ["ALL"]

[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = "-q --strict-markers"
markers = [
    "gpu: requires a CUDA device — excluded from `./m check`",
    "slow: too slow for the default gate",
    "download: needs the network — excluded from `./m check`",
]
```

**Line by line:**
- `line-length = 100` appears **once**, and both the linter and the formatter read it from here. That
  single fact is what the story at the top of this part was about.
- `extend-exclude = ["notebooks", "days"]` — teaching code and notebook code are written to be
  *read*, and linting them would push them toward being written to be *linted*. A three-line loop
  that shows a mechanism should survive review even where a vectorized one-liner would score better.
- `select` turns on rule families: `E`/`F` are the classic error checks, `I` sorts imports, `UP`
  modernises syntax, `B` catches likely bugs, `SIM` simplifications, `PTH` prefers `pathlib`, `RUF`
  the tool's own rules. Naming them explicitly means adding a family is a visible commit rather than
  a surprise from an upgrade.
- `ignore = ["E501"]` switches off "line too long" because the **formatter** owns line length. Two
  tools enforcing the same rule is how you get a file that cannot satisfy both.
- `per-file-ignores` for `days/**/lab/*.py` — the learner's own scratch code is exempt entirely. A
  linter that shouts at somebody's first attempt at backpropagation is a linter that gets disabled.
- `--strict-markers` is the line that matters most in the pytest block. Without it, a typo in
  `@pytest.mark.gpu` — say `@pytest.mark.gpo` — is silently accepted, the gate's `-m "not gpu"` does
  not exclude it, and a GPU test runs in a CPU-only gate. With it, the typo is an error.
- The three `markers` are declared here so `--strict-markers` has something to be strict about, and
  each says *why* it is excluded. `gpu` and `download` exist because the gate must run on a laptop
  with no CUDA and no network.

Verify the file is read, rather than assuming:

```bash
uv sync
uv run ruff check --show-settings . 2>/dev/null | grep -i "line.width\|line_length" | head -2
uv run python -m pytest --markers | head -4
```

**Line by line:**
- `ruff check --show-settings` prints the configuration ruff **resolved**, not the configuration you
  wrote. This is [1.3](../01-the-toolchain/1.3-observed-is-not-available.md)'s habit applied to
  config: ask the tool what it believes.
- `pytest --markers` lists the markers pytest knows about. Your three should appear. If they do not,
  pytest is reading a different config file — or none — and `--strict-markers` is protecting nothing.

## When it breaks

The loud failure, and the reason `--strict-markers` is worth the line:

```console
$ uv run python -m pytest -q
'gpu' not found in `markers` configuration option
```

A test used a marker that is not declared. Under strict mode this is an error rather than a warning,
which is the entire point — the alternative is the silent version below.

The other loud one, on a fresh clone:

```console
$ uv run python -c "import akshara"
ModuleNotFoundError: No module named 'akshara'
```

Almost always `[tool.uv] package = true` is missing, so `uv` created an environment but never
installed *this* project into it. `uv sync` after adding the line fixes it.

**The silent version, which is the dangerous one here.** Drop `--strict-markers`. Misspell a marker
on a GPU-requiring test. Now:

```console
$ uv run python -m pytest -q -m "not gpu"
....                                                     [100%]
4 passed
```

Four passed. Green. And the GPU test ran inside a gate that was supposed to exclude it — or, on a
machine without CUDA, it errored in a way that got attributed to something else. Worse is the
inverse: a marker filter that matches nothing at all reports success while testing nothing, and
"green" is indistinguishable from "empty". Detect it by asking how many tests were actually
**selected**:

```bash
uv run python -m pytest -m "not gpu" --collect-only -q | tail -2
```

**Line by line:**
- `--collect-only` finds tests without running them, so the last line reports how many the filter
  selected.
- A count of `0` next to a passing gate is the shape of Silent Failure #4 from the plan's §6 — you
  have not measured an improvement, you have measured nothing, and both print green. **Always know
  the number of tests your gate ran**, not just its colour.

## In production

**What a research engineer does instead of the teaching version.** They treat this file as the
project's public interface and review changes to it more carefully than changes to code. A new
dependency is a supply-chain decision (Principle 13), a changed pin is a changed experiment, and a
loosened lint rule is a permanent one. On larger projects the dev group splits further — `test`,
`lint`, `docs` — so CI jobs install only what they need and a slow job does not wait on an unrelated
package.

**What degrades at scale.** Two things. Dependency groups drift into `dependencies` because it is one
character shorter to put them there, and the container on Day 156 quietly grows by a gigabyte.
And `ignore` grows: every ignored rule was added for one file on one afternoon and then applied to
the whole project forever. `per-file-ignores` is the mechanism that keeps an exception local; the
review question is always *"does this need to be global?"*, and the answer is almost always no.

**The failure that only shows with real traffic.** `requires-python` is the field that decides
whether the free notebook on Day 67 can even resolve your environment. Colab's interpreter moves
without asking, and a pin of `==3.12.*` there means the day either works or fails *immediately and
loudly*, which is what you want on metered hardware. A loose `>=3.10` means it resolves to whatever
that machine has and you find out from the numbers, later, quietly.

**The review comment.** *"This adds a dependency — which day's document introduces it, is it pinned
with `==`, and is there a `docs/PACKAGES.md` row?"* Three questions that are really one question:
can somebody reproduce this in six months.

**The interview question.** *"How do you stop a test suite from passing because it ran nothing?"* The
answer is `--strict-markers` plus checking the collected count, and what is being probed is whether
you have ever been fooled by a green tick. Everyone has. The useful part is what you changed
afterwards.

**Compute tier: T0.** Laptop CPU. The pytest markers configured here are precisely what keeps the
gate runnable on a machine with no GPU, which is what makes T0 a real guarantee rather than an
aspiration.

## Check yourself

Run this. It prints two **numbers**: how many tools read their settings from this one file, and how
many tests your gate would actually select:

```bash
grep -c '^\[tool\.' pyproject.toml
uv run python -m pytest -m "not gpu" --collect-only -q 2>/dev/null | tail -1
```

**Line by line:**
- The first counts `[tool.*]` sections — every one is a tool whose behaviour is now stored in git
  instead of in somebody's editor.
- The second is the count of tests the default gate would run. **Today it is zero, and that is
  correct** — there are no tests until Day 59. Write the number down, because a gate that reports
  green while selecting zero tests is only acceptable while you *know* it is zero.

**Say this out loud, without scrolling up:** what does `--strict-markers` actually prevent — and why
is a passing test suite that selected zero tests worse than a failing one?
