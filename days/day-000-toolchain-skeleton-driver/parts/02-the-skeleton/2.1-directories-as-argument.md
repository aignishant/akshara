# 2.1 — The skeleton: every directory is an argument about what belongs where

## One-line answer

A directory layout is not filing — it is a set of decisions about **what is allowed to live next to
what**, made once at the start when they are free, because the alternative is making them a hundred
and sixty times under pressure and differently each time.

---

## The story

A project starts as one file. Then a second file, next to it. Then a folder, because there are now
nine files and nine is too many to look at.

Six months later somebody new opens the repository and cannot find where the real work happens.
There is a folder of scripts, and a folder of notebooks that also contains scripts, and a folder of
utilities that everything imports and nobody owns. There is a file at the top level with a name that
made sense to one person on one afternoon. There are three places a new function could plausibly go
and no way to choose between them, so it goes wherever the last similar function went, which is how
the fourth place gets created.

Nobody made a bad decision. **Nobody made a decision at all** — each file went somewhere reasonable
given the files that already existed, and the layout is the accumulated residue of a hundred local
choices, none of which was ever about the layout.

The cost is not tidiness. The cost is that "where does this go?" becomes a question with no answer,
and a question with no answer gets a different answer every time it is asked.

---

## The idea in plain language

A directory is a claim. `tests/` claims that things inside it are tests, which really means: things
inside it are allowed to be slow, allowed to import anything, and not allowed to be imported *by*
anything. That is a rule about dependencies wearing the costume of a folder.

The useful way to read a layout is to ask, for each directory, **what would be wrong to put here**.
A directory that cannot answer that is not doing any work.

Three ideas make the layout in this project legible.

**Separation by lifecycle, not by topic.** The obvious way to organise is by subject — put everything
about tokenizers together. The better way is by *how the thing changes*: code you write and rewrite,
configuration that must be reproducible, artifacts that are outputs, teaching that is append-only.
Things with the same lifecycle belong together because they are backed up, ignored, reviewed and
deleted together.

**The commit boundary is a real boundary.** Some things go in git and some things must never
(Principle 9: weights and data never are). That line runs straight through the layout, and a layout
that ignores it means the rule depends on people remembering it.

**Generated and hand-written never mix.** A directory holding both is a directory where someone will
eventually hand-edit an output and lose the edit, silently, on the next regeneration.

---

## Why Akshara needs it

This repository has a harder version of the problem than most software projects, because it holds
five kinds of thing that behave completely differently:

| Kind | Changes when | Committed? | Regenerated? |
| --- | --- | --- | --- |
| Model code (`akshara/`) | you write a day | yes | no |
| Run configuration (`configs/`) | you launch a run | **yes** | no |
| Artifacts (weights, data) | every run | **never** | not by us |
| Teaching (`days/`) | a day is written | yes, append-only | no |
| Ledgers (`docs/`) | a day finishes | yes | **three of them are** |

A single flat folder makes those five indistinguishable, and the consequence is not aesthetic. It is
that a 400MB checkpoint ends up in git history, permanently, and the repository becomes
unclonable — the specific failure part [3.2](../03-gitignore-first/3.2-the-checkpoint-that-cannot-be-removed.md)
is about.

Concretely later:

- **Day 39** builds the model, and the day document says *"create `akshara/model/attention.py`"*.
  That instruction only works if the layout already exists and means something.
- **Day 64** writes a tokenized corpus to disk. It goes to `data/`, which is ignored, and the
  document has to be able to say so without inventing a convention on the spot.
- **Day 67** produces a checkpoint and a `docs/RUNS.md` row. The checkpoint is outside git; the
  config that produced it is inside. That pairing is the whole of Principle 9 and it is expressed as
  two directories.

---

## The mechanism

Create it. Every directory, in one command, before anything needs it:

```bash
mkdir -p akshara/{tokenizer,model,train,infer,eval,serve} \
         configs scripts tests notebooks \
         days docs/adr
```

**Line by line:**
- `mkdir -p` creates parents as needed and does not complain if a directory already exists, which
  makes the command safe to re-run. A setup command you are afraid to run twice is a setup command
  you will hesitate over.
- `akshara/{tokenizer,model,train,infer,eval,serve}` is brace expansion — the shell rewrites it into
  six paths. The six subpackages are the **pipeline stages**, in the order the curriculum builds
  them: text becomes tokens, tokens become predictions, predictions get trained, trained models get
  sampled, samples get scored, scores get served.
- The backslashes continue the line. One command rather than three keeps the layout a single
  decision rather than three separate ones.
- `docs/adr` is created now, before there is an ADR, because a decisions folder that appears later
  implies decisions before it did not need recording. They did.
- Notice what is **not** here: no `data/`, no `checkpoints/`, no `runs/`. Those are created by the
  code that writes to them, and they are ignored by git. Creating them now would invite committing
  them.

What each directory claims, and what would be wrong to put in it:

| Directory | Holds | Wrong to put here |
| --- | --- | --- |
| `akshara/` | the model package — every line typed by you from a day document | anything generated; anything that only runs once |
| `configs/` | one file per training run, committed | the outputs those configs produced |
| `scripts/` | repo tooling: the depth check, the trace and tracker generators | model code — if it imports `akshara`, it is not tooling |
| `tests/` | pytest, CPU-only, deterministic, offline | anything that downloads or needs a GPU without a marker |
| `notebooks/` | Colab/Kaggle notebooks, output stripped before commit | the only copy of any logic (see the discipline on Day 1) |
| `days/` | the teaching — one folder per day, append-only | project code; the learner types that from the document |
| `docs/` | the plan, the ledgers, the ADRs | anything a script regenerates *and* a human edits |

Python needs one more thing before `akshara/` is importable:

```bash
touch akshara/__init__.py akshara/{tokenizer,model,train,infer,eval,serve}/__init__.py
touch tests/__init__.py
```

**Line by line:**
- `__init__.py` is what makes a directory a package Python can import from. Without it,
  `from akshara.model import GPT` fails on Day 39 with a `ModuleNotFoundError` that looks like a
  missing install and is actually a missing file.
- `touch` creates an empty file, or leaves an existing one alone. Empty is correct: these files
  exist to mark a boundary, not to hold code.
- `tests/__init__.py` prevents two test files with the same name in different directories from
  colliding — a failure that produces a confusing "duplicate basename" error much later, on the day
  you least want to debug your test runner.

## When it breaks

The loud failure, on the day the layout is first used in anger:

```console
$ uv run python -c "from akshara.model import GPT"
Traceback (most recent call last):
  File "<string>", line 1, in <module>
ModuleNotFoundError: No module named 'akshara'
```

Two different causes produce this identical message, which is why it wastes time. Either the package
is not installed into the environment (fixed by `uv sync`, given `pyproject.toml` declares the
project — part [2.2](2.2-one-file-owns-the-config.md)), or the directory exists but has no
`__init__.py`. Distinguish them without guessing:

```bash
uv run python -c "import akshara, pathlib; print(pathlib.Path(akshara.__file__).parent)"
```

**Line by line:**
- If this prints a path, the package is importable and your problem is a **sub**module — a missing
  `__init__.py` one level down.
- If it raises the same `ModuleNotFoundError`, the package itself is not on the path and the problem
  is the environment, not the layout.
- `akshara.__file__` is the observation habit from
  [1.3](../01-the-toolchain/1.3-observed-is-not-available.md) applied to imports: ask the object
  where it came from rather than assuming which copy answered.

**The silent version.** Two directories both look like plausible homes for the same module, so the
same logic gets written twice — once in `akshara/train/` and once inside a notebook. Both work. They
drift. Weeks later a fix lands in one of them and the run that mattered used the other. Nothing
errors, the loss curve looks fine, and the model you shipped was trained by the copy nobody was
maintaining. The detection is uncomfortable and cheap:

```bash
grep -rn "def train_step" --include=*.py --include=*.ipynb . | grep -v '\.venv'
```

**Line by line:**
- Any function that matters should appear **once**. More than one hit is a fork you did not decide
  to create.
- `--include=*.ipynb` is deliberate: notebooks are where the second copy always lives, because a
  notebook is the easiest place to paste something rather than import it. Day 1's notebook discipline
  exists for exactly this.

## In production

**What a research engineer does instead of the teaching version.** They enforce the layout with
imports rather than with goodwill. `scripts/` may not import `akshara`; `akshara/` may not import
from `notebooks/`; `tests/` may import anything and be imported by nothing. On a larger codebase
these become lint rules that fail CI, because a layout that depends on everyone remembering it
degrades at exactly the rate the team grows.

**What degrades at scale.** The specific decay is that `utils/` appears. It is always `utils/`. It
starts as two functions with no obvious home and becomes the module everything imports and nobody
owns, at which point it is a circular-dependency generator with a friendly name. The defence is the
question this part opened with: a directory must be able to say what would be **wrong** to put in it,
and `utils/` cannot.

**The failure that only shows with real data.** `data/` and `checkpoints/` are absent from the
skeleton on purpose, and their absence is load-bearing. The moment they exist inside the repository
tree, someone runs `git add -A` on a tired evening. Part
[3.1](../03-gitignore-first/3.1-ignore-before-it-exists.md) is the mechanism that makes that
survivable; the layout is the first line of defence, and `./m done` is the last.

**The review comment.** *"Why is this in `scripts/` and not in `akshara/`? Does anything import
it?"* The dependency direction is the real question — "is it library code or is it tooling?" — and
the folder is just where the answer got written down.

**The interview question.** *"Walk me through your repo layout."* What is being probed is not
tidiness; it is whether you can name the **constraint** each directory encodes. "Configs are
committed and checkpoints never are, because the repo has to reproduce a model without containing
one" is an answer about engineering. "That's where the configs go" is an answer about filing.

**Compute tier: T0.** Laptop CPU. Creating directories needs nothing, and the layout is what makes
the T1 notebook on Day 67 able to find the code it is supposed to run.

## Check yourself

Run this. It prints the **number** of directories the skeleton claims, and the number of packages
Python can actually see:

```bash
find akshara scripts tests configs days docs notebooks -type d | wc -l
uv run python -c "import pkgutil, akshara; print(sum(1 for _ in pkgutil.iter_modules(akshara.__path__)))"
```

**Line by line:**
- The first number counts directories on disk — the claim you just made.
- `pkgutil.iter_modules` walks the package and counts importable submodules — the claim Python
  actually believes. It should be `6`, one per pipeline stage.
- When the second number is lower than you expect, an `__init__.py` is missing, and you have found it
  now rather than on Day 39 in the middle of building a transformer.

**Say this out loud, without scrolling up:** pick any two directories in the table and say what would
be **wrong** to put in each — then say which line in the layout is the one that keeps a checkpoint
out of git history.
