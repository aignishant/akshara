# 1.3 — Observed is not available: the first bite of "never invent a version"

## One-line answer

A tool that *lists* a version is telling you what it could fetch, not what you have — and the version
that goes in the ledger is always the one you **observed running**, because Principle 6 records
reality rather than availability.

---

## The story

Someone writes down the version of a component in a report. They got the number from the tool's own
listing, which is about as authoritative a source as exists. The number is correct: that version is
real, it is published, the listing is not lying.

Months later the report will not reproduce. The investigation takes two days and ends somewhere
mildly humiliating: the listing was showing what was **available to download**, and the machine had
never downloaded it. It had been running a slightly older one the whole time. Every command
succeeded. Every output was real. The one number that was wrong was the one written down, and it was
wrong in a way that was invisible from the report itself, because the report had no way to say
"this is what I could have had" versus "this is what I ran".

The lesson is not "check twice". It is that **a listing and a running process answer different
questions**, and only one of them is evidence.

---

## The idea in plain language

Two questions look identical and are not:

| Question | What answers it | What it is |
| --- | --- | --- |
| *What version could I get?* | a listing, a registry, a docs page, a changelog | **availability** |
| *What version is running?* | the process itself, reporting on itself | **observation** |

Availability is a fact about the world. Observation is a fact about your machine. They agree most of
the time, which is precisely what makes the disagreement dangerous: a habit that works ninety-nine
times teaches you to stop checking on the hundredth.

Principle 6 of the plan says *never invent a version number*. The word "invent" is doing more work
than it first appears. Recalling a version from memory is obviously inventing. But **copying a
version from a listing is also inventing**, in the sense that matters: you have written down a number
you did not verify was in use. The ledger's job is to record what produced the result, and only the
running process knows that.

So the rule has a sharper form than "look it up":

> Record the version that **answered**, not the version that was **offered**.

---

## Why Akshara needs it

Because you are going to hit this today, on this machine, with this toolchain — it is not a
hypothetical.

Run the interpreter listing and read it carefully:

```console
$ uv python list | grep 3.12
cpython-3.12.13-windows-x86_64-none    <download available>
cpython-3.12.12-windows-x86_64-none    C:\Users\...\uv\python\cpython-3.12-...\python.exe
cpython-3.12.10-windows-x86_64-none    C:\Users\...\Python\Python312\python.exe
```

The highest 3.12 in that list is **3.12.13**, and it is the obvious number to write down. It is also
wrong. The right-hand column says `<download available>` — that interpreter is not on the machine.
The one `uv` will actually run is **3.12.12**, the highest that has a path instead of a promise.

This document observed exactly that on `2026-08-25` [measured here: Windows 11, `uv python list`].
Your listing will differ, and yours is the one that counts.

Where it bites later:

- **Day 67**, the pretraining run, produces a `docs/RUNS.md` row. If the environment column records
  an interpreter that was never installed, the row is decorative.
- **Day 145** studies supply-chain attacks against model checkpoints. The habit you are building
  here — *verify the artifact, not the announcement* — is the same habit that day depends on, applied
  to weights instead of interpreters.
- **Every `docs/PACKAGES.md` row for the next 161 days** is generated by this rule.

## The mechanism

Ask the running process, always. Three commands, one per kind of thing you will need to record:

```bash
# 1 — the interpreter that actually answers
uv run python -c "import sys; print(sys.version.split()[0])"

# 2 — a package that is actually importable
uv run python -c "import importlib.metadata as m; print(m.version('ruff'))"

# 3 — a tool that is actually on the path
uv --version
```

**Line by line:**
- `sys.version.split()[0]` trims the full version banner — which also contains the build date and
  compiler — down to just `3.12.12`. The full string is useful in a bug report; the short one is what
  a ledger column holds.
- `importlib.metadata.version` reads the metadata of the **installed** distribution, from the
  environment. It is the package-level equivalent of `sys.executable`: the environment reporting on
  itself rather than a config file stating an intention.
- Note what is *not* here: no `pip show`, no reading `pyproject.toml`, no listing. Those answer the
  availability question. All three commands above answer the observation question.
- `uv --version` is the exception that proves the rule — `uv` is a single binary outside the
  environment, so the binary reporting on itself *is* the observation.

Now the shape of a ledger row, which is where the observation goes:

```text
| Package | Version  | Date       | Day | Why                                              |
| ------- | -------- | ---------- | --- | ------------------------------------------------ |
| uv      | 0.12.3   | 2026-08-25 | 0   | One binary owns the environment. `uv --version`.  |
| python  | 3.12.12  | 2026-08-25 | 0   | Runtime. Observed with sys.version, NOT the list. |
```

Four columns, and every one of them is load-bearing. The version is the observation. The **date** is
what makes it falsifiable later — "3.12.12 on 2026-08-25" is a claim you can check against, whereas
"3.12.12" alone quietly implies "still". The day ties it to the document that added it. The `Why`
records what you would need to know before removing it.

And when a lookup genuinely fails — no network, a registry down — the rule does not bend into a
guess. It bends into a `TODO` **containing the command**:

```text
| torch | TODO(uv run python -c "import torch; print(torch.__version__)") | — | 57 | Pending install |
```

That row is honest and actionable. A row saying `torch | 2.x | ...` from memory is neither.

## When it breaks

The loud failure, when you ask about something that is not installed:

```console
$ uv run python -c "import importlib.metadata as m; print(m.version('torch'))"
Traceback (most recent call last):
  ...
importlib.metadata.PackageNotFoundError: No package metadata was found for torch
```

`PackageNotFoundError` is the observation question answering honestly: *nothing here.* This is the
correct outcome on Day 0, where `torch` has not arrived yet — and it is the answer you want, because
the alternative is a tool that cheerfully reports a version for something you cannot import.

**The silent version, which is this part's whole subject.** Nothing errors. You copy `3.12.13` from
the listing into `docs/PACKAGES.md`, every command on the machine keeps working, and the ledger now
contains a version that has never run on your computer. There is no traceback, because nothing is
broken — you simply wrote down a different true fact than the one you needed.

This is **Silent Failure #4** — *noise mistaken for improvement* — arriving through the environment
rather than through a seed. Two runs recorded under "3.12.13" that were actually 3.12.12 and 3.12.13
would be compared as though the environment were held constant. The detection is the diff:

```bash
uv python list | grep -c "<download available>"
uv run python -c "import sys; print(sys.version.split()[0])"
```

**Line by line:**
- The first line counts how many interpreters in your listing are **promises rather than files**.
  Any number above zero means the listing contains entries you must not copy from.
- The second line is the answer you are allowed to record. If it does not match the top of the
  listing, you have just personally reproduced the failure in this part's story, which is the best
  possible way to learn it.

## In production

**What a research engineer does instead of the teaching version.** They stop transcribing versions by
hand at all. The environment emits its own manifest at the start of every run — interpreter, key
package versions, git commit, hardware — and that manifest is written next to the outputs. A human
copying a number into a table is a step that can be skipped under pressure; a run that refuses to
start without recording what it is has no such failure mode. `docs/RUNS.md` in this project is the
hand-operated version of that, and the ledger row is deliberately small enough to survive being
written by a tired person at the end of a day.

**What degrades at scale.** One version in one table is easy to keep true. A dozen packages across a
dozen experiments is not, and the entries that go stale are never the ones you are looking at — they
are the ones from three months ago that you are now trying to compare against. Staleness in a ledger
is invisible by construction, which is why every row carries a date: the date does not prevent
staleness, it makes staleness **detectable**.

**The failure that only shows with real traffic.** A pinned version resolves to different *builds* on
different platforms — a CUDA wheel here, a CPU wheel there — with the same version string. Your
laptop and the Day 67 notebook will genuinely do this. At that point the version number stops being
sufficient on its own and the hardware column in `RUNS.md` is carrying real information, which is why
it exists.

**The review comment.** *"Where did this version come from — did you run it, or read it?"* It sounds
pedantic until the first time the answer is "read it", and it is the single highest-value question to
ask about any table of numbers in this repository.

**The interview question.** *"How do you know which version of a library produced a given result?"*
The weak answer describes a config file. The strong answer distinguishes the intent from the
observation and says which one the artifact records — and mentions that the interesting failures are
the ones where the two disagree and nothing crashes.

**Compute tier: T0.** Laptop CPU, no network required beyond what `uv` already downloaded.

## Check yourself

Run this. It prints the **number** you are allowed to write in the ledger, and the number you are
not:

```bash
echo "offered: $(uv python list | grep -o '3\.12\.[0-9]*' | head -1)"
echo "observed: $(uv run python -c 'import sys; print(sys.version.split()[0])')"
```

**Line by line:**
- The first line scrapes the highest 3.12 from the **listing** — the availability answer, and the
  number you must not record.
- The second line asks the **running interpreter** — the observation, and the only number that goes
  in `docs/PACKAGES.md`.
- If the two differ, you have reproduced this part's story on your own machine. If they match today,
  they will not always, and now you know to look.

**Say this out loud, without scrolling up:** what is the difference between the version a tool
*lists* and the version a process *reports* — and why does a ledger row need a date next to the
number to mean anything at all?
