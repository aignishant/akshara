# 1.2 — uv owns the environment: one binary for interpreter, packages and lock

## One-line answer

`uv` is a single program that installs the interpreter, creates the environment, resolves and
installs packages, writes a lockfile recording the **exact** resolved versions, and runs your code
inside that environment — which means the ownership problem from
[1.1](1.1-the-four-pythons.md) has exactly one owner and it is committed to git.

---

## The story

A team splits the job of "managing the environment" across four tools, because each one is the best
at its part. One installs interpreters. One creates isolated folders. One installs packages. One
records what was installed so it can be recreated.

Every tool works. The problem is the seams. The interpreter installer does not know the isolation
tool exists, so it upgrades an interpreter that something else was pointing at. The package installer
writes a list of what it installed, but the list records what was *asked for*, not what was
*resolved* — so it says `numpy` when what actually landed was one specific build of one specific
version. Six months later someone recreates the environment from that list and gets different
software, and the list still looks correct, because it never claimed otherwise.

Nobody made a mistake. Each tool did its job. **The bugs live in the gaps between them**, which is
where bugs live in every system built out of components that do not know about each other.

The alternative is not a better tool for each job. It is one tool that holds all four jobs, so
there are no gaps for anything to fall into.

---

## The idea in plain language

Four separate responsibilities, one program:

| Responsibility | The question it answers |
| --- | --- |
| **Interpreter management** | Which Python version, and where does it come from if the machine does not have it? |
| **Environment creation** | Where does this project's isolated set of packages live? |
| **Package resolution and install** | Given "I want `torch`", which exact version — and which exact versions of the twenty things `torch` depends on? |
| **Locking** | Write down everything that was actually resolved, so it can be reproduced byte for byte. |

Two terms need defining, because the difference between them is the whole point.

**Resolution** is the step where a request turns into a decision. You ask for `torch`; something has
to choose a version, then choose versions for everything `torch` needs, then check those choices are
mutually compatible. The output of resolution is a specific set of specific versions.

A **lockfile** is that output, written to disk. This is the distinction people miss: a dependency
list says *what you asked for* (`torch`), a lockfile says *what you got* (`torch==2.x.y` plus every
transitive dependency at an exact version, plus hashes). Reinstalling from a dependency list re-runs
resolution and may decide differently today than it did in March. Reinstalling from a lockfile
re-applies a decision that was already made.

For this curriculum the two files are `pyproject.toml` (what you asked for, with exact pins) and
`uv.lock` (everything that was resolved, including things you never named). **Both are committed.**
That pairing is what makes Principle 9 — *seeds, configs and code are committed* — a fact rather
than an intention.

## The mechanism

Install `uv` first. It is one binary and it does not need a Python to install it, which is the point
— it cannot be caught in the problem it exists to solve.

```bash
# Windows (PowerShell). Run this in PowerShell, not Git Bash.
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```

**Line by line:**
- `irm` downloads the install script; `iex` executes it. This is the vendor's documented one-liner
  and it installs a single executable into your user profile — no administrator rights, nothing
  system-wide, nothing that can conflict with the four interpreters from 1.1.
- `-ExecutionPolicy ByPass` is needed because a default Windows install refuses to run downloaded
  scripts. It applies to **this one invocation only** and does not change the machine's policy.
- **Read the script before you pipe it into a shell**, at least once, at that URL. That is not
  paranoia about this particular vendor; it is Principle 13 — *blast radius before capability* — and
  a habit worth having before Day 145, where you will study exactly this attack shape against model
  checkpoints.
- On macOS or Linux the equivalent is `curl -LsSf https://astral.sh/uv/install.sh | sh`.

Now confirm the version you actually got, and pin the interpreter:

```bash
uv --version
uv python pin 3.12
cat .python-version
```

**Line by line:**
- `uv --version` prints the version **observed on your machine**, which is the only version you are
  allowed to write down (Principle 6). This document observed `uv 0.12.3` on `2026-08-25`
  [measured here: Windows 11, `uv --version`]. If yours differs, yours is the true one and yours goes
  in the ledger.
- `uv python pin 3.12` writes the file `.python-version` containing `3.12`. From now on every `uv
  run` in this directory uses a 3.12 interpreter, and if one is not present `uv` downloads it. This
  is the sentence that ends part 1.1's problem: the answer to "which Python?" is now a committed file
  rather than a search path.
- `3.12` and not `3.13`: the plan's §5 fixes the version, and a curriculum that silently moved to a
  newer interpreter mid-way would be changing the experiment. Version choices are amendments
  (Principle 14), not conveniences.
- `cat .python-version` proves the file exists rather than assuming the command worked. Verify the
  artifact, not the exit code.

Create the environment and prove which interpreter answers:

```bash
uv sync
uv run python -c "import sys; print(sys.executable); print(sys.version)"
```

**Line by line:**
- `uv sync` reads `pyproject.toml`, resolves, writes `uv.lock` if it is missing, creates `.venv/`,
  and installs. One command for four jobs — that is the whole argument of this part.
- `uv run` is the enforcement half. It guarantees the command runs inside `.venv`, regardless of what
  is on your `PATH`, which is why **every** Python command in every later day begins with it.
- `sys.executable` should now print a path inside this project's `.venv`. Compare it against the list
  you produced in 1.1's *Check yourself*: none of those four is the answer any more.
- Printing `sys.version` as well is deliberate — `sys.executable` tells you *which* interpreter and
  `sys.version` tells you *what* it is. You will want both in a bug report.

## When it breaks

The most common loud failure, on a machine where the pin cannot be satisfied:

```console
$ uv run python -c "print(1)"
error: No interpreter found for Python 3.12 in managed installations or search path
```

It means exactly what it says, and the fix is one command:

```bash
uv python install 3.12
```

**Line by line:**
- This downloads a managed 3.12 into `uv`'s own directory. It does not touch, upgrade or replace any
  of the interpreters from 1.1 — which is the property that makes it safe to run on a machine you
  did not set up and do not want to disturb.

The second loud failure, which reads worse than it is:

```console
$ uv sync
  × No solution found when resolving dependencies:
  ╰─▶ Because torch==2.4.0 depends on Python>=3.8,<3.13 and you require Python>=3.13,
      we can conclude that your requirements are unsatisfiable.
```

This is resolution **refusing to guess**. Two of your requirements genuinely cannot both be true, and
`uv` is telling you which two rather than installing something that half-works. Read the second line:
it names the conflict directly. The equivalent situation with a tool that resolves loosely is an
install that succeeds and a crash three days later.

**The silent version.** You edit `pyproject.toml` by hand, change a pin, and run your training script
without re-syncing. `.venv` still contains the old version. Everything runs. Your `docs/RUNS.md` row
records the pin you *wrote*, not the package that was *loaded*, and the ledger is now lying — which
is worse than having no ledger, because you will trust it. The detection is a one-liner, and it
belongs in any bug report about a run that will not reproduce:

```bash
uv run python -c "import importlib.metadata as m; print(m.version('ruff'))"
```

**Line by line:**
- `importlib.metadata.version` reports what is **installed and importable right now**, read from the
  environment rather than from your config file. It is the `sys.executable` of package versions.
- Substitute whichever package you are suspicious about. When this disagrees with `pyproject.toml`,
  the file is aspirational and the environment is real. Run `uv sync` and believe the environment.

## In production

**What a research engineer does instead of the teaching version.** They never run `uv sync` by hand
in a hot path. It goes in the first cell of the notebook, the first line of the container build, the
first step of the CI job — because the environment is rebuilt from the lockfile in every context
where results are produced, and a human remembering to sync is not a mechanism. Locally, `.venv` is
disposable: the standard response to environment weirdness is `rm -rf .venv && uv sync`, which is
seconds, rather than an investigation, which is not.

**What degrades at scale.** With one package the difference between a pin and a lock is invisible.
`torch` alone pulls in dozens of transitive dependencies, and it is always a transitive one that
moves — something you never named, four levels down, that changed a default. The lockfile is the only
artifact that constrains those. This is also why `uv.lock` is committed even though it is generated:
it is a **record of a decision**, and records of decisions are exactly what this repository exists to
hold (Principle 9).

**The failure that only shows with real data.** A dependency resolves differently on Linux than on
Windows — different wheels, different platform-specific pins. Your laptop and the Day 67 notebook are
different platforms, so this is not hypothetical for this project; it is scheduled. A cross-platform
lockfile is what makes the notebook run reproduce the laptop run, and it is why the `RUNS.md` row
carries a hardware column: the environment and the hardware are two different facts and both change
the result.

**The review comment.** *"`uv.lock` isn't in this diff, but `pyproject.toml` is. Which versions did
CI actually install?"* An unanswerable question, and the reason the two files always move together.

**The interview question.** *"What is the difference between a requirements file and a lockfile, and
when does it bite?"* The answer that shows experience names the transitive dependency: the bite is
almost never the package you pinned, it is the one you did not know you had.

**Compute tier: T0.** Laptop CPU. No GPU is involved and none of this is deferred to bigger hardware
— the lockfile written here is precisely what makes the T1 GPU session on Day 67 reproducible.

## Check yourself

Run this. It prints two **numbers** — how many packages the lock resolved, and how many you actually
named:

```bash
uv sync
uv run python -c "import importlib.metadata as m; print(sum(1 for _ in m.distributions()))"
grep -c '==' pyproject.toml
```

**Line by line:**
- `m.distributions()` enumerates every installed distribution in the active environment; summing them
  counts what is genuinely there. On a fresh Day 0 environment this number is small, and it will grow
  every time a day adds a package.
- `grep -c '=='` counts the exact pins **you wrote**. The gap between the two numbers is the
  transitive tree — the packages you never named and that the lockfile is protecting you from.
- Today the gap may be zero or near it, because almost nothing is installed yet. Note the number
  anyway: on Day 57, after `torch`, run it again and see what the lockfile is doing for you.

**Say this out loud, without scrolling up:** what does `uv.lock` record that `pyproject.toml` does
not — and which of the two would you need to reproduce a training run from six months ago?
