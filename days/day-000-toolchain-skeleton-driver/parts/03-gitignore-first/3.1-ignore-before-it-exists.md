# 3.1 — Ignore it before it exists: the artifact rule, written on an empty repo

## One-line answer

`.gitignore` is written **now**, on a repository that contains no weights, no datasets and no
secrets, because the only reliable moment to decide what must never be committed is the moment
before anything you could commit exists.

---

## The story

A rule that costs nothing to follow is a rule everyone follows. A rule that arrives after the thing
it governs is a rule that has to be enforced.

Consider the difference between two orders of events. In the first, someone sets up a repository and
writes down "large binary outputs do not go in here" while the repository is empty. The rule costs
nothing — there is nothing to exclude, no work to redo, nobody to disappoint. It is a sentence in a
file.

In the second, work happens first. Something is produced — big, valuable, the result of hours. It
sits in the folder. Somebody runs the command that adds everything. It goes in. Now the rule costs a
great deal: removing it means rewriting history, which means everyone who has a copy has a different
history, which means a conversation.

The rule is identical in both cases. What changed is when it was written relative to the thing it
was about. **The first version is a decision. The second version is an argument.**

And this is not really about discipline, because the person in the second story is not careless.
They are tired, at the end of something that finally worked, running the command they always run.
That is the moment the rule has to already exist, because that is precisely the moment nobody is
thinking about rules.

---

## The idea in plain language

Git tracks files. `.gitignore` is a list of patterns for files git should pretend not to see: they
will not show up as untracked, and `git add -A` will skip them.

Two properties of it matter, and the second is the one people learn the hard way.

**It is a plain-text list of patterns, and order matters.** `*.pt` ignores every file ending in
`.pt`. `data/` ignores a directory and everything under it. A line beginning with `!` un-ignores
something a previous line caught — which is how you ignore `.env` but keep `.env.example`.

**It only applies to files git is not already tracking.** This is the crucial one. `.gitignore`
prevents a file from *becoming* tracked. It has no effect on a file that already is. Adding a pattern
after the fact changes nothing about the file, and — worse — nothing appears to happen, so it looks
like it worked.

There is a third idea that is really the point of this part. This project has **two separate reasons**
for a file to be excluded, and they are usually taught as one:

| Reason | Example | What goes wrong if committed |
| --- | --- | --- |
| **Secrets** | `.env`, an API token | Disclosure. The token is now public and must be rotated. |
| **Artifacts** | a checkpoint, a tokenized corpus, a dataset | Permanence. The repository is now permanently large, and unclonable. |

Ordinary software projects mostly care about the first. This project cares about the second at least
as much, because the second cannot be undone by changing a password. Today is about the **artifact**
rule; Day 1 handles the secret rule when `.env` and the Hugging Face token arrive (OPS-02).

---

## Why Akshara needs it

The plan's Principle 9 is the whole reason: *seeds, configs and code are committed; weights and data
never are.* The repository holds what **reproduces** a model, never the model.

Where each pattern gets used, specifically:

- **Day 64** writes a tokenized corpus as a memory-mapped binary file. It is large, it is derived
  from the raw corpus, and it can be rebuilt from a committed script. `*.bin` and `data/`.
- **Day 67** produces the pretraining checkpoint — the single most valuable output of Phase 10 and
  the single most tempting thing to commit, because it took a whole session to make.
  `*.safetensors`, `checkpoints/`.
- **Day 80** quantizes to 4 bits and produces `.gguf`. **Day 89** produces LoRA adapters. **Day 134**
  produces a diffusion checkpoint. Every one is an output of a committed config.
- **Day 156** builds a container. A repository whose history contains checkpoints makes that image
  enormous and the clone step slow, forever.

The thing that makes this urgent rather than tidy: **git history is append-only in practice.**
Deleting a file in a later commit does not remove it from history — it is still in every clone, still
downloaded on every fetch. The only real removal is rewriting history, and part
[3.2](3.2-the-checkpoint-that-cannot-be-removed.md) is about how bad that is.

---

## The mechanism

Write the file now, on the empty repository:

```bash
cat > .gitignore <<'EOF'
# ---------------------------------------------------------------------------
# Principle 9 — the repo holds what *reproduces* a model, never the model.
# Written on Day 0, before any of these files exist. That order is the point.
# ---------------------------------------------------------------------------

# Model weights, in every format anyone has invented
*.safetensors
*.gguf
*.bin
*.pt
*.pth
*.ckpt
*.onnx

# Datasets and tokenized corpora
data/
datasets/
*.arrow
*.npy
*.npz

# Training outputs
checkpoints/
runs/
outputs/
wandb/
*.log

# Python
__pycache__/
*.py[cod]
.venv/
*.egg-info/

# Tooling caches
.pytest_cache/
.ruff_cache/
.ipynb_checkpoints/
EOF
```

**Line by line:**
- `cat > .gitignore <<'EOF'` writes a here-document. The **quotes around `EOF`** matter: they stop
  the shell expanding anything inside, so `*.pt` reaches the file as `*.pt` rather than being
  expanded against whatever happens to be in the directory.
- `*.safetensors`, `*.gguf`, `*.bin`, `*.pt`, `*.pth`, `*.ckpt`, `*.onnx` — one weight format per
  line, including formats this project will not produce for a hundred days. You are not predicting
  which you will use; you are making sure the answer is "ignored" whichever it turns out to be.
- `*.bin` is broad on purpose. It catches the Day 64 memmap and also the legacy PyTorch checkpoint
  format — the pickle you must never load (Principle 13, and Day 145's subject).
- `data/` and `checkpoints/` end in `/` so they match **directories only**. A file named `data`
  would not be ignored, which is correct — it would be a file you wrote, not an artifact.
- `.venv/` is here because the environment from
  [1.2](../01-the-toolchain/1.2-uv-owns-the-environment.md) is an **output**, rebuilt by `uv sync`
  from the lockfile. Committing it would commit thousands of files that are already fully described
  by two lines in `uv.lock`.
- `*.py[cod]` is a character class matching `.pyc`, `.pyo` and `.pyd` in one line.
- **Not here yet:** `.env`. It arrives on Day 1 with the token it protects (OPS-02), so that the rule
  and the reason land together.

Now prove it works — and notice that "prove" means something specific:

```bash
mkdir -p checkpoints
uv run python -c "open('checkpoints/fake.safetensors','wb').write(b'x'*1024)"
git status --short
git check-ignore -v checkpoints/fake.safetensors
```

**Line by line:**
- The first two lines manufacture the exact situation you are defending against: a plausible-looking
  weight file in a plausible-looking directory. Testing a guard by triggering it is the only test
  worth running.
- `git status --short` should show **nothing** about that file. Silence here is the success
  condition, which is why the next line exists.
- `git check-ignore -v` is the observation habit from
  [1.3](../01-the-toolchain/1.3-observed-is-not-available.md) applied to git: it names the **file and
  line number of the rule that matched**. Silence proves nothing on its own — it is equally
  consistent with "the rule worked" and "git never looked". This command makes git say why.
- Clean up with `rm -rf checkpoints` when you are done, or leave it — it is ignored either way.

## When it breaks

The loud failure, when a pattern does not match what you assumed:

```console
$ git check-ignore -v checkpoints/fake.safetensors
$ echo $?
1
```

No output and exit code `1` mean **not ignored**. This is the failure mode people miss, because it
looks like nothing happened — and "nothing happened" is what success looks like too. Exit code `1` is
the difference. Any time you extend `.gitignore`, check with `check-ignore` rather than by eye.

The second loud one, the day someone tries to fix it too late:

```console
$ git rm --cached checkpoints/model.safetensors
rm 'checkpoints/model.safetensors'
$ git count-objects -vH
size-pack: 412.83 MiB
```

The file is untracked going forward and the repository is still 412 MiB, because the object is still
in history. That is part [3.2](3.2-the-checkpoint-that-cannot-be-removed.md), and it is why this part
insists on the order of events rather than the content of the file.

**The silent version, which is the one this part exists to prevent.** You add a pattern for a file
that is **already tracked**. Git ignores the new pattern entirely — ignore rules do not apply to
tracked files — and reports nothing:

```console
$ echo "*.pt" >> .gitignore
$ git status --short
 M .gitignore
```

The `.gitignore` change is staged. The `.pt` file is still tracked, still committed on every future
commit, still growing the repository. Nothing warns you, and the file you edited says the right
thing. Detect it by asking git what it is **actually tracking** rather than what you told it to
ignore:

```bash
git ls-files | grep -E '\.(safetensors|gguf|bin|pt|pth|ckpt|npy)$|^data/|^checkpoints/'
```

**Line by line:**
- `git ls-files` lists **tracked** files — the ground truth, unaffected by `.gitignore`.
- Any output at all is a problem that `.gitignore` cannot fix and that gets worse with every commit.
- This exact check runs inside `./m done` (part
  [4.3](../04-the-driver/4.3-the-gate-that-refuses.md)), because a rule enforced only by remembering
  it is not enforced.

## In production

**What a research engineer does instead of the teaching version.** They add the artifact patterns to
a template and never write them by hand again, and they put the tracked-files check in CI rather than
in a habit. The deeper move is architectural: artifacts get written to a path that is **outside the
repository entirely** — an environment variable like `AKSHARA_CHECKPOINT_DIR` pointing somewhere
else — so that committing them is not merely forbidden but impossible. `.gitignore` is a guard rail;
writing outside the tree is not needing one.

**What degrades at scale.** The pattern list ages badly. A new file format arrives — a new
quantization container, a new index format — and the list does not know about it. The list is a
denylist, and denylists are always behind. Some teams invert it: ignore everything, then explicitly
un-ignore source files. That is stricter and more annoying, and on a repository where a single
mistake is permanent, the annoyance is priced correctly. This project stays with the denylist and
compensates with the `./m done` check, which is a *behavioural* backstop rather than a pattern.

**The failure that only shows with real data.** Not one enormous file — many small ones. Ten thousand
`.npy` shards, each a few hundred kilobytes, none individually alarming. Git stores them
individually, the pack file grows, and `git status` slows to seconds. Nobody notices until clone time
becomes a complaint. `data/` as a directory rule catches the whole class, which is why directory
rules beat extension rules where you can have them.

**The review comment.** *"This PR adds `checkpoints/best.pt` — was that intentional?"* If that comment
is ever needed, the guard has already failed; the point of Day 0 is that this comment never has to be
written.

**The interview question.** *"What happens if you commit a 2GB file and then delete it in the next
commit?"* The answer that shows experience: nothing useful — the repository is permanently 2GB
larger, every clone downloads it, and fixing it means rewriting history and coordinating with
everyone who has a copy. The follow-up that shows more: *"so I write `.gitignore` before the first
run, not after."*

**Compute tier: T0.** Laptop CPU. Nothing here needs a GPU, and the rules written here are what keep
the T1 checkpoint from Day 67 out of a repository that would otherwise never recover from it.

## Check yourself

Run this. It prints the **number** of artifact patterns you are protected by, and the number of
artifact files currently tracked — which must be zero:

```bash
grep -cE '^\*\.|^[a-z]+/$' .gitignore
git ls-files | grep -cE '\.(safetensors|gguf|bin|pt|pth|ckpt|npy)$|^data/|^checkpoints/'
```

**Line by line:**
- The first counts extension and directory patterns — the size of the guard.
- The second counts tracked artifact files. **It must print `0`.** `grep -c` exits non-zero when it
  finds nothing, which is harmless here; the number is what you are reading.
- If the second number is ever above zero, stop and read part
  [3.2](3.2-the-checkpoint-that-cannot-be-removed.md) before making another commit.

**Say this out loud, without scrolling up:** why does adding a pattern to `.gitignore` do nothing for
a file that is already tracked — and what is the difference between the *secret* reason and the
*artifact* reason for excluding a file?
